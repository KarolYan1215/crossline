# 一个输入框：对话、命令与主动助手（设计稿）

状态：**已审定**（2026-10-09），按第 8 节分阶段实现，每阶段在真实账号上验证。

## 1. 为什么要重做：一次失败的完整链路

2026-10-08 02:53，本人在待决事项上点了「不等了」，12 秒后在首页输入框打出「撤销刚刚的不等了」。

1. 当时由前端正则 `looksLikeScheduleCommand` 决定一句话走「路由」还是「直接收集」。正则里没有「撤销」，这句被直接写成一条收集（`captures`）。
2. 收集会自动交给任务分析 Skill（`crossline-automation-stripper`）。它只会把一句话变成任务，于是报 `ANALYSIS_POLICY_BLOCKED`（「缺少待撤销对象标识」）。
3. 结果：任务页多出一条「未分类 · 已阻塞」，待决事项多出一问；本人想撤销的「不等了」没有撤销。

撤销后来补进了路由（7f69a68），同一句今天能识别。但底下的结构问题都还在：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 正则当分诊台：没命中的都默认是新任务 | 「那个别等了」「算了恢复吧」「今天想早点睡」都会变成任务 |
| 2 | 任务分析没有「这不是任务」的出口 | 非任务只能变成阻塞的收集，留在任务页和待决事项里 |
| 3 | 路由 Skill 说明里有 `event`、`profile`，`INPUT_ROUTE_SCHEMA` 的 enum 里没有 | 严格结构化输出下这两类永远选不到，「周四三点和导师开会」走不通。**已修**，并加了说明与 schema 一致的测试（`apps/worker/src/input-router.test.ts`） |
| 4 | 首页「快速收集」与小助手是两个框 | 一个问题先路由约 10 秒，再交给小助手约 19 秒 |
| 5 | 发送后只显示「已收到」 | 本人看不到系统理解成了什么，结果散落在任务页、待决事项和计划页 |
| 6 | 很多操作说不出口 | 批准、回答待决事项、开始计时、标记步骤完成、改可用时段，都只能去对应页面点 |
| 7 | 每句都附带约 18k token 的全量上下文 | 慢，系统变大后会装不下 |

真实账本里一共 6 条收集，路由只被调用过 3 次：这个框目前几乎没有被用起来。

## 2. 已定决策（2026-10-09 与本人逐轮确认）

| 主题 | 决定 |
|---|---|
| 入口 | 首页一个框包揽收集、命令、问答。小助手面板是同一会话的展开视图。其他页面的入口进入同一会话，按页面调整指令和上下文（在任务页，「这一步」就是这个任务的当前步骤） |
| 执行 | 只读的查询和解释直接回答。凡是写入（包括新建任务）都先出理解卡，多项时一键「全部执行」，也可以逐项修改或删除 |
| 兜底 | 识别不了或有歧义时，在框下原地追问一句，带 2–4 个选项。不再默认当成任务 |
| 能力 | 全部操作：处理待决与提案、执行中的操作、改计划与时间、查询与解释。前提是系统理解整个状态 |
| 上下文 | 快照加按需查询：每轮带一份简短概况，细节由模型调用只读查询工具去取 |
| 会话 | 存账本，按天分段，电脑和手机看到同一段 |
| 速度 | 先快后准：低档模型先出理解卡；没把握或涉及多步时自动升到中档重判 |
| 新任务 | 轻卡确认（标题、主线/项目、截止、关联里程碑），确认后后台再跑完整分析 |
| 文件 | 读文件内容后提出动作：课程大纲 → 提取日期并归入项目；作业 → 挂到任务或新建任务；成果 → 作为正在做的任务的证据 |
| 纠错 | 理解卡上的字段可以直接点改，也可以接着说一句纠正。纠正记入个性化偏好 |
| 主动 | 会话开头给今日要点。此外在需要问精力、提醒进度和截止时，主动冒出对话气泡，像一个真实的助手 |
| 主动频率 | 每天条数跟随通知档位。气泡上的按钮即确认，24 小时内可撤销 |
| 时段提醒 | 只提醒影响截止的块，按「最晚开始时刻」倒推提前量，保证来得及完成 |
| 精力询问 | 只在用得上时问，不限次数；距上次记录超过 3 小时即可再问；答案立刻用于重排今天和之后已排的块 |
| 精力来源 | 作息推算加个人校准；手机健康数据；为以后接入其他可穿戴设备留好接口 |

## 3. 架构

```
首页框 / 小助手面板 / 各页入口
        │  {text, files, mentions, page:{kind, entityId}}
        ▼
  对话会话（账本，按天）──────────────┐
        │                              │ 主动消息也写进同一会话
        ▼                              │
  一个回合（worker，Skill crossline-concierge）
   ├─ 快照：今天、待决数量、最近操作、当前页面对象
   ├─ 只读查询工具（Codex 动态工具 item/tool/call）
   └─ 输出：回答 + 拟执行动作[] + 追问[]
        │
        ▼
  理解卡（页面）── 点改 / 一句话纠正 / 全部执行
        │
        ▼
  动作注册表 apply() ── recordOp（24h 撤销）── 账本
```

### 3.1 会话

- 新表 `conversations`（id、workspace、day、page 摘要）和 `conversation_messages`（role：`person` / `assistant` / `nudge`；正文；附带的理解卡或追问；时间）。存账本的理由与可用时段相同：备份要能恢复，换设备要能接着说。
- 每天第一次打开时开一段新会话，开头是今日要点（见 4.1）。旧会话可以翻看。
- 一个会话对应一个 Codex 线程。线程丢失（`SKILL_THREAD_LOST`）时，用当天的消息历史重开，做法同访谈。
- 现在的 `sessionStorage` 小助手记录不再使用。

### 3.2 一个回合

Skill `crossline-concierge` 取代 `crossline-input-router`（P1 删除）和小助手 `crossline-assistant`（P2 删除，任务对话框的入口与记录框都并入同一会话）：路由和问答合成一次调用。

- **快照**（每轮附带，约 1–2k token）：现在时刻与时区；今天已排、预排和固定日程的摘要；待决数量与最紧急的 3 条；最近 24 小时的可撤销操作（id 与标签）；当前页面对象（任务、里程碑、计划日）；本人的主线列表。
- **只读查询工具**（Codex 动态工具：`thread/start` 时声明，调用以 `item/tool/call` 请求到达，由 `SkillTools` 应答）：`find_tasks`、`get_task`、`find_milestones`、`list_asks`、`get_plan`、`list_recent_ops`、`list_agent_results`、`get_forecast`、`find_materials`、`read_material`、`get_profile_facts`（`CONCIERGE_TOOL_SPECS`）。所有工具只读，不暴露屏幕活动的窗口标题。
- **数据从哪来（实现时的决定）**：待决、排程、预测这些读取函数都在 web，worker 拿不到。因此 web 每轮在进程内算出一份完整的「上下文包」（`ConciergePack`，`apps/web/lib/conversation.ts` 的 `contextPack`，不调用模型）随请求交给 worker；查询工具从包里取（`answerFromPack`），只有 `read_material` 由 worker 从账本读文件全文。进入提示的只有几行概况（`conciergeSnapshot`）。数据是本人按下发送那一刻的状态，不需要 worker 反向调用 web。
- **输出**（严格结构化）：
  - `reply`：给本人看的一段话（问答的回答、对理解卡的说明）；
  - `actions[]`：每项是动作注册表里的一个动作 id 加参数，附一句 `summary`；
  - `clarify`：识别不了或有歧义时的一个问题，带 2–4 个选项，选项本身就是候选动作；
  - `confidence`：`high` / `low`，供分档升级使用。
- **校验**：动作 id 必须在注册表里，参数用注册表生成的 schema 校验，引用的对象必须存在（`actionProblem`）。引用不存在的对象时把问题退回模型修正（它可以查 id），至多两次；之后只保留能执行的项，其余在回答里说明（`keepUsable`）。执行前用当时的状态再检查一次，卡片可能等了一会儿。

### 3.3 动作注册表（`packages/core/src/actions.ts`）

应用里每个写操作都登记为一个类型化动作：

```ts
type ActionSpec = {
  id: string;                    // "task.create" | "ask.answer" | "timer.start" …
  label: string;                 // 理解卡上的动词：「新建任务」「回答待决」
  args: JsonSchema;              // 由此生成 Skill 的输出 schema
  risk: "internal" | "commitment" | "external";
  preview?: (ctx, args) => Impact;   // 改计划类复用 lib/impact.ts
  apply: (ctx, args) => { ok: true; op: Op } | { ok: false; code: string };  // 必经 recordOp，可撤销
};
```

首批动作（由现有函数包装，不重写业务逻辑）：

| 组 | 动作 |
|---|---|
| 收集 | `task.create`（轻卡，确认后进入分析）、`note.add`（只记一笔，不是任务） |
| 待决与提案 | `ask.answer`（复用 `answerAsk`）、`ask.snooze`、`proposal.approve` / `proposal.reject`、`milestone.approve_drafts`、`target.confirm`、`agent_result.accept` / `reject` |
| 执行 | `timer.start` / `pause` / `stop`、`step.done`、`progress.report`、`duration.log`（「刚才做了 40 分钟」） |
| 计划与时间 | `task.due`、`task.defer`、`task.estimate`、`step.estimate`、`event.create`（一次性或周期）、`availability.block`（「这周五下午不可用」）、`availability.set`、`importance.set` |
| 主线与目标 | `goal.add`、`milestone.draft`、`line.add` |
| 记录 | `energy.report`、`record.note` |
| 其他 | `undo`（按 op id）、`profile.tell`（转给访谈） |

- 理解卡、气泡按钮、各页面按钮最终都调用同一个 `apply`，同一件事只有一条代码路径。
- `requiredApproval` 仍是策略的唯一来源：`external` 级动作（对外发送、写非 Crossline 日历、交易）不进注册表。
- 注册表生成 Skill 的输出 schema，并有一条发现式测试：每个动作都有 schema、`apply` 和撤销逆操作。第 1 节第 3 条那种契约漂移从此无处发生。

### 3.4 理解卡

- 框下按项显示：动词、对象（可点开）、关键字段（日期、时长、主线、任务）、计划类的影响预览（「作业 2 下一段从周一 9:00 移到周二 14:00」）。
- 字段可以直接点改（复用 `ui/` 里的日期芯片、时长条、选择器）；也可以接着说「不是作业 2，是作业 3」，同一回合重出卡片。
- 「全部执行」逐项调用 `apply`，各自登记撤销；某项失败只标红那一项，并说明原因。
- 纠正（改了模型给的字段，或用话纠正）写入 `preference_entries`，来源记为「输入框纠正」。

### 3.5 先快后准

- 每轮先用低档模型。满足任一条件时，用中档模型在同一线程重判一次：`confidence: low`；涉及 3 个以上写动作或跨 2 个以上对象；校验拒绝；本人在这段会话里纠正过一次。
- 只读问答在低档答完即止。
- 目标：理解卡 5–10 秒内出现，重判时卡片显示「正在仔细核对」。用模型用量页记录实际耗时，按观测值调整。

### 3.6 文件

P3 实现：文件经 `/api/conversation/files` 存为本人的资料并当场读出文本（与访谈上传同一条 `uploadSources`），再以 id 随这句话进入回合；概况列出每个文件的类型、能否读出文本、所属项目和开头 400 字，需要更多时用 `read_material`。动作：`dates.read`（交给访谈读日期，走现有的确认批次）、`material.file`、`material.attach`（归入任务的项目并按新材料重新安排步骤）、`evidence.submit`（未开始的任务先开始；PDF/Word 另存一份文本供验收引用）。离线时仍按原方式收集。


文件上传后先抽取文本（已有的抽取管道），交给同一回合，并附上「文件类型猜测」（大纲、作业、成果、个人资料）。模型据此提出动作：`dates.extract`（归入项目后走现有日期确认批次）、`material.attach`（挂到任务）、`evidence.submit`（交到正在做的任务）、`task.create`。

### 3.7 页面上下文

每个页面向会话传 `{page, entityId}`，快照里加一段该页的说明和对象详情，例如：

- **任务对话框**：当前任务和步骤；「这一步」「做完了」指它。
- **主线页**：打开的里程碑；「把截止改到 11 月底」指它。
- **计划页**：所看的日或周；「这天下午不可用」指它。

任务对话框里现有的任务专属小助手并入这个机制。

### 3.8 退役

- 前端 `looksLikeScheduleCommand` 分诊：删除，所有输入都进同一回合。
- `crossline-input-router`、`crossline-assistant`：由 `crossline-concierge` 取代；离线时的纯文本收集保留（离线队列只做 `task.create`，联网后照常进入回合）。
- 任务分析 Skill 保留，只在 `task.create` 确认后运行；它新增一个出口：判断「不是任务」时退回会话变成追问，而不是阻塞的收集。

## 4. 主动引擎

**原则：何时开口由规则决定（系统本来就有确定的信息），措辞用模板，只有本人打字回复时才调用模型。** 主动消息不消耗模型额度。

### 4.1 每天的开头

当天第一次打开时，会话以一条要点开始：今天的固定日程、已排的块、影响截止的事、最紧急的 1–3 个待决（可以直接在对话里答）。待决事项页和卡片保留，内容是同一份。

### 4.2 触发源

| 类别 | 触发 | 气泡与按钮 |
|---|---|---|
| 截止相关的时段 | 见 4.3 | 「14:00 做 ECE 555 作业 2 · 拆解题目（30 分）」开始计时 / 推迟到… / 今天不做 |
| 时段落空 | 影响截止的块结束时未开始 | 「那段没开始，补在 16:00–16:30？」采纳 / 换个时间 / 其实做了 |
| 计时 | 超出通常时长 50%；计时停止 | 「已 45 分钟，比通常多一半」做完了 / 还差一点 / 卡住了 |
| 精力 | 见第 5 节 | L / M / H |
| 进度与截止 | 余量跌破阈值、风险等级变化 | 「ECE 548 期中还剩 5 天，按现在节奏差约 4 小时」加时间 / 看计划 / 接受 |
| 后台完成 | 助手准备完成、分析完成、验收出结果 | 「ECE 548 题源与自测包备好了」打开 / 稍后 |
| 等待到期 | 等待项到了约定日 | 到了 / 推迟 / 不等了 |

### 4.3 「最晚开始时刻」与提前量

对每个有截止的任务：按剩余步骤的保守估时（p85），在截止前的可用时段里从后往前排，得到「最晚开始时刻」。余量 = 最晚开始时刻 − 现在。

- 余量首次低于 1 天时提醒一次，告诉本人还剩多少可用时间。
- 当天该任务的块开始前 15 分钟提醒。
- 块落空时立即给出补救时段：取下一个能放下的空档，并说明对截止的影响。
- 不影响截止的块不提醒，靠 Crossline 日历上的 10 分钟提醒。

这和预测器（`forecastGoals`）用同一套估时与时段，提醒和计划页看到的数字一致。

### 4.4 打扰控制

- **不打扰：** 计时进行中、日历上正在开会、上一条回答不足 20 分钟。专注状态需要「应用与窗口」级屏幕活动，目前未开启，不使用。
- **断点批量：** 不紧急的消息攒到块开始或结束、计时停止、离开后重新打开页面时再说。
- **上限：** 跟随通知档位（少 3 / 标准 6 / 多 10）。截止相关的时段提醒和当天截止不计入。
- **学习：** 每条气泡有「少问这类」；同一类连续忽略 3 次自动降频，记入个性化偏好。

### 4.5 送达与记账

- worker 的主动引擎复用通知的 2 分钟时钟。每条消息写入账本，记为 `assistant.nudge`：fingerprint 去重，带过期时间和按钮（按钮即动作 id 加参数）。待决徽标、早报、推送和气泡数的是同一份。
- **页面可见：** 每 30 秒取一次新消息（以后可换 SSE）；首页在对话里冒泡，其他页面在角落冒小气泡，点开是同一会话。页面每分钟上报一次心跳。
- **10 分钟内没有可见页面：** 走现有的桌面通知或手机推送。同一条消息只送一个渠道。
- 按钮调用注册表的 `apply`，点击即确认，登记撤销。打字回复进入正常回合。

## 5. 精力模型

> 2026-10-14 起由 [energy-and-ecosystem.md](energy-and-ecosystem.md) 取代以下内容中的模型部分：多夜睡眠债、睡眠惯性、午后低谷、当日容量、学到的效率系数、手机起床 / 就寝时刻、Siri「记一下」。本节保留作背景。

### 5.1 层次

| 层 | 内容 | 状态 |
|---|---|---|
| ① 作息推算 | 三过程模型（Åkerstedt & Folkard）：醒后时长的指数项加昼夜正弦项。起床 ≈ 连续 5 小时以上无屏幕活动后的首次活动；入睡 ≈ 前一晚最后活动。先验取访谈里本人说的「上午 9–12 点效率最高」 | 采用，不新增采集 |
| ② 个人校准 | 每次 L/M/H 自评按「几点、醒了多久、睡了多久」回归，学出本人的曲线；把握度随数据增加 | 采用 |
| ③ 手机健康数据 | iPhone 快捷指令每天早上把健康 App 的睡眠时段和 HRV 摘要 POST 到 tailnet 地址（只读进入），覆盖 ① 的推断 | 采用 |
| ④ 其他可穿戴 | Oura、WHOOP、Garmin 等 | 留接口，暂不实现 |
| 键盘鼠标节奏、3 分钟反应测试 | 研究证据偏弱，或需要新的采集路径 | 不采用 |

### 5.2 接口

```ts
interface EnergySource {
  id: string;                                   // "screen-activity" | "ios-health" | "oura" …
  readSleep(day: string): Promise<SleepEpisode[]>;           // 入睡、起床、来源、把握度
  readPhysiology?(day: string): Promise<{ hrvMs?: number; restingHr?: number }>;
}
```

可穿戴设备是一个新的 `EnergySource` 实现，模型和询问逻辑不变。原始数据只存当天摘要，不存逐分钟记录；进入导出的同样是摘要。

### 5.3 什么时候问

同时满足三条才问：

1. 接下来的安排取决于精力：下一段可以在高精力和低精力工作之间选，或者已排的块对精力有要求；
2. 模型对当前时段的把握低；
3. 距上次精力记录超过 3 小时。

不限次数。回答写入 `energy_observations`，立即对今天剩余的块和之后已排的块重新排程（复用 `scheduledBlocks` 与 `schedule.keep` 的局部重排），并用于校准 ②。

## 6. 安全与隐私

- 新增的外部读入只有 ③：数据从本人的手机发到本人的 tailnet 地址，不写任何外部服务。
- 查询工具只读；写入只经注册表，`external` 级动作不在注册表里。
- 窗口标题不进入任何模型上下文；精力模型只用活跃分钟数。

## 9. 已补充确认（2026-10-09）

- P5 实现（2026-10-10）：模型在 `packages/core/src/energy-model.ts`（`sleepFromGaps`、`mergeSleep`、`alertness`、`calibrate`、`predictEnergy`、`phaseShiftFromPeak`、接口 `EnergySource`），装配在 `apps/web/lib/energy.ts`。作息来源：worker 在独立的「作息记录」开关（`activity.sleepTracking`，默认关闭，2026-10-10 本人决定不并入屏幕活动的同意）打开时，记录 4 小时以上无活动的起止（`activity.longGaps`，只有两个时刻，最多 40 段），关闭即删除；手机快捷指令把睡眠起止和当天 HRV/静息心率发到 `POST /api/health/sleep`（`Authorization: Bearer` 令牌，设置里生成、只显示一次、只存哈希）。昼夜峰值按可用时段里「高精力」窗口移动；自评把模型分数换成本人的 L/M/H（样本少时向默认靠拢），8 次一致七成以上为「把握高」，4 次一致六成以上为「中」。排程器对把握不低于「中」的时段用预测精力，否则用可用时段自带的精力；当前时段仍以本人刚说的为准。问精力（`energy_check`）：3 小时内有排程工作、模型把握低、上次自评超过 3 小时，且答「低」和答「高」会让未来 3 小时的安排不同（2026-10-14 起的信息价值门槛，见 docs/energy-and-ecosystem.md §6）；夜里与忙时不问，不计入每日上限。快捷指令文件需要在 macOS 上签名才能一键导入，Windows 上做不到，所以设置里给的是分步说明。

- P4 实现（2026-10-10）：引擎放在 web（`apps/web/lib/nudges.ts`，`instrumentation.ts` 每 2 分钟一轮），因为日程、待决、预测都在 web；规则是 core 里的纯函数（`packages/core/src/nudges.ts` 的 `nudgeCandidates`/`planNudges`）。主动消息是会话里 `role: "nudge"` 的消息，按钮是卡片选项（`kind`：action / href / ack / mute / say），点即回答。触发：截止 7 天内任务的时段开始前 15 分钟；这样的时段结束 30 分钟内未开始；截止 14 天内的任务余量不足一天（不足零为「来不及」，算紧急）；计时超出该步通常时长一半；6 小时内助手做完待审阅、准备步骤已备好、新提案待批准。打扰控制：23:00–08:00 只说时段开始与计时超时（都跟随本人自己的活动）；同时完成的后台工作合成一条；计时中、日历会议中、20 分钟内刚回答过时只放行紧急的；当天计数上限按通知档位（少 3 / 标准 6 / 多 10，时段开始提醒不计）；「少问这类」静默一周，同类连续 3 条没回应静默 3 天。送达：最近 10 分钟有可见页面（每分钟 `/api/presence`）时在页面显示（首页对话与右下角气泡预览），否则由 worker 的通知轮次发到桌面与手机，每条一次。开场白在当天第一次打开对话时生成，最紧急的待决事项可直接在开场白里点选回答。

- P2 实现：复核在 web 端触发，首读的卡片先显示并标「正在用更强的模型仔细核对」，复核期间不能执行，页面每 3 秒取一次结果；复核改动了提议时卡片标「已核对并修改」。当天一旦有过更正，此后的回合直接用中档模型。
- 任务对话框只保留一个入口（原来的指令框和记录框合并）。旧小助手的「把脚本存为任务材料」与「提议里程碑模板」在 P3 迁回为 `material.save`（存为任务项目下的资料，不进 `materials` 表，以免让材料准备误以为已备好）和 `template.add`（扁平的标准字段，经 `templateCriterion` 转成存储形状）。

- 追问的选项：选一个即执行它所指的候选动作（选择就是确认，与主动气泡的按钮同理）；没有候选动作的选项（「都不是」）把光标放回输入框。
- 模型不可用时，原话照样存进会话，卡片提供「作为新任务收集」，点了才收集。

- 每日开头要点在当天首次打开页面时出现。
- `note.add` 的笔记不单独成栏，在会话历史里可搜索即可。
