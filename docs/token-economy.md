# Token 经济：把额度花在核心功能上（2026-10-21）

本人要求：分析系统每个调用模型的环节，尽量减少 token、提高缓存命中，把 token 优先花在核心功能上；三轮对话确认了下面的方案。教程准备的分级与流程见 `task-preparation.md`，模型闸门与调度见 `model-scheduling.md`。

## 1. 测量（托管站 10-17 至 10-22，全部账号，954 次记录在案的运行）

- 输入 30.3M，其中缓存 72%；输出 2.9M，其中推理 2.1M（72%）。
- 计价：ChatGPT 订阅额度下缓存输入按 1/10 扣（Codex 定价页），输出远贵于输入（估算按 8 倍，未证实）。**真正的花费是输出（尤其推理）和未缓存输入。**
- 按加权（未缓存 + 0.1×缓存 + 8×输出）算 ChatGPT 额度：访谈 21%、拆步骤 16%、教程撰写 13%、validation-reviewer 12%（主要是公开 skill 候选审查，缓存只有 24%）、教程检索 10%、访谈整理 7%、倒推 5%。
- **没记账的大头：Codex 记忆。** 结构化后台 Skill 在账号自己的 Codex 上开着 `memories.generate_memories/use_memories`。每个线程闲置 6 小时后，Codex 用 `gpt-5.6-luna`（low）读整份裁剪后的记录写一条摘要（stage-1），每 6 小时用 `gpt-5.6-terra`（medium）合并（phase-2），都扣同一个账号的额度，`model_usage` 不记。10-20 起 510 次 stage-1，**usage_count 全为 0**：结构化 Skill 没有 shell 读不了 MEMORY.md，输出被 JSON 限定从不引用。几个账号的记忆还混在机主运行时的同一份记忆里。
- 已有问题：
  - 前缀被打乱：Codex 路径上 SKILL.md 正文被插在每次都变的 JSON 之后；拆步骤、撰写、助手把逐任务内容拼进开发者指令，固定的 STYLE 被推到变化内容后面；JSON 把 `today` 放最前。新线程的命中常只有 15–40%。
  - repair 让模型整份重写 JSON；倒推 36 次里 12 次 repair，邮件分拣（Qwen）57 次里 16 次。
  - SiliconFlow 上 Qwen 零缓存，V4.1-Flash 缓存只收 2%。
  - 非核心后台（公开 skill 搜寻与审查、主线技能编译、调研、飞轮、画像重写、原型策展）没有总量上限；公开 skill 搜寻加审查约占 ChatGPT 额度 14%。
  - `insight-compiler` 76 次 `MINE_SKILL_BLOCKED` 循环（已由 W-114 修）。

## 2. 决定（本人，2026-10-21）

1. **关 Codex 记忆**：结构化后台 Skill 关闭生成与使用。已累积的记忆先备份，按 `model_usage.thread_id` 找回所属账号，把其中「失败与改进」「偏好信号」按规则迁入各账号的经验教训表，再删掉记忆文件。
2. **账本吸取 Codex 记忆的设计**（都不新增每线程一次的模型调用）：
   - 经验教训表（主线 × 任务类型）：由规则从已有事件抽取——助手结果的退回备注、验收「部分」的违背项、超出保守估时的步骤、重复的错误码；最多 5 条进拆步骤和助手的输入。
   - 使用计数：偏好与事实记被用次数和最近使用；结果被采纳时累加；进上下文时按使用挑选。
   - 索引加按需读取：拆步骤和收集分析只拿一行一条的事实索引，用 `read_ledger` 读全文；不能调工具的模型仍给全文。
   - 自动过期与增量编译：30 天未用的估时、重要性、推迟类偏好失效（本人确认过的不动）；主线技能编译用稳定的材料 id，只传变化的材料加上一版规则。
3. **非核心后台每周最多占额度 20%**，只在额度宽裕或夜间跑，超了暂停到下周。设置 → 后台任务只给一个「节省额度」开关（默认开），不展示数字；加权成本只在后台记账，用来判断暂停。
4. **公开 skill**：只在主线设立时（访谈完成或新增主线）为这条线搜一轮；之后每月补充一次；本人要求时可再搜。不再「覆盖全部需求」地连续多轮。
5. **前缀重排**：只改顺序不改内容——固定指令、风格、Skill 正文、画像与偏好在前，`today` 和逐次变化的数据在后。目标：新线程命中 ≥ 70%。
6. **开发者模型上的简单 Skill** 按实测加权成本挑模型：缓存价和 repair 都计入每次运行的成本。
7. **推理强度先对比再定**：在真实任务上比较拆步骤、倒推、教程撰写降一档前后的质量和 token，结果出来再逐个决定；开发者模型的规划类先把思考封顶 2048。

## 3. 实施（2026-10-22）

- 记忆：结构化 Skill 与助手线程都关掉 Codex 记忆；worker 启动时一次性把已累积的「失败与改进」「偏好信号」按 `model_usage.thread_id` 迁入各账号的经验教训，记忆文件移到 `<data>/backups/codex-memories-<日期>/`，不删除。
- 前缀：10 个 Skill 按 `stableKeys` 排序输入、逐次说明放进 `runNote`，同一 Skill 的开发者指令逐字节相同（测试数据上拆步骤的共同前缀 8% → 96%）。限制：Codex 路径上 SKILL.md 总在本次输入之后（`turn.rs`），且 `prompt_cache_key` 是线程 id，新线程不保证命中；命中率以上线后的 `skill.run` 日志为准。
- 经验教训表（迁移 20）、使用计数与过期、事实索引加 `read_ledger`、主线技能增量编译、「节省额度」（迁移 21 的 `model_usage.purpose`）、公开 skill 设立一轮加每月补充加 Skill 库「再检索一轮」、开发者模型简单 Skill 按 `skillYuanPerRun` 选：见 CLAUDE.md「Token economy」。
- 托管账本副本实测：拆步骤事实 15.6k → 12.0k 字，收集分析上下文 87.1k → 74.1k 字，研究线主线技能重编 12k → 1.2k 字。
- 未做：推理强度对比（第 7 条，待在真实任务上跑）；Codex 路径的技能目录（`skills.include_instructions`）仍开着，它随并发开关的 skill 变化，关掉会改提示内容，留待决定。

## 4. 访谈整理（2026-11-13，第六次回放之后）

测量：第六次回放 16 轮，整理 35 次，输出 139k token，其中推理 106k（76%）；输入 2.2M，缓存 89%。服务器上的思考对比（`sponsor-eval/<model>.effort.jsonl`，DeepSeek-V4.1-Flash，同一份整理样例）如下：

| 思考设置 | 输出 | 其中推理 | 用时 |
|---|---|---|---|
| 不限 | 5830 | 4469 | 62 秒 |
| 封顶 2048 | 3509 | 2048 | 39 秒 |
| 关闭 | 1172 | 0 | 11 秒 |

做了两件事，都要在下一次回放里核对质量：

- **思考封顶**：整理的三条通道在开发者模型上都封顶 2048（`EXTRACT_THINKING_BUDGET`，`SkillRunOptions.thinkingBudget`）。模型名写成 `<model>@think:2048`，网关把它转成服务商的 `thinking_budget`。只对开发者模型生效，账号自己的 ChatGPT 不变。
- **画像通道批量读**：访谈进行中，画像各节和推断两条通道等到有 3 条新回答（`PORTRAIT_BATCH`），或最早一条已等 10 分钟（`PORTRAIT_WAIT_MS`），才运行一次。每次运行都会重读整份画像、从头推理，按每条回答各跑一次，大部分输出都花在一句话上。账本通道仍然每条回答都跑，因为开始标准和下一轮的问题都要等它。访谈结束后立刻全部读完。

账目按通道分开记（`purpose: interview:<lane>`），回放的 `bySkill` 显示为 `crossline-onboarding-extract:<lane>`。

第七次回放（19 轮）核对后，整理输出从 139k 降到 60k，每轮成本约降 27%。两处调整：

- 画像两条通道在 2048 下 7 次里有 3 次要修复，改为封顶 4096（`PORTRAIT_THINKING_BUDGET`）；账本通道仍是 2048，没有修复。
- 推断通道一开始就批量读，整场只跑了 3 次，日志里没有可出卡的候选。现在只有日志里已有至少两条候选时它才等批；不够时每条回答都跑。

**2026-11-17 起访谈阶段不再设限**（本人：「访谈阶段不对用户的 token 数或者上下文做限制……至少应该和原有的 harness 框架（如 Codex）一样好用，自由度一样高」；每月 ¥30 的赞助上限不变）。上面这些为省钱加的限制都撤了：

- 整理三条通道不再封顶思考（`EXTRACT_THINKING_BUDGET` 2048、`PORTRAIT_THINKING_BUDGET` 4096 和当天先提的推断通道 8192 都删了），开发者模型按服务商默认想。
- 画像两条通道不再等批：`PORTRAIT_BATCH` 由 3 改 1，每条回答到了就读；一次运行读它运行期间攒下的全部回答。`CROSSLINE_PORTRAIT_BATCH` 仍可设回批量。
- 整理和研究线程从 `mid` 升到 `top`；对话、整理、研究、画像撰写四个 Skill 进 `NEVER_DOWNGRADED`，额度紧时也不降档（`model-policy.ts`）。
- 访谈对话和研究线程空闲一小时才释放（其他对话仍是 `THREAD_KEEP_MS` 10 分钟），过 0.75 窗口或约 12 万 token（先到者，2026-11-27 本人决定，`INTERVIEW_COMPACT_TOKENS`）就在两轮之间压缩（其他仍是 `COMPACT_AT` 0.6；运行时自己 0.8）（`threadKeepMs`、`INTERVIEW_COMPACT_AT`，`skill-runner.ts`）。

花费会上去，用下一次回放量。留着的：每次读的回答数和文件字数（`REPLIES_PER_RUN`、`TEXT_TOTAL` 等）只是分段，没读完的下一次接着读，不丢内容；确定性校验、安全规则和访谈的交互设计（每轮题数、卡数）不动。

第八次回放（17 轮）发现画像各节通道整场没读过一条回答。没跑过的画像通道从账本通道的水位起读，可这个水位每条回答都在往前走，所以永远凑不齐 3 条待读，访谈结束时又算作“已读完”，结果说过的要点是 0 条。现在账本通道第一次往前走时，先把没跑过的画像通道的起点钉在原来的水位（`pinned`，`readLaneState`）。

## 5. 画像撰写的长 JSON（2026-11-14，第九次回放之后）

画像撰写一次写完整份报告，约 1.2 万 token 的单个 JSON。在开发者模型上，大约每 9 次尝试有 1 次解析不出来；第八次回放连续 3 次失败，报告没写成。每次修复都要把整份报告从头重写（输入约 8.5 万，输出约 2.5 万）。用第九次回放的账本单独重跑撰写 15 次，开着 `CROSSLINE_RECORD_DIR` 记录原始回答（录音只留在服务器上）：2 次失败，两次都是内容完整、只有括号错了。一次是 `insights` 数组闭合后多出一个 `}`，把根对象提前关了，后面的字段接着写；另一次是少一个 `}`。都不是截断：被截断的回答在 Codex 里会让这一轮失败（`SKILL_TURN_FAILED`），不会报 `SKILL_SCHEMA_INVALID`。

现在解析失败时，先按输出 schema 修括号（`packages/codex/src/json-repair.ts`，`repairJsonBrackets`），只删、补括号，字符串、数字和键原样保留：
- 没有东西可关、或者会在回答没写完时就关掉根对象的闭合符，删掉。
- 遇到当前对象没有、外层对象有的键，说明中间的对象没关，替它们补上。
- 结尾最多再补一层，前提是回答以闭合符结束。

字符串没写完、结尾停在值或逗号上、还开着两层以上，或者要改超过 4 处，都不修，仍按原来的方式让模型重写。修好的回答照常过校验；日志记一条 `skill.json_mended`（只有长度）。两份录音都修好了，结构与 schema 一致。录音里有本人的话，不进仓库；测试用的是同样形状的假数据（`json-repair.test.ts`）。

第十六次回放（2026-11-16）画像又一次三连失败：三份回答都完整（每份约 9.4k 输出 token），括号修补救不回来，原始回答没留。之后：
- 文字里没转义的引号也修：一个 `"` 后面 JSON 接不下去（键后不是 `:`，值后不是 `,`、闭合符或结尾），就按文字转义，最多 24 处，另算预算。
- 解析不了时日志记 `skill.json_unparsed`：长度、出错位置、是否以闭合符结尾、是否在打转（结尾 80 字在前 6000 字里又出现两次），不记内容。退回说明写出错位置；在打转时直说。
- 画像三次都解析不了时，换一个新线程再写一次（`portrait.fresh_retry`），最多多花一次撰写的钱。
- 不改一个字的其他坏法也修（2026-11-17）：文字里直接打出来的换行、制表符（转义）；JSON 没有的反斜杠转义，如 `\'`、Windows 路径（把反斜杠转义）；闭合符前多出的逗号（删掉）；对象前后的说明文字，如「以下是报告：」、结尾的「希望有帮助」（删掉，前提是里面没有括号和引号，第二个对象绝不拼进来）。
- 第十七次回放（2026-11-17）：8 份回答没能直接解析，6 份修好（4 份 extract、2 份画像），`portrait.fresh_retry` 一次没用上，三个人设的画像都写出。另 2 份 extract 被拒：模型的推理后半段漏进了回答，开头的 `<think>` 不在文字里（`chat-bridge.ts` 因此认不出），以 `</think>` 结束，后面是完整的对象。之后解析失败时，回答里有 `</think>` 就丢掉最后一个 `</think>` 之前的部分，只在后面那段能单独解析或修好时才收（`skill-runner.ts`，日志的 `skill.json_mended` 带 `thinking`）。两份都脱敏成回放夹具（`extract-r17-thinking-before-*`）。`chat-bridge.ts` 也在完成的消息里去掉它（没见过开头的 `<think>` 时，只留最后一个 `</think>` 之后的部分），纯文字回答同样不露推理。
- 回放脚本（`scripts/persona-eval.ts`）默认设 `CROSSLINE_RECORD_DIR` 为输出目录下的 `answers/`：模拟的人不是真人，被拒收的原始回答都留下，下次解析失败能看到原文。线上不录。

## 6. 访谈额度不到一小时用完（2026-11-28）

本人的访谈从额度恢复到 `SKILL_USAGE_LIMIT` 约 22 轮。`model_usage` 记了 131 次运行、输入 7.7M、未缓存 1.8M，其中整理 57 次、对话 24 次。读运行时自己的 rollout（`codex-home/sessions`，每个请求的 `last_token_usage`），06:00–06:47Z 真实未缓存输入 4.03M：整理 2.84M（推断 1.14M、画像各节 1.10M、账本 0.60M），对话 0.85M。

原因有四：

1. **每轮三次是设计。** 三条通道每条回答各跑一次（`PORTRAIT_BATCH = 1`，本人 2026-11-17 决定）。没有重复重试。账本通道有一次挂了 38 分钟（06:07→06:46，`SKILL_SCHEMA_INVALID`），只是推迟了账本，不多花钱。
2. **账记少了一半。** 一轮里查一句原话（`evidenceTools`）就是两次请求，`thread/tokenUsage/updated` 的 `last` 只是最后一次，收集器却按轮取 `last`。rollout 里输入 15.2M，`model_usage` 只记了 7.7M。现在按轮取 `total` 的增量（这一轮的 `total` 减去它第一次读数之前的 `total`，`createUsageCollector`，`usage.test.ts`）；没有 `total` 时仍按 `last` 记。
3. **每次运行的第一次请求，约 1.4 万 token 之后全部没缓存。** 缓存按 Responses 的 session id 路由，也就是线程 id。每次运行一个新线程，就是一个新键，服务商把它送到没见过这段提示的机器上。一次输入与一分钟前那次 65k 字里有 60k 字相同的整理，命中的只有开头共用的 1.4 万 token。另外运行时把用户消息记在注入的 `<skill>` 块之前（vendor/codex `core/src/session/turn.rs`），所以 SKILL.md（25k 字）总在变化的输入之后，这一点我们改不了。
   - 修法：`SkillRunOptions.cacheGroup`。一组里第一次运行照常开线程，它的线程和第一轮就是锚点。之后每次运行改用 `thread/fork {threadId: 锚点, beforeTurnId: 第一轮, ephemeral: true, excludeTurns: true}`。临时 fork 沿用父线程的 session id 作缓存键（`session.rs` `fork_cache_key`），也带着父线程的工具。
   - fork 拿到新线程会拿到的全部设置：沙箱、审批、开发者指令、`config`。返回后照样核对 `untrusted`、`readOnly` 和空的 `instructionSources`。
   - 开发者指令、工具或模型与锚点不同（`anchorKey`），就开新线程，由它当新锚点。fork 失败（rollout 没了）就记 `skill.anchor_lost`，开新线程。
   - 算力节点只放行 `ALLOWED_METHODS`，不含 `thread/fork`。被拒一次后，这个运行时就不再 fork（没有放宽节点的边界）。
   - 锚点只在内存里，每个运行时一份；重启后重新开始。整理每个工作区每条通道一组。不用于另一服务商、续接线程和保留线程的对话。
4. **画像的要点每次都在原地改。** 同一通道 22 次运行、21 对相邻输入：facts 一次没变；画像要点（39k 字）有 16 对变了，变的是旧要点的 `text`、`quotes`、`log`。facts 原来排在画像之后，所以每次都跟着丢。
   - 现在 `stableKeys` 里 facts 在 `profile` 之前。用 rollout 重放，相邻两次共享的输入前缀：11-28 由 42.5% 升到 63.7%（画像各节、推断都是），11-27 由 20.0% 升到 23.0%，账本通道没有画像，不变。
   - 试过把要点按最后修改排序，只多 1%：改了的旧要点仍在它原来的位置打断前缀。所以没做。

**画像两条通道合成一条（本人 2026-11-28 决定）。** 画像各节和推断两条通道每条回答都各自重读整份画像（约 6 万字），合成一条 `portrait` 通道（`EXTRACT_LANE_KEYS.portrait`），一次运行写两组字段：每条回答的整理由三次变两次，约少三分之一次运行。
- 输入、模型、思考都不变：两组字段原来就读同一份画像、同样的原话和评分。`profileTask` 原来只给画像各节通道，现在给合成的通道。
- 等批的规则合在一起：日志里可出卡的假设不到两条，或本人有更正还没读，就每条都读；否则按 `PORTRAIT_BATCH`。
