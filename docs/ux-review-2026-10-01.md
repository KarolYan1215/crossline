# 第三轮：设计分析与修复

## 1. 无标准的起步里程碑让首条作业停在最后一步

**根因。** 闸门的 `pass` 早就改成「本作业兑现了自己的证据要求」（`validateMilestoneGateResult` 的注释写明了原因：整个里程碑几乎不可能由一次提交达成），里程碑标准只用来记录进度。但 `buildMilestoneGateContext` 和 `applyMilestoneGate` 里还留着旧设计的前置检查：里程碑没有标准就拒绝判定（`MILESTONE_NEEDS_CRITERIA`）。新账号预置的起步里程碑都没有标准，所以绑到它们的作业注定卡死。

**取舍。** 备选是给起步里程碑硬塞默认标准（等于替用户编标准，违背「标准归用户」）或让分析回避它们（那这些作业就脱离了里程碑）。选择让闸门按作业自己的契约判定：契约是用户批准计划时认可过的标准，闸门并没有发明任何标准；代价是这类里程碑没有进度记录，页面上明确这样说。

**改动。** 去掉两处前置拒绝；`criteriaVerdict` 为空数组即合法。分析上下文给每个里程碑带 `hasSuccessCriteria`，技能提示在「同样合适」时优先选有标准的（只是平局时的倾向，不强行改绑）。Approvals 提案卡片提示「绑定的里程碑还没有标准，验收只按必需证据判定」。里程碑与 Review 页的文案同步改掉。

## 2. `required` 形同虚设

**根因（两层）。** ① 分析技能的说明里从未解释 `required`，模型随意填（一次真实运行里材料全 false、证据全 true，另一次证据全 false）。② 闸门把所有契约项都当作 pass 的必要条件，不看 `required`，于是页面标「（可选）」的项其实不可缺——标签与门槛不一致。

**设计。** `required` 的含义定为「缺了它就不算交付」：
- 闸门只拿 `required !== false` 的项当 pass 门槛（旧契约没有该字段则按必需处理，失败时向严格方向倒）；可选项仍被判定、仍出现在 `contractCoverage`，只是不拖后腿。
- 分析校验新增：证据要求里至少一条必需，否则 `ANALYSIS_EVIDENCE_REQUIRED_MISSING`（带可读原因，进入模型的修复轮）。全可选的契约是「谁也判不过」的契约。
- 分析技能提示写明 `required` 的含义、至少一条必需、不要全标必需。
- 页面按 `required === false` 才显示「（可选）」（旧写法在字段缺失时会误标可选）。

## 3. 调度器：90–360 分钟的作业排不进计划

**根因（两层）。** ① 分析技能没说明 `interruptible`，模型把不少本该可拆分的长作业标成 `false`（真实运行记录里也能看到）。② 低置信度作业按 p85 预留，不可中断的作业就要求**一个**连续 p85 长的空档——360 分钟的连续空档几乎不存在，作业永远排不进去，提示还只说「需要连续 360 分钟」，没说卡在哪。

**设计。**
- 源头：技能提示规定 `interruptible` 默认 true，只有真的必须一口气做完（现场会议、不能暂停的单次实验）才为 false；长工作是多次，不是不可中断。
- 调度：不可中断 + 低置信度 + p85 放不进最长空档但 p50 放得下时，按「一个空档能容纳的最大预留（不低于 p50）」排，并给出 `BUFFER_CLAMPED` 提示（计划页显示）。这是在**不违背不可中断约束**的前提下，只缩缓冲。p50 都放不下的，仍不排，但提示改成「最长的连续空档只有 X 分钟，可补充更长的可用时间或确认其实可以分几次做」。空档只计能量足够的。
- 未改：可中断作业本来就能跨天拆分，p85 预留不变（这是有意的保守缓冲）。

## 验证
- 单元：core（必需项规则、helper）、闸门（无标准里程碑可判、可选项不拖后腿、必需项缺失不能 pass、预检拒绝落账）、调度（缓冲收缩、明确的阻塞原因、可中断照常拆分、低能量空档不计）。全量 694 个测试、typecheck、e2e 通过。
- 真实 Codex 端到端（空账本、起步里程碑无标准）：同一条捕获重新分析 → 核心证据（对比图、对照结果）必需、脚本可选、三个 `interruptible` 全是 true；提交满足必需项的证据（未交可选脚本）→ 闸门约 34 秒自动验收，`criteriaVerdict: []`。
- 红队：手工作业 + 空洞证据「写完了，感觉不错」→ `insufficient`，原因「缺少结论小节全文及其中的 P99 降幅数字」，作业被挡下。

## 遗留 / 风险
- 现有数据库里已存在的 AI 契约仍是旧的全可选形态：现在它们不再有「可选拖后腿」的问题（可选项不挡 pass），但「没有任何必需项」的旧契约会让闸门只剩 `incomplete` 和 `blockers` 两道关。重新分析可得到新契约；是否做迁移（把单条证据项自动升为必需）需要另行决定。
- 无标准里程碑下自动验收的信任来源是「用户批准过计划」。如果之后希望对这类里程碑更保守（例如首次自动验收前要人工确认），可以在闸门前加一个开关。
- 低置信度缓冲被压缩后，该作业实际留的余量比 p85 少；计划页会显示提示，但不会再次提醒。

## 新发现

1. **你的真实登录看不到旧账本里的真实数据。** 真实库里只有 1 个已验证的邮箱账号，它在 9/29 首次登录时拿到一个全新的空 workspace（`个人 workspace`，只有 4 个起步里程碑、3 个示例作业，外加你后来做的 1 条已验收作业）。而旧的 `personal-crossline` 账本里有更丰富的真实历史——12 个里程碑（含 3 个带可度量标准的已批准里程碑）、18 条作业、24 条捕获、一份可用时间设置——因为它不在 `workspaces` 表里，worker 的 `listWorkspaces()` 循环也不会处理它，**从界面和后台任务两侧都完全不可达**。`docs/user-guide.md` 把「不自动继承」写成了设计，但没给「认领旧账本」的路径，也没有任何提示告诉用户「磁盘上还有一份你的旧数据」。连带后果：可用时间设置没带过来，Plan 页会一直显示「默认时区/时段预览」。
2. **回归（本轮已修）：旧契约全标可选会让闸门门槛变空。** 你账本里已有的 AI 契约是「所有项显式 `required:false`」（旧分析从没被告知 `required` 的含义）。第三轮把「只有必需项算门槛」落地后，这类契约的门槛会变成空集，退回「什么都不报也能 pass」。`requiredContractRequirements` 现在对「全部显式可选」的契约按全部项把关（与以前一致）。同时发现 runner 传给模型的 `required` 与写入层各算各的（模型被告知没有必需项，写入层却按全必需抛错），已统一为同一个 helper；新增两条回归测试。
3. 其余配置核对无问题：真实 SMTP、Microsoft 客户端 ID、监督令牌均已配置；dev 模式下 `private` 的 CSP 会触发一条 React `eval` 报错，仅 dev 有，不影响页面水合与登录。
