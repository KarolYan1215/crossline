# 执行闭环与实测容量：30 天模拟改前 / 改后（2026-10-30）

设计稿：`docs/plans/closed-loop-1030.md`。分支 `claude/closed-loop-1030`。规则与页面见 `docs/rituals.md` §6。

## 怎么跑的

- 种子：本机账本 `data/crossline.db` 的一次 SQLite 在线备份（只读打开），改前与改后用**同一份**备份。
- 三种策略各 30 天，`--seed 7`，模拟日 2026-10-29 至 11-27。不调用任何模型，`fetch` 全部拒绝（每次运行被拒 0 次）。
- 改前：同一个模拟脚本（`scripts/month-sim.ts` 本分支版本，新模块按可选导入）跑在设计稿那一提交（226597da5d）的应用代码上；改前重跑与上一轮的 v3 数字逐项相同（模拟是确定的）。
- 「只加实测容量」：第二块提交后（9e81012714）的中间一轮，只有实测容量，没有推断、收口、逾期处理。
- 改后：本分支最终代码（99a6a5401f 之后只改了文档）。
- 汇总：`sim-data/analyze.mjs` 的输出存在 `sim-data/closed-loop/`；计时分钟由新脚本 `scripts/month-sim-timed.ts` 从结束账本读出。

```powershell
pnpm exec tsx scripts/month-sim.ts --strategy diligent --days 30 --seed 7 --source <备份.db> --out <dir>\diligent.json
node docs/reports/2026-10-30-overnight/sim-data/analyze.mjs <dir>
pnpm exec tsx scripts/month-sim-timed.ts <结束账本目录 crossline-month-sim-*> <dir>\diligent.json
```

## 判定

- **计划兑现率 ≥70%：没有达到。** 改后 0.55 / 0.24 / 0.35（改前 0.42 / 0.17 / 0.22）。按系统自己看得到的计时算，认真和超载已到 0.69 / 0.68。差距来自三处，前两处是设计本身的取值：
  1. 上限是实测中位数 × 1.25，按定义比通常的一天多排四分之一；开始率 0.9 时，计时兑现的上限约 0.8 × 0.9 ≈ 0.72。
  2. 模拟里计时覆盖整块，「真值」做的分钟是块长 × 执行度 × 精力（约 0.8）。系统只能看到计时，所以实测比真值高一截，上限也跟着高。
  3. 有截止的工作在上限内排不下时照样越过上限排（「截止永远优先」，与原来疲惫日只限无截止工作一致）。拖延型一个月有 57 小时排在上限之外，这是它兑现率最低的主因。如果改成越过上限的截止工作不排、只预警，拖延型的兑现率会明显上去，但那是改「截止优先」，需要本人定。
- **每周承诺在超载周触发：部分达到。** 拖延型 4/4 周出现（第 4 周还因超载追问一次），认真型 2/4。超载型 0/4：它的计时天数里每天计时 4–5 小时，中位 × 1.25 后每周可用 32–49 小时，比需求高，系统看不出超载。原因同上第 2 点；加上缺失的日子不进中位数、而上限每天都给，周容量偏高。
- **截止预警先于过期：达到。** 三个可比的截止都在到期前至少 4 天预警，改后没有一个从未预警（改前认真型的小测 3 从未预警）；作业 4 的预警从 4–5 天提前到 9–14 天（拖延、超载）。
- **确认次数：白天下降，收工按人而异。** 白天单独问的完成确认从 30–49 条降到 6–11 条。收工页上，拖延和超载每块点击降到 0.36 / 0.54，认真型几乎没降：推断与模拟真值一致的只有 18%。这在模拟里主要是度量问题——模拟的真值是「这一步是否做完」（隐藏的所需分钟），推断看到的是「这块时间里有没有在做」，块 id 又随重排复用；真实账号上要看推断和本人回答的一致率。
- **「一键」写坏数据**：超载型 29 → 39。70% 规则在模拟里挡不住，因为模拟的计时总覆盖整块；真实计时短于块时才起作用（单测覆盖）。
- **自动收口**：认真 2、超载 5 个任务在本人步骤做完后自己交上（改前这类任务一个月都交不上）。
- **材料提前**：只有一个带材料合同的任务进入窗口；认真型那次点开始不再被「材料准备中」挡住，超载型仍挡了两次（模拟的替身每天 0.9 的概率备好）。另一个一直挡着的是种子里已在「准备中」的任务，本地没有 worker 准备它。

## 对设计稿的偏离（取最保守的做法）

- 屏幕活动没有分类时段的日子，用「电脑前的一天」的每小时活跃分钟代替（不分类别，可能含娱乐）；设计稿说冷启动用它，没说它没有类别。
- 文件夹的文件改动只计数（每天几次），不加分钟，也不让缺失的一天变成有信号。
- 「类别与主线相符或为通用工作类」：现有类别表没有类别到主线的映射，四个工作类别（编程、科研工具、写作、阅读）都当通用工作类；沟通、会议、浏览、娱乐不算。
- 收工页的「做了」只在这一块加上已记分钟够这一步通常估时的 90% 时才推断，否则「部分」：「完成」会把步骤勾掉，块做满不等于步骤做完。
- 外部截止判定从严：课程项目、日期对作业、来源不明（分析从文字里读到的、导入的）都算外部、要问；只有本人改过、每周承诺推过、系统顺延过的才算自定。本人给的「实际最后期限」记为 `work_order.due_confirmed`，仍是外部，再过期会再问。
- 里程碑那一路没动：课程的和本人在目标设置里打的截止仍是问，其余自动顺延两次后问（10-21 的规则）。
- 截止工作越过实测上限照排（见判定第 1 条第 3 点）。
- 测试与 e2e 下实测容量默认关（`CROSSLINE_MEASURED_CAPACITY`），两套看板按所述时间录制；页面上照样显示实测数字，写「按所述排」。

## 没做的

- 推送 ✓做了 / ✗没做 没有在真手机上试过；service worker 里的写法与确认页相同，路由有单测。
- 模拟没有屏幕活动和 Codex 用时（种子里的屏幕记录停在 10-23），推断与容量在模拟里几乎只靠计时。
- 风险卡的「降标准」仍是去主线页，没有在卡上直接改。
