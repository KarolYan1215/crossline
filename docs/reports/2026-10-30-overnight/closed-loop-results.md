# 执行闭环与实测容量：30 天模拟改前 / 上一轮 / 本轮（2026-10-30）

设计稿：`docs/plans/closed-loop-1030.md`。分支 `claude/closed-loop-1030`。规则与页面见 `docs/rituals.md` §6。

## 三列各是什么

| 列 | 应用代码 | 模拟里的计时 |
|---|---|---|
| 改前 | 设计稿那一提交 226597da5d（没有实测容量） | 按真值做的分钟（本轮修正后的模拟） |
| 上一轮 | ce6ebfe22a：实测容量 × 固定 1.25；越过上限的截止工作排在其余紧急工作之后 | 覆盖整块（旧模拟） |
| 本轮 | 本分支最终代码：系数自适应（1.0 起）；越过上限的截止工作照排、当天最前、块上警告 | 按真值做的分钟 |

- 种子：本机账本 `data/crossline.db` 的一次 SQLite 在线备份（只读打开），三列用同一份备份。三种策略各 30 天，`--seed 7`，模拟日 2026-10-29 至 11-27。不调用任何模型，`fetch` 全部拒绝（每次运行被拒 0 次）。
- 「改前」是把本轮的模拟脚本跑在旧代码上，新模块按可选导入。旧代码不用计时排程，所以修正计时前后，改前的兑现率与第一轮相同（0.42 / 0.17 / 0.22），只有「计时 / 排的」变了。
- **模拟偏差的修正**：上一轮的模拟里，人开始一块就计时到块结束，而模拟的「真值」做的分钟是块长 × 执行度 × 精力（约 0.8）。系统只能看到计时，所以实测比真值高，上限也跟着高。本轮改为计时只跑真值那么多分钟（`scripts/month-sim.ts`）。所以上一轮与本轮之间，同时有代码变化和度量变化，不是纯粹的代码对比。
- 汇总：`sim-data/analyze.mjs` 的输出存在 `sim-data/closed-loop/`（`before-`、`after-`（上一轮）、`round2-`（本轮）、`capacity-only-` 四份）；计时分钟由 `scripts/month-sim-timed.ts` 从结束账本读出。

```powershell
pnpm exec tsx scripts/month-sim.ts --strategy diligent --days 30 --seed 7 --source <备份.db> --out <dir>\diligent.json
node docs/reports/2026-10-30-overnight/sim-data/analyze.mjs <dir>
pnpm exec tsx scripts/month-sim-timed.ts <结束账本目录 crossline-month-sim-*> <dir>\diligent.json
```

## 判定

- **计划兑现率 ≥70%：没有达到。** 本轮 0.50 / 0.18 / 0.32；改前 0.42 / 0.17 / 0.22。本轮比上一轮低，原因有二，都来自本人第二轮的决定和模拟的修正：
  1. 越过实测上限的截止工作照排，而且排在当天最前（本人：超出实测就是可能会来不及，优先排程，在块上警告）。一个月里排在上限之外的有 45 / 106 / 16 小时。拖延型被排上的多是它做不完的截止工作，这一项把它的兑现率拉回到改前的水平。
  2. 模拟的计时改成按真值，实测不再虚高，上限从 309 / 194 / 326 分钟降到 201 / 155 / 164。系数一直停在 1.0：三种人物没有一周兑现到 85%，也就没升过档（<60% 时 1.0 已是最低档）。
  - 不算越过上限的那部分，排在上限之内的工作兑现率约为：认真 78 h ÷ (156 − 45) h ≈ 0.70，超载 35 ÷ (111 − 16) ≈ 0.37。拖延型的上限之内几乎只剩截止工作。
- **每周承诺在超载周触发：达到。** 三种人物四周都出现了有推或砍的承诺卡（改前 0 周，上一轮 2 / 4 / 0 周）。超载型上一轮因为计时虚高看不出超载，本轮修正后看出来了。
- **截止预警先于过期：达到。** 三个可比的截止，到期前至少 4 天都有预警。认真型的小测 3 改前从未预警，本轮提前 8 天。作业 4 在拖延型上提前到 15 天。
- **确认次数**：白天单独问的从 30–49 条降到 4–11 条；收工页每块点击 0.88 / 0.81 / 0.65（改前 1.00 / 0.84 / 0.81），推断都对用了 23 / 6 / 9 个晚上。推断与模拟真值一致的只有 30% 上下。这在模拟里主要是度量问题：模拟的真值是「这一步是否做完」（隐藏的所需分钟），推断看的是「这块时间里有没有在做」，而且块 id 会随重排复用。在真实账号上，要看推断与本人回答的一致率。
- **一键写坏数据**：超载型 27 / 39 / 32。模拟的人累了就一键，而 70% 规则只拦计时不足七成的块；按真值计时后，做了 70%–100% 但步骤没做完的块仍会被记成完成。这一点要看真实计时才能判断。
- **自动收口**：认真型 3 个、超载型 5 个任务在本人步骤做完后自己交上（改前这类任务一个月都交不上）。

## 对设计稿的偏离（取最保守的做法）

- 兑现率的分子按天取「实测分钟」与「当天排的分钟」的较小值，计划之外多做的不算兑现；分母只算有信号、有排程的日子。
- 屏幕活动没有分类时段的日子，用「电脑前的一天」的每小时活跃分钟代替（不分类别，可能含娱乐）。
- 文件夹的文件改动只计数，不加分钟，也不让缺失的一天变成有信号。
- 「类别与主线相符或为通用工作类」：现有类别表没有到主线的映射，四个工作类别（编程、科研工具、写作、阅读）都当通用工作类。
- 收工页的「做了」只在这一块加上已记分钟够这一步通常估时的 90% 时才推断，否则写「部分」：「完成」会把步骤勾掉。
- 外部截止判定从严：课程、日期对作业、来源不明的都算外部，要问；本人给的「实际最后期限」仍算外部。
- 越过上限的截止工作「当天最前」：用的办法是先排它们和它们等的紧急工作（占最早的空），再按上限排其余。整个任务越过上限，它所有的块都带警告。
- 测试与 e2e 下实测容量默认关（`CROSSLINE_MEASURED_CAPACITY`）；页面照样显示实测数字，写「按所述排」。

## 没做的

- 推送 ✓做了 / ✗没做 没在真手机上试过。
- 模拟里没有屏幕活动和 Codex 用时（种子里的屏幕记录停在 10-23），推断与容量几乎只靠计时。
- 系数的升降档没有在模拟里出现过（一直 1.0），只有单测覆盖。
