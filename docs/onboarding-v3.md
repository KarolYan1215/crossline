# 登录与访谈 v3（设计，2026-10-14）

机主在本机装好安装版后，以新用户身份看了登录页和访谈页，结论是「登录页很丑、没有可视化；访谈和设计不一样；全是文字」。本文是随后六轮问答确定的方案，按阶段实现，每阶段走查后再进下一阶段。

## 审查发现（2026-10-14，安装版 0.1.0）

登录页
1. 只有一个「C」、标题、一句话和一个普通按钮，看不出产品做什么。
2. 按钮写「用 ChatGPT 登录」，没有标识。OpenAI 的 Sign in with ChatGPT 文档要求写「Continue with ChatGPT」，用官方标识，与其他登录方式同等醒目。
3. 点按钮后在新标签页打开 OpenAI，原页面只显示一行灰字；没有「登录 → 回来 → 开始」的步骤，第一次启动 Codex 的半分钟没有进度，也没说数据只在本机、模型用本人额度。

访谈页
4. 顺序与 2026-10-12 的「先加材料」不一致：第一屏是「先设定主线」，材料在第二屏。（2026-10-08 的设计写的是先设主线，两份设计本身矛盾。）
5. 第一屏先讲六层概念（主线、长期目标、里程碑、任务、步骤、日程），设完主线后又讲一次。
6. 设主线要先理解「参与主次 / 硬约束 / 底座 / 平行」四个概念和四条长规则，只有一个空输入框。
7. 页头说「右侧为实时画像」，第一屏没有右栏，1440 宽时右侧约 40% 空白。
8. 小助手旁浮着只写「10 月 14 日 周三。」的气泡；顶部导航的今日、主线、计划、任务点了都回到访谈。
9. 每轮等 1–4 分钟只有一行灰字；右侧画像几乎都是文字块，「能量地图」是四格文字，阶段条是一排字，「开始使用前还差 N 项」是文字列表；看不到总时长。
10. 12–13px 灰字、细边框，主线颜色在访谈里没有用到，整体像线框稿。

## 决定

### 登录页
- 左右分屏。左边：Crossline、一句「几条人生主线，排进同一张日历」、一段示意动画（几条主线依次接入、一周日历块依次落位；`prefers-reduced-motion` 时为静态）。右边：「Continue with ChatGPT」主按钮（官方标识）、三步说明（在新标签页登录 ChatGPT → 回到这里自动进入 → 回答几轮问题，约 N 分钟拿到第一版一周安排）、「数据只存在这台电脑 · 模型用你自己的 ChatGPT 额度」。
- 等待状态是三步里的当前一步在动，第一次启动 Codex 显示真实进度。
- 风格沿用画像的「编辑杂志」风：米白纸底、衬线标题、墨线分隔，主线色用于图形。

### 访谈页：三栏
- **左栏**：材料与日历（拖入文件、录音、授权文件夹、接入日历；每个来源显示读取状态和读出了什么）、长期目标选取（属性候选拼成「成为 … 的 …」并采用）、已确认的事实与日期（可当场纠正或确认）。
- **中栏**：对话流，输入框始终在底部。
- **右栏**：按阶段切换的实时构建图，可以点回看之前阶段的图；「开始使用」五项标准做成分段进度环放在右栏顶部，并显示预计剩余时间。
  - 开场：主线网络
  - 现状：一周日历骨架（接入的日历、课表、可用时段）
  - 指南针：价值雷达，工作观与人生观对照
  - 能量：「擅长 × 热爱」点阵与心流时刻
  - 细节：里程碑时间轴草图
  - 结束：画像海报，以及用本人内容画出的六层结构图（「你的计划是这样搭起来的」）
- 顶部阶段条带名称，旁边写预计时间。导航在开始使用前不显示四个工作视图。

### 引导性开场
参考机主给的「人生设计师」写法，只取设计引导对话的方式，不照搬内容：
- 第一条消息用大白话说清前提（人生像一件可以反复改的作品，起点是承认现在真实的位置）、接下来的流程、大概时间和能拿到什么。
- 紧接着一道带选项的问题定语气：冷静客观 / 温柔体贴，**默认冷静客观**，之后在设置里可改（2026-10-18 起只留两种；「直接犀利」会引出点破、反转式的 AI 腔，已停用，存着的旧选择按冷静客观处理）。
- 对话用第二人称「你」（只限访谈对话；按钮和其他页面的文案仍按 `docs/copy-style.md`）。
- 仍不做「三个五年版本」和「原型行动清单」（维持 2026-10-08 的决定）。

### 提问节奏：混合
- **事实类**（身份、主次排序、哪条主线有固定日程即硬约束、每周可用时间、项目与截止日）：选项卡片，一批答完。主次和硬约束放进首轮事实卡；开始时可选接入日历，接入后由日历推断，首轮问得更准。
- **深度类**（最焦虑的问题、工作观、人生观、心流、执念）：一次一个，答完给一句简短而切中要害的反馈再追问，追问结束回到主线。用现在允许的最高档模型（`gpt-5.6-sol` medium），不用快速模型。

### 等待
- 实时进度：正在读哪个文件、已整理出几条事实和日期，右栏的图边读边长（需要把运行中的事件传到页面）。
- 等待时可以做别的事：确认已读出的日期、调整主线顺序、采用长期目标。
- 可以离开；下一轮好了时发桌面通知、标签页标题加「● 新问题」、托盘图标提示。

### 日历接入
- 保留 ChatGPT 的日历连接器（Google / Outlook，`calendar-apps.ts`）。
- 在 app 里自建、不依赖用户的 ChatGPT 账号：
  1. 先做订阅地址：粘贴日历的私密 iCal 地址（苹果、Google、Outlook 都能导出），只读，无需授权，配各家图文步骤。
  2. 再逐个加官方授权直连（Google 需机主注册 Google Cloud 项目，内测期最多 100 个手动添加的测试用户；微软需改 Entra 设置；苹果用 CalDAV 加用户自己生成的应用专用密码）。

### 文件夹授权
- 授权一个文件夹路径，递归读取所有子文件夹中能读的文件（PDF、Word、文本、Markdown、幻灯片），默认跳过 `.git`、`node_modules`、缓存；单个文件上限 50 MB，超过的只记文件名。读前显示文件数和总量。
- 持续跟踪：新增或修改的文件在后台重读，用于以后的任务规划和材料准备；设置里可随时取消授权。
- 模型按文件夹名和内容自动归属主线，一个文件夹可属于多条主线；左栏可修改。

## 阶段
1. 合并 `claude/elegant-pascal-ksk86u`（17 个更新提交）。
2. 登录页。
3. 访谈三栏骨架、引导性开场、语气选择、混合节奏、右栏按阶段的图、进度环与时间。
4. 等待体验：运行事件传到页面、等待时可操作、三种通知。
5. 日历订阅地址。
6. 文件夹授权与跟踪。
7. 日历官方直连（逐个）。

每阶段：实现 → 测试 → 以用户视角走查（摩擦、阅读量、语言、视觉）→ 给机主看 → 下一阶段。

- 阶段 2（2026-10-14）：登录页完成。`app/login/page.tsx`（本机版分支）、`login-preview.tsx`（四条示例主线依次接入、一周日历块依次落位，减少动态效果时静止）、`local-login.tsx`（三步、当前一步转圈、Codex 启动时显示已等待秒数）、`login.css`。标题用画像的衬线体（`.pt-serif`），界面用到的固定标题在 `app/ui/serif-strings.ts`，字体子集随之重建。手机宽度下隐藏示意图（标签会缩到 12px 以下；安装版只在桌面上用）。

- 阶段 3（2026-10-14）：访谈三栏完成。

- 阶段 4（2026-10-14）：等待体验完成。
  - 运行时把答案边写边推（`item/agentMessage/delta`），runner 新增 `onProgress`（`SkillProgress`：thinking / writing / checking，带修正与重发次数，写作阶段每半秒一次）。答案按 schema 顺序出，`reply` 在最前，所以 `readPartialTurn`（`packages/core/src/onboarding-progress.ts`）能在一轮结束前读出回复的前半段，并数出已写的问题、事实和日期。这些都不入账、不信任，验收后的答案一到就替换。
  - worker 在一轮运行时把进度写进账本 `onboarding.progress:<会话>`（写作阶段每秒最多一次，另有 15 秒心跳，读文件时也不会被当成停止），结束即删；网页 `GET /api/onboarding/progress` 读取，超过 45 秒没更新视为没有在跑。
  - 中栏的等待气泡（`turn-progress.tsx`）：正在读哪几个文件 → 正在写（回复逐段出现）→ 正在核对引文和日期；已整理几条事实、几个日期、几个问题；已用时间。刷新页面后若后台仍在跑，会接上并在结束时自动载入，期间不能再发一轮。
  - 等待时可做别的事：左栏（长期目标、待补充的事实、事实修改、上传）和日期确认在一轮进行中仍可操作；确认日期不会打断这一轮的等待状态。
  - 提醒：页面不在前台时标签页标题加「● 新问题」；允许后由页面自己发桌面通知（「好了用桌面通知提醒我」）；安装版另有托盘气泡——网页在用户离开 90 秒后往 stdout 写一行 `@crossline:notify {…}`，启动器检查（只许本应用的页面路径）后转给托盘，点气泡打开访谈；手机推送照旧。
  - 预览：`scripts/install-preview-progress.ts [秒]` 在预览账本里模拟一轮进行中的进度。
- 阶段 5（2026-10-14）：日历订阅地址完成。
  - 粘贴日历的私密 iCal 链接（`webcal://` 或 `https://`），只读、不用登录、不依赖 ChatGPT 账号；卡片（`app/connectors/calendar-subscriptions.tsx`）在访谈左栏和设置 → 日历与连接，附苹果 / Google / Outlook 三家取链接的步骤（点「链接在哪里？」展开）。
  - 链接本身是钥匙：只存在 worker 的 DPAPI 密钥库（`ical-<id>`），账本只记名称、域名和最近一次读取的结果（`calendar.subscriptions`），不进导出和备份，换电脑要重新粘贴。
  - 添加前先读一次（`addSubscription`）：打不开、不是日历文件、不是 https 都当场拒绝，不存下来每轮失败。读取走 `safeGet`（公开域名、每次跳转都查 DNS、5 MB 上限、只收日历类内容类型）。
  - 解析用 Mozilla 的 ical.js 2.2.1（无依赖，MPL-2.0）：`readIcal`（`packages/connectors/src/ical.ts`）展开重复日程，应用改期与跳过（`RECURRENCE-ID`、`EXDATE`），文件自带的时区、Outlook 的 Windows 时区名、文件没定义的 IANA 时区和 UTC 都按各自的方式换算（含夏令时切换）；全天、标为空闲和已取消的不算占用。
  - 每个订阅是现有同步里的又一个 `CalendarSource`（键 `ical:<id>`）：没有增量游标，每次读都是全量，所以只对自己的日程有权威；读失败时保留上次的日程并在卡片上说明原因；移除时立刻从计划里拿掉它的日程。没有配置 Graph 的机器（安装版）也照常同步。
  - 访谈：日历里未来七天的日程（`calendarWeek`）首轮必带、之后只在变化时带给访谈，Skill 先从中读出固定日程和已占用的时间，再请本人确认，而不是从零问起；右栏「一周」把日历日程画成灰块，接上日历后从第一阶段起就能看。
- 阶段 6（2026-10-14）：文件夹授权完成。
  - 卡片（`app/connectors/source-folders.tsx`）在访谈左栏和设置 → 日历与连接：填文件夹完整路径 → 「查看」先说要读几个文件、共多大、几个只记文件名、跳过几个依赖/缓存/隐藏文件夹，并列出前几个文件名 → 「授权并读取」后在后台读，读完显示「已读 N 个文件」；「取消授权」后不再读取，已读的内容保留。
  - 规则（`packages/core/src/source-folders.ts`）：递归，不跟随链接；跳过隐藏、`node_modules`、构建输出、缓存、回收站等目录；跳过隐藏文件、Office 锁文件和 `isSecretPath` 认作密钥的文件（`.env`、私钥、密码库……）；读 PDF、Word、文本/Markdown/CSV，单个超过 50 MB 只记文件名；幻灯片、表格、旧版 Word 暂只记文件名；图片和录音不读（私人内容，请主动上传）。拒绝整个磁盘、整个用户文件夹、系统文件夹、应用数据文件夹和 Crossline 自己的数据。每个文件夹最多读 1000 个文件、走 20000 项。
  - 读取（`apps/worker/src/source-folders.ts`）：每个文件按内容哈希复制进应用自己的 `sources/` 再读（与上传同一条提取路径 `extractDocument`），所以原文件移走也不影响；每轮 worker 重扫，按大小与修改时间只读新增或改动的，每个文件夹每轮最多 40 个，其余下轮继续。
  - 主线归属：新 Skill `crossline-folder-classifier`（低档，intake 类后台任务）按文件夹名、文件名和几个文件的开头提议它属于哪几条主线（可多条，可为空，附理由），每个文件夹只问一次；本人在卡片上点主线即改为自己的选择（`linesBy: "person"`），之后模型不再覆盖。步骤规划在任务自己的文件少于 3 个时，会补上归在该任务主线下的文件夹里的材料。
  - 访谈：每轮只读能放进预算的新文件（最多 12 个、约 6 万字），其余留到下一轮并告诉访谈还有几个在等（`sourcesWaiting`），不再出现「标记已读但正文被截掉」；左栏的上传列表不再逐个列出文件夹里的文件。
  - 预览：`scripts/install-preview-server.ts` 的替身后台直接调用同一组 worker 函数，文件夹授权可在预览里真实走通。
- 阶段 7（2026-10-14）：官方直连暂不做。机主的条件是「机主设置好之后，用户能直接连上」，核实下来不满足：
  - Google：日历读取（`calendar.readonly`）属于敏感权限。项目处于「测试」状态时，最多只能有 100 个由机主手动加入的测试用户，每次授权 7 天后失效；要让任何 Google 账号都能用，必须先通过 Google 的敏感权限审核（官方说 3–10 个工作日，还要隐私政策、首页、演示视频等材料）。
  - Microsoft：个人账号（outlook.com）注册好应用后大概率可以直接同意，但未查到官方明确说法；学校和公司账号自 2025 年 11 月起，第三方应用读日历默认要管理员批准，学生（如 UW 账号）多半无法自己连上。
  - 苹果：CalDAV 不需要机主设置，但要用户自己生成应用专用密码再填进来。苹果日历已能用订阅链接接入，暂不另做。
  - 在此之前，订阅链接（阶段 5）对三家都不需要机主做任何设置，用户可以直接用。若以后要做 Google 直连，需要机主先完成 Google 的敏感权限审核。

## 访谈的两层（2026-10-19，重设计 P2）

机主的决定：用户只等对话；整理放到后台，出错在后台修复，不挡住用户。

- **对话层**（`crossline-onboarding`，原 Skill 和原线程，顶档）：只写 `reply`、`questions`、`coverage`、`nextAction`、`stage`（`ONBOARDING_DIALOGUE_SCHEMA`）。读用户的原话和文件原文，不引用编号。每轮的主线和项目 id 是本轮生成的枚举（`onboardingDialogueSchema(ids)`），问题只能挂在已有的主线和项目上；整理层同一轮刚新建的项目尚未入账，问题上的未知项目清空为「关于整条主线」，不退回。之后每轮带 `recorded`：上一轮以来整理层写入的事实（每条一行），对话层据此不重问、不矛盾。
- **整理层**（新 Skill `crossline-onboarding-extract`，中档，规划优先级）：每次新开线程，读还没整理的回复和文件（编号句子），加上已有事实的短索引、各主线的描述与定语、当前画像；写事实、项目、日期、定语与改目标请求、可用时段、主线之间的联系和画像（`ONBOARDING_EXTRACT_SCHEMA`）。更早的内容不整段放进上下文，用两个查询工具按需读：`search_evidence`（按词找句子）、`read_sentences`（按编号读，带前后句）。查到的编号都可以引用。
- **何时运行**：每轮对话一开始就并行启动整理，用户拿到回复不等它。只有对话层说「访谈可以结束」时才等整理跑完，再读完成清单，免得刚说的事实还没入账就被判为缺项。每个工作区同一时间只跑一个整理；运行中又来请求，结束后再跑一遍；超出一次预算的文件（12 个、约 6 万字）接着下一遍读。
- **进度记录**：每个会话的整理水位（已整理到第几条回复）、失败次数和下次重试时间存在 `onboarding.extract:<会话>`；待整理的文件存在 `onboarding.extract.docs`（文件 → 整理时第一句的编号；重新提取过的文件编号变了，就再整理一次）。失败后按 1、5、30 分钟退避，由 worker 的定时任务重试（`onboardingExtractPass`）；用户的下一轮回答会立即再试。
- **页面**：访谈页状态接口返回 `organizing`（待整理的回复数、文件数、正在失败时的原因）。整理没完成时右栏显示「正在整理刚才的回答…」，页面每 5 秒刷新一次，「开始使用」等整理完成再出现；整理一直失败时不挡用户，显示「系统会自动重试」。
- **兼容**：存下的每轮只含对话层的字段；旧会话里的轮次照常读。旧的整轮输出结构 `ONBOARDING_TURN_SCHEMA` 删除；两层仍由同一套校验规则检查（各补上另一层的空字段后检查，再裁回自己的字段）。赞助模型的选型要求访谈两层都通过合规测试（`SPONSOR_EVAL_VERSION` 5）；样例访谈只测对话层。
- **开始前核对一次**（P2c）：开始标准达成、整理也跟上之后，右栏按钮是「核对后开始使用」，打开一页清单：每条主线的描述、已采用的长期目标、当前项目和截止；每周可用时段（总时长和来源：本人设置 / 访谈推定 / 按总时长平均 / 默认）；每周固定日程。「确认无误，开始使用」后才放行其他页面，第一批里程碑草稿也等它；有不对的回到访谈直接说。已经在用的账号（确认上线前已达标，或已有里程碑、任务）不需要再核对。
- **审查后修复**（同日）：
  - 已有会话的整理水位在 worker 启动时回填到最后一条回复（`backfillExtractWatermarks`，每个工作区一次；整理跑过的工作区不再回填），否则上线后第一轮会把所有旧访谈从头再整理一遍、重写已确认的画像。
  - 每轮最多读 6 条回复，其余接着下一轮。定时重试受额度（核心任务）和「规划」暂停约束；用户自己的回答仍立即触发。
  - 日期 id 改由内容生成（日期、时间、类型、标题；每周安排按星期和时间），新开线程的整理每次都从 d1 编号，按模型的 id 合并会让后一轮的 d1 覆盖前一轮还没确认的 d1。
  - 已有的模型连接合规记录里只有旧的整轮结构，视作两层都通过，不会在上线后把自带模型的账号挡在访谈外。
  - 整理进行中又来的请求带上自己的会话，下一轮优先处理、绕过退避；进行中的那一轮失败也会再跑一轮。访谈要结束时等的是「这条回复已整理」，而不只是等当前这一轮结束；有阻塞性补问时最多等 30 秒，免得刚回答的问题又在下面出现一次。
  - 线访谈里出示的文件也排队，跟主访谈一起整理；重读按对话层的节奏排队（每轮 12 个），不再一次把全部文件排进去。整理中途被重新排队的文件不会被这一轮标成已整理。
  - 意外异常也走退避；一次整理的写入（事实、文件标记、水位）放进一个事务。「符合」只在它是本轮最后一条回复时才认作对新画像的确认。上一轮对话失败时出示过的文件，若已按当前内容整理过，不再重复整理。
- **画像按段维护**（P3）：画像分四段，`situation`（真问题、不可改变的处境、可设计的问题、重新定义）、`compass`（工作观、人生观、两者是否一致、正北、施瓦茨价值）、`energy`（能量地图、心流、所说与所做、执念与真正想要的）、`synthesis`（一句话画像、核心矛盾、注意力分配）。整理层只在新内容涉及某段时整段重写该段（附依据句子编号），不再每轮重写全部；对话进入下一阶段后，上一阶段的段落用查询工具回看全部相关回答再整段定稿（`profileTask.finalize`）；三段都定稿后才写综合段（`profileTask.synthesize`），之前写的综合段被忽略。每段的依据句子和是否定稿存在 `profile.sections`。画像确认的指纹只看综合段（一句话画像和核心矛盾），各阶段定稿不再触发重新确认；旧格式（含真问题）的确认按旧算法继续有效。

## 精简与回报（2026-10-19，机主与测试者反馈后的决定）

测试者反馈「问得太细，耐心很快没了」。调研结论（问卷长度、选项数量、进度条、个性化反馈的研究）和机主逐条确认的做法：

- **五个部分**：定向 → 主线 → 处境 → 指南针 → 能量，之后出画像报告。原来的「细节」阶段取消：项目的目标、证据、评分占比和其余截止，从文件和对话里推断，仍缺的在拆步骤时或在待决事项里再问。清单里的项目项标为延后（`deferred`），不再挡住访谈结束（`interviewComplete`、`interviewOwnedOpen`）。单条主线的访谈仍用 `details`。
- **截止日期**：提示词告诉用户说个大概时间就行；每条主线最多问两三个影响计划的核心截止，当前项目的截止优先。用户的大概说法算本人确认（整理层写成「2026-12-15（12 月中，大概）」）；能从文件或对话推出来的写成「推断：…」，不算开始标准，截止题里多出一个选项「就按 …」，点一下变成本人确认（`DEADLINE_GUESS_PREFIX`）。只有一条主线还没有任何项目知道截止时，截止题才阻塞；同一条线其他项目的截止题不阻塞，开始使用后进待决事项。
- **选项**：不设硬上限，问到清楚为止；提示词从「8–14 个候选」改为「覆盖常见答案，通常 3–6 个」，选项说明 ≤80 字且只在标签说不清时写。深度题可以是开放回答，配最多三个示例。
- **处境**：「五年不变的周二 / 十年后」换成「如果接下来三个月节奏不变，最先出问题的是哪件事」。每部分的话题写在提示词里，各问一次。
- **拉回主线**：用户聊偏时，回复用一句话接住、说明已记下，回到当前部分。
- **进度账**（`progress`，对话层每轮必写）：当前部分、已谈清、未谈、本轮回答后这一部分是否完成、下一步问什么。存在会话里，下一轮开头原样交还给模型（`progressLines`），右栏显示「第 3/5 部分 · 处境 · 已谈清 2/3」和「接下来：…」（`progressView`）。阶段仍由提示词控制，代码只保存、交还和显示。
- **精简账本**：每轮给模型的不再是完整清单、全部问题编号和 40 行新记录，而是：进度账、开始标准缺项（≤8 条）、整理层摘要（≤15 行，由代码从账本拼出：各主线描述、长期目标、项目和截止，每周时长，深度部分已写的一句，刚记下的 ≤5 条；`interviewAbstract`）、最近 15 道题。更早的重复题由代码按编号和相似度删掉。
- **观察卡**（`insight`）：处境、指南针、能量每轮一张，把用户不同回答里的两句原话连起来，再用一个短句点出两者之间的模式（如「反馈快的事在挤占反馈慢的事」；2026-10-19 用户确认允许），不给建议、不评判性格。代码核对每段引文都在它所引的回复里、至少两条不同回复（`checkInsight`），不符就丢掉卡片、不退回整轮。用户点「准 / 不准」（`POST /api/onboarding/insight`，存 `onboarding.insights`）：下一轮和整理层都会看到；三个深度部分各有一条「准」，等同确认画像（`portraitConfirmedByInsights`）。
- **阶段回报**（都由代码计算，`apps/web/lib/onboarding-board.ts` `weekCapacity`，`packages/core/src/onboarding-pace.ts`）：
  - 定向：**文件读出的清单**。文件里的日期和每周课程直接采用（`import_dated_items` 改为 `automatic`，`adoptPendingDates`），读取时把握低的不加入；清单逐项可「移除」或「加入」（`POST /api/onboarding/dates/item`，`changeAdoptedDate`）。
  - 主线：**你的一周**。每周可用小时、固定安排占用、剩余小时按主线主次分（底座两倍，或用户设的份额），未来四周的截止数和挤在一起的截止（三天内两个以上）。
  - 开始标准达成：**本周骨架草稿**。把空闲时间按主线权重分成块，画在一周图上，并列出每条线约几小时；只是草稿，开始使用后按真实任务排程。
- **收尾与等待**（同日走查后）：对话层宣布可以结束时记下「收尾」（`markFinishing`），整理层把它当作访谈已完成：定稿全部深度段并写综合段，没有新回复也会跑（最多两次）；综合段不算访谈欠的项（`portrait_synthesis` 延后）。结束访谈的一轮最多等整理层 90 秒，之后画像类清单项不再把结束改回提问。开始按钮只等开场与主线部分的回答和文件（`extractBacklog().frontReplies`），深度部分的回答排在后面不影响开始使用。

## 访谈到设置（2026-10-30）

机主要求：访谈里本人说过的偏好，应该在访谈中就变成系统设置。审计结论：此前只有「可用时段」会被系统读取；「几点后别提醒」「专注多久一段」「别让助手回邮件」都只存成事实文本，没有功能读取。

- 提取层输出 `settings[]`，只允许 `INTERVIEW_SETTING_KEYS` 里的键，每项必须引用本人的回复；隐私同意不在其中。
- 「核对后开始使用」列出这些设置，默认勾选，附本人原话；确认时生效。开始使用之后才说的设置，作为一张待决卡片出现（全部应用 / 保持现状）。
- 新增两个设置：免打扰时段 `notify.quietHours`（默认 23:00–08:00，可跨零点）和晨间简报时间 `notify.briefTime`；设置页「时间与提醒」可改，输入框也能改。
- 能量部分加问作息；本人说的作息 `sleep_window` 在没有睡眠记录时作为精力曲线的平常夜晚。本人说出最清醒、最困的时段时，提取层重写可用时段的精力高低。
- 规则修正：回答「不确定」的问题可以再问一次（不再无限兜底同一个泛问题）；用数字衡量的项目要问目标数字；只有「日常工作、没有截止」的固定日程主线不生成里程碑；同一条链里前面的分数线不得高于最后的目标。

验证：`scripts/onboarding-eval.ts` 三位模拟用户（自由设计师、上班族极简版、机主档案）改前改后各跑一轮，`scripts/interview-handoff.ts` 读出交接结果。报告见 `docs/reports/2026-10-30-interview-review.md`。

## 访谈能结束（2026-10-31，虚构人物走查的 P0）

走查（`docs/eval/persona-walkthrough-2026-10-31.md`）里两位虚构用户到 26 轮上限还没结束：开始标准早已满足，模型说「可以开始使用」却仍是 `ask`，只剩选定长期目标这一项本人才能做的事，而这道题被筛掉了。改动：

- **开始标准满足后，前段没有可问的就结束**：主访谈的开始项全部完成、不在画像模块阶段、本轮没有卡片也没有剩下的题（模型的题都被筛掉）时，这一轮直接按 `ready_for_milestones` 结束并记下收尾；画像类清单项不再把结束改回提问。其余缺项在开始使用后进待决事项。提示词同时规定：说「可以开始使用」的那一轮必须是 `ready_for_milestones`。
- **长期目标在对话里选**：还没有长期目标、但已有候选定语的主线，由 app 出一道题（`LINE_GOAL`，`gap-goal-<线>`，多选、可自己写，选项是候选定语），本人点选即采用（`adoptLineGoal`，`line.updated` 记 `via: "interview"`）。这道题挡住开始，但不让一轮等它；单条主线的访谈不出。模型不再自己问长期目标。
- **零题轮**：网页重新筛题后一轮若一题不剩，又没有卡片和 app 的题，就补一道当前阶段的开放题（`openStageQuestion`），不再出现「要回答却没有题」的一轮。
- **「还缺」不过时**：整理层还欠着回复时，右栏开始标准里未完成的组显示「整理中」，不列旧的缺项名。
- 取舍卡点 2、4 写明偏向哪一端，见 `docs/profile-and-agent-kit.md`。

## 少问、不重复、说人话（2026-10-31，走查的 P1 与 P2）

同一次走查的其余问题：一位虚构用户的应急存款被问了 6 次，另一位的可用时段和组会各问了两次；「硬约束」「定语候选」原样出现在给本人的话里，课程模板的「上课、组会、值班」给了仓库主管；回复里出现本人没说过的细节和时间；叙事题太抽象，第一题还把父母排除在外；首屏 6 道评分题，一轮最多 5 问且选项重复；性别和学段被默认。改动：

- **清单只给系统看**：清单项多了 `ask`（给本人的问法），标签和说明留给系统。模型要结束而清单还欠着时，回复只加一句「开始之前还想再问几件事」，问题用缺项的 `ask`（至多两个），没有 `ask` 的缺项用本阶段开放题；开始项的补问同样用 `ask`。「固定日程已收集」也认回复里写明星期和钟点的事实（`statesSchedule`），主线描述也认本人说的 `description` 事实，免得同一件事被一问再问。
- **重复问**（`resolveRepeats`）：同一条主线、同一个项目的题，相似度 0.6 就算同一题（其余仍是 0.85）；不论措辞，同一件事最多问两次（`MAX_ASKINGS`，按改写一跳串起来算）；同一轮里意思相同的两题只留第一题；选项去重（`withDistinctOptions`）。项目不同的两题（两个项目的截止）不算重复。
- **内部用语兜底**（`withPlainTerms`）：回复、问题、选项和进度里的「硬约束」「定语/候选定语」「开始标准」「检查清单」换成日常说法；提示词同时禁止用这些词。目标提议的说明从「分数线」改成「目标」。
- **固定安排按这条线的身份问**：学生问上课和学期，上班的问工时、排班、例会，带孩子的问接送；不把学生的话术给上班的人。
- **回复里的事实只来自本人或文件**：时间、数字、细节照本人原话，不为通顺添加；不猜性别、学段、职业、家庭，称「你」或名字，不用他/她。整理层和画像撰写也照此只记本人说过的。
- **叙事题给具体起点**：每道叙事题给两三个日常的例子答案；答「没有」「想不起来」时改问一件最近的小事（最近一次被夸、上个月最顺的一天）；第一题不再排除父母；叙事阶段的开放题改成「说一件你这几年做过、现在想起来还挺得意的事」。
- **一轮更短**：模型的题每轮最多 3 道（各阶段都算，单条主线的访谈除外）；app 的非阻塞题只在一轮不足 4 道时加入；评分卡一轮合计至多 3 项（`ITEMS_PER_ROUND`）；兴趣卡（想不想做）不和事实题同轮。

## 时间挡位（2026-10-31，机主的决定）

上面每一次压缩都是为了省时间。机主决定让本人自己选：开场卡上先问「访谈问多细？」，开始后对话上方也能改（`onboarding.depth`，`/api/onboarding/depth`；没选过的账号按 `quick`）。挡位只决定问多少，本人原话、文件优先、不重复问、说人话这些规则在每一挡都一样。数值在 `packages/core/src/onboarding-depth.ts`（`DEPTH_PACE`），提示词在访谈 SKILL.md 的「How thorough」一节。

| | 快速 `quick` | 标准 `standard` | 事无巨细 `thorough` |
|---|---|---|---|
| 时长 | 约 50 分钟（就是上面压缩后的访谈） | 约 80 分钟 | 约 2 小时 |

## 折叠与回执（2026-11-10，机主的决定）

机主定的规则：一次性的卡片做完就消失，能反复用的留着，每一步都能撤销。

- **过去的轮次折成一行**（`round-fold.ts` 的 `foldThread`）：最新一轮之前的每一轮（模型的话加上本人随后的回答）折成「第 N 轮 · 一句话摘要」，摘要取模型回复的第一句；开场卡的回答折成「开场 · …」。点开看全文。最新一轮和正在发送的回答不折。
- **观察卡（准 / 不准）**：评过的随所在轮次折进去，折叠里仍能改评；过去轮次里没评的留在折叠行下面，评完才折进去。最新一轮上评完留约 1.5 秒回执（`receipt.tsx` 的 `Receipt`），带 撤销；撤销是 `POST /api/onboarding/insight` 的 `verdict: "clear"`，删掉这一轮的评价，卡片回来。
- **其他一次性卡片**：日期卡（「加入日历」或「都不加入」）和公开测评的「不是我的结果」做完后留约 1.5 秒回执，没有撤销（这两步没有反向接口）。「已带入公开测评结果」那一行是能反复用的（可移除），照旧留着。

## 三层路由与整理提速（2026-11-12，四次回放之后）

### 问题

四次回放都卡在整理层，表现有三种：

- **开始标准晚到。** 第 14 轮她就给了课表，第 24 轮账本里才有。这期间模型说「齐了」，结束按钮却按不动。
- **结束后干等。** 按「结束并出报告」后，要等最后两次整理（5 分钟、9 分钟）加画像（4 分钟）。
- **单次整理太长。** 回放 3 的一次整理用了 27 分钟、输出 2.6 万 token。10 次整理合计 5342 秒、19.5 万输出 token，其中推理 10.8 万。

根因在代码里（`onboarding-extract.ts`）：

1. **每次整理都把假设日志（最多 40 条）、职业方向（带招聘要求矩阵）、十个维度整份重写。** 指令写着「每次都把……整份重写」，Skill 写着「没有新内容也原样抄一遍」。新内容通常只有一两条，其余全是重抄，输出 token 和推理时间都花在重抄上。
2. **一个工作区一次只跑一个整理。** 课表这种开始标准要的事实，和画像的长推理排在同一个队列里，要等前一次画像重写跑完。
3. **三层之间没有分工。** 对话层是交互优先级，不占槽位。整理、调研、画像都是后台。整理里「记事实」和「推画像」两种负载被绑成一次运行。

### 外部做法（调研）

- **前台对话、后台记忆分开跑**：Letta 的 sleep-time agent 把记忆整理从对话回路里拿出去，后台用更大的模型、不受延迟约束（[Letta](https://letta.com/blog/sleep-time-compute)，[论文 2504.13171](https://arxiv.org/abs/2504.13171)）。我们已经是这个结构。问题是后台本身太慢，还挡住了前台要的事实。
- **只输出变化，不重写全量**：Mem0 让模型对已有记忆做增、改、删、不变四种操作，而不是重写记忆库。论文报告 p95 延迟比全上下文方案低 91%（[2504.19413](https://arxiv.org/abs/2504.19413)）。JSON Whisperer 让模型输出 JSON patch，token 少 31%，质量在全量重写的 5% 以内（[2510.04717](https://arxiv.org/abs/2510.04717)）。「To Diff or Not to Diff」在长文本编辑上用差量，准确率不变，延迟和成本降三成以上，并提醒按行号定位的差量格式脆弱，要用稳定 id 定位（[2604.27296](https://arxiv.org/abs/2604.27296)）。
- **按字段拆成独立任务并行**：子任务真的独立时，拆开能降延迟、质量几乎不降；但约四分之一的任务有隐藏依赖，盲拆有风险（[ParallelPrompt 2506.18728](https://arxiv.org/abs/2506.18728)）。
- **抽取不靠高推理强度**：多份评测里，结构化抽取的 low/medium/high 准确率几乎一样，延迟差两到五倍（[LlamaIndex](https://llamaindex.ai/blog/the-cost-of-overthinking-why-reasoning-models-fail-at-document-parsing)，[Shift Technology](https://www.shift-technology.com/resources/reports-and-insights/the-state-of-ai-in-insurance-vol.-viii-reasoning-models)）。这一条只记下，这次不改：要先在我们自己的回放上测。

**批判。**

- 增量输出唯一的精度风险是「漏改」：模型改了一条假设，却没把相关的另一条一起改。对策有两个：
  - 账本里的完整列表每次照常给模型看（输入不减，只减输出）；
  - 模型要改的是哪一条，用稳定 id 指明（假设 `id`、维度 `D0–D9`、职业按 `role`），不靠位置。
- 拆通道的风险在依赖关系上：画像要用到事实。画像两条通道通过 `search_evidence` 读全部原话，不依赖账本是否已写完。推断和画像各节互相读对方上一次写的结果，晚一轮，不阻塞。

### 设计

**整理拆成三条通道，同一个 Skill，按通道裁剪输入、输出和优先级。**

三组字段互不依赖：账本记事实，画像各节写叙述，推断写假设、职业和维度。所以三条通道并行跑，不排队。

| 通道 | 写什么 | 输入 | 每次读几条回复 | 优先级 | 谁在等它 |
|---|---|---|---|---|---|
| 账本（ledger） | 事实、项目、日期、主线描述与定语、目标改动、可用时段、设置、量表文字答案 | 新回复、待读文件、事实索引、主线和项目；**不含画像** | 6 | 访谈中 interactive，其余 intake | 开始标准、下一轮 |
| 画像各节（sections） | 画像各节、主线之间的飞轮 | 新回复、完整画像、观察卡评价、调研结论、`profileTask` | 12 | planning | 报告 |
| 推断（insights） | 假设日志、职业方向、十个维度、`dropCareers` | 新回复、完整画像、观察卡评价、调研结论 | 12 | planning | 下一轮的观察卡、报告 |

- **水位。**
  - 每条通道有自己的水位和失败退避，键是 `会话#通道`。
  - 账本通道沿用原来的水位：开始标准、`caughtUp`、`extractionReached` 等的仍是它，含义不变。
  - 画像通道第一次跑之前，继承账本的水位（`readLaneState`）。部署时进行到一半或已经结束的访谈，不会从第一条回复重读。
- **并发。**
  - 每条通道一次只跑一个；三条可以同时跑。
  - 后台槽位每个账号 2 个，两条画像通道（planning）可能同时占满几分钟。访谈进行中的账本通道因此按 interactive 跑，不占这两个槽位：本人在等它（开始标准、下一轮的问题），它的输出也小。访谈结束后，以及单条主线的访谈和笔记，账本通道仍是 intake。
  - 内存过线时 interactive 也排队（`model-gate.ts`），所以多出的这一路不会压垮机器。
- **触发。**
  - 每条回复同时请求三条通道（`requestAllLanes`），回合只等账本。
  - 画像通道自带合批：一次运行几分钟，这期间到的回复下一次一起读。
  - worker 的定时检查按通道补跑：哪条通道有到期的回复，就跑哪条。
- **不读文件的通道。** 只有账本读文件；画像两条通道需要时用 `search_evidence` 查。
- **只走账本的会话。** 单条主线的访谈和零散笔记不碰画像，账本通道对它们按一次写全部来跑，和以前一样。
- **结束访谈。**
  1. 等账本追上最后一条回复。
  2. 等推断、画像各节也追上。
  3. 再跑一次画像各节，把综合写完。
  - 三步共用 20 分钟上限。
- **单次运行（`all`）。** 测试和评测脚本里的单次整理不分通道，仍是原来的一次写全部。

**推断通道只输出变化。**

- `hypotheses`：只写新的假设，和状态、表述、依据有变化的假设，用原 `id`，写整条。账本按 `id` 合并：同 `id` 替换，新的追加，没写到的保持原样。推翻的假设改成 `refuted`，不删。
- `dimensions`：只写有变化的维度，按 `D0–D9` 合并。
- `careers`：只写新的方向和有变化的方向（按 `role` 合并，写整条）。不再成立的方向写进 `dropCareers`（职业名列表）。
- 职业的 `hypothesisIds` 可以引用账本里已有的假设，不限于这次写的。

**三层的分工（负载）。**

| 层 | 跑什么 | 优先级 | 并发 |
|---|---|---|---|
| 对话 | 每轮一次，线程常驻 | interactive，不占槽位 | 每个访谈一个 |
| 账本整理 | 每条回复一次，小输出 | 访谈中 interactive，其余 intake | 每个工作区一个 |
| 画像各节 | 合批，整节重写 | planning | 每个工作区一个 |
| 推断 | 合批，增量输出 | planning | 每个工作区一个 |
| 调研 | 对话提出的问题，各自一条线程 | background | 每个访谈最多 4 条 |
| 画像报告 | 结束后一次 | background | 一个 |

- 账号内的两个后台槽位：两条画像通道各占一个；访谈中的账本通道不占槽位；调研排在画像通道之后。
- 账号之间：闸门按「最久没被服务的账号」轮转（`model-gate.ts`），不改。

### 验证

用同一个模拟用户（y）回放，对比回放 3、4：

- 她给出课表到开始标准满足之间隔了几轮；
- 单次账本整理和画像整理的输出 token 与用时；
- 按结束到报告写好的用时；
- 推断条数和被判「准」的比例（精度不能降）。

## 要点账本（2026-11-12，第五次回放之后，机主的决定）

### 问题

画像各节在阶段结束时整段重写（一次可到 20k token），段落之间的说法没有出处可查；观察卡和推断的假设各是一套，同一个方向在访谈里被换个说法再提一次；职业方向名字稍有不同就记成两条。

### 规则（只对新访谈和机主点名的两个账号）

- **要点**：画像的内容先记成要点（`ProfileModel.points`，`packages/core/src/profile-points.ts`），每条可以是一段话，必须引用她的原话（`quotes`），可以附调研线程找到的网页（`external`，只收 `researchUrls` 里的）。没有引用的要点不收。来源三种：`stated`（她说的）、`confirmed`（她对观察卡说「准」）、`corrected`（她对观察卡说「部分对」时写的纠正）。
- **只写变化**：画像通道每轮只输出 `pointChanges`（add / revise / retract）；只有她自己说的要点能被改或撤回，改和撤回要写理由，留在 `log`。段落只在该节定稿时写一次，报告最后才从要点写成。
- **推出来的不是要点**：模型推断的结论进假设日志（`hypotheses`）。观察卡就是假设日志里的一条（`hypothesisId`），对话每轮拿到日志和要点（`hypothesisLog`、`points`），已经问过、已经被判、或已被推翻的假设不会再出卡；卡上没有对应假设时，代码按卡建一条 `c<回合>`。
- **三个按钮**：准 → 假设 `supported`，记一条 `confirmed` 要点；不准 → `refuted`；部分对 → 必须写一句纠正，纠正作为原话记成 `corrected` 要点，假设保持未定。改判或撤销先还原上一次的效果（`rateInsight`，`packages/db/src/insight-rating.ts`；回放脚本用同一个函数）。卡上判过的假设之后的整理不再改动（`settledOnCard`）。
- **职业方向两层**：行业 + 职能为一个方向（`k<n>`），具体岗位或实习进 `entries`。同一方向只有写明 `change` 的理由才会被替换，理由记进 `log`；新方向要写 `differs` 说明和已有方向的区别。
- **页面**：访谈中只显示她确认过的要点和假设（`PointsList`）；阶段定稿（`sectionsFinal`）之后才显示针对该阶段的当前看法。
- 老访谈保持段落写法（`coverage.rules` 没有 `points`）。

### 账号迁移（`scripts/points-migrate.ts`）

- 机主的账号：备份账本后 `--split`，主访谈改用新规则，并把已有段落的各节记进 `profile.points.split`；画像通道下一次运行把段落拆成带原话引用的要点，跑完删掉这个设置。旧段落保留不动。
- 一位反馈用户的账号（只有访谈）：`--export` 导出全部消息（只放服务器，不进仓库），用新规则在副本上从头回放并重测，然后 `--reset` 清空账号，下次登录从访谈开头走。

### 观察卡从日志里挑（2026-11-13，第六次回放之后）

第六次回放的 12 张卡都是对话当场新推的假设，整理记下的 25 条一条也没问过（两边相似度不超过 0.16）。现在由代码挑候选（`cardCandidates`），每轮放进对话上下文的 `cardFrom`：

- 最多 3 条；
- 必须还没定论、没出过卡、至少有两条回答支撑；
- 每条附上它依据的回答和原话；
- 排序：出卡最少的维度优先，其次依据多的，再次早的。

有候选时，观察卡只能从里面挑一条；都接不上这一轮的话就不出卡。没有候选时，对话才可以新推一条。

第七次回放之后补了三处，否则候选一直是空的：

- 卡一出现就给那条假设记上 `cardKey`，不管有没有评，所以没评的卡不会再被挑出来。
- 整理新写的假设一律按日志编号 `h<n>`（`numberNewHypotheses`）。它照着卡的 `c<seq>` 往下编过，会和下一张卡撞号；新卡的 id 撞号时也加后缀。
- 推断通道在候选不足两条时不等批（见 `docs/token-economy.md` §4）。


### 用户视角的几处修正（2026-11-14，第八、九次回放之后）

按本人读到的样子重看了第八次（17 轮）和第九次（20 轮）回放，有五处问题：

- **自伤的经历被反复用。** 第三轮按「安全」处理过、本人说现在没有了之后，第四、五、十五轮的观察卡仍然从这段经历推断，第十轮的选项里还出现了「情绪上又来一次大三上那样」。第九次回放更是在问安全确认的那一轮就放了一张观察卡。现在由应用把关（`disclosureReplies`、`handlesDisclosure`，`packages/core/src/onboarding-pace.ts`）：回复里带求助热线的那一轮不出观察卡；引用了引出这件事的那条回答、或安全确认那条回答的观察卡，会被拿掉。Skill 的「安全」也写明，之后整场不在选项、例子和回复里提这件事，除非本人自己再提起。
- **观察卡命中率低，同一主题反复出。** 两次回放各出了 14 张卡，第九次评分是准 2、部分对 8、不准 4。被评「部分对」的卡，多数是「你要的不是 A，是 B」这种句式，本人的更正几乎都是「A 也是真的」。另外，对话只看得到最近 4 条评价，「难受时自己消化」这一主题出了四张卡。现在 Skill 要求：推断是补充，不去否定本人说过的动机；被更正过的主题，下一张卡要把更正写进去并带上新证据，否则换一个维度。看得到的评价从 4 条增加到 12 条（`OBSERVATIONS_SHOWN`）。卡的频率不变，仍然是有证据就可以出（2026-11-12 的决定）。
- **同一个故事被要了五次。** 高峰、最骄傲、自己定方向的一件事、写报告的方法，问的是不同问题，本人每次讲的却都是同一场比赛。Skill 现在要求：问这类问题之前先看线程，在题干里把讲过的那件排除。
- **调研结果整段贴进对话。** 第十、十三、十四轮的回复里逐条列出各家的截止日期、出勤要求和学历门槛。调研结论本来就在右栏显示，现在回复只说改变下一步的那一条结论，一两句。
- **第九次回放到第 19 轮才能开始使用。** 第 7 至 18 轮只差固定日程和可用时间两项，但画像部分在前、不限轮数是已经定下的顺序，所以这次没改。真实页面上，左栏的事实问题随时可以回答，回放里的扮演者不会去答它们。如果这个等待在真实账号上也明显，要重新决定顺序。

### 第十次回放之后的修正（2026-11-14）

第十次回放（22 轮）验证了上面五处：观察卡从 12 张降到 5 张，没有一张被评「不准」；安全那一轮没有卡；同一个故事只被要了 2 次；画像写成。按本人读到的样子，还剩下面几处。规则只写在 Skill 里时模型并不总照做，所以这次能在代码里把关的都放进了应用（`packages/core/src/onboarding-reply.ts`），Skill 里同时写明。

- **安全那一轮的回复仍在解读那段经历。** 求助热线后面接着写「回到前面：你敬佩的人……和那段时间正好相对」。现在应用把这一轮的回复截到求助渠道为止，后面只保留问句（`safetyReplyOnly`）。Skill 写明这一轮只做三件事：接住、问一句现在、给求助渠道。
- **「最骄傲的一件事」又把第一轮讲过的那次考试要了一遍。** 一旦问过一次「最有成就感 / 最骄傲 / 高峰」，之后同类问题的题干如果没有排除讲过的那件，应用会加上「除了前面讲过的那件，」（`withoutToldStory`）。Skill 在能量阶段的 D7 那里也写明了要排除。
- **调研细节仍有大段进回复。** 回复重复了已完成调研线程里三个及以上的日期或数字，就退回让模型重写这一轮（`researchCopied`，`RESEARCH_FIGURES_MAX` = 2）。重写还是不行，就按原样保留（`softAccept`），不会因此丢掉一轮。第十次回放里第 14、15 轮会被退回，第 18 轮（两个数字，是改变下一步的那一条结论）不会。
- **回复和观察卡说同一件事。** 回复里和卡片字面重合一半以上的句子，应用会删掉（`withoutCardEcho`）。本人在卡上评这条推断，不需要读两遍。在第十次回放上测过：第 13、18、20 轮各删掉一句，都是确实重复的句子。
- **回复里否定本人自己说的理由。** 比如「分数本身就在给你回报，不必等到以后有得选」。「推断是补充」这条规则原来只约束观察卡，现在 Skill 写明 `reply` 同样适用。这一条没法在代码里判断，只靠 Skill。
- **按「结束并出报告」之后等了约 70 分钟。** 撰写要等最后两次画像整理跑完，而服务商当时一直在慢慢出字（约 3 token/秒），所以 idle 看门狗不会触发。现在 `finishInterview` 最多等 `FINISH_BUDGET_MS`（8 分钟），时间到了就用已有的记录写画像，整理在后台继续跑；日志记一条 `onboarding.finish_late`。画像撰写逐字读本人的每一条回答，晚到的整理只会补上最后几条回答的要点，所以不再为它重写一版画像，本人可以自己按「重新生成」。persona-eval 也改成和应用一样：在同一时刻写画像，并记录从按下到写成的分钟数（`waitedMinutes`）。
- **答过的时段，后两轮回复还说「还在记录」。** 时段第 14 轮就答了，开始标准第 17 轮才满足。现在做三件事：(1) 事实阶段（开场、主线）开始标准还没满足时，对话先等这条回答的整理，最多 60 秒（`START_WAIT_MS`）；(2) `startStandard` 里答过、还没写进记录的项单独列在 `answered`，不再算作 `missing`；(3) 回复里说「还在记录」「记下后就能开始」的句子会被删掉（`withoutRecordingTalk`）。
- **收尾问题问了两遍。** 本人对「还有什么想聊的吗」答了「没有了」，下一轮又被问一遍。原因有两个：Skill 要求这一轮再问一次；而且模型的问题被当作重复去掉之后，应用又补上了自己的收尾问题。现在本人这样答过之后，下一轮不放收尾问题（`saidNothingMore`），回复只说按「结束并出报告」就会出报告，输入框照样可以写。
- **本人勾过的「有自己的茶室这样的事业」没进职业方向。** 三条候选全是稳定岗位，第 19 轮回复提了一句「后来没有再说起」，但没有追问。现在对话、整理和画像撰写三个 Skill 都写明：本人说过或勾过想要的事业形态，只要本人没否掉，至少一个方向要写它（进入途径可以是兼职或副业试做），或者问一次为什么不考虑。这一条也只靠 Skill。

第十一次回放（18 轮）上又看到三处，一并修了：

- **开始标准在第 8 轮就满足了，可课表到第 12 轮才问。** 整理把开场卡里的「有固定日程的主线：学生」记成了 `fixed_schedule`，值里既没有哪天也没有几点，而固定日程的槽位原来只要有值就算收集到。现在这类槽位的值必须说出哪天或几点，或者说清定不下来（「不固定」「记不清」），才算这一项有了（`statesSchedule`，`packages/core/src/interview-checklist.ts`）。
- **收尾问题还是问了两遍。** 收尾问题和卡通形象的问题在同一轮，本人两题都答了，原来的判断要求每一行都在回答收尾问题，所以没认出来。现在只要收尾问题答了「没有了」，回答里也没有答题以外的话，就认（`saidNothingMore`）。
- **本人刚说完「现在没有这种念头了」，安全回应又问一遍「现在是否还有」。** Skill 现在写明：本人在同一条回答里已经说了，就不再问。

第十一次回放还剩三处，随后修了：

- **观察卡七张都只得「部分对」。** 第十、十一次回放的七张卡，模式都对，原因都猜错了（本人改的都是「为什么」）。现在 Skill 要求卡写模式、原因留给本人：原因只在本人说过或者有一道区分题支持时才写，否则写两种可能，并在 `questions` 里放一道能分开两者的题。候选清单把假设的另一种解释一起交给模型（`cardCandidates` 附上「另一种解释」，`packages/core/src/profile-points.ts`）。
- **回复里替本人定了日期**（「试做定在 11 月 17 日周二」，本人只选了做哪件事，没说哪天）。现在回复里「定在 / 安排在 / 约在…某月某日」的日期，必须出现在本人的回答、调研结论、文件或记录的事实里，或者是今天，或者是本人在最近一条回答里说的星期几落到的那天；否则退回重写一次，提示把日期放进 `questions` 让本人选（`inventedDates`，`packages/core/src/onboarding-reply.ts`）。Skill 写明「日期由本人定」。
- **长期目标只有一个候选词也让本人选**（「经济学方向」）。一个词不是选择。现在候选词不到 3 个（`GOAL_CANDIDATES_MIN`，`packages/core/src/profile-gaps.ts`）就不出选目标的题，节奏提示改为「候选词还不够（N 个）」，这一轮去问能引出候选词的问题。

### 第十二次回放之后的修正（2026-11-14）

第十二次回放有五处：本人更正过的前提在后面的卡上又出现；观察卡太多、一轮插一张；日期题反复问；长期目标的候选词来源不对（把本人敬佩的人的特质当成了一条主线的目标词）；以及本人还没决定报考的考试被当成截止、回复里出现自造的分类词。机主的要求：卡的数量不减，准备好的卡在同一轮一起出、本人连着答；目标词可以归纳，但规则和来源要对；问题账本实时更新，不重复问同一件事，但更深一层的追问不算重复；定不下的日子允许给范围，后台换算，不给本人看；不要 AI 腔和截断式的短语；引导本人做选择，不替本人定死目标，抓人格底色和三观，不抓很快会变的具体事。

**观察卡**

- **一轮最多三张，一起出。** 对话的输出从 `insight` 改为 `insights`（数组，`INSIGHTS_PER_ROUND = 3`，`packages/core/src/onboarding-turn-schema.ts`）。保存时第一张仍是 `insight`，其余放 `moreInsights`；评分键是 `<会话>#<轮>` 和 `<会话>#<轮>.<n>`（`insightKey`，`packages/db/src/insight-rating.ts`），每张卡单独评、单独进账本。页面把一轮的卡一张接一张显示（`cardsOf`，`apps/web/app/onboarding/round-fold.ts`），有一张没评的轮次不折叠；评分接口接受 `index`。
- **卡从日志里挑，不另编。** 要点规则下，卡要么点名 `cardFrom` 里的一条假设（`cardCandidateIds`，给模型的候选从 3 条增到 4 条），要么在日志一条可挑的都没有时新建一条，一轮最多一条新的。和之前任何一张卡、或同一轮另一张卡说的一样的，丢掉。
- **更正之后先停卡。** 本人评了「部分对」或「不准」，而假设那条线（`insights` lane）还没读到这次评价时，这一轮不出卡（`cardsWait`，`apps/worker/src/onboarding-extract.ts`），节奏提示告诉模型 `insights` 写 `[]`；那条线也会因为这次更正马上跑一次。每次运行开始时记下 `readAt`，读到之后，准备好的卡在下一轮一起出。
- **更正原文交给两边。** 之前给假设那条线的 `observations` 把「部分对」写成「不准」，不带本人的更正，对话那边每条只给 60 个字。现在两边都给全文（只限本场访谈），格式是「部分对：卡 → 本人更正：…」；Skill 要求建立在被更正前提上的其他假设一起改写或推翻。

**日期**

- **粗略的日子是答案。** 「下周」「11 月底前」「12 月中」「这学期内」「寒假」「两周内」等由 `roughWindow`（`packages/core/src/rough-dates.ts`）换成一段日子；本人回答里的这类说法，支持这段日子里的任何一天（`supportsDate`），截止记为这段时间的最后一天并保留原话。本人看到的是自己的话，不会被追问是哪天。
- **问题账本按日期题的规则过滤**（`resolveRepeats`，`apps/worker/src/question-ledger.ts`）：对话自己的日期题（`DATE_ASK`），同一件事（同一主线和项目）一轮只留一个；和一个答过「还没定」的日期题相近的（`SAME_DAY_SIMILARITY`），丢掉；本人两次答「还没定」以后（`undecidedAnswer`），对话不再问日期，排期交给日历。应用自己的截止题（`gap-`）照旧。答过「还没定」的日期题也不再算作可以重问一次的「不确定」。

**目标词和写法**

- 目标题不再说「从你说过的话里整理出的词」，改为「想成为怎样的<主线>？下面几个词是按目前聊到的整理的」。提取 Skill 允许归纳，但定语说的必须是本人想在这条主线上成为的样子；敬佩的人的特质、对一般人的评价、别的主线上的样子，只有本人说了想在这条线上也那样才能用，`refs` 引用归纳所依据的句子。
- 三个 Skill（访谈、提取、画像）都加了同一条粒度规则：写人格底色、价值排序、反复出现的动机和规则，具体的事只作证据；半年后换了方向就不成立的说法往上抽一层，对谁都成立的说法换成只属于这个人的。访谈和画像加了写法规则：平实短句，不用 AI 腔的词和排比金句，不把一个人压成一句带评判的短语。访谈 Skill 写明：引导本人选择，不替本人定死目标或日期；本人还没决定做的事，它的日期不是截止；不自造分类词指本人的事。
- 模拟回放（`scripts/persona-eval.ts` 和 `crossline-eval-persona`）逐张评卡：`insights: [{index, verdict, correction}]`。
