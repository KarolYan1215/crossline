# Identity, sessions, and private deployment (stages two–six)

> Moved verbatim from `CLAUDE.md` on 2026-11-04. Add new notes for this area here, not to `CLAUDE.md`.

This was, until recently, a single-user app with no login at all — `OWNER_ID = "local-owner"` / `WORKSPACE_ID = "personal-crossline"` were the only "identity" anywhere in the repo. Stages two through six replaced that with real accounts, real per-workspace isolation, and real cross-device access over a private network, without ever adopting multi-tenant collaboration UI — it is still built for exactly one real person, just no longer a hardcoded one. `docs/user-guide.md` is the user-facing walkthrough; this section is the "what broke and why it's built this way" record the rest of this file already keeps for everything else.

**Two databases, two schemas, one story.** `auth.db` is Better Auth's own SQLite file (`user`/`session`/`account`/`verification`), migrated by calling `better-auth/db/migration`'s `getMigrations` directly (`packages/auth`'s `migrateCrosslineAuth`) rather than the separately-published `@better-auth/cli`, which trails this repo's pinned `better-auth` version and could generate a different schema than the one actually running. `crossline.db` gained `principals`/`workspaces`/`workspace_members`/`tailscale_bindings`/`device_leases`/`audit_events` in migration 5; `principals.better_auth_user_id` is a plain string reference to the other database, not a SQL foreign key, matching this repo's existing "deliberately absent foreign keys" stance. `session: { cookieCache: { enabled: false } }` is load-bearing, not a default left alone: every request re-checks `workspace_members` from the database, so a revoked session or a demoted role takes effect on the very next request, not after some cache window — `scripts/gate-identity-check.ts` signs a real session out and re-checks it to prove this rather than asserting it from the config alone.

**Mail that does not go out is said, not hidden (2026-10-10).** Better Auth sends verification and OTP mail through `runInBackgroundOrAwait`, which catches every error and only logs it, so a provider in test mode refusing every address but its owner's (a 550) still answered sign-up with success and the page said 「已发送验证邮件」. `deliver` in `packages/auth` notes the failed address and throws a typed `VERIFICATION_EMAIL_FAILED` (the resend route awaits the sender directly), and an `after` hook on the sending paths turns a noted failure into that error in the same request. The login page offers 「重发验证邮件」 after `EMAIL_NOT_VERIFIED`, and a six-digit **email code** (`emailOTP` plugin, only where mail can be sent) signs in — and on first use signs up — without a password; the web calls its two endpoints through `authClient.$fetch` because the plugin-typed client's type is not portable. Without mail (`isEmailAuthConfigured`), sign-up, reset and the code are not offered at all.

**Calendar invitations are the second kind of outgoing mail (2026-11-10).** Path (b) of the calendar write (docs/calendar-write-setup.md) sends iMIP invitations through Resend's HTTP API with the key of the Resend SMTP account auth mail uses (never the SMTP relay: it rebuilt invitations as multipart/mixed and Outlook showed a plain attachment, tested 2026-11-11), from `calendar@mail.crossline.lol` (`CROSSLINE_CALENDAR_FROM`), only to the address the person set (`calendar.imip.recipient`, default the account email). No Resend account means `CALENDAR_IMIP_NO_MAIL` on the settings card, never a fallback sender. Tests never send: a fake sender, or `CROSSLINE_AUTH_TEST_MAILBOX_DIR`.

**Sign in with ChatGPT, for a copy run on the person's own machine** (`packages/auth/src/chatgpt.ts`, opt-in `CROSSLINE_CHATGPT_SIGNIN=1`). OpenAI's open-source flow: the first sign-in registers the install (`client_id=dynamic_agent_client` plus a persisted `ext_agent_host_id`; the issued `oaiapp_…` id comes back on the callback and is kept in `data/chatgpt-signin.json`, never in the ledger), PKCE S256 with state and nonce in a signed cookie, identity scopes only (`openid profile email`; models keep running through the person's own Codex login). OpenAI accepts only `http://127.0.0.1:<port>/auth/callback`, so `app/auth/callback/route.ts` forwards to the plugin's endpoint and the button shows only when the page is opened at 127.0.0.1 — a hosted site would need a partner client id. The ID token is verified with node's crypto against OpenAI's JWKS (issuer, audience = issued id, expiry, nonce) and `sub` is the account; Better Auth's own `handleOAuthUserInfo` links or creates the user. `ext_agent_host_id` goes on every authorize request and `agent_name_hint` (registration only) is `crossline`, the app-server's `clientInfo.name`, as OpenAI's sign-in page asks. **Same email, same account** (2026-10-13, replacing explicit-only linking, which refused the owner's own Google/ChatGPT sign-in with no way to link): `accountLinking: { enabled: true }` with no trusted providers, so a sign-in joins an existing account only when the provider verified the address (Google's `email_verified`; ChatGPT's `email_verified === true`) and the local account's email is verified too (`requireLocalEmailVerified`). Setup: `docs/setup-google-oauth.md`, `docs/setup-siwc.md`.

**`requireAccessContext` (`packages/auth/src/index.ts`) is the one place a request becomes an `AccessContext`.** It calls Better Auth's `getSession`, then — on a session's first-ever appearance — creates `principals`/`workspaces`/`workspace_members` for it in one transaction (a brand-new, empty workspace; logging in never adopts the old `personal-crossline` ledger data still sitting on disk), then separately checks that principal actually belongs to the workspace it is asking for. That second check did not exist anywhere before stage two — `packages/db/src/isolation.test.ts`'s own doc comment named the gap explicitly ("nothing verifies the caller is allowed to use this workspaceId"), and `scripts/gate-identity-check.ts` now proves two independently-signed-up accounts land in different workspaces and cannot see each other's work orders. `listPlanChanges` was the one `list*` method in `packages/db` that took no `workspaceId` at all — a real cross-tenant read, found and fixed while wiring stage three through, not a hypothetical.

**Eliminating the hardcoded identity was pure surface area, not depth.** Every API route gained an `access = await resolveAccessContext(request)` early-return, every exported function in `apps/web/lib/crossline.ts` gained a leading `ctx: AccessContext` parameter, every worker background job switched from a hardcoded owner to looping `listWorkspaces()`. `apps/web/lib/no-hardcoded-identity.test.ts` is the guard against regression — `import.meta.glob` over `apps/web/**` and `apps/worker/**` asserting the literal strings `"local-owner"`/`"personal-crossline"` appear zero times outside test files, the same "discovery test, not per-callsite" pattern `csrf-protection.test.ts` already uses.

**Each account runs on its own Codex (2026-10-10; `packages/codex/src/runtime-registry.ts`, design in `docs/model-providers.md`).** There used to be one app-server and one CODEX_HOME for the machine, with memories on, so a second account read the owner's Codex memories and spent the owner's ChatGPT quota. Now the machine owner's workspace (`runtimeOwner` in `apps/worker/src/owner.ts`: marked once in `RUNTIME_OWNER_SETTING`; else `CROSSLINE_RUNTIME_LEGACY_WORKSPACE`; else the first workspace created) keeps the existing runtime with everything — memories, web search, images and the shell assistant, which works for no one else (`AGENT_OWNER_ONLY`). Every other workspace gets its **own** home (`%LOCALAPPDATA%\Crossline\runtimes\<ws>\codex-home`, its own `auth.json`, which also sidesteps openai/codex#48465) and its own process, started on use, stopped after 30 minutes without an event (longer than the 20-minute stall limit, so a working turn is never cut), at most three at once. Every model run the worker starts for a workspace takes its client from `accountClient` (`apps/worker/src/index.ts`: the registry's start-on-use handle; the running runtime only was used before, so an invited account — whose quota is read from the ledger and never starts its runtime — had its background passes skipped once the runtime went idle, 2026-10-19). A successful login (and a provider's finished conformance run) calls `afterConnected` in the worker (`onConnected` on the registry, `onConformance` on the provider service): the quota is read again, which clears a 「后台自动工作已暂停」 written before the login, and capture analysis, backplanning and the first drafts run at once instead of at the next tick (2026-10-18). An account that has not connected one gets `RUNTIME_UNCONNECTED` from every model route — it **never** falls back to the owner's runtime. The supervisor picks the runtime from the verified capability's workspace (`modelClient`), and the worker's runners take `clientFor(workspaceId)`; lanes and the config lock are per runtime, the spend mode is cached per workspace. A guest connects in 设置 → 模型连接 with ChatGPT in the browser (only when the page is open on this machine — Codex calls back to its own localhost), a **device code** (from anywhere, a phone included), or an **API key**, which passes straight through to that runtime and is never kept, logged or echoed (`apps/web/app/api/codex/account/login.test.ts`); signing out deletes the guest's home. An API-key login has no quota windows, so its reading is this month's spend (`model_usage` × `CROSSLINE_API_PRICE_PER_MTOK`, deliberately high by default) against `model.budget.monthly` (default $10). Not verifiable without the Codex binary: real device-code and API-key logins, and per-process memory — run `scripts/codex-smoke.ts` on the Windows host.

**Codex supervisor capability tokens close the one real gap stage four's scope allowed touching:** before this, anything on the same machine that could reach 127.0.0.1:3211 could make the worker run a Codex skill — no `dynamicTools`/`skillQueue`/per-entity concurrency work was in scope, because none of it has a second real caller to matter yet. `packages/codex/src/capability.ts` signs a 30-second HMAC token (`CROSSLINE_SUPERVISOR_CAPABILITY_SECRET`, deliberately independent from `BETTER_AUTH_SECRET` — one leaking must not compromise the other) carrying the caller's real `AccessContext` plus a `jti` and the worker's own `supervisorBootId` (regenerated on every worker restart, so a token signed before a restart is dead on arrival). Every supervisor route except `GET /v1/codex/status` (needed to discover the current `supervisorBootId` in the first place) verifies it; a discovery test scans every route handler the same way `csrf-protection.test.ts` does, so a new route that forgets the check fails on day one.

**The offline workbench (`apps/web/app/offline-queue.ts`) is real Dexie now, not hand-rolled IndexedDB.** The database name is `crossline-offline-${workspaceId}`, not a fixed name — switching accounts never carries the previous principal's cached commands into the new session, for free. Payloads are encrypted with a non-extractable AES-GCM `CryptoKey` (browsers support storing `CryptoKey` objects in IndexedDB via structured clone directly) before being written. `CommandEnvelope` now dispatches `work_order.start/pause/resume/complete` through the same `transitionWorkOrder` state machine the online routes use — reusing its existing `expectedWorkOrder`/`PROPOSAL_VERSION_CHANGED` optimistic-concurrency check rather than inventing a second one. `classifyReplay` gained a third outcome, `"conflict"` (HTTP 409, distinct from `"dead_letter"`'s permanent rejection and `"retry"`'s transient one): a stale command against a work order that moved on under it lands in Dexie's `conflicts` store, shown in full with its reason rather than silently discarded or silently overwriting whatever the other device already did. A device must additionally hold an unexpired, unrevoked lease (`device_leases`, 24-hour, `POST /api/auth/device-lease`, renewed automatically on a successful sync) for its queued commands to be accepted at all — `issueDeviceLease` had no reader and no revoke UI until this pass found the gap while writing `docs/user-guide.md`'s "撤销设备" section: `listDeviceLeases` and a `GET`/`DELETE` on the route were missing entirely, so a lost device's lease could be revoked at the store layer (tested) but never actually reached from the app. `apps/web/app/connectors/device-leases.tsx` is the card that closes it.

**Private cross-device access rides Tailscale Serve, not a public deployment.** `CROSSLINE_DEPLOYMENT_MODE` is `local | private | external`: both `local` and `private` still bind loopback only — Serve's own TLS-terminating reverse proxy is what makes `private` reachable from elsewhere on the tailnet, the app itself never opens a non-loopback socket. `private` is the first mode that turns on HSTS/CSP/`X-Content-Type-Options`/`Referrer-Policy`/`X-Frame-Options` (`apps/web/next.config.mjs`'s `headers()`; the pages' CSP with a nonce from `proxy.ts` since 2026-10-28) — loopback-only traffic never needed them, since nothing outside the device could address it at all. `external` (real public exposure) is still refused at build time; `docs/external-deployment.md` tracks its remaining prerequisites, and `docs/private-network-deployment.md` covers the `private` setup end to end, including the one-time manual steps (enabling Serve at the tailnet level, adding a second Google OAuth redirect URI). The original plan assumed Tailscale Serve might forward some notion of node identity to the backend; verified against Tailscale's own docs before building on it, and it does not — only `Tailscale-User-Login`/`-Name`/`-Profile-Pic`, and Tailscale strips any spoofed versions of those headers on the way in, so they are trustworthy but incomplete. `tailscale_bindings.node_key TEXT NOT NULL` was written against the wrong assumption and never actually usable; migration 6 made it nullable and narrowed the uniqueness constraint to `(workspace_id, tailscale_login)`. The binding itself (`apps/web/app/connectors/tailscale-trust.tsx`, `POST/DELETE /api/connectors/tailscale`) is purely an audit record an already-logged-in owner creates by choice — Tailscale identity headers never participate in any access-control decision, on purpose, so "trust this Tailscale identity" cannot become an accidental login bypass. `apps/worker/src/export.ts` had its own stale-hardcoded-identity bug found in the same pass: it defaulted `CROSSLINE_WORKSPACE_ID` to `"personal-crossline"`, which stage three made real accounts never actually use, so an unset env var would have silently exported an empty snapshot; it now auto-detects a single real workspace and requires the var explicitly otherwise. `scripts/backup-crossline.ps1`/`restore-crossline-backup.ps1` now carry `auth.db` alongside the ledger (`scripts/checkpoint-auth-db.ts` WAL-checkpoints and copies it; `scripts/read-auth-db-counts.ts` reads it back after restore) — a backup that cannot restore a working login is not a backup, the same principle the ledger's own retired-table checks already apply.

**Device mode: the hosted site is the one primary ledger (2026-10-22, the owner's decision; docs/device-mode.md).** The resident install on the owner's Windows machine used to keep a whole copy of the account, synced hourly by `scripts/ledger-sync.ts`, so both workers ran the same backplans, step plans and assistant runs on one ChatGPT quota and one side's results were then overwritten. Now a local install linked to the hosted account is a *device*: `apps/worker/src/index.ts` reads `<data>/device/link.json` plus a DPAPI token (`device/link.ts`) and, when linked, hands over to `runDeviceWorker` (`apps/worker/src/device/worker.ts`) — no Codex, no model, no plan (`passesFor("device")`: screen activity, folders, local recordings, agent-history time, uplink; `device-mode.test.ts` scans the device files' imports). Results go through a file outbox (`device/outbox.ts`: written before sending, idempotency key per item, backoff 30 s → 1 h, 401/403 stops, permanent refusals to `dead/`) to `POST /api/device/{activity,sources,recordings}` with the `device` token scope (made and revoked on the hosted Settings → 通用 「这台电脑」 card); activity leaves as category aggregates and an 8-hex app hash, never a title; folder files as text by sha256; recordings as local Whisper transcripts, never audio. Consents, folder authorizations and exclusions stay on the device's one local page `/device`; `apps/web/proxy.ts` redirects every other page to the hosted origin while linked, and the web's background loops skip. Lost on a device: the shell assistant, Graph calendar writes, desktop toasts and model-filed folder lines. The scheduled whole-ledger sync is retired (`install-ledger-sync.ps1` refuses without `-IKnowThisSpendsTwice`; the scripts remain for one-off moves). **The device keeps a one-way mirror** (2026-11-03, the owner: 「本地账本和服务器账本应该始终同步，无论谁的账号」, read as server → device only, so nothing runs twice; docs/device-mode.md 「本机账本的镜像」): `GET /api/device/snapshot` (`device` token, `mirrorSnapshot` in `packages/db/src/mirror.ts`: identity tables, `MACHINE_SETTINGS` — now exported from `@crossline/db` and shared with `scripts/migrate-workspace.ts` — token hashes and the server's `device.`/`node.` bookkeeping left out; gzip, ETag a hash of the body, 429 `DEVICE_SNAPSHOT_TOO_SOON` for a second body within a minute) is fetched by the device worker at start and every 10 minutes (`apps/worker/src/device/mirror.ts`) and replaces the local workspace's rows in one transaction, keeping the device's machine settings, `activity_segments`, `local-activity:*` rows and the files and transcripts it read itself (whose `src-N` wins); a daily `crossline.db.mirror-<day>.bak` (3 kept); state in `data/device/state.json` `mirror`, shown on `/device`. A server newer than the device refuses as `RESTORE_UNKNOWN_TABLE`/`_COLUMN` until the device updates; files (materials, sources, portrait) are not copied. **A device may also be the owner's compute node** (2026-10-23, docs/compute-node.md; `apps/worker/src/node/`): with 「作为算力节点」 on in both the hosted 「这台电脑」 card (`NODE_COMPUTE_SETTING`, runtime owner only, `/api/device/compute`) and the device page (`<data>/device/node.json`, `/api/device/node` → `/v1/device/node`), the device worker's `startNodeAgent` connects out to `wss://<site>/node` with the device token (Caddy → the hosted worker's `createNodeHub` on `CROSSLINE_NODE_PORT`, 3213 on the hosted beta), starts `codex app-server` per connection (`spawnAppServerLines`, this machine's own Codex login) and relays its JSON-RPC lines; the owner's model runs are spread over the server's runtime and every ready node (2026-10-23, the owner: the device-mode computer is stronger and only computes, helping the server): `startCodexSupervisor`'s `ownerNodes` makes the owner's client a `createRuntimePool` (`packages/codex/src/runtime-pool.ts`), and `runGated` binds each run when it gets its gate slot (`bindForRun`) — a node with room first, a linked device (priority 2) before the standalone node (1), the less loaded of a kind, else the server — and the run keeps that runtime to the end; a conversation's later turn goes back to the node its thread was started on (else `SKILL_THREAD_LOST` and a rebuild); the model gate adds the owner's ready node capacity to its share and background limit (`extraCapacity`, capacity from each node's `hello`, one per logical core and at most one per GB, 4–16, `CROSSLINE_NODE_CAPACITY` to set it; the owner's planning passes and assistant also start that many more at once, `workspaceConcurrency`) and does not hold the owner's run for this process's memory while a node has room (`nodeRoom`); several nodes of one account are kept by `role:host`, the same computer reconnecting replacing only its own connection (sign-in, the quota read and the shell assistant stay on the server). The node refuses methods outside `ALLOWED_METHODS`, any shell or full access, maps server paths into its mirror and work directories (`rewriteParams`), mirrors plugin directories from the server's skill roots before installing them (`files`), copies a turn's pictures from the server (`image`) and relays provider threads' gateway requests (`gw`, the key added on the server). Codex versions must match (4009); the site switching it off lets it go at the next 15 s heartbeat; a node gone is a disconnected client, so runs fail over and kept threads are rebuilt (`SKILL_THREAD_LOST`). `device-mode.test.ts` holds the agent to the raw app-server and to starting nothing itself; `scripts/node-check.ts` runs hub and agent against the real local Codex in a throwaway home. **The standalone node** (「Crossline 节点」, 2026-10-23, docs/compute-node.md): `scripts/package-node.ts` bundles `apps/worker/src/node/standalone.ts` with the relay and `ws` into one minified `main.mjs` (it fails if any other Crossline source enters the bundle), beside `node.exe` and the vendored Codex 0.163.0 release build, into a per-user Inno Setup exe (`installer/crossline-node.iss`, autostart on by default). The program pairs by a code (`POST/GET /api/node/pair` without an account, `POST /api/node/pair/approve` by the runtime owner on the 「这台电脑」 card; `apps/web/lib/node-pairing.ts`, pending pairings in memory for ten minutes, 12 codes an hour per address), which makes the node its own token (`NODE_TOKEN_SETTING`, never the device token) and switches the node on; it keeps the token with DPAPI, signs in to ChatGPT or with an OpenAI API key (`loginNodeWithApiKey` in `node/control.ts`, the key kept only by that Codex home, never sent to the site, logged or echoed; a linked device's page offers the same) in its own Codex home, serves its page on `127.0.0.1:47391` (host-checked, a custom header on every POST), and goes back to pairing when the hub closes it with `NODE_TOKEN_REVOKED` (the hub re-authenticates every connection each heartbeat). `scripts/node-standalone-check.ts [--main <main.mjs>]` runs the source or the packaged bundle against a stand-in site. **Every account may pair its own node, and a node may run the shell assistant (2026-11-03, the owner: 「剪辑、工作流生长、外部任务，执行外部任务（不包括发送，报名和支付的最后一步），都需要放到节点安装包上，让所有下载节点安装包的用户都可以用」; docs/compute-node.md 「方案 C 与 P3：已实现」).** Pairing is no longer only the runtime owner's: any account approves its own pairing code, the node token is bound to that workspace, and the node runs only that account's work (the gateway relay only that workspace's own HMAC route; usage counted by the server from the gateway stream, never from the node). The installer is published at `NODE_INSTALLER_URL` (`packages/core/src/device.ts`, the `crossline-releases` repo, Ed25519-signed `node-latest.json`). 「允许在这台电脑上执行命令（shell 助手）」 is off by default and kept on the node (node page section 4, `/device` node card, reported in `hello`); with it on `nodeShellHost` makes `assistantMode` `shell` and the worker runs the assistant there (`modeFor` → `node`), and workflow growth, `media_edit` (the installer bundles FFmpeg) and 「建成自动化」 follow it. The node itself refuses full access or the shell tool unless the switch is on, a thread whose working directory is not a direct child of `<node dir>/tasks`, any approval but `untrusted`, sandbox/approval config keys, and any `turn/start` that changes cwd, approval, sandbox, permissions, roots or environments (`refusal` in `node/protocol.ts`); every command is still approved by the server's guard, which also treats the node's token, Codex home and browser profiles as secret paths. Inputs go to the node as copies in 8 MB chunks and results come back with sha checks before the answer is checked (`node/task-sync.ts`, `node/task-files.ts`: 400 files, 300 MB, no traversal or symlinks, never `audit.json`/`progress.json`); a node gone is `AGENT_RUN_LOST`, retried. An account with a ready node (`nodeComputeOn`) also gets the opportunity agent, the form filler, the 报名资料卡 and the favourites reader through its own node's browser, never the server's screen; for such accounts the form engine stops before the last click every time (`personSubmits` in `form-engine.ts`, 「最后一步由本人点击」), free events included. Not verified on a real node: a hosted shell run, chunk transfer over a real network, an FFmpeg edit, a non-owner registration. `apps/worker/src/testing/fake-node.ts` is the stand-in. After an independent review the same day: approving a code first returns a preview (the computer's self-reported host, OS and version, and what it will receive) and only `confirm: true` binds, wrong codes 10 an hour per account; the pair route's per-address limit takes the right-most `X-Forwarded-For` hop; the node's config check is an allowlist (`CONFIG_ALLOWED`, everything else `NODE_CONFIG_REFUSED`, any `..` in a path `NODE_PATH_REFUSED`); the assistant's inputs pass `ownedInputs` (`agent-task.ts`: only this workspace's own source documents, task output, materials and authorized folders, never the data or state directory; the owner's own shell is not filtered) in every mode; the developer's-model route refuses a model it does not list; `/v1/device` is not mounted on the public beta (`standardDeviceService`) and `/api/device/{link,node}` answer 404 there; the node declines any command naming its own folders or `CODEX_HOME` (`namesNodeSecret`), hides `CODEX_HOME`, `CROSSLINE_*` and key/secret/token-named variables from commands, and the standalone node keeps its sign-in with `cli_auth_credentials_store="keyring"` (nodes signed in before 1.2.1 sign in once more). **Tray and desktop pet** (2026-10-28, docs/compute-node.md 「托盘与桌宠」): the installer's entry point is now `CrosslineNode.exe` (`installer/node-tray/CrosslineNode.cs`, system `csc` against the WebView2 SDK 1.0.2365.46 managed DLLs, which ship beside it with `WebView2Loader.dll`; version and SHA-256 pinned in `package-node.ts` `WEBVIEW2`, Microsoft's Authenticode signature checked; read from the NuGet cache or `--webview2-dir`). It starts `main.mjs --tray` in a kill-on-close job and speaks the launcher's line protocol (commands `open`/`pause`/`resume`/`check-update`/`install-update`/`quit`; events `ready`, `status` on change, `update-*`); its menu: 显示小帮手 (Ctrl+Alt+H by `RegisterHotKey`, a balloon says so when another program holds it), 打开 Crossline 网页, the node's state, 暂停算力 (the relay stops until 继续 or the next start), 节点设置与登录, 检查更新, 开机时启动 (the installer's Run value `Crossline Node`, on by default), 退出. The 小帮手 window is WebView2 with its own profile (`%LOCALAPPDATA%\Crossline Node\webview2`, signed in once there) loading `<site>/helper?pet=1`: frameless, topmost, out of the taskbar and cut by a window region to the rectangles the page reports (`{type:"shape"}`, `shapeRects`) — a colour key drew the shape but let every click through, since WebView2 draws through DirectComposition; dragged by following the cursor (`WM_NCLBUTTONDOWN` never starts a move from inside WebView2); its place in `pet.json`; the sign-in and any other page of the site shown in an ordinary window, the first page after a sign-in sent back to the 小帮手 once; off-site links in the person's browser. It sends the page the pointer's position anywhere on the screen and the computer's idle time (`GetLastInputInfo`). `--site`/`--no-node` and `CROSSLINE_NODE_HOME` are for testing against a local site.
