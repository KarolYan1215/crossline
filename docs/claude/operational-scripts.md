# Operational scripts (`scripts/`)

> Moved verbatim from `CLAUDE.md` on 2026-11-04. Add new notes for this area here, not to `CLAUDE.md`.

- `start-crossline.ps1` — launches the **built** web app + worker, each under `keep-running.ps1`, (requires `pnpm build:prod` first, which builds into `apps/web/.next-prod`; fails fast if its `BUILD_ID` is missing). The resident app has its own build directory because `pnpm build`/`pnpm verify` write `.next`: a verify run while the server was up replaced the hashed CSS it was still naming, and every page lost its styles (found from the phone address on 2026-10-07, where nothing was cached). Idempotent by design: it skips the web app when port 3210 already listens, and always launches the worker because a free supervisor port does not prove the worker is dead. The worker guards itself with a heartbeat lock at `data/worker.lock` — a redundant copy logs `worker.already_running` and exits 0 rather than opening a second SQLite writer, a stale heartbeat (3× the tick interval) is taken over, and `EPERM` from `process.kill(pid, 0)` counts as alive.
- `keep-running.ps1 -Name web|worker` — the loop each resident process runs under (2026-10-15): starts it, waits, writes the exit (time, code in hex, minutes run) to `data\logs\restarts.log`, keeps the previous logs under a timestamp, and starts it again after 5 s (backing off to a minute when it keeps dying at once). It holds `data\<name>.keeper.lock`; `start-crossline.ps1` starts a keeper only when none is alive, so a crash is down for seconds instead of up to the watchdog's fifteen minutes. The web had died twice that day with `0xC0000409` and nothing on stderr; `restarts.log` is where the next one is recorded. To restart one, kill the process listening on its port and its keeper starts it again; to stop one, kill its keeper first.
- `install-startup.ps1` — registers a Windows Scheduled Task with two triggers: at logon, and repeating every 15 minutes. The repeating one is the watchdog for the keeper loops, which run only while this Windows user is logged on. Modifies Windows Task Scheduler; only run when the user explicitly asks.
- `backup-crossline.ps1` — exports the ledger to JSON, zips it, encrypts with DPAPI (current Windows user), and verifies SHA-256 before deleting the plaintext temp file. Its `& pnpm` call (and the one in `restore-crossline-backup.ps1`) is wrapped in `& { $ErrorActionPreference = 'Continue'; … }`: under `'Stop'`, PowerShell 5.1 turns a native command's stderr line into a terminating error whenever stderr is redirected, which is every non-interactive host. The script died before reading `$LASTEXITCODE`, so the backup worked by hand and silently never ran unattended.
- `ledger-sync.ts` — keeps the owner's ledger the same here and on the hosted server (docs/ledger-sync.md, 2026-10-20): the side the person last acted on (`lastPersonActivity`, never a system write) is copied whole over the other through `pack-for-server.ts` + `migrate-workspace.ts --replace`, the losing side's ledger copied aside first; machine-local settings (runtime owner, calendar accounts, push, folders, model connection, mailboxes) stay on each side (`--keep-settings`); equal stamps do nothing; `scripts/install-ledger-sync.ps1` registers it hourly. The server side is `deploy/server/ledger-sync.sh` (`stamp`/`pack`/`preview`/`apply`), which the `[migrate]`/`[migrate-apply]` commits also run, with the three scripts it needs mounted over the image's copies so a sync never waits for an image rebuild.
- `migrate-workspace.ts` — moves one workspace between two installs on the same machine (2026-10-14: the resident copy's account into the installed app at `%LOCALAPPDATA%\Crossline`). It exports the source through an online backup, swaps in the target's workspace and owner ids, rewrites paths under the source data directory, copies `materials/`, `sources/` and the portrait folder, and imports into a target that holds exactly one workspace with no person data (its seeded rows are cleared; identity tables are never copied). Dry run by default, `--apply` to write; stop the target app and back up its `data\` first. `--copy` (2026-11-04) copies into a second account of the same ledger: the ids of the tables keyed by a ledger-wide id (events, captures, materials, conversations, waiting items…) are renewed in every string, device/node tokens and machine settings stay the target's, calendar cursors and invite codes are not copied; on the server `server.yml` action `clone`/`clone-apply` with args `<from-email> <to-email>` runs it through `ledger-sync.sh clone` (apply stops the app and copies the ledger aside), and `sponsor`/`sponsor-apply` with `<email>` runs `grant-sponsor.ts`.
- `restore-crossline-backup.ps1` — decrypts a backup and **rebuilds a working SQLite ledger** from it via `pnpm restore`, then reads every table back through the normal query path to verify. `CrosslineStore.importSnapshot` only ever rebuilds into an empty workspace (`RESTORE_TARGET_NOT_EMPTY`), the CLI refuses the live database (`RESTORE_TARGET_IS_LIVE_LEDGER`) and refuses to overwrite an existing file (`RESTORE_TARGET_EXISTS`). Replacing the live ledger stays a manual act. Snapshot table and column names are validated against `sqlite_master`/`PRAGMA table_info` before reaching SQL.
