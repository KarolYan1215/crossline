# Operational scripts (`scripts/`)

> Moved verbatim from `CLAUDE.md` on 2026-11-04. Add new notes for this area here, not to `CLAUDE.md`.

- `start-crossline.ps1` — launches the **built** web app + worker, each under `keep-running.ps1`, (requires `pnpm build:prod` first, which builds into `apps/web/.next-prod`; fails fast if its `BUILD_ID` is missing). The resident app has its own build directory because `pnpm build`/`pnpm verify` write `.next`: a verify run while the server was up replaced the hashed CSS it was still naming, and every page lost its styles (found from the phone address on 2026-10-07, where nothing was cached). Idempotent by design: it skips the web app when port 3210 already listens, and always launches the worker because a free supervisor port does not prove the worker is dead. The worker guards itself with a heartbeat lock at `data/worker.lock` — a redundant copy logs `worker.already_running` and exits 0 rather than opening a second SQLite writer, a stale heartbeat (3× the tick interval) is taken over, and `EPERM` from `process.kill(pid, 0)` counts as alive.
- `keep-running.ps1 -Name web|worker` — the loop each resident process runs under (2026-10-15): starts it, waits, writes the exit (time, code in hex, minutes run) to `data\logs\restarts.log`, keeps the previous logs under a timestamp, and starts it again after 5 s (backing off to a minute when it keeps dying at once). It holds `data\<name>.keeper.lock`; `start-crossline.ps1` starts a keeper only when none is alive, so a crash is down for seconds instead of up to the watchdog's fifteen minutes. The web had died twice that day with `0xC0000409` and nothing on stderr; `restarts.log` is where the next one is recorded. To restart one, kill the process listening on its port and its keeper starts it again; to stop one, kill its keeper first.
- `install-personal.ps1` / `install-personal.cmd` — install the owner's own local copy (`Crossline-Personal-<version>.exe` from `package-installer.ts --personal`): stop the installed tray, copy `%LOCALAPPDATA%\Crossline\data` to `backups\before-personal-<stamp>`, then run the setup silently with a desktop shortcut. The `.cmd` is for a Claude desktop session, which must start it outside the MSIX container through WMI (`Win32_Process Create`; powershell.exe is refused there). `docs/plans/desktop-local-1122.md`. The `.cmd` takes the backup stamp as an optional second argument only in the shape `yyyyMMdd-HHmmss`, else asks the installed app's `node.exe` for the local time: a caller built it from `%date%` and left `before-personal-周一022611-…` folders (renamed to `20261123-…` on 2026-11-25).
- `install-startup.ps1` — registers a Windows Scheduled Task with two triggers: at logon, and repeating every 15 minutes. The repeating one is the watchdog for the keeper loops, which run only while this Windows user is logged on. Modifies Windows Task Scheduler; only run when the user explicitly asks. It calls `install-backup-schedule.ps1`, the one definition of the `Crossline Backup` task (daily 03:00, `-Keep 14`, under `conhost --headless`, as the logged-on user because DPAPI is per user).
- `backup-crossline.ps1` — the nightly encrypted backup of the ledger this machine actually uses (rewritten 2026-11-25). Data directory: `-DataDirectory`, else `CROSSLINE_DATA_DIR`, else the installed app's `%LOCALAPPDATA%\Crossline\data` when it holds a `crossline.db`, else `<repo>\data`; the scheduled task passes none, so an app reinstall cannot move it off the real ledger. `scripts/snapshot-ledger.ts` takes `crossline.db` and `auth.db` by SQLite's online backup from read-only connections (integrity-checked, DELETE journal mode on the copy) and writes one `crossline-<workspace>.json` per workspace from a throwaway copy — this checkout's `CrosslineStore` never opens, and so never migrates, the live ledger. The archive also carries Codex memory (`copy-codex-memory.ts`; the installed app's home is `state\codex-home` beside `data\`), `materials/`, `sources/`, `portrait/` and `backup-info.json`; never `secrets\`, `launcher-secrets.json` or `push-vapid.json`. Zipped with .NET `ZipFile` (PS 5.1's Compress-Archive names entries with backslashes), DPAPI-encrypted for the current user, SHA-256 verified, `-Keep` newest kept. **Every run appends one line to `backupsackup.log`** (成功 with file, data directory, workspaces, size, hash; or 失败 with the reason); a failure also shows a Windows notification and exits 1. Why: from 2026-10-10 to 11-25 no backup was written and nobody knew — the task exported the development ledger `<repo>\data`, `export` refuses a ledger with two workspaces (it gained a second on 10-10), and `conhost --headless` returns 0 whatever PowerShell exits with, so Task Scheduler's Last Result showed 0 every night. Do not trust that column; read `backup.log`. Native calls run with `$ErrorActionPreference = 'Continue'` inside (`Invoke-Native`): under `'Stop'`, PowerShell 5.1 turns a native command's stderr line into a terminating error whenever stderr is redirected. The file carries a UTF-8 BOM: PowerShell 5.1 reads a BOM-less script in the system code page (GBK here), which garbles its Chinese strings. To run it by hand from a Claude desktop session, start it outside the MSIX container (`Start-Process explorer.exe '"<a .cmd>"'`; WMI refuses powershell.exe), or SQLite's shared-memory file is written into the container's private copy.
- `ledger-sync.ts` — keeps the owner's ledger the same here and on the hosted server (docs/ledger-sync.md, 2026-10-20): the side the person last acted on (`lastPersonActivity`, never a system write) is copied whole over the other through `pack-for-server.ts` + `migrate-workspace.ts --replace`, the losing side's ledger copied aside first; machine-local settings (runtime owner, calendar accounts, push, folders, model connection, mailboxes) stay on each side (`--keep-settings`); equal stamps do nothing; `scripts/install-ledger-sync.ps1` registers it hourly. The server side is `deploy/server/ledger-sync.sh` (`stamp`/`pack`/`preview`/`apply`), which the `[migrate]`/`[migrate-apply]` commits also run, with the three scripts it needs mounted over the image's copies so a sync never waits for an image rebuild.
- `migrate-workspace.ts` — moves one workspace between two installs on the same machine (2026-10-14: the resident copy's account into the installed app at `%LOCALAPPDATA%\Crossline`). It exports the source through an online backup, swaps in the target's workspace and owner ids, rewrites paths under the source data directory, copies `materials/`, `sources/` and the portrait folder, and imports into a target that holds exactly one workspace with no person data (its seeded rows are cleared; identity tables are never copied). Dry run by default, `--apply` to write; stop the target app and back up its `data\` first. `--copy` (2026-11-04) copies into a second account of the same ledger: the ids of the tables keyed by a ledger-wide id (events, captures, materials, conversations, waiting items…) are renewed in every string, device/node tokens and machine settings stay the target's, calendar cursors and invite codes are not copied; on the server `server.yml` action `clone`/`clone-apply` with args `<from-email> <to-email>` runs it through `ledger-sync.sh clone` (apply stops the app and copies the ledger aside), and `sponsor`/`sponsor-apply` with `<email>` runs `grant-sponsor.ts`.
- `restore-crossline-backup.ps1` — decrypts a backup and **rebuilds a working SQLite ledger** from it via `pnpm restore`, then reads every table back through the normal query path to verify. `CrosslineStore.importSnapshot` only ever rebuilds into an empty workspace (`RESTORE_TARGET_NOT_EMPTY`), the CLI refuses the live database (`RESTORE_TARGET_IS_LIVE_LEDGER`) and refuses to overwrite an existing file (`RESTORE_TARGET_EXISTS`). Replacing the live ledger stays a manual act. Snapshot table and column names are validated against `sqlite_master`/`PRAGMA table_info` before reaching SQL. Since 2026-11-25 it rebuilds every `crossline-*.json` in the backup (one per workspace; older backups carry one) and reads back `auth*.db`, and leaves the raw `crossline.db` copy, the files and `backup-info.json` (where and when it was taken) in the output directory. Use a short `-OutputDirectory` (`<repo>
estored\…`): `materials\` paths reach 155 characters and Expand-Archive fails past 260. Drill of 2026-11-25: the installed app's ledger (1 workspace, 1546 events, 56 work orders, 4134 rows) rebuilt and matched the raw copy; `auth.db` read back 1 user, 7 sessions.
- `points-migrate.ts` — moves one named account to the interview's points rules (2026-11-12, `docs/onboarding-v3.md` 「要点账本」). Run it inside the app image against the data directory. `--split` makes the main interview use the rules and has the worker's portrait lane split the old paragraphs into cited points once. `--export <file>` writes the account's interview messages and ratings out (mode 600; keep it on the server). `--reset` clears the account as Settings' 「清空数据重新开始」 does, and refuses the machine owner. Dry run by default; `--apply` writes. Back up first. It never prints the person's words.

- `scripts/skill-catalogue.ts` — regenerates `packages/core/src/skill-catalogue.ts` (each Skill's SKILL.md description, which 小帮手's `find_system_part` routes by). Run after adding a Skill or changing a description; `apps/worker/src/skill-catalogue.test.ts` fails while it is stale.

## 规则登记、评测与消融（2026-11-25，docs/plans/harness-1125.md §10）

These run on the owner's machine only. CI (`ci.yml`) runs none of the model evaluations: the repository is public and CI holds no model credentials. What is deterministic is in vitest and runs everywhere: `packages/core/src/rule-spec.test.ts` (the register's completeness and the lint) and `scripts/eval-lib.test.ts` (golden extraction, ablation, pass^k arithmetic).

- **`RULE_SPEC`** (`packages/core/src/rule-spec.ts`) registers every regex, word list or validator that judges natural language: `id`, `file`, `kind` (`invariant | evidence | semantic | style | money`), `mode` (`enforce | record | fallback`), its readers and when it is retired. `ruleFired(id, detail)` writes one JSON line to `<CROSSLINE_DATA_DIR>/telemetry/rule-fired.jsonl` (the sink is `installRuleTelemetry` in `packages/db/src/rule-telemetry.ts`, installed by the worker and the web server; nothing in the browser or in tests). Same pattern as `owner-disputes.jsonl`: never the ledger. A `detail.key` makes a firing count once per process (a title read on every render). Fallbacks fire whenever they decide because the model's field is missing.
- **Registering a rule** (also what the main session does after merging a branch that changed rule behaviour in `opportunity-discovery.ts`, `task-merge.ts`, the interview files…): add an entry to `RULE_SPEC`, put `// rule: <id>` on the pattern's line or the line above it (the test checks every entry has one in its own file, and every tag names an entry), and call `ruleFired` where it decides if a firing count is useful. A pattern that does not judge natural language (a date format, a template's grammar) takes `// not-nl: <why>` instead. If the lint fails after a merge because existing literals changed text, register them, or — when the change only moved them — regenerate the baseline: `CROSSLINE_RULE_BASELINE=update pnpm vitest run packages/core/src/rule-spec.test.ts` and review the diff of `rule-spec.baseline.json` (it must only lose or rename entries, never gain a new word list).
- **Run-time mode**: `CROSSLINE_RULE_MODE="completion.legacy-title=record,opportunity.far-words=record"` or `setRuleModes(...)`. Only rules that read `ruleApplies(id)` change behaviour under `record` (today the three fallbacks: `completion.legacy-title`, `opportunity.far-words`, `attribute.guess-kind`); `money` and `invariant` rules ignore every override.
- **`scripts/pass-k.ts`** — pass^k, pass@1 and the disagreement rate of `crossline-mail-triage` (`mail-intake-1120.json`), `crossline-milestone-gate` (three hand-written evidence cases) and `crossline-step-planner` (three tasks), each run k times through the real worker path on an in-memory ledger. Spends quota: reads `account/rateLimits/read` first and prints `NOT RUN` above `--max-used` (80 %). A worktree has no `vendor/codex` build, so point it at the installed app's runtime; it uses the installed app's Codex home (`%LOCALAPPDATA%\Crossline\codex-home`) and installs this checkout's plugin there, as `gate-eval.ts` does:

  ```powershell
  $env:CROSSLINE_CODEX_PATH="$env:LOCALAPPDATA\Crossline\app\codex\codex.exe"; $env:CROSSLINE_CODEX_SUPERVISOR_PORT='3396'
  pnpm exec tsx scripts/pass-k.ts --suite mail --k 3 --limit 3
  ```
- **`scripts/golden-from-corrections.ts <copy.db>`** — the person's corrections (undo, gate override, changed estimate or due day, declined proposal, renamed task, chosen completion mode) as cases in `apps/worker/src/testing/golden/<kind>.json`. Only a copy: restore a backup first (`scripts/restore-crossline-backup.ps1 -OutputDirectory <repo>\restored\<name>`) and pass the `crossline-restored-*.db` it writes; a file in `data\` or under `%LOCALAPPDATA%\Crossline\data` is refused. The golden files are personal data and gitignored; only `README.md` and the made-up `example-*.json` are committed.
- **`scripts/ablate.ts --rule <id> [--telemetry <rule-fired.jsonl>]`** — replays the rule's samples (fixtures and golden cases) with its verdict used and only recorded, and prints how many answers it changes and which mode agrees with the label. No model call. `--list` shows which rules have an ablation (`ABLATIONS` in `scripts/eval-lib.ts`; add one there for a rule you want to judge).
- **Every month, automatically** (since 2026-11-26): the Claude Code scheduled task `crossline-monthly-review` (`%USERPROFILE%\.claude\scheduled-tasks\crossline-monthly-review\SKILL.md`, the 1st at 10:00 while the desktop app is open) restores the newest nightly backup to a copy, runs `pnpm review:ledger` on it, reads `rule-fired.jsonl`, ablates record/fallback rules with ≥ 30 samples and ≥ 95 % agreement, runs `pass-k.ts` when a SKILL.md changed that month, and commits what it removed to a local branch `maint/monthly-<YYYY-MM>` with a report in `docs/maintenance/monthly-<YYYY-MM>.md`. It never pushes or merges (docs/plans/harness-1125.md §18).
