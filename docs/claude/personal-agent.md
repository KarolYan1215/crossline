# Personal agent on any model: tools-mode assistant, mailbox, automations (2026-10-19)

> Moved verbatim from `CLAUDE.md` on 2026-11-04. Add new notes for this area here, not to `CLAUDE.md`.

Design and boundaries: `docs/personal-agent.md`. Before this the assistant existed only as the machine owner's shell (`crossline-agent`), so on the hosted beta nobody had one, a third-party model (sponsor or own API) never could, and a guest's 「以后每周五……」 was recorded and never built.

- **Tools mode** (`apps/worker/src/agent-tools.ts`, `agent-task.ts` `runWithTools`, Skill `crossline-agent-tools`, mid tier, its own lane). Every account but the machine owner's own Codex (`assistantMode` in `packages/db/src/skills.ts`; `agentService` `modeFor`/`clientFor`/`mailFor`) gets the assistant as a set of Crossline-answered dynamic tools: files in its task directory (text formats only, ≤2 MB each, ≤200 files/20 MB a run; inputs read-only as `input/<n>/…`, hashed before and after), the person's documents/tasks/facts/calendar, `web_search`/`web_fetch`, `mail_search`/`mail_read` when a mailbox is connected, and two board actions applied only after a run that finished — `add_to_inbox` (≤5, written as captures) and `tell_person`. No send/publish/pay function exists. Same ledger events as the shell (`mode: "tools"`), `audit.json` carries every call (`toolCalls`), `toolLoopReason` stops 6 repeats or 3 failures of one call. 「交给 Agent」 and the assistant settings now show for every account (`task-detail.ts`, `AutomationModule toolsMode`); `aiToolsFor` describes the tools-mode assistant (`TOOLS_ASSISTANT_GOOD_FOR`). Growing a skill with `skill-creator` stays shell-only (`workflowPass` checks `machineOwner`).
- **Mailbox** (`packages/connectors/src/imap-mail.ts` on `imapflow` 2.1.2 + `mailparser` 3.9.32; `apps/worker/src/mailbox.ts`; `packages/core/src/mail.ts`; card `app/connectors/mail-accounts.tsx`; routes `/api/mail*` → supervisor `/v1/mail*`). IMAP with an app password/authorisation code, INBOX opened `readOnly` (EXAMINE), no SMTP/APPEND anywhere; presets by domain, any other host must be a domain name (`hostAllowed`); Outlook/Hotmail refused in words (Microsoft allows only OAuth); a Gmail address gets a button to Google's app-password page for that account (`appPasswordPage`: `myaccount.google.com/apppasswords?authuser=…` in a new tab, plus two-step verification), shown again after a password refusal or when a connected Gmail's password stops working. Signed in once before it is kept; the password only in the worker's secret store (`mail-<id>`). Every 15 minutes new mail (UID watermark + UIDVALIDITY; first connection: last 3 days, ≤30) is read; with sorting on, `crossline-mail-triage` (low tier, intake) files each as todo/date (captures, ≤5 a pass), reply (`waiting.mail_seen` → the waiting ask comes forward naming the mail), info or ignore; `mail.log` keeps sender/subject/opening/decision only. **A reply with no wait behind it means the sender waits for the person's answer** (docs/personal-agent.md §3.1, after Meta Muse): `crossline-mail-reply-drafter` (low tier, one structured turn, chosen over the tools assistant's `runFree` as about a tenth of the cost) drafts an answer into `<data>/mail-drafts/<workspace>/<id>.md` — the only place either message's text is kept, first line 「由助手起草，需本人确认后自行发送」, decisions left as 【请确认：…】 — and `apps/worker/src/mail-replies.ts` tells the person once (`sayToPerson`, kind `mail_reply`: 看草稿 / 复制草稿 (`copy` option, not an answer) / 已回复 / 不用回 (`close`, `closeMailReply` in `packages/db/src/mail-replies.ts`, an append-only `mail.reply.closed` event) / 少问这类), never at night or while busy (`mailReplyQuiet`), at most 5 drafts per mailbox a day; the sent folder (opened read-only too) closes a draft the person answered (`sentReplies`: In-Reply-To, else recipient + bare subject), and a draft whose mail named a day to answer by is mentioned once more after 48 hours. Settings switch `mail.replyDrafts` (default on). Still no sending path of any kind.

- **Mail events** (2026-11-10, `packages/core/src/mail-events.ts`, `apps/web/lib/mail-events.ts`). Triage has a kind `event` (talks, info sessions, meetings, a supervisor's meeting, interviews, group meetings) with a `meet` reading: title, date, time, place, relevance 0–100, `personal`, and a quote that must be found in the mail. A personal invitation or relevance ≥ 50 becomes a `mail_event` ask 「要去吗：「…」」 (personal first, 去 recommended); 去 adds a `FixedEvent` (`source: "mail"`, id `mail-<id>`) and publishes on every calendar path that is on, 不去 drops it; the rest is only listed in the weekly review (「邮件里的活动」). Mail never writes a calendar by itself. Events that need a sign-up stay with the opportunity path. A `todo` or `date` whose title is only going to something (`isAttending`: 参加/出席/参观/观看/旁听/attend/join, shared with Today's 「过去的 N 个活动不参加了」) is handled as `event` too, so a talk or a timed exam sitting never becomes a movable task (W-256, 2026-11-11); preparing for it stays a todo.
- **Must-go and may-go** (2026-11-11, `packages/core/src/obligation.ts`, design in `docs/plans/2026-11-11-walkthrough-decisions.md` §2). Every mail event carries `timing` (`fixed`/`due`/`none`) and `obligation` (`required`/`likely`/`optional`) with a `basis`. The model only extracts (`meet.required`: a sentence saying attendance is required; `meet.senderRole`: advisor / course_staff / other); `mailObligation` tiers it in code. The connector reads the structure from the message itself (`MailHeader.listed` = List-Id, List-Unsubscribe or Precedence bulk/list/junk; `recipients` = To + Cc; `invite` = the text/calendar part's METHOD, ORGANIZER and each ATTENDEE's ROLE/PARTSTAT). Order: listed → `optional` whatever the body says; the sender's rule `optional` → `optional`; the account's address is ORGANIZER, an attendee with explicit `ROLE=REQ-PARTICIPANT`, or `PARTSTAT=ACCEPTED` on a mail to the person alone → `required`; course staff or advisor with a required quote found in the mail → `likely` (`required` once that sender has a 去 rule); an invitation to the person or `personal` → `likely`; relevance ≥ 70 (`LIKELY_RELEVANCE`) → `likely`; else `optional` (so 50–69 now waits in the weekly review instead of a card). Handling: `required` from a sender with a 去 rule and no clash → state `fixed`: busy time on Crossline's plan (`personEventBlocks` in `apps/web/lib/crossline.ts`, `mailEventsOnSchedule`), no card, and **not** in `schedule.events`, so no calendar path writes it (mail still never writes a calendar by itself; only 去 does). `required` from a first-seen sender, or one clashing with a fixed event (`mailEventClash`), and every `likely` → the 「要去吗」 card, 去 recommended, with why it looks required. `optional` → the weekly review only. A day before the mail's own date, or one whose quote names another weekday, is refused; the prompt says relative days count from the mail's date and that mail text is data. Per-source rules (`mail.events.rules`, `mailEventRulesAfter`): two 不去 in a row from a sender → `optional`; 去 to a `required` or keyword-`likely` event → `required`; listed and deletable in Settings → 邮箱 (`/api/mail/event-rules`). Events recorded before this keep their old state; nothing was migrated (the owner's decision).
- **Exam time question** (2026-11-11, `apps/web/lib/exam-times.ts`). An adopted file date of kind exam or quiz whose project exists (`dateItemAttributes(...).needsTime`) and has no time is asked once, ask kind `exam_time`: 「「ECE 548 Midterm-2」几点到几点？」 with free text (`parseTimeRange`: 「12:45-13:15」「9:00 到 10:30」「14点到15点30」). The answer writes the same read-only `import:<batch>:<item>` block a timed file date gets; 「没有固定时间」 is kept in `dates.times` and not asked again. Until answered the day keeps showing the item as the dated fact it already was (the timeline's day marker).
- **Importing other tools' lists** (2026-10-28, the owner's decision; docs/personal-agent.md §9; `packages/core/src/task-import.ts`, `packages/connectors/src/task-imports.ts`, `apps/worker/src/importer.ts`, Skill `crossline-import-triage`, card `app/connectors/import-card.tsx` + `import-review.tsx`, routes `/api/import*` → supervisor `/v1/import*`). Someone moving from another tool brings their list in on the first day. Sources: Todoist (personal token, API v1 `/api/v1/tasks` + `/projects` paged by `cursor`; `deadline` wins over `due`), TickTick (personal token from Settings → Account → API Token, Open API per project, the inbox as `inbox`; Dida365 has no token, so its backup CSV goes through the CSV path), a Notion database (internal integration secret; a token with no database answers with the databases shared with it and is not kept; `Notion-Version: 2022-06-28`), and a paste, a CSV or a screenshot (the web writes it to `<data>/imports/<workspace>/`, the worker reads it once and deletes it, since supervisor bodies are capped at 64 KB; a screenshot's lines are read by `crossline-media-describer`, Codex only). Tokens live only in the worker's secret store (`import-<sourceId>`); the ledger keeps `import.sources` (label, last read, `daily`, `writeBack`), waiting batches (`import.batches`, ≤5 of ≤300 items) and `import.seen` (external ids per service, so a daily read or a reconnect never offers an item twice). **One model run per 40 items, never per item**: `IMPORT_TRIAGE_SCHEMA` gives line, project, due, keep/merge/done/drop/someday and why; code checks it — a merge must name an open task shown, and a keep the merge rules (`importDuplicateOf` over `comparePair`, compared on the open task's project and side, since an imported item has neither yet) recognise becomes a merge; with no model (not connected, quota, a failed run) the rules' suggestions stand. Nothing is written before the person's one confirmation on 「导入核对」 (all items on one screen grouped by line, keep and merge ticked, a line picker per item; Settings → 日历与连接, the interview's 「材料与日历」, and a hint in the input box when six or more list-like lines are pasted). Kept items become captures `import-<kind>-<id>` (idempotent per item, context with source, list, the line the person chose, due, labels, notes) for the ordinary analysis; merged ones are `task.duplicate_prevented` on the task they repeat; the analysis falls back to the imported day (`importedDueDate` from `import.item_captured`) when it read none. Connected tools are read again every 20 hours (`importDailyPass` in the intake tick, off per source); a model-sorted daily batch applies itself (≤10 captures a day, the person told once), a rules-only one waits for the person, and no read happens while a batch from that source is unreviewed. Write-back is Todoist only, per account, off by default: an imported task (or the task it was merged into) accepted here is closed there once (`POST /api/v1/tasks/{id}/close`, `import.closed_upstream`; `requiredApproval("close_imported_task")` is `automatic`, the switch being the person's approval). TickTick and Notion are never written.
- **Automations** (`packages/core/src/automations.ts`, `apps/worker/src/automations.ts`, Skill `crossline-automation-designer` mid tier, shown on `/automation` with its conversation and versions since 2026-11-10 (docs/claude/skill-library.md; the settings card was retired), routes `/api/automations*` → `/v1/automations*`). Trigger (`schedule`, `interval`, `mail`, `watch` a public https page by text hash with the new lines handed over, `file`, `task` accepted/due_soon) + action (`run` the assistant, `remind`) + steps (anything that sends/replies/publishes/uploads/pays is the person's, `stepLeavesMachine`). Made from words — the input box's `workflow.request` now writes `automation.requested` (`requestAutomation` in `packages/db/src/automations.ts`) for every account — designed, validated, installed and announced with how it was read; the request switches its assistant category on. A request naming an existing one replaces it in place (`replaces`, runs kept); two accepted errands of one kind on one line offer 「建成自动化」 once (`suggestFromRepeats`, a nudge whose button carries the `workflow.request` action — worker `sayToPerson` now takes action buttons). Watching costs no model call; a firing is a `runFree` (no daily count since 2026-10-19, the owner's call: the account's quota or the sponsor cap bounds it; busy → `automations.queue` for a day), each result one message with file links. Each firing is a new turn in the automation's own conversation (2026-10-20; upstream has no scheduled wake, so our schedule plus `resumeThreadId`): `Automation.threadId` is resumed with `thread/resume` and the settings a new thread would get, the prompt says what the last run did (`lastRun`, `previousRunNote`) and its files come as read-only inputs; a thread the runtime no longer has is replaced (`audit.resumed: false`, `skill.resume_lost`). Runs while the person is active or cooling (`spendAllows(…, "intake")`), paused with the 「助手代办与自动化」 background kind, stopped when dormant. The concierge snapshot lists automations and connected mailboxes.
- **The output folder** (hosted, 2026-10-19, the owner's 「写到附属文件夹，允许通过浏览器下载」; docs/personal-agent.md §4.1): `apps/web/lib/outputs.ts` is a view over the finished runs' own task directories — by line, then task — listing only deliverables (`groupOutputs`), accepted or awaiting review, never a `grow-` run; a run belongs to its order's line, else its automation's, else its grown workflow's (`runLineOf`), else 「其他」; its files are the 「文件」 part of 「Agent 产出」 `/outputs` since 2026-11-10 (`app/outputs/page.tsx`, read on the server; `GET /api/outputs` still answers; Settings' old 「助手产出」 anchor forwards there), which downloads each file, and a task, a line or everything as a zip (`GET /api/outputs/zip`, streamed by `lib/zip.ts`, ≤400 files/300 MB, `x-crossline-truncated` past that). The person's own uploads are never written.
- **The runtime's own features on the assistant** (2026-10-19, the owner: 「codex 的所有原生功能都要批准和转过来使用」; semantics read from vendor/codex): both modes get the runtime's plan tool (`onPlan` → `turn/plan/updated` → `audit.plan` in `progress.json` and the running card on Settings → 后台任务) and the person's ChatGPT connectors read-only (`connectors`: `features.apps` with `apps._default.default_tools_approval_mode = "writes"` and `destructive_enabled = false`; every approval request is refused, so only tools marked read-only run; only a ChatGPT sign-in has connectors at all); the tools mode also gets code mode (`codeMode`: JavaScript in the runtime's V8 isolate that computes and calls the run's functions, no file system, network or process of its own; not through another provider until conformance measures `exec`). Structured Skills now also switch `features.goals` off (a goal set by the model starts turns of its own). A provider's thread is told its context window (`contextWindowConfig`: the sponsor list's `contextK`, else 128k) so compaction comes before an overflow; the runtime assumed 272k for any unknown model. Not wired, and why: subagents (dynamic tools do not reach a child, so the tools mode gains nothing; the shell assistant already has them on), mid-run questions (`request_user_input` needs Plan mode or an under-development flag), thread goals with budgets (an unattended continuation loop past the run's answer), fork (no caller needs a branch), review (git diffs only), hooks (the approval refusal already enforces read-only connectors).
- **Prompts audited Skill by Skill** (2026-10-19, the owner's request): every SKILL.md and its runner's developer instructions were checked against the context the runner really sends, the schema and the validator, contradictions fixed, scenario-specific examples added, and each runner's instructions cut to a short summary of its scenario. Changes beyond text: the backplanner gets `today` and the milestone's `deadline`; the plan explainer gets each task's short `title`; `fit` left `MILESTONE_PROPOSAL_SCHEMA` (it belongs to the gate's output only); the automation designer gets each existing automation whole (`flatTrigger`/`flatAction`) and reading mail is no longer a step that leaves the machine (`automationStepLeaves`); the validation reviewer sees score lines with their bare lines. **Long-term goal attributes are adjectives** (the owner's rule: 「用本人原话、短而具体、贴合这条线的身份，长期目标是形容词，不要把动词之类的强行组合成形容词」): `attributeProblem` (`packages/core/src/line-attributes.ts`) refuses a model's candidate that is 「能/会/善于…」 plus a verb, a count, a leading action verb, an achievement at the end or over 12 characters (`ONBOARDING_ATTRIBUTE_NOT_DESCRIPTIVE`), the keep path drops such items without emptying a line (`attributesOnRecord`), the goal splitter drops action parts of old model-written suggestions, the dialogue is told whether a line already has candidates (`goalPicker`), and the shared style (`style.ts`) says it for every Skill. What the person wrote or chose keeps its wording.
- **Sandboxed shell** (on for the hosted beta since 2026-11-04; docs/personal-agent.md §8). On the vendored Codex's own Linux sandbox, no Codex patch: `agent.sandbox` starts the assistant thread under the named profile `crossline-task` (`sandboxProfile`: `:minimal` read, inputs read, task dir write, `/data` and `/state` deny — the deny also stops Codex ever re-running a command unsandboxed — network off, `shell_environment_policy.inherit = core`), verifies `activePermissionProfile` (`SKILL_SANDBOX_UNSUPPORTED` otherwise, and the start retry never drops those keys), keeps `untrusted` so the guard still sees every command, gives the board/mail/inbox functions and web tools beside the shell, and waits at the model gate. `modeFor` picks `sandbox` for non-owners when `CROSSLINE_SANDBOX_SHELL=on` and `probeSandboxShell` (`apps/worker/src/sandbox-probe.ts`) really starts a bubblewrap sandbox; providers then get `capabilities.shell`. On the hosted beta (the owner's decision of 2026-11-04) the image has bubblewrap and python3, `ensure-env.sh` sets `CROSSLINE_SANDBOX_SHELL=on`, and `run.sh` gives the worker container alone `deploy/server/seccomp-sandbox.json` (Docker's default plus the namespace/mount/pivot_root calls) and the AppArmor profile `crossline-sandbox` (docker-default plus `userns`, `mount`, `pivot_root`); the host's `kernel.apparmor_restrict_unprivileged_userns` stays on, so nothing else on the host gains user namespaces. A grown workflow is repaired by the assistant after one failure of its own (`FAILURES_TO_IMPROVE` 1), on the person's card note, or from the input box (`workflow.fix`, the snapshot lists each workflow's id and last run); growing new workflows runs wherever the sandbox starts, not only on the owner's shell.
- **Asking mid-run** (2026-10-19, Codex's `request_user_input`): both assistant modes get `askPerson` (`SkillRunOptions`, turned on with `tools.experimental_request_user_input.enabled` + `features.default_mode_request_user_input`; the runtime's `item/tool/requestUserInput` is answered by `withPersonQuestions` in `skill-runner.ts`). The worker's `ledgerQuestion` (`agent-dispatch.ts`) writes `agent.question.requested`, says it once to the phone (`sayToPerson`, kind `agent_question`), waits up to ten minutes for `agent.question.answered` (待确认 `#assistant`, `QuestionAnswer`, `POST /api/agent/questions/[id]`), else `agent.question.expired` and the run is told to take the safest option and list the question in `needsHuman` (`QUESTION_UNANSWERED`). `personAsker` (`agent-task.ts`) puts at most `QUESTIONS_PER_RUN` (2) to the person and records each with its answer in `audit.questions`.
- **Self-check and the person's design** (2026-11-04, docs/personal-agent.md §8.1): `selfCheckPass` (`apps/worker/src/self-check.ts`, daily per account or 「立即自检」 → `POST /api/selfcheck`) runs one probe per feature (outputs, assistant questions, workflows, mail, automations, sandbox, node, remote browser), keeps `selfcheck.last`, records what it repaired and tells the person once a week only what it could not. 「我的设计」 (`packages/core/src/personal-design.ts`, `design.personal`): a whitelist of rule thresholds (`DESIGN_KNOBS`, out of range refused) and per-Skill standing notes (≤600, appended as the run note, never loosening the Skill's rules), changed from the input box (`design.change`) or Settings → 我的设计 (`/api/design`), previewed, confirmed, undoable, pausable. The worker writes its own sandbox probe into `assistant.sandboxShell`, which the web's `assistantMode` reads.
- **Supervisor `services`** (`packages/codex/src/index.ts`): worker services answer their own prefix for the caller's workspace; a write with a browser `Origin` is refused like every other supervisor write.
- **Conformance**: `MAIL_TRIAGE_SCHEMA` and `AUTOMATION_PLAN_SCHEMA` are new cases; until a record runs them, `SCHEMA_PROXIES` lets the measured schema of the same shape stand in (calendar filing; the input box's answer), so a provider measured before 2026-10-19 is not refused the new Skills.
