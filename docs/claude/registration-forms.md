# Registration forms (2026-11-01)

The opportunity agent's B track (docs/opportunity-agent.md §10–§13, §16; safety boundary below). A run is a `StoredFormRun` in setting `opportunity.formRuns` (`packages/db/src/form-runs.ts`), queued by the discovery track through `queueFormRun` or `POST /v1/forms/queue` (web `POST /api/forms`). The worker's `createFormService` starts the oldest queued run (the tick, plus a 30-second watch of windows waiting for the person), drives it page by page with `fillForm` — snapshot → `crossline-form-filler` → `judgeAction` → do → read back (`valueMatches`; sensitive by `hashForm`) → screenshot in `data/forms/<ws>/<run>/` → next — and stops with `waiting_person` + `stoppedFor` (a `opportunity_form` nudge links to `/settings#apply`), where 继续 resumes on the page the window shows (a closed window restarts from the opportunity page; a captcha holds the site through `siteHold` until 继续). After a submission the confirmation page is quoted; with a mailbox connected, a mail from the registration host's own domain confirms the one run it names (`receiptRun`: when several runs share the domain, ≥60% of the title's words in the subject or opening, else none) and marks the opportunity confirmed — a run still `ready_to_submit` or `waiting_person` counts as submitted by the person —, else the person is asked after 48 hours; without one the page confirms it. Confirmed → a `schedule.events` fixed event `opportunity-<id>` from `startsAt` (two hours; none when the quote names no time). Saving a missing profile item resumes the run waiting on it. Settings → 报名资料卡 (`apply-card.tsx`, `lib/apply-profile.ts`) shows the profile (sensitive items only as held), which runs used each item, and every run with its stop, held reasons, checklist and latest screenshot. On the hosted beta (no screen) a run goes to a browser on the machine owner's compute node (`browser: true` in its hello; `driveFormContext` in `node/browser.ts` is shared, form operations relayed over the node's connection) and waits while none is connected. When the filler finds nothing to do on a page, two fallbacks run, each at most once a page, and only propose: Stagehand v3 (`@browserbasehq/stagehand` 3.7.3, MIT; `observe()` only, never `act()`, Skill `crossline-form-observer`, `stagehandFallback`), then browser-use 0.13.14 (MIT, Python; `browserUseFallback`, `apps/worker/src/browser-use.ts`, `packages/core/src/form-browser-use.ts`), installed only by the person's press on 报名资料卡 (PyPI, about 350 MB, Python 3.11+ on the computer; `POST /api/forms/browser-use` → `/v1/forms/browser-use`, venv `<data>/tools/bu`, never on the hosted worker). browser-use never touches the person's window: the page's DOM, redacted, is loaded into a throwaway headless browser (empty temporary profile, CSP with no script, form submission, connection or frame, every request refused but the copy and the run hosts' stylesheets) whose loopback DevTools port it uses; every action of its own is removed but `done`/`scroll`/`find_text`/`dropdown_options`, and it gains `propose_field`, which records role, name, operation and value; vision, the judge and highlights are off and `allowed_domains` is the run's hosts. Its model is Skill `crossline-form-browser-agent` (Codex only) behind a one-run-token loopback endpoint, text only and redacted again; `browserUseActions` maps the proposals onto the real page's snapshot for the engine. Tests: `packages/core/src/form-fill.test.ts`, `form-browser-use.test.ts`, `apps/worker/src/form-engine.test.ts` (both fallbacks, browser-use from a test venv when present), `browser-use.test.ts` and `form-service.test.ts` (real local Chrome against fake pages served in the test; skipped without a browser).

**Egress guard, fail-closed gates, saved website logins (docs/plans/harness-1125.md §2, §3, §5; 2026-11-25).** The owner's decision of 2026-11-25 widened the boundary: the 报名资料卡 may hold website logins (host, username, password) used only to sign in while filling a form; no payment of any kind, and captchas, two-factor, one-time codes and magic links stay the person's.
- *Egress.* While the engine fills, `driveFormContext` aborts every request but GET/HEAD to a host off the run's hosts (`onHosts(url, runHosts(host))`) and reports each such host once to `onBlocked(url, "egress")`, i.e. the existing `opportunity.form.blocked` event. On when the window opens and when `fillForm` starts (继续 included); lifted (`driver.egress(false)`) whenever the window becomes the person's — every `hold` and the `ready_to_submit` gate. The node driver has the same guard (`egress` is in `FORM_METHODS`). Not covered: WebSockets (not routed by `context.route`) and data carried out in a GET's query.
- *Fail closed.* A filler that throws counts as no answer (`engine_failed`); a pre-submit check that throws or times out counts as not run (held: 「提交前总核没有通过」). A card field stops the run (`payment`) before a model is asked; a page that shows a price is held before submit even when the opportunity was said to be free. Tests in `form-engine.test.ts`.
- *Login vault.* `login-<host>` in the worker's secret store holds `{username, password}` as JSON; the ledger keeps only `apply.logins` = `[{host, savedAt}]` (`LOGIN_VAULT_SETTING`, `readLoginVault`), events reuse `apply.profile.saved`/`removed` with `{login: host}`. Routes: worker `GET/POST /v1/apply-logins`, `DELETE /v1/apply-logins/<host>` (formService, prefix registered in index.ts), web `POST /api/apply-logins` and `DELETE /api/apply-logins/[host]` (`writeGuard`: `isCrossSiteWrite` then the session; nothing echoed back). The worker answers only for the machine owner on a computer with a screen (`loginsHere`); a hosted server — its owner or an account whose forms open on its own compute node — gets `LOGIN_VAULT_LOCAL_ONLY` and never stores one. UI: 报名资料卡 → 网站登录 (hosts listed, password box `type=password`, never shown again), only where `screen`.
- *Use.* `fillForm` gets `logins` (`savedLogins`: `loginFor` — https, the page's exact host or a known alias, never a subdomain) only for this computer's own window. On a page `pageStop` calls a login, or the filler calls `pageKind: "login"` (a username step), `tryLogin` reads the login and the driver's `login` types it on the top-level page only (`current.locator` never looks into a frame), then presses the form's button. Refused, so the page goes to the person: no saved login, a field or text asking for a second factor (`SECOND_FACTOR`), more than one password box, a form with any box besides username and password (a sign-up), a button that does not read as signing in (`LOGIN_BUTTON`), a value that does not read back. Two login pages at most per run and the password once: a wrong one is never retried. The model is told only `savedLogin: true`; everything it or the ledger sees passes `redactLogin` (snapshot, errors, injected lines, stop detail, fallbacks); screenshots mask every password box and the filled username box. The page record keeps `loggedIn: <host>` and `opportunity.form.page` carries `login: <host>`. `login` is not one of the node's methods, so a password never crosses a node's connection. The `crossline-form-filler` Skill text does not mention `savedLogin` yet.
- *Node mode check (§6).* The vault never leaves the person's computer. The sensitive profile items did until §9.3 below.

**Sensitive items on the person's computer; runs wait for it (docs/plans/harness-1125.md §9.3–§9.4, the owner's decisions of 2026-11-25).**
- *Where they live.* `sensitiveHere` (= `loginsHere`: the machine owner's own computer with a screen) keeps them in this worker's secret store as before. Every other account the form service serves — the hosted owner, an account whose forms open on its own compute node — keeps them only on that computer: `createNodeBrowsers({ vault })` (`NodeVault` in `node/browser.ts`; the device worker gives its DPAPI store under scope `node-vault`, the standalone node one DPAPI file per item in `<node home>/vault/`, only on Windows — off it no vault and nothing in plain text). The node's `hello` says `vault: true`; the hub's `browserFor` prefers such a node and its link carries `vault`. The hosted ledger keeps only `apply.sensitive`.
- *Saving and removing.* `/v1/apply-profile/<slot>` for such an account goes through `saveSlotOnComputer` / `removeSlotOnComputer` (`form-profile.ts`): a sensitive value goes over the node's connection as `{op: "vaultPut", slot, value}` (in the worker's memory for the call only), the computer writes it, reads it back and answers only `{sha256}`; the record says held only when that hash matches the value sent (`vaultHash`, plain sha256 of the exact string), and any older server copy is deleted then. No connected vault node: `409 SENSITIVE_NEEDS_COMPUTER`, nothing changed; a mismatch: `409 SENSITIVE_VERIFY_FAILED`. Removing needs the computer too (`vaultRemove`). Plain items stay ledger facts.
- *Filling.* The session records `sensitiveAt`: `here`, `computer` (a vault node) or `nowhere` (a node too old to hold them). On a vault node `formOpen` carries `vault: [held slots]`, the node reads those values into memory for that form only, `profileValues(…, "computer")` gives the engine `{{profile.<slot>}}`, and the node's `fill`/`select` type the held value for an exact placeholder (`NODE_VAULT_MISSING` when it has none, `NODE_PLACEHOLDER_REFUSED` for any other text containing one). Every form answer passes `redactHeld` (the same rule as core's `redactSensitive`: the value and its digits-only form) before it leaves the computer, so snapshots, read-backs, the address and errors carry the placeholder; the engine's hash read-back compares placeholder with placeholder. `nowhere` gives the engine no value, so a sensitive field fails its read-back and the run holds (`verify_failed`) rather than send anything.
- *Moving the old copies.* The form service's pass (every 30 s), when the account's window is a connected vault node, runs `moveSensitiveToComputer` before starting a queued run: each held slot still in the server's store is `vaultPut`, and the server copy is deleted only when the computer's hash matches; a mismatch, an error or no answer keeps it (`apply.sensitive.move_failed`, slot and host only) and is tried again after 10 minutes. A move is an `apply.profile.saved` event with `movedToComputer: <host>`. Nothing logs or records a value.
- *Waiting for the computer.* `/v1/forms/queue` accepts a run for an account with its own computer (`nodeAccount`) while that computer is offline (`waitsForComputer`); runs queued from the offer card (web `queueFormRun`) already did. A queued run starts only when a window exists. While none does, `computerAskDue` (core `form-fill.ts`) picks runs still queued, not yet asked, whose earliest deadline ahead starts (00:00 UTC of that day) within 48 hours: one `sayToPerson` of kind `form_computer` (push policy `interrupt`: only the person can wake the computer or submit themselves), the run keeps `computerAskedAt`. No Today line, not counted in the brief. Every form of such an account needs the computer anyway (the browser is there), so there is no separate "needs a login or a sensitive item" check.
- *Not covered.* Two computers of one account (a device-mode PC and a standalone node) have separate vaults: items move to the strongest vault node connected at the time, and a form opened on the other misses them. Only the computer the server reaches is trusted to answer the hash; a computer that lies about it would cause the server copy to be deleted. Not run against a real node connection or the real DPAPI files; tests use an in-memory vault. Tests: `apps/worker/src/form-vault.test.ts` (move verify-then-delete, failures keep the copy, no value in logs or the ledger, save/remove routes, redaction, the 48-hour push, and a real local Chrome on a node that types the held value while the server sees only the placeholder), `node/node.test.ts` (the `vault` flag on the link).
