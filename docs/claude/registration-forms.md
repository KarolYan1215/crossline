# Registration forms (2026-11-01)

> Moved verbatim from `CLAUDE.md` on 2026-11-04. Add new notes for this area here, not to `CLAUDE.md`.

The opportunity agent's B track (docs/opportunity-agent.md §10–§13, §16; safety boundary below). A run is a `StoredFormRun` in setting `opportunity.formRuns` (`packages/db/src/form-runs.ts`), queued by the discovery track through `queueFormRun` or `POST /v1/forms/queue` (web `POST /api/forms`). The worker's `createFormService` starts the oldest queued run (the tick, plus a 30-second watch of windows waiting for the person), drives it page by page with `fillForm` — snapshot → `crossline-form-filler` → `judgeAction` → do → read back (`valueMatches`; sensitive by `hashForm`) → screenshot in `data/forms/<ws>/<run>/` → next — and stops with `waiting_person` + `stoppedFor` (a `opportunity_form` nudge links to `/settings#apply`), where 继续 resumes on the page the window shows (a closed window restarts from the opportunity page; a captcha holds the site through `siteHold` until 继续). After a submission the confirmation page is quoted; with a mailbox connected, a mail from the registration host's own domain confirms the one run it names (`receiptRun`: when several runs share the domain, ≥60% of the title's words in the subject or opening, else none) and marks the opportunity confirmed — a run still `ready_to_submit` or `waiting_person` counts as submitted by the person —, else the person is asked after 48 hours; without one the page confirms it. Confirmed → a `schedule.events` fixed event `opportunity-<id>` from `startsAt` (two hours; none when the quote names no time). Saving a missing profile item resumes the run waiting on it. Settings → 报名资料卡 (`apply-card.tsx`, `lib/apply-profile.ts`) shows the profile (sensitive items only as held), which runs used each item, and every run with its stop, held reasons, checklist and latest screenshot. On the hosted beta (no screen) a run goes to a browser on the machine owner's compute node (`browser: true` in its hello; `driveFormContext` in `node/browser.ts` is shared, form operations relayed over the node's connection) and waits while none is connected. When the filler finds nothing to do on a page, two fallbacks run, each at most once a page, and only propose: Stagehand v3 (`@browserbasehq/stagehand` 3.7.3, MIT; `observe()` only, never `act()`, Skill `crossline-form-observer`, `stagehandFallback`), then browser-use 0.13.14 (MIT, Python; `browserUseFallback`, `apps/worker/src/browser-use.ts`, `packages/core/src/form-browser-use.ts`), installed only by the person's press on 报名资料卡 (PyPI, about 350 MB, Python 3.11+ on the computer; `POST /api/forms/browser-use` → `/v1/forms/browser-use`, venv `<data>/tools/bu`, never on the hosted worker). browser-use never touches the person's window: the page's DOM, redacted, is loaded into a throwaway headless browser (empty temporary profile, CSP with no script, form submission, connection or frame, every request refused but the copy and the run hosts' stylesheets) whose loopback DevTools port it uses; every action of its own is removed but `done`/`scroll`/`find_text`/`dropdown_options`, and it gains `propose_field`, which records role, name, operation and value; vision, the judge and highlights are off and `allowed_domains` is the run's hosts. Its model is Skill `crossline-form-browser-agent` (Codex only) behind a one-run-token loopback endpoint, text only and redacted again; `browserUseActions` maps the proposals onto the real page's snapshot for the engine. Tests: `packages/core/src/form-fill.test.ts`, `form-browser-use.test.ts`, `apps/worker/src/form-engine.test.ts` (both fallbacks, browser-use from a test venv when present), `browser-use.test.ts` and `form-service.test.ts` (real local Chrome against fake pages served in the test; skipped without a browser).
