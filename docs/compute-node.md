# 算力节点：本人的电脑替托管站跑模型运行时和浏览器

2026-10-23 设计。本人要求方案 A（只给本人的账号用）和方案 B（所有账号都可以用）一起设计。同日实现了 P0 连接和 P1 远程运行时（只给本人的账号，见「已实现」）；P2–P4 和方案 C 未做。

## 起因

- 托管站只有 3.5 GB 内存、2 个 CPU，worker 容器的上限是 1350 MB。2026-10-23 读收藏时，Chromium 两次被内核按内存上限杀掉：当时 4 个空闲的访客 Codex 运行时占了约 800 MB。
- 本人的 Windows 电脑长期空闲，内存、CPU 和显卡都比服务器强。
- 设备模式（docs/device-mode.md）已经定下两件事：**托管站是唯一主账本**；本机连上托管账号以后只发本机读到的东西。这份设计不改这两条。电脑多出的一个角色，是替托管站跑**运行时**。

## 已实现（P0 + P1，2026-10-23）

代码在 `apps/worker/src/node/`：`protocol.ts`（帧、方法白名单、路径改写）、`hub.ts`（服务器端）、`agent.ts`（电脑端）；`scripts/node-check.ts` 在本机真实 Codex 上跑一遍（临时 CODEX_HOME，不调用模型）。

**和上面设计的不同（做时简化）：**

- **不另发令牌。** 节点用设备模式的 `device` 令牌登录，另加两个开关：托管站「这台电脑」卡片的「作为算力节点」（`node.compute`，只有服务器运行时的主人账号能开，即方案 A），和电脑设备页 `/device` 的同名开关（`<data>/device/node.json`）。两边都开着，服务器才接受。网页版关掉后，15 秒内的下一次心跳就断开节点。
- **帧更简单。** `{t: "hello" | "welcome" | "rpc" | "files" | "files-answer" | "image" | "image-answer" | "gw" | "gw-head" | "gw-data" | "gw-end"}`，没有按工作区分路：一条连接只服务一个工作区。
- **每条连接起一个新的 app-server。** 电脑在连接建立时启动 `codex app-server`（本机默认的 CODEX_HOME，即本人已登录的 ChatGPT），用自己的 id 初始化，断开就停掉。这样新连接的请求 id 不会和上一条连接的回复撞上；断开前的线程按 `SKILL_THREAD_LOST` 在下一轮重建。
- **服务器怎么挑：协同（2026-10-23 改）。** 本人的意思是：设备模式的电脑算力更强，但不留账本，只作计算节点，帮服务器一起算。所以不是「有节点就全交给节点」，而是按次分配：
  - `startCodexSupervisor` 的 `ownerNodes` 给出本账号在线的节点，本人账号的客户端变成一个池子（`packages/codex/src/runtime-pool.ts` `createRuntimePool`）：服务器自己的运行时加上所有就绪的节点。
  - 每次运行拿到闸门名额时（`runGated` 里的 `bindForRun`）才挑一台，整次运行都用它：先挑有空位的节点，设备模式排在独立节点前面（`ROLE_PRIORITY` 2 对 1），同类里挑负载比例低的；节点都满了或一台都没有，就在服务器上跑。`skill.run` 日志里的 `runtime` 字段记着跑在哪台节点上。
  - 对话的后续回合回到开线程的那台（池子记着节点开的线程）；那台不在了，就落到别处，按 `SKILL_THREAD_LOST` 重建。
  - 池子之外的请求（登录、额度读取、状态）和 shell 助手（`codexSupervisor.client`）始终在服务器。服务器自己的运行时在池子里就是原来那个客户端对象，配置锁、线程保持等按客户端记的状态和 shell 助手共用。
- **闸门把节点算进去。** 节点的容量（每台在 `hello` 里报，默认每个逻辑核一路、每 GB 内存至多一路，4–16 路，`nodeCapacity`；本人的电脑 16 核 32 GB 即 16 路；`CROSSLINE_NODE_CAPACITY` 可直接指定。本人：「每个节点默认远强于服务器，可以支持多个线程」）加到本账号的份额和后台总名额上（`extraCapacity`）；节点有空位时，本账号的下一次运行不受服务器内存高水位限制（`nodeRoom`，看池子的 `load`），因为它不会在服务器上跑。
- **就绪前先装插件。** 节点连上后，服务器经节点的运行时装 Crossline 插件（`installLocalPlugin`），插件目录先镜像到电脑（`files`），必需的 Skill 都在才算就绪。
- **版本必须相同。** 节点和服务器的 Codex 版本（`userAgent` 里的版本号）不同就拒绝（4009）。2026-10-23 两边都是 0.163.0。
- **图片。** 回合交给模型的图片（输入框截图、收藏笔记的图）是服务器上的路径，节点先按 `image` 帧取过来再交给本机运行时；只给服务器临时图片目录和数据目录里的 png/jpg/gif/webp，单张不超过 20 MB。
- **一个账号可以同时有几台节点。** 每台按「种类:主机名」认（`device:PC`、`standalone:PC`）：同一台电脑重连（休眠醒来、重启）替换它自己原来的连接，不碰别的节点。设备模式的电脑和独立节点同时在线就一起干活；网页版卡片逐台列出主机、种类、同时几路和状态。（同日先做过「先在线的保留、后来的待命」，随后按本人「协同」的要求改成现在这样。）
- **电脑端拒绝的东西。** 白名单外的方法（`command/exec`、`account/logout`……）、`danger-full-access`/`workspace-write`、shell 工具、权限档案，一律回错误给服务器，不交给本机运行时。

**实测（`scripts/node-check.ts`，本机 0.163.0，临时 CODEX_HOME）：** 1.9 秒连上，经镜像装好插件、找到全部 45 个 Skill，0.1 秒开出线程（工作目录映射到节点自己的目录），完全访问被拒。

**本人开启的步骤：**

1. 托管站 设置 → 通用 →「这台电脑」：生成设备令牌，在电脑的 `http://127.0.0.1:3210/device` 连接（设备模式，docs/device-mode.md）。
2. 同一张卡片上「作为算力节点」选「开启」。
3. 电脑的设备页上「作为算力节点」选「开启」。后台服务重启后几秒内连上；卡片显示「已连接」。

电脑关机、休眠或断网时，节点 45 秒没有回音（每 15 秒问一次，所以最多约 60 秒）就被判离线，本人的模型工作回到服务器，什么都不用做。

**还没做：** P2（收藏读取的浏览器、媒体下载和转写交给节点）、P3（shell 助手）、P4（方案 B：其他账号）和方案 C；闸门里节点的独立容量池（现在节点的运行仍按服务器闸门排队）。

## 独立安装包「Crossline 节点」（2026-10-23，本人账号）

本人要求做成一个 exe：电脑上不用装 Codex、不用装 Crossline 完整版，也不拿到源码。

**包里有什么（`scripts/package-node.ts` → `dist/node-installer/Crossline-Node-Setup-<版本>.exe`，`installer/crossline-node.iss`）：**

- `main.mjs`：`apps/worker/src/node/standalone.ts` 连同中继（`agent.ts`、`protocol.ts`）和 `ws` 打包、压缩成一个 68 KB 的文件。打包脚本按 esbuild 的输入清单检查，Crossline 自己的文件只能是这三个，多一个就失败（`NODE_BUNDLE_TOO_WIDE`）。Skill、提示词、计划和校验都不在包里：节点连上后由服务器经镜像装插件。
- `node.exe`（打包时运行的那个 Node）。
- `codex\codex.exe`、`codex\codex-code-mode-host.exe`：从 `vendor/codex`（rust-v0.163.0，带 Windows 迁移校验和补丁）编译的 release 版，打包时核对 `--version` 是 0.163.0。
- 用到 VC++ 运行库的模块旁边放运行库（dumpbin 检查）；许可证；`start.vbs` 用 wscript 无窗口启动。
- 每用户安装到 `%LOCALAPPDATA%\Crossline Node\app`，不要管理员权限；默认勾选「登录 Windows 时自动运行」（`HKCU\...\Run`，带 `--autostart`）。

**程序做什么（`standalone.ts`）：**

1. **配对。** 没有令牌时向网页版 `POST /api/node/pair` 要配对码（不需要账号），在本机页面上显示 `XXXX-XXXX`，每 3 秒用拿到的秘密 id `GET /api/node/pair?id=` 问一次。本人在网页版「这台电脑」的「独立节点」填入配对码（`POST /api/node/pair/approve`，只有服务器运行时的主人账号能批，即方案 A）。网页版为这台电脑单独生成节点令牌（`node.token.sha256`，不会替换设备令牌），并打开「作为算力节点」。程序取走令牌，令牌只交出一次。配对码 10 分钟有效，过期自动换新；同一地址一小时最多要 12 个码。待批的配对只存在网页进程里，网页重启就作废，程序会重新要。
2. **令牌保存。** 用 Windows 自带的数据保护（DPAPI，经 PowerShell）加密存到 `token.bin`，只有当前 Windows 用户能解开；启动时读一次放在内存里。
3. **登录。** 程序有自己的 Codex 目录（`%LOCALAPPDATA%\Crossline Node\codex-home`）。本机页面上点「登录 ChatGPT」走 Codex 本来的浏览器登录，花的是这个账号自己的额度；也可以填 OpenAI 的 API key（本人 2026-10-23：「节点也要支持 api key」，`node/control.ts` `loginNodeWithApiKey`），按用量计到这个 key 上。key 只交给本机 Codex 存在它自己的目录里，不发到网页版、不写日志、不回显；只接受 `sk-` 开头的形状。Codex 在真正跑模型之前不检查 key，填错会在第一次运行时报错。页面上可以「退出登录 / 换账号」。设备模式的电脑在设备页「节点的 Codex 登录」同样可以填 API key（`POST /api/device/node {apiKey}` → `/v1/device/node`）。
4. **中继。** 配对且登录后启动 `startNodeAgent`，用的是包里的 `codex.exe` 和自己的 Codex 目录。网页版解除配对或换了令牌，下一次心跳（15 秒内）断开（4004 `NODE_TOKEN_REVOKED`），程序删掉令牌、回到配对。
5. **本机页面。** `http://127.0.0.1:47391/`（被占用就换一个端口，写在 `node.lock` 里）：配对码、登录、运行状态、退出。只认 `127.0.0.1:<端口>` 这个主机名（防 DNS 重绑定），POST 必须带页面自己加的请求头（别的网站无法驱动它）。同时只运行一份：再点快捷方式只会打开已运行那份的页面。

**实测（`scripts/node-standalone-check.ts`，本机 Codex 0.163.0、临时目录、替身网站，不调用模型）：** 源码版和打包压缩后的 `main.mjs` 都通过：配对码配对成功；全新 Codex 目录读作未登录，中继不启动；页面正常；不带请求头的 POST 和别的主机名被拒；ChatGPT 登录能发起（拿到 `auth.openai.com` 地址，不打开窗口、不真的登录）；重启后从 DPAPI 读回令牌，不再要新码；磁盘上的令牌不是明文。

**方案 C 留在设计里：** 现在只有服务器运行时的主人账号能批配对。给其他账号开放前要做「别人的节点不受信任」那一节：网关自己数用量、中继只转发该工作区的路由。

## 浏览器读取放到节点（2026-10-24，P2 的第一块）

起因：收藏在服务器上读到约 1360 条时，worker 容器的内存满了（上限 1350 MB，其中 5 个 Codex 运行时各约 200 MB）。而本人的电脑一直空着。本人问：「为什么现在的工作流程没有在我自己的电脑上运行」。

现在节点也能跑读取用的浏览器（`apps/worker/src/node/browser.ts`）：
- 节点在 `hello` 里报 `browser: true`，前提是本机有 Chrome 或 Edge（`findBrowser`；`CROSSLINE_NODE_BROWSER` 可指定别的浏览器）。
- 服务器的 `browserFor` 选出这样的节点。本人账号读收藏时（`startFavouritesRun` 的 `onNode`），读取的每一步都通过节点连接发过去执行：打开、翻屏、取文字、取接口回答、下载图片视频。图片和视频按 8 MB 分块传回（`browser-chunk`）。
- 浏览器是本人电脑上可见的 Chrome 或 Edge 窗口，用节点自己的配置目录（`<节点目录>/browser-profiles/<网站>`）。服务器不占内存，网站看到的是本人家里的网络。
- 第一次在节点上读时如果没登录，会请本人在那个窗口里登录（`loginOnNode`）。中途要验证时，窗口自动提到最前（`front`），图片恢复加载，小帮手在网页上弹出「已在电脑上完成」。本人在窗口里完成后点它，读取接着往下（`waitForNodeDone`/`nodeDone`，走 `login_done`）。15 分钟内没完成就照旧停下。
- 节点端浏览器的每个请求都只能去公网 https 域名（`publicHttpsOnly`：不允许 IP、localhost、内网地址或非 443 端口），服务器发来的页面碰不到本人的内网和这台电脑本身。
- 读取逻辑（翻屏、判断验证、记账）仍在服务器上，节点只执行浏览器操作。`driveContext` 由服务器和节点共用，所以两边读到的东西一样。
- 独立节点安装包 1.1.0 起附带 playwright-core（`node_modules/playwright-core`），不附带浏览器，用本机已装的 Chrome 或 Edge。设备模式直接用仓库里的 playwright-core。

## 没有节点时

托管站必须能独立运行，这是前提：节点是加速，不是依赖。2026-10-23 先给服务器自身加了内存限额（docs/skills-library.md「内存限额」）：

- 收藏读取的浏览器开之前先等出 700 MB 空间，运行期间这部分空间留给它，用量到上限的 90% 就自己停，不再被内核杀掉；
- 模型闸门把这份空间算进后台工作的高水位；
- 访客运行时会先于本人的运行时和 worker 被内核选中。

四个容器的硬上限加起来是 3.1 GB，主机 3.5 GB，容器不用 swap。代价是收藏列表长到服务器装不下时，只能读到上限处（具体条数看 `collect.list_progress` 的实测），这正是节点要解决的事。

## 核心决定

1. **账本、计划、校验都留在托管站。** 电脑不持有任何账本文件，也不写账本。两份账本互相覆盖、额度花两遍，是设备模式刚刚退役的问题，这里不再出现。
2. **电脑只做「远程的 Codex 运行时」。** 托管站的 worker 照常拼上下文、发 `thread/start`/`turn/start`、回答动态工具、校验答案、写账本。区别只在于这条 JSON-RPC 流的另一端是电脑上的 `codex app-server`，不是服务器上的子进程。`JsonLineRpcClient` 本来就只要一个 `writeLine`，`RuntimeSidecar` 本来就只要 `client/stop/onExit`，所以换成远程的不用改任何 Skill 的运行器。
3. **由电脑去连服务器，不反过来。** 电脑主动连到 `wss://app.crossline.lol/node`，所有流量都走这一条连接。家里不开端口，不暴露 IP，DNS 不动。用户永远只访问 crossline.lol。
4. **电脑不在就回落到服务器。** 运行时注册表每次挑运行时都先看电脑在不在：不在，就用服务器上的运行时，和今天一样。跑到一半断线，按 `SKILL_THREAD_LOST` 处理：调用方在服务器上重建线程，这条路已经存在。
5. **方案 A 和 B 是同一套机制，只差白名单。** 电脑端有一份允许的工作区名单，默认只有本人；B 是往名单里加人，并且分级（见下）。

## 已核实：开发者模型走的是 Codex 框架

2026-10-23 在代码和托管站账本上核实。开发者模型（SiliconFlow）**不是**光杆调用 API，和 ChatGPT 走的是同一套：

- **入口相同。** `runRouted`（`packages/codex/src/skill-runner.ts`）里 `decideRoute` 选中 provider 后，同样调用 `startIsolatedThread`/`startAgentThread`，在 Codex app-server 上开线程。
- **只换模型来源。** 线程参数里带 `modelProvider: "sponsor"` 和 `model_providers.sponsor`，其 `base_url` 是 worker 本机的模型网关（`model-gateway.ts`）。网关按请求加上服务器的 key，再转给 SiliconFlow；`chat-bridge.ts` 负责 Responses 与 Chat Completions 之间的翻译。
- **框架的其余部分完全一样：**
  - Skill 注入（`$crossline:<skill>`）
  - `outputSchema` 结构化输出
  - 动态工具（`read_ledger`、`search_material`、`web_search`）
  - 修复回合（同一线程上把校验意见发回去）
  - 停滞检测
  - 线程压缩
  - `thread/tokenUsage/updated` 用量统计
- **实跑记录。** 托管站账本最近 14 天，`model_usage` 里 DeepSeek-V4.1-Flash 共 362 次运行，其中 361 次带 Codex 的 `thread_id`；Qwen3.5 两个型号的 58 次、GLM-5.3-Flash 的 4 次，全部带线程 id。用量来自 Codex 自己发的 `thread/tokenUsage/updated`，只有在 Codex 线程里跑才会有这条记录。
- **provider 线程上少了哪些能力（`capabilityGap`）：** OpenAI 托管的网页搜索（用 Crossline 自己的 `web_search`/`web_fetch` 代替）、图片、shell 助手、ChatGPT 连接器、记忆，还有 code mode（provider 上还没测过 `exec`）。

## 架构

```
用户浏览器 ──https──> app.crossline.lol（Caddy）
                          ├─ web 容器（页面、API，不变）
                          └─ /node ──> worker 容器：节点网关（新）
                                         ▲  一条 wss 连接，多路复用
                                         │
                       本人电脑：设备模式 worker + 节点进程（新）
                          ├─ codex app-server × N（每个工作区一个 CODEX_HOME）
                          ├─ 模型网关中继（loopback，转回托管站的模型网关）
                          ├─ Chromium（收藏读取，仅本人）
                          └─ 转写（SenseVoice/Whisper，可用 GPU）
```

### 连接与鉴权

- **令牌。** 实现时改为直接用 `device` 令牌加两边的开关（见「已实现」）。原设计是另发一个 `node` 范围的令牌，撤销其中一个不影响另一个。
- **入口。** Caddy 把 `app.crossline.lol/node` 转给 worker 容器的节点网关（新端口，只在 docker 网络内）。连接时先验令牌，再验节点声明的机器 id。同一账号同时只认一个节点。
- **复用。** 一条 wss 上分多路，每帧带 `{ch, kind, data}`：
  - `rpc:<workspace>`：某个工作区运行时的 JSON-RPC 行，原样转发；
  - `gw:<id>`：模型网关请求的中继（见下）；
  - `job:<id>`：非模型的任务（浏览器、转写），和文件分块上传；
  - `ctl`：心跳（15 s）、容量声明、开关运行时、清理指令。
- **断线。** 心跳 45 s 没回音就当节点离线：该节点上所有正在跑的线程按 `SKILL_THREAD_LOST` 结束，租出去的任务收回给服务器跑。

### 运行时注册表怎么挑

`createRuntimeRegistry` 增加「节点池」。`client(workspaceId)`/`handle(workspaceId)` 的选择顺序：

1. 该工作区在节点的白名单上，节点在线、有空位、没被本人暂停 → 节点上的运行时（`RemoteSidecar`：`client` 是一个把行写进 `rpc:<ws>` 通道的 `JsonLineRpcClient`）；
2. 否则 → 服务器上的运行时，规则和今天一样。

**线程不跨机器。** 一条线程在哪里开，就一直在哪里跑。保留的会话线程（访谈、输入框）记录它在哪台机器上（`threadHost`）；那台机器不在了，就当作 `SKILL_THREAD_LOST`，从消息重建。现有的 `threadRoutes`（路由变了就重建）照此推广到「机器变了就重建」。

### 模型闸门与内存

- 节点的运行不占服务器的内存，也不受 `CROSSLINE_MEMORY_HIGH_WATER` 约束。闸门（`model-gate.ts`）给节点单独一个池子，容量由节点在 `ctl` 里声明，例如「运行时 8 个、同时 6 次运行」。
- 每账号 2 个后台位、交互优先、等久了升级，这些规则两边共用，按账号计数，不按机器分开算。
- 节点优先给本人用。白名单上的其他账号只用剩下的空位，见方案 B。

### 模型网关：key 不离开服务器

provider 线程的 `base_url` 现在是 `http://127.0.0.1:<port>/<HMAC 路由>`，指向服务器 worker 的回环地址，在电脑上没有意义。改法：

- **节点端中继。** 节点在本机回环上起一个中继，和服务器网关同一种路径形状。线程定义里的 `base_url` 换成节点中继的地址：服务器开线程时就知道线程在节点上，所以 `urlFor` 按运行时所在的机器给地址。
- **转发。** 中继把整个 HTTP 请求包成 `gw:<id>` 帧发回服务器，服务器网关加上 key 转给上游，把流式回复原样传回去。
- **结果。** 开发者模型的 key、访客自己的 API key 都只留在服务器，永远不到电脑上。代价是每个模型请求多一次「电脑到服务器」的往返，比起模型自己的耗时可以忽略。
- **ChatGPT 线路不经过中继。** 节点上的 Codex 直接用本机的 ChatGPT 登录去连 OpenAI。

### 节点端必须自己守的规矩

服务器一旦被攻破，节点就是一条进入本人电脑的路。所以节点不全信服务器发来的东西，在转给本机 app-server 之前逐条过滤：

- 只放行运行器用到的 JSON-RPC 方法，其他一律拒绝：`thread/start|resume|unsubscribe|compact/start`、`turn/start|interrupt`、`config/read`、`skills/list`、`plugin/*` 安装、`model/list`、`account/*`、`mcpServer/tool/call`。
- **`danger-full-access`、`features.shell_tool`、`code_mode` 只对本人工作区放行，而且要本人在节点设置里打开「允许 shell 助手在这台电脑上运行」。** 其他工作区的线程强制 `sandbox: read-only`、关闭 shell。节点改写参数后，再用 `thread/start` 的返回值核对实际生效的设置。
- `cwd` 一律改写到节点给这个工作区划的目录下（`%LOCALAPPDATA%\Crossline\node\<ws>\`），服务器给的路径不用。
- 不在白名单上的工作区，`rpc:<ws>` 通道直接拒绝。白名单在节点本机配置，服务器不能改。

### 技能文件

运行时要在本机装上 `crossline` 插件（仓库里的 `skills/marketplace`），和每个工作区的 `crossline-mine`/`grown`/`public` 库插件。

- **仓库插件：** 节点安装包自带，版本和服务器一起发布。版本不一致时节点拒绝上线，服务器照常自己跑。
- **库插件：** 由账本派生，服务器经 `job` 通道下发文件和哈希，节点写进 `node\<ws>\skill-library\` 再安装，和服务器的 `installLibraryPlugin` 同一套逻辑（哈希没变就不重装）。

### 运行时版本与合格记录

provider 的合格记录绑定「运行时二进制哈希」，换了哈希记录就过期。节点上是 Windows 版 `codex.exe`，服务器上是 Linux 版，二进制哈希必然不同。处理办法：

- 节点和服务器必须是同一个上游版本（`codex-baseline.json` 里的提交）；版本不同，节点不能上线。
- 合格记录改为按「上游版本 + 平台」判断是否过期，并记下测量时的平台。

开发者模型的测量照旧在服务器上跑，节点不参加测量。

## 方案 A：只给本人的账号用

白名单只有本人工作区。分四步：

| 步骤 | 搬到电脑上的东西 | 说明 |
| --- | --- | --- |
| A1 | 本人的 Codex 运行时：所有结构化 Skill、输入框、访谈、工具型助手 | 本人在电脑上用 ChatGPT 登录一次节点的 CODEX_HOME。服务器上的登录保留，用作回落；两边各自登录，refresh token 互不影响（**不要**把服务器的 `auth.json` 拷到电脑上，同一个 refresh token 在两处轮换会让一边失效）。 |
| A2 | 收藏读取（Chromium）、笔记媒体下载、视频转写 | 作为 `job` 交给节点。节点用本机的 Crossline 浏览器配置，在本人的电脑、本人的网络环境里读，读到的笔记 md、图片、视频分块传回服务器的输出目录。图片描述仍是 Skill，走 A1 的运行时。服务器 Xvfb 上的登录配置留作回落。 |
| A3 | shell 助手（`crossline-agent`） | 任务目录在节点上；输入文件由服务器下发，产出物（含 `progress.json`、`audit.json` 和哈希）跑完后传回，服务器照常核对产出物。需要本人在节点设置里打开。 |
| A4 | 录音转写、整理时间段 | 手机上传的录音转发给节点，在 GPU 上转写，只把文字传回；节点离线就回到服务器夜间的 SenseVoice。 |

A 的收益：服务器 worker 不再跑本人的运行时和 Chromium，最近两次崩溃的原因就没有了；本人的工作不用和访客抢服务器内存。

## 方案 B：其他账号也用这台电脑

同一套机制，白名单上加人。但电脑上会经过别人的数据，所以分两级，每一级都要**那个人自己同意**，不是本人替他们打开：

| 级别 | 电脑上跑什么 | 电脑上会有什么 | 前提 |
| --- | --- | --- | --- |
| B1 | 只跑走 provider 的线程：开发者模型、该账号自己的 API | 线程内容：上下文、对话、回答，以及 Codex 的 rollout 文件；**没有任何凭据**，key 留在服务器 | 该账号在 设置 → 模型连接 里同意「在开发者的电脑上运行」；隐私页写明 |
| B2 | 该账号自己的 ChatGPT 运行时 | 除 B1 的内容外，还有该账号的 `auth.json`（ChatGPT 登录） | B1 的前提加上单独同意；登录在节点的运行时上完成（设备码），`auth.json` 只存在节点上该账号的 CODEX_HOME 里 |

**B 不做的事：** 不替其他账号跑浏览器读取（收藏等），也不跑 shell 助手。用本人家里的 IP 替别人读小红书，等于给别人当住宅代理，正是「不用代理」那条边界禁止的，也会把本人的 IP 和账号一起拖进风险。

**B 在电脑上的数据保留：**

- **rollout 隔离与清理。** 非本人工作区的 CODEX_HOME 放在单独的目录里，Codex 的 rollout（`sessions/`）在线程释放后 24 小时内删除。会话线程（访谈）因此可能找不到，按 `SKILL_THREAD_LOST` 重建，本来就支持。
- **删除跟着走。** 账号在托管站删除或取消同意时，服务器经 `ctl` 让节点删除该工作区的整个目录；节点离线时排队，下次上线先执行删除，再接新任务。
- **不进备份。** 节点目录不进任何备份。

**B 的容量和优先级：**

- 本人的工作永远排在前面。
- 本人在用电脑时（屏幕活动读取器显示有输入），节点只保留本人的运行，不再接其他账号的新运行，和录音转写的 `recordingPace` 同一个思路。
- 其他账号用节点，只是比在服务器上更快、更不容易排队；节点不在时照常用服务器，功能不变。

**服务条款：** B2 是用本人的设备承载别人的 ChatGPT 登录，和用服务器承载访客运行时是同一个风险（做托管内测时已向本人指出），换到这台电脑上不会消失。B1 不涉及 ChatGPT 登录。

## 方案 C：每个人用自己的电脑给自己的账号跑

本人 2026-10-23 提出：让别人通过网页授权，把自己的电脑也设为节点。可以，但**只给自己的账号跑**，等于把方案 A 推广到每个账号。

### 怎么接

1. 在托管站 设置 →「这台电脑」点「把这台电脑设为算力节点」，下载安装包。复用现有的 Inno Setup 安装包、托盘和启动器（docs/local-installer.md），加一个节点模式；只装节点模式时，本地不起网页和账本。
2. 节点第一次启动时向托管站要一个配对码，显示在托盘窗口里；本人在网页上输入配对码并确认。服务器随后发一个 `node` 令牌，只对这个工作区有效。流程和 Codex 的设备码登录同一种，不用手动复制令牌。
3. 本人在节点上用自己的 ChatGPT 登录。`auth.json` 只存在本人的电脑上。

只开网页不够：浏览器里起不了 `codex app-server`，一定要装本地程序。目前只有 Windows 安装包，Mac 版要另做（上游有 Mac 版构建）。

### 好处

- **ChatGPT 登录待在本人自己的电脑上，自己的额度给自己用。** 服务器不再替访客保存 `auth.json`。托管站替访客承载 ChatGPT 登录的服务条款问题，在这一级大部分消除。
- **shell 助手可以开给每个人。** 现在只有本人能用，因为它在本人的电脑上执行命令。到了各自的电脑上，就是本人自己的选择，节点设置里的开关默认关。
- **服务器内存压力按人数分出去。**

### 代价

- **笔记本会合盖、休眠。** 有开发者模型或服务器端登录的账号，离线时回落到服务器。只用 ChatGPT 登录的账号，可以在设置里选「只用我的电脑」：节点离线时后台工作等待；本人在页面上发起的操作，明确提示「你的电脑不在线」。
- **节点上的 Codex 必须和服务器是同一个上游版本**，否则不让上线（见「运行时版本与合格记录」）。

### 别人的节点不受信任

- **用量由服务器的模型网关自己数。** 开发者模型和 provider 的请求从节点中继回服务器网关，再由网关加 key；token 由网关从上游回复里统计，月度上限按网关的数字算。节点报的 `thread/tokenUsage/updated` 只用来显示，不用来计费。否则一个改过的节点可以少报，或者借中继任意调用开发者的 key。
- **中继只转发这个工作区自己的 HMAC 路由**，而且只转发 provider 的对话接口。
- **节点交回的答案照常由服务器校验后才写账本**；动态工具只回答这个工作区的数据。一个改过的节点最多弄坏它自己的账号。
- 节点不能自己声明工作区，只能用令牌里绑定的那一个。

### 不做：别人的电脑给第三人跑

即「志愿者算力池」：A 的电脑给 B 的账号跑。不做，原因有三：

- B 的对话、文件和画像会落到一个陌生人能读的地方，包括 rollout 文件、内存和调试工具，删除也无从保证。
- 答案可以被有意改坏。校验只挡格式，挡不住内容，比如写歪的计划、夹带指令的教程。
- 凭据或开发者的 key 迟早会经过别人的手。

方案 B 能成立，是因为本人本来就是运营者：用户把数据交给服务器，也就是交给本人。陌生人的电脑没有这个前提。

## 显卡

现在模型都在云端，显卡只在这几处有用：

- **转写：** SenseVoice/Whisper 用 onnxruntime 的 CUDA 执行器。A4 用得上，录音在白天也能马上转完，不必等夜里。
- **本地模型（可选）：** 在节点上跑 Ollama 等，作为开发者模型的一个候选。它必须和其他候选一样，过一遍合格测量和真实工作对比（`scripts/sponsor-compare.ts`）才能用。2026-10-13 测过 qwen3:8b，19 个 Skill 合格，但质量低于现在的主模型。这一项单独决定，不在 A/B 范围内。

## 实现步骤

1. **P0 连接**
   - 托管站：`node` 令牌、Caddy 的 `/node` 路由、worker 的节点网关（多路复用、心跳、容量）、节点状态卡片。
   - 节点：在设备模式 worker 里加节点进程（连接、重连、退避）。
2. **P1（A1）远程运行时**
   - `RemoteSidecar`、注册表的节点池、线程所在机器的记录与重建、闸门的节点池。
   - 节点中继和 `urlFor` 按机器给地址。
   - 节点端过滤、技能文件下发、版本检查。
3. **P2（A2、A4）任务通道**
   - `job` 帧与文件分块上传。
   - 收藏读取的 `CollectDriver` 在节点上实现，媒体和转写跟着搬。
4. **P3（A3）shell 助手**
   - 任务目录的下发与回传，产出物核对。
5. **P4（B1、B2）**
   - 白名单与各级同意、隐私页、rollout 清理、删除同步、本人在场时节流、节点上的设备码登录。

每一步都保留回落：关掉节点，或者节点不在，系统行为和今天一样。
