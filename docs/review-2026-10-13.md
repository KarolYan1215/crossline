# 系统评审（2026-10-13）：真实账本复核、竞品与大厂对标、第一性原理方案

## 0. 结论

1. **10-10 评审修好了「管道」，但使用没有回来。** 10-10 以来三天里，收集、计时、实测时长、回答待决事项都是 0。最后一次计时是 9 月 27 日，已经 16 天。
2. **系统在你不用的时候花得更多。**
   - 7 天用掉 1391 万 tokens，10-10 时是 913 万。
   - 其中约 714 万（51%）用在给**没人开始的任务**写操作手册：资料检索 428 万、写作 225 万、设计 61 万。这期间新建了 18 本手册，没有一本被打开计时。
   - 助手又跑了 21 个任务，一个也没人审阅。
3. **决策负担变重，没有变轻。**
   - 待决事项：本周 31 项，另有 54 项排在以后，共 85 项（10-10 时为 25 项）。
   - 本周的 31 项中：
     - 12 项是缺输入的倒推提问，11 项是步骤规划的提问；
     - 关系候选 9、调研结论 6、里程碑草稿 6。
4. **根因不在算法，在产品形态。** 现在的形态有三个特点：
   - 系统**拉**着人来看：要打开网页才能看到；
   - **提前**生成大量计划和材料；
   - 把**决定**推给人。

   这三点叠在一起，人只要几天不来，积压就越滚越大，回来的代价越来越高，于是更不来。大厂产品已经收敛到相反的形态：
   - 每天一次简报，**推**给人；
   - 主动做事，但只读、只起草；
   - 改动以草稿呈现，用常驻规则代替逐次审批。

   见第 5 节。
5. **方案主线**：
   1. 后台开销跟着人的参与走：人不来就休眠，只为 48 小时内要做的事做准备。
   2. 一天一个入口：早上一条简报，最多 3 个决定，其余按默认处理。
   3. 回来时先清理积压，而不是把 85 项摊开。
   4. 登录与模型走平台已有的身份和额度：Sign in with ChatGPT、Google。

**原评审的三处方法问题**
1. **把「摩擦」当成唯一解释。** 摩擦解释不了「修完摩擦后仍是 0」。更基本的问题是，人有没有理由每天回来。
2. **对「生成」没有设上限。** 原评审建议了很多新能力（分享入口、语音、邮件接入、每日批次），却没有一条约束系统自己少做：少提议、少准备、少问。
3. **「一个月高强度模拟」至今没跑。** 原因是额度（第 1 节）。现在看，就算跑了，它也测不出最关键的「人会不会回来」。这只能靠真实使用数据，或对照期。

## 4. 重点问题逐条回答

### 4.1 用户的信息管理是否有效

**结构上有效，流量上无效，而且方向反了。**
- **有效的部分**：
  - 来源可追溯：事实逐字引用，日期带原文。
  - 归属有规则，跨线关系可证伪。
  - 今天的确认流程能把真实执行情况低成本地写回（第 3 阶段，真实 ECE 数据跑通）。
- **无效的部分**：
  - **进来的少**：入口只有网页输入框、访谈和上传。日常变化没有低成本入口：邮件里的截止、导师说定的事、课程网站的更新。
  - **生成的多**：系统自己产出的信息量（34 个里程碑提议、18 本手册、21 份助手产出）远大于人输入的信息量（0）。信息系统的价值在于帮人找到、记住、按时想起，而它现在主要在制造需要人读的新信息。
- **对标**：
  - Akiflow 汇 20 多个来源进一个收件箱；Todoist Ramble 用语音随口说，生成带日期的任务，逐条确认后保存。
  - Google CC：回复它的晨报邮件就能交代任务。
  - Gemini Daily Brief：每天早上把邮件和日历压成三段，每条可勾掉或展开对话。
  - 共同点是**入口零结构、出口极短**。

### 4.2 Agent 能否代替用户完成琐碎任务

**能做，但做的大多是没人要的。**
- 真实产出质量可以：材料目录、考试清单、复习提纲。守卫、审计、去重都到位。
- 问题有三个：
  1. **时机错**：它在任务进日程之前很久就做（准备步骤一批准就派发），产出到人手上时已经不新鲜，或者根本没人去看。
  2. **出口错**：产出进「待审阅」队列，而不是出现在人做这件事的那一刻（块开始时的面板里）。
  3. **看不见过程**：运行中看不到步骤流，也不能中途接管（10-10 已指出，仍未做）。
- **对标**：
  - Dots、Gemini Spark、Copilot Tasks 都是「主动但只读、只起草」，并且有统一的定时任务管理页。
  - 各家都没公开过 agent 的成功率；TheAgentCompany 基准里最好的 agent 只完成 30%。
  - **结论**：代办杂事的价值，取决于产出在需要的那一刻出现在人面前，而不在于做了多少。

### 4.3 能否提升用户自己的工作效率

**目前不可回答，按现在的数据也永远回答不了。**
- 实测时长 0 条，按时达成率「尚无到期里程碑」。
- 文献里没有 AI 自动排程提高个人产出的对照实验。12 人 14 天的主动规划 agent 研究发现：用户逐渐不用，主要问题是 agent 抢先、僵化、过度承诺（arXiv 2509.24073）。这和本人账号的轨迹一致。
- **要回答，需要两样东西**：
  1. 回流数据：今天的确认流程是第一步。
  2. 对照期：例如两周用、两周不用，用 `scripts/trial-report.ts` 比较。

### 4.4 用户摩擦能否优化

能。按影响排序，其中第一项不是界面摩擦，是**回来的代价**：

| # | 摩擦 | 现状 | 方向 |
|---|---|---|---|
| 1 | 几天不来，回来面对 85 项 | 一周窗口过滤 | 回归流程：先清理，再给 3 件事（第 6.3 节） |
| 2 | 每天要主动打开网页 | 早报只在桌面、一行字 | 早上一条推送简报，按钮即答案（第 6.2 节） |
| 3 | 决定来源太多 | 倒推、步骤、关系、调研、草稿各自提问 | 决定预算：每天最多 3 个，其余按默认（第 6.2 节） |
| 4 | 计时要找任务 | 块开始提醒带「开始计时」；块结束一键确认（今天上线） | 观察一周数据再调 |
| 5 | 收集只有网页框 | 手机分享入口、输入框 | 系统听写进输入框；转发邮件（需要收信通道，后排） |

### 4.5 可视化是否还需优化

需要，但不是加图。
- **缺一张「回流」图**：每周收集、计时、确认、交付。它是系统体检的第一项，现在没有。
- **今日页信息过载**：时间轴、待决堆、飞轮图谱、输入框、负荷面板并列。几天没来的人回来，第一屏应该只有「今天做什么」和「需要你定的 3 件事」。
- **飞轮图谱**：37 个点仍拥挤。默认只显示有跨线关系的里程碑，其余折成「另有 N 个」（10-10 已建议，未做）。
- **计划页**：「容量与需求」「完成预测」有用；「计划 vs 实际」「估时散点」在实测数据为 0 时只是空图，应该改成一句话加入口，而不是空坐标轴。

### 4.6 登录流程是否通畅

**对本人通畅，对任何其他人不通。**
- 邮箱注册：Resend 测试模式只能发给本人。本机实测，别人注册时会如实报错，但仍然注册不了。
- Google 登录：变量为空，按钮不显示。
- Sign in with ChatGPT：代码已有，默认关闭，只在 127.0.0.1 显示，真实回调还没跑过。
- 通行密钥：计划 4.17，未做。
- **对标**：Notion 提供 Google、Apple、Microsoft、通行密钥、邮件验证码、SAML，并且是 Sign in with ChatGPT 首批合作方；Todoist 提供 Google、Apple、邮箱。
- **建议顺序**（本地版）：
  1. Sign in with ChatGPT：身份和额度一次拿到，第 7 节。
  2. Google：一个 OAuth 客户端即可，也是写日历要用的同一个授权。
  3. 邮件验证码：需要在 Resend 验证一个域名。
  4. 通行密钥。

### 4.7 能否接入用户自己的 Codex

**能，而且已经有一半。** 每个工作区一个运行时，支持浏览器、设备码、API key 三种登录。缺的是：
- 平台推荐的 Sign in with ChatGPT 额度共享；
- 凭据加密存储；
- 能力和一致性测试的准入。

详细接口见第 7 节。有一条硬约束：OpenAI 文档写明 app-server 的登录**从来不允许用于商业或托管服务**。Crossline 只能作为本地或开源应用这样用；任何托管版本都必须改走 Sign in with ChatGPT。

### 4.8 能否兼容其他基于 API 的模型

**能，分三档，见第 7.4 节。**
- Codex 的 `model_providers` 现在只接受 `wire_api = "responses"`，`chat` 已删除，网上很多教程已经过时。OpenAI、Azure、OpenRouter、Ollama、LM Studio、vLLM 都能接。但 strict 结构化输出是否真的执行，取决于对方，必须实测。
- Anthropic、Gemini 用 Vercel AI SDK 直连，只给结构化 Skill 用。schema 需要方言转换，被剥掉的约束由现有校验器执行。
- 联网研究、画像插图、带 shell 的助手、apps 日历读取，仍然只走 Codex 的 OpenAI 路径。

**市场分成两头**：
- Motion 全自动，被批「不可信」；

Crossline 现在是「全自动排程 + 大量逐项审批」，两头的缺点都占了：排程会动，决定也多。

| Apple | 分享表单**建议**提醒事项，由人确认 | 无自动排程 | App Intents 是第三方接入 Siri 的唯一入口 | 设备端优先 |

### 5.3 大厂收敛的原则，与 Crossline 的差距

| 原则 | 大厂做法 | Crossline 现状 | 差距 |
|---|---|---|---|
| 一天一个入口 | Daily Brief、CC 晨报、Scheduled | 早报只在桌面、一行；今日页要主动打开 | 大 |
| 主动但只读 | Spark、Dots 调研只读，有变化才通知 | 后台大量**生成**（里程碑、手册、助手产出） | 大，方向相反 |
| 改动先草稿、后确认 | Planner 草稿卡片、Spark 提议 | 排程默认生效（本人选择），草稿逐条批 | 中 |
| 常驻规则代替逐次审批 | Outlook 常驻指令、Dots Custom Rules | 按类别授信（助手），其余逐项问 | 中 |
| 日历自主权从窄处放开 | 先放 1:1、专注时间 | 只写名为 Crossline 的日历（这一点做得对） | 小 |
| 过程可看、可停 | Dots 云桌面、Copilot Tasks 可审阅取消 | 只有事后审计 | 中 |
| 定时任务统一管理页 | Gemini、ChatGPT、Codex automations | 后台 pass 分散，设置页只显示用量 | 中 |
| 身份和额度由平台提供 | Sign in with ChatGPT、模型选择器 | 自建邮箱注册，默认关闭 SIWC | 大 |

**Crossline 独有、仍然成立的**：
- 本地账本，数据不出机器（五家里没有一家是本地优先的账本）；
- 跨线关系可证伪；
- 引用逐字核验；
- 日历写入硬锁；
- agent 哈希审计；
- 估时回测校准；
- 块结束一键确认。

## 6. 第一性原理方案

### 6.0 从底层看

一个个人执行系统的价值只有一个来源：**它让人在对的时间做了对的事，并且人愿意持续把现实交还给它。**

由此推出四条约束：
1. **人的注意力是最稀缺的资源**：每天给系统的注意力大约几分钟。凡是要人读、要人定的东西，都在花这笔预算。
2. **计划的价值随时间衰减**：提前三周写好的手册，到用时多半已经不对。准备应该**刚好及时**。
3. **系统的开销应该跟着人的参与走**：人不来，系统就该少做；不能在人不来时花得更多。
4. **回来的代价必须低于不来的代价**：几天不来之后，回来看到的应该比离开时更少，而不是更多。

现状四条都违反了。下面每一项方案都对应一条约束，并给出可验证的跑通标准。

### 6.1 开销跟着参与走（约束 2、3）

**现象**：51% 的 tokens 用在没开始的任务上；人 16 天没计时，后台照跑。

**方案**：
- **参与度信号** `engagement(ws)`，只用账本里已有的事件：最近一次本人主动行为的时间。主动行为包括：开始或确认计时、回答待决事项、输入框发言、批准或丢弃、完成提交。页面在前台（`presence.visibleAt`）不算：那可能只是开着。
- **三档**：

  | 档位 | 条件 | 后台允许做什么 |
  |---|---|---|
  | 活跃 | 48 小时内有主动行为 | 照常 |
  | 冷却 | 2–7 天没有 | 只做 core：收集分析、日历读取、提醒；不新建手册、不派新的助手任务、不重设计里程碑、不调研 |
  | 休眠 | 7 天以上没有 | 只读日历和提醒；每 3 天一条「回来时会先帮你清理」 |

- **刚好及时的准备**：手册、教程、助手准备步骤，只为**未来 48 小时内有排程块**的任务生成（读 `schedule.stepStarts` 与 `schedule.upcoming`），而不是一批准就生成。
- **实现落点**：`packages/core/src/cost.ts` 的 `backgroundSpend` 加一个输入 `engagement`；worker 里各 pass 已经统一调用 `spendAllows`，改一处即可。
- **跑通标准**：账本副本上把「最后主动行为」设为 3 天前，跑一次 worker tick，没有新的 `manualbook.*`、`agent.task.requested` 或 `milestone.proposed`；设为 1 小时前，照常运行。按真实 7 天数据估算，开销降到原来的一半以下。
- **已实现（2026-10-13，R1）**：`engagementTier` + `lastPersonActivity` + `spendAllows` 的 `intake` 类；教程与助手准备只为 48 小时内开始的任务，输入变了或满 7 天重做。真实账本副本（`scripts/engagement-check.ts`）：本人最后一次主动操作 10-10 07:49 → 冷却，额度正常时也只放行收集分析与日历归类；过去 7 天建的 25 本手册、41 次助手运行全部属于从未开始的任务，进入冷却后都不会再发生；本周有块的 24 个任务里，48 小时内开始的 13 个才可能做教程。

### 6.2 一天一个入口，决定有预算（约束 1）

**现象**：85 项待决，决定来自五六个互不相干的生成器。

**方案**：
- **决定预算**：每天最多交给人 3 个决定，按「影响的截止日 × 重要性」排序；其余**按默认处理并写明可撤销**，或干脆**不生成**。具体到各个来源：
  - **倒推缺输入**（12 项）：默认「先拆出一个『取得它』的步骤」，即现有的拆分模式，不再提问。人在执行那一步时自然会回答。
  - **步骤规划提问**（11 项）：默认采用规划给的推荐选项，写成「假设：」事实。人在任务卡片里可以改，与访谈的「假设代替追问」同一机制。
  - **关系候选**（9 项）：只在周报里批，不进每日。
  - **调研结论**（6 项）：只在周报里批。
  - **里程碑草稿**：重设计只提议差异；未被本人动过的草稿 14 天无人理会就自动归档。
- **早上一条推送简报**（替代桌面早报那一行），三段式：
  - 今天要做的（时间轴前三块）；
  - 需要你定的（最多 3 个，按钮即答案）；
  - 昨天的确认（「昨晚 N 块待确认」）。

  在 iPhone 上，点通知打开 `/brief`，同一页面完成全部回答。
- **实现落点**：
  - `apps/web/lib/pending.ts` 加 `dailyBudget`；
  - `apps/web/lib/asks.ts` 给每类 ask 标「可默认」及默认动作；
  - `apps/worker/src/notify.ts` 的 brief 改为结构化推送；
  - 新页面 `app/brief`。
- **跑通标准**：在当前真实账本副本上，每日待决从 31 项降到 3 项以内；每一个被默认处理的事项都能在「最近自动生效」里撤销。
- **已实现（2026-10-13，R2，按本人决定改为「只问只有本人知道的」，不设数量上限）**：倒推缺输入不再提问（拆分模式已把取得每项输入拆成步骤）；步骤提问只对重要任务提出（规则：计分作业、里程碑重要性 ≥ 60；加规划模型自己的 `importance.longTerm` 判断），不重要的写成「假设：」；重要且本人执行的任务开联网先调研最优做法再规划。真实账本副本：提问 29 → 18（倒推缺输入的 12 个消失），本周待决 32 → 28、以后 54 → 46。剩余的 11 个步骤提问来自本规则之前的旧计划，关系候选 9、调研结论 6 仍计入待决，处理方式待本人决定。

### 6.3 回来时先清理（约束 4）

**现象**：几天不来，积压越滚越多；回来第一屏就是一墙待决。

**方案**：「回归流程」。冷却或休眠后的第一次主动打开，先进 `/return`：
1. 一句话说明离开期间发生了什么：多少块没做、哪些截止临近、哪些已经过期。
2. 系统先做的清理，可撤销：
   - 过期的块全部顺延，不逐条问；
   - 14 天无人理会的草稿和提议归档；
   - 过期的「在等」项标为待跟进。
3. 只问 3 件事：最近截止的风险、一个最重要的决定、要不要调整本周可用时间。
4. 然后进入正常的今日页。

**实现落点**：
- `apps/web/lib/return.ts`：纯函数，从账本计算离开期间的变化；
- `app/return/page.tsx`；
- `gateUntilReady` 旁边加一个 `returnGate`。

**跑通标准**：在当前真实账本副本上（16 天未计时），打开今日页先到 `/return`。清理后待决不超过 3 项，并且离开期间每一项变化都有记录、可撤销。

**已实现（2026-10-13，R3，按本人决定改为一键判定 + 对话）**：`returnDue`、`returnView`、`answerReturn`（完成并问用时 / 做了一部分勾步骤 / 没做顺延 / 不做了，可一次顺延其余）、`cleanStale`（14 天归档，可撤销），页面下方是当天的对话输入框。真实账本副本（`scripts/return-check.ts`）：本人从 10-10 07:49 离开 3 天，打开今日页会先到回归页，列出 20 项期间排过时间或已到截止的任务（最早是 10-12 到期的 ECE 555 作业 2），期间助手做完 12 项、日历变化 2 次、10-19 有截止；目前没有满 14 天无人处理的提议或草稿。「待决不超过 3 项」不由回归页单独达成，交给 R2（只问必须由本人回答的）。

### 6.4 助手产出在用时出现（约束 2）

**方案**：
- 派发时机：只派发 48 小时内有块的步骤，同 6.1。
- 出口：产出挂在**那一块**上。块开始的提醒和日程面板里直接显示「已备好：材料目录（打开）」。不再进待审阅队列，除非是整件交付（`delegateWhole`）。
- 过程可见：运行中的助手任务在设置的「自动化」页显示步骤流（worker 已经记录了 commands 和 changes），可以中止（新增 `POST /v1/agent/tasks/:id/cancel`）。
- 统一的「后台任务」管理页：列出所有定时 pass 和助手任务的下次运行时间、上次结果、本周开销，可以暂停。对标 ChatGPT Scheduled 中心和 Gemini 的定时动作页。

**跑通标准**：账本副本上，一个 48 小时后有块的准备步骤被派发，产出出现在该块的面板里；一个三周后才有块的步骤不派发。

**已实现（2026-10-13，R4，按本人决定产出挂在所有任务卡上）**：`app/task/prepared.tsx` 的「已备好」行出现在每张任务卡和日程面板的块概览上（教程 + 最多 3 份文件，助手的辅助脚本不列），块开始的提醒正文附「已备好：…」；设置新增「后台任务」模块：当前参与度档位、六类后台工作（收集分析 / 规划 / 教程 / 助手 / 调研 / 夜间飞轮）各自的上次运行、近 7 天次数与 tokens，可逐类暂停（`background.paused`，助手沿用 `agent.paused`）；正在运行的助手任务每 4 秒显示搜索、命令与写入的文件，可中止（`POST /v1/agent/tasks/:id/cancel`，中止记为 `AGENT_CANCELLED`，不自动重跑）。48 小时窗口派发已在 R1 落地。真实账本副本：29 张未完成任务卡中 25 张显示「已备好」。未在真实运行时上做过一次中止（只有单测），各类后台工作的「下次运行时间」没有做——它们按 tick 和条件触发，没有固定时刻可显示。倒推缺输入的分组卡片随 R2 一起删除。顺带修正：待决事项的入口默认用真实时间而绕过了 `CROSSLINE_FIXED_NOW`，e2e 里推迟到的日期早于真实今天，卡片答完又回来；现统一用 `appNow()`。

### 6.5 回流入口与回流图（约束 1）

1. **回流图**：系统体检第一项，按周显示收集、计时、确认、交付四条柱。
2. **听写**：输入框支持系统听写，手机键盘自带，不新增依赖。PWA 输入框加一个提示即可。
3. **转发邮件**：需要一个收信地址。本地应用没有公网入口，可以由 Gmail 筛选器转发加 Graph 或 Gmail 只读拉取实现。工作量大，放到第 4 阶段的日历和邮箱整理之后。

## 7. 自带 Codex 与多模型：接口设计

### 7.1 三种接法与选择

| 接法 | 官方支持 | 适用 | 不能做的 |
|---|---|---|---|
| (a) Crossline 自起 app-server，每个工作区一个 CODEX_HOME，浏览器、设备码或 API key 登录（现状） | 本地、开源应用可用；app-server 本身标为实验性，**不得用于商业或托管服务** | 机主；访客兜底 | — |
| (b) 接入用户已装的 Codex：复用 `~/.codex` 或连它的 app-server | 不支持：ws 传输标为不受支持，桌面端没有公开接入点；复用 auth.json 会碰上 refresh token 轮换竞争（#40267）和 #48465 | **不用** | — |
| (c) Sign in with ChatGPT 额度共享：OAuth 拿到令牌，按官方配置作为自定义提供方 `openai_chatgpt_plan` 注入 app-server | 官方路径 | **访客首选**；任何托管版本必须走它 | 图像生成、托管 MCP 或连接器（apps 日历）、文件上传、`previous_response_id`；额度只能从错误码得知 |

### 7.2 接口

```ts
type ProviderKind =
  | "codex-chatgpt"          // 自管 CODEX_HOME，浏览器或设备码登录（机主、访客兜底）
  | "codex-siwc-plan"        // Sign in with ChatGPT 套餐令牌 → env_key=ACCESS_TOKEN
  | "codex-apikey"           // OpenAI / Azure API key，经 Codex
  | "codex-responses-compat" // OpenRouter / Ollama / LM Studio / vLLM，经 Codex
  | "direct-anthropic" | "direct-gemini"; // Vercel AI SDK 直连，只给结构化 Skill

interface ProviderCapabilities {
  strict: "enforced" | "best-effort" | "none"; // 以一致性测试结果为准，不信对方宣称
  dialect: "openai-strict" | "anthropic" | "gemini-jsonschema";
  dynamicTools: boolean; hostedWebSearch: boolean; imageGeneration: boolean;
  hostedConnectors: boolean; shellAgent: boolean; reasoningEffort: boolean;
}

type CredentialRef =
  | { store: "codex-home"; codexHome: string; mode: "keyring" | "file" }
  | { store: "dpapi"; path: string }   // data/secrets/<ws>/<provider>.bin，不进账本、导出和备份
  | { store: "siwc"; path: string }    // 含 refresh_token，原子写入
  | { store: "none" };                 // 本地模型

type QuotaReading =
  | { kind: "windows"; primary?: Window; secondary?: Window; allowed: boolean | null } // account/rateLimits/read
  | { kind: "budget"; spentMicros: number; capMicros: number | null }                  // model_usage × 价目表
  | { kind: "plan-opaque"; lastLimitError?: string; at?: string }                       // SIWC：只有流里的错误码
  | { kind: "unmetered" };                                                               // 本地模型
type Window = { usedPercent: number; resetsAt: number | null; windowMins: number | null };

interface ModelProvider {
  id: string; workspaceId: string; kind: ProviderKind; label: string;
  capabilities: ProviderCapabilities; credential: CredentialRef;
  conformance: ConformanceRecord | null;
  listModels(): Promise<Array<{ id: string; label: string }>>;
  quota(): Promise<QuotaReading>;
  driver(): TurnDriver; // 共用现有的 runTurnsUntilValid（修正循环、校验器不变）
}

interface SkillNeeds { tier: "top" | "mid" | "low"; critical: boolean; tools: boolean; webSearch: boolean; image: boolean; shell: boolean; connectors: boolean }
type Route = { provider: ModelProvider; model: string; effort: string } | { blocker: string };
declare function route(skill: string, workspaceId: string): Route;
// 依次按：工作区偏好 → 能力覆盖 needs → 一致性测试已通过 → 额度允许，取第一个合格的；
// 永不回落到机主的运行时；没有合格的就返回 blocker，写成待决事项。

interface ConformanceRecord {
  providerId: string; model: string; dialect: string; runtimeVersion: string;
  ranAt: string; passRate: number; repairRate: number; p95Ms: number;
  failures: Array<{ case: string; code: string }>;
}
```

### 7.3 关键流程

1. **连接**：设置 → 模型连接，选一种接法。
   - SIWC：浏览器跳转 → 回调 → 校验已授予 scope 里有 `chatgpt.tokens.use.direct` → 令牌写入 `siwc` 凭据 → worker 以 `env_key` 注入、启动该工作区的 app-server。
   - API key：浏览器 POST → supervisor → DPAPI 写入。账本只存类型和末 4 位。
2. **一致性测试**（准入）：对每个导出的 `*_SCHEMA` 跑一个最小真实提示，另加长文本、`anyOf` 联合、深层嵌套三个对抗用例。
   - 判定：能 `JSON.parse`、通过 `structuredOutputProblems`、通过对应的 `validate*`。
   - 准入线：critical Skill（验收门、收集分析）要求 strict 执行、通过率 100%、修正率 ≤ 5%；其余 ≥ 90%。
   - 结果写成 `model.provider.conformance` 事件，设置页显示「可用于哪些功能」。
   - 换模型、换运行时版本，或满 30 天，都要重测。
3. **路由**：`route(skill, ws)` 替代现在 `model-policy.ts` 的单表。需要图像或连接器的 Skill 在 SIWC 和第三方提供方上直接不可用，写明原因。shell 助手只走机主运行时。
4. **续期**：SIWC 令牌由 worker 刷新，刷新后重启 sidecar 并 `thread/resume`；现有 `SKILL_THREAD_LOST` 的重建路径已覆盖线程丢失。
5. **额度**：

   | 提供方 | 读法 |
   |---|---|
   | ChatGPT 登录 | 读窗口 |
   | API key、直连 | 读预算；没设上限时后台工作不跑 |
   | SIWC | 读不到额度，把 `subscription_sharing_usage_limit_exceeded` 映射成 `SKILL_USAGE_LIMIT` 并退避 |
   | 本地模型 | 不计费 |

   这些读数都汇入现有的 `backgroundSpend`。
