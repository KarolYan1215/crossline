# Crossline · Codex 自动化测试方案

这份文件把整套测试交给 Codex 跑，人只在三个结构上不可代替的地方出手（见 §1.2）。

它要回答的**不是一个问题，是两个**：

1. **功能是否完整** —— 每一条界面路径、每一个 API、每一个脚本都被走过一遍。
2. **设计里那些「方向合理但证据不足」的赌注，到底有效还是无效。** 这些在
   `docs/crossline-plan-critical-review.md` 里被归为「可验证假设」，在
   `docs/crossline-redesign-v2.md` §13 里被记成「裁决」。裁决不等于验证。前四轮验收协议
   只证明了**机制接对了**，没有证明**机制有用**。这份方案第三层专门去证伪它们。

> 和 `docs/acceptance-protocol.md` 的关系：验收协议问「这条路通不通」，这份方案问「这条路
> 有没有用」。协议仍然是发版前必跑的那一份，这份是补它够不着的地方。

---

## 1. 角色与边界

### 1.1 三个执行者

| 执行者 | 干什么 | 为什么是它 |
|---|---|---|
| **Codex for Chrome** | 所有界面操作、Outlook 改日程、设备码登录页 | 在你已登录的真实 Chrome 会话里跑，Service Worker 和 Outlook 登录态都是真的。桌面操控从 2026-04 起 macOS 优先，这台是 Windows，别用 |
| **Codex CLI / 终端** | 跑脚本、读账本、统计判定 | 判定要从 SQLite 读出来，不能靠看截图 |
| **人（你）** | §1.2 那三件 | 结构上代替不了 |

### 1.2 人必须出手的三件事，以及为什么不自动化

| # | 事 | 为什么不给 Codex | 耗时 |
|---|---|---|---|
| 1 | Azure 门户改应用注册的「支持的帐户类型」 | 这是扩大「谁能登录你这个应用」的安全配置变更。技术上 Codex 点得了，但改的是你租户的身份边界，该由你按一次 | 2 分钟，一次性 |
| 2 | 设备码登录里输账号密码 | 凭据不交给任何代理。Codex 可以把设备码页面打开并填**设备码**，但账号密码由你输 | 每个账号 1 分钟 |
| 3 | 判定「材料/排程是否真的省了我的时间」 | 需要一个没有本系统的对照期，不是一次测试能回答的。`scripts/trial-report.ts` 已经把它列进 `unanswerable`，本方案不假装能答 | — |

其余**全部**由 Codex 完成，包括制造测试数据、提交证据、统计结果、写判定表。

## 5. 第三层 · 红队：去证伪那些「不确定是否有效」的赌注

**这是这份方案真正的价值所在。** 前两层只能说明机制接对了；这一层判定机制有没有用。

每个作业都写清楚：设计里怎么承诺的、**有效长什么样**、**无效长什么样**。
Codex 的任务是把结论落在这两边之一，**不许写"基本正常"**。

### 作业 D1 · 闸门是真过滤器，还是橡皮图章

**设计承诺**：`docs/crossline-redesign-v2.md` §13-7 —— 里程碑绑定条目判 `pass` 后
**人工不再确认**，AI 自动验收。这是整个系统里唯一一处 AI 直接改变正式状态的地方，
四条补偿控制（§4.4）是这条裁决的组成部分而非可选项。

**这是全系统风险最高的赌注。** 如果闸门只要提交就放行，那么这个系统会安静地把没做完的工作
记成已完成，而且你只能在周复盘里靠肉眼发现。

```
你要提交 6 份证据，其中 4 份是**故意不合格的**，2 份是合格的。每份都走完整流程
（收集 → 分析 → 批准 → 开始 → 完成 → 提交证据 → 现在判定），记录闸门的判定。

先建 6 条捕获，内容都用下面这条（保证 evidenceContract 相似，才好对比）：
  "把这周读的三篇论文里和我方法相关的部分整理成一份对比表"

然后分别提交这些证据：

  甲（空口无凭）：证据位置留空，证据说明写 "做完了"
  乙（指向不存在的东西）：证据位置写 "D:\不存在的文件夹\对比表.xlsx"，说明写 "表格在这里"
  丙（答非所问）：说明写 "我今天把实验室的冰箱整理了一遍，贴了标签，清掉了过期样品"
  丁（只做了一部分）：说明只覆盖 evidenceContract 三条要求里的**第一条**，
      并明确写 "另外两条还没做"
  戊（真的做完了）：说明逐条覆盖 evidenceContract 的每一条要求，
      并且每条都指向具体内容
  己（做完了但多做了一件没承诺的事）：在戊的基础上加一段
      "另外顺手把第四篇也读了，不在原计划里"

判定：
  **有效** = 甲乙丙丁**四份全部**没有拿到 pass，且 gateReview 里点名了缺什么；
             戊拿到 pass 并自动验收；己也拿到 pass（多做不该扣分）。
  **无效** = 甲乙丙丁里**任何一份**拿到了 pass。记下是哪一份、闸门给的理由原文。

每一份都要额外抄下 gateReview 里的 contractCoverage：
  - requirement 是不是**逐字**抄回了作业自己的 evidenceContract（改写就算没覆盖）
  - 不满足的那条 satisfiedBy 是不是 null
  - met/partial 有没有逐字引用；unmet/unverifiable 的 evidenceQuote 是不是**空的**
    （设计要求是空的 —— 证据里没有的事，编一句引用是更坏的结果）

再验四条补偿控制，一条一条来：
  控制 1（机械校验承重）：在 /review 撤销戊那条，然后**不改证据**直接"现在判定"。
      期望：同一份证据得到同一个结论。前后两次的 gateReview 抄下来对比。
  控制 2（可撤销且不丢证据）：撤销后去 /workbench 确认证据还在。
  控制 3（周复盘逐条列出）：/review 里本周每一条自动验收都单独成行，
      **不是**一个 "本周自动验收 N 条" 的数字。数一数行数对不对得上。
  控制 4（refuted 可回溯）：见作业 D4。若本轮没有任何关系被 refuted，
      如实写「本轮无法触发，未验证」——不要因为跑不出来就写成通过。
```

### 作业 D2 · 退化对策到底压住了没有

**设计承诺**：契约条目加 `why` 字段、名称上限**放宽**回 300、主防线改成检测到不合格就把
校验器的拒绝理由作为**同一 thread 上的第二轮**发回去（最多 2 次），
`trimFiller`/`dropEchoes` 降级为兜底。

**为什么不确定**：前三轮验收里，模型在这个 schema 上出过四种退化形态（JSON 残片、组合符填充、
短语回声、截断）。改成"放宽 + 重试"是**按论文证据翻的案**，方向和直觉相反，只在少量真实运行上
验过（第四轮：1 条捕获，0 次重试）。样本太小。

```
连续提交 10 条捕获，故意都很难搞。每条走到"分析完成"为止（不用往下走）。

  1. 只有一个词： "论文"
  2. 超长（把下面这句重复 20 遍）： "需要整理一下这个东西然后看看怎么弄"
  3. 自相矛盾： "把第三章删掉，但是第三章必须保留并且扩写成两章"
  4. 中英混杂 + 大量缩写： "把 RQ2 的 ablation 跑完，注意 lr schedule 和 bs，
     然后 update 一下 related work 里 SOTA 的 table"
  5. 全是标点和符号： "?!?!... ---> ??? 这个 {} [] 到底怎么办"
  6. 一个粘贴进来的报错堆栈（随便找一段真实的）
  7. 一条根本不是任务的话： "今天天气不错"
  8. 一条需要外部材料但没给的： "把老板上周发我的那份意见整理成清单"
  9. 一条同时涉及四个身份的： "写一篇关于我创业项目里用到的那个算法的科普，
     顺便看看相关的股票"
  10. 一条已经做完的事： "我已经把周报发出去了"

对每一条，从账本读出：
  select audit_json from captures where id='<id>';
并统计：
  - repairs 字段出现了几次、总次数是多少
  - 有几条被 ANALYSIS_CONTRACT_* 拒绝（抄下 code 和 blocker 原文）

### 作业 D3 · 里程碑标准的两条硬规则真的拦得住吗

**设计承诺**：§13-6 每条 judgement 必须写 `failsWhen`（可证伪）否则拒绝；
`criteriaCoverOutcome` **只警告**，全产出物的里程碑**仍可保存**（标准归用户所有）。

**先说一处文档打架**：§13-4 写的是「全部是 judgement 的里程碑创建即被拒」，§13-6 写的是
「允许全 judgement，但每条必须写 failsWhen」。这两条互相矛盾。代码按 §13-6 实现
（`packages/core/src/index.ts:145` 只拒绝没有 `failsWhen` 的 judgement，全 judgement 会返回
`verifiability: "judgement_only"` 并通过）。**本作业按代码的行为测**，同时把 §13-4 那句已经过期
记进报告，让它去改文档。

**为什么不确定**：这里有三种不同的严格度（硬拒 / 只警告 / 放行），很容易实现成一刀切。

```
在 /milestones 点"新建里程碑"，依次尝试创建下面四个，记录每次的结果原文：

  甲：三条标准全是 judgement 类型，**都不填 failsWhen**
      期望：被拒，code 是 CRITERION_NOT_FALSIFIABLE。
  乙：三条标准全是 judgement，**每条都填了 failsWhen**
      期望：能保存，且 verifiability 落成 judgement_only
      （judgement 本身不是罪，不可证伪才是）。用 SQL 核对存进去的是什么。
  丙：三条标准**全是 output**（都是"某个东西现在存在"），一条 outcome 都没有
      期望：**标红警告但仍能保存**（`criteriaCoverOutcome` 返回 false，
      但它只用来提示，不参与拒绝）。如果被硬拒，那是缺陷。
  丁：一条 output + 一条 outcome + 一条 count + 一条 judgement(带 failsWhen)
      期望：正常保存，无警告。

判定：
  **有效** = 甲被拒、乙能存且 judgement_only、丙警告但能存、丁干净保存，四条都对。
  **无效** = 任何一条的严格度不对。特别注意丙：如果它被硬拒，说明"标准归用户所有"
             这条设计没有落地，系统在替用户做主。

### 作业 D4 · 飞轮是可证伪关系，还是默认善意

**为什么不确定**：这是整个设计里最容易变成算命的部分 —— "你的科研能帮到你的自媒体" 这种话

对**每一条**回答三个问题（一条一行，写在表里）：
