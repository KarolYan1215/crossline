# 系统评审：真实账本、临时账号走查与竞品对标（2026-10-10）

## 0. 结论

Crossline 在**规划的严谨程度**上已超过所有对标产品：
- 多主线共用一本账，跨线关系有证伪条件；
- 阈值带余量，引用逐字核验；
- 日历写入有硬锁，agent 全程留审计。

但它目前**没有成为本人每天收东西、做事的地方**。两周真实账本里：
- 收集 6 条，输入框里本人只说过 2 句话；
- 计时 2 次，实测时长 0 条；
- 完成并验收的任务 3 个，已批准未开始的任务 29 个。

系统在本人的输入很少的情况下，生成了很多计划：
- 主线页有 54 个已归档里程碑、19 个新草稿；
- 7 天内用了 913 万 tokens，额度进入经济模式（任一窗口用到 85% 以上）。

所以首要问题不是规划算法，而是三件事：
1. **现实回流太少**：收集、计时、交付的摩擦太大。
2. **决策负担太重**：25 项待确认，每天 4.3 次决定。
3. **新用户进不来**：注册邮件只能发给本人；没有批准的里程碑之前，收集的任务不分析、不排程。

本轮走查还发现并修复了一个**跨账号数据泄露**：本机的微软日历登录被同步进每个账号。

## 3. 问题清单

### P0：阻断或安全

**P0-1 同一台机器上的所有账号共用一个 Codex：同一份记忆、同一份额度。** 未修复，设计见 `docs/model-providers.md` §1.2。
- **原因**：worker 只起一个 app-server，用一个 `CODEX_HOME`，跨运行记忆开着；而记忆按整个家目录全局合并。
- **影响**：临时账号的访谈读得到本人的 Codex 记忆，也在花本人的 ChatGPT 额度。今天临时账号两轮访谈就用掉本人额度里的约 6 万 tokens。
- 只要有第二个人用这台机器上的 Crossline，这就是真实的隐私问题。

**P0-2 邮件注册只对本人可用，界面却显示「已发送验证邮件」。** 未修复，需要本人操作。
- **原因**：SMTP 走 Resend 测试模式，只能发给 karolyan1215@gmail.com；发给其他地址一律 `550`。Better Auth 在后台发送，失败只进日志（`web.err.log`），注册页照样提示已发送。Google 登录的两个变量为空，按钮不显示。
- **影响**：除本人以外，任何人都无法完成注册。「10–30 名首批外部试用者」的目标在登录这一步就卡住了。
- **怎么修**：
  1. 在 Resend 验证一个域名，并把发件地址换到该域名下。
  2. 配置 Google OAuth，减少一个密码。
  3. 发信改为同步等待，失败时注册页说明原因。

**P0-3 用 API key 登录时，所有后台工作会悄悄停掉。** 未修复，见 `docs/model-providers.md`。
- **原因**：运行时对 API key 账户不返回额度窗口（`account/rateLimits/read`），worker 里写着 `if (!signal.available) return`。
- **影响**：换用 API key 的人会看到：自动分析、倒推、助手全都不动，界面也没有任何提示。

### P1：设计问题

**P1-1 新用户的冷启动是一条死路。**
- **现象**：临时账号设好主线、答了两轮访谈、加了 5 个日期，在输入框写「周二前完成 ECE 555 作业 3 的前两题，大概要 3 小时」。卡片识别正确（截止 10/13，3 小时）；执行后任务停在 `captured`，不分析、不排程。
- **原因**：
  - 自动分析要求工作区已有批准的里程碑，而且额度处于正常模式。新账号两者都不满足。
  - 本人账号现在处于经济模式，**自动分析对本人自己也已停止**。
- **对标**：Reclaim 和 Sunsama 第一天就能把任务放进日历；Motion 恰恰因为「要配置 2–4 周才见效」被批评。
- **建议**：
  - 没有里程碑时，任务先按主线和截止日直接排程，归入「未挂里程碑」，事后再归档。
  - 经济模式下，自动分析降一档运行，而不是不运行。当前 `NEVER_DOWNGRADED` 把它挡在降档之外，结果是完全不运行，比降档更差。

**P1-2 现实回流太少，模型生成的计划越来越多。**
- **数据（14 天）**：

  | 指标 | 数量 |
  |---|---|
  | 收集 | 6 条 |
  | 输入框里本人的发言 | 2 句 |
  | 计时 | 2 次 |
  | 实测时长 | 0 条（估时校准、精力模型都学不到东西） |
  | 精力自评 | 4 次 |
  | 已验收任务 | 3 个 |
  | 已批准未开始的任务 | 29 个 |
  | 里程碑 | 已归档 54、已批准 22、草稿 19 |

- **原因**：
  - 收东西的入口只有网页输入框，手机上要打开 PWA；没有分享菜单、语音、转发邮件。
  - 计时要先找到任务再点「开始计时」。
  - 交付要上传证据。
- 这些单看都合理，叠在一起，本人就不再把现实交还给系统。规划越做越细，现实却没有回来。
- **建议**：
  - 日历块到点时问一句「开始了吗」，一点即计时。
  - 完成时「用了多久」一点即记。
  - 手机分享目标与语音输入。
  - 把「本周回流」（收集、计时、交付）做成系统体检的第一项。

**P1-3 待确认太多，计划反复变动。**
- **数据**：
  - 每天决定 4.3 次，当前待决 25 项。
  - 54 个已归档里程碑：架构师重做过很多次；今天又生成了 19 个新草稿。
  - 「收集到排入」中位 964 分钟。
- **原因**：
  - 草稿要逐条线批准。
  - 每次重设计都替换未动过的草稿。
  - 访谈、日期、目标、关系、助手结果各有入口。
- **对标**：Morgen 一次批整份计划，Sunsama 每天早上批一次。
- **建议**：
  - 每天一个「今天批这些」的批次，只含本周要定的：本轮已按一周窗口过滤。
  - 里程碑重设计改为只提议差异（新增、改日期、删除），而不是整批换掉。

**P1-4 排程与本人说的投入比例脱节。**
- **数据**：计划页显示近 4 周计划投入为研究 100%、创业 0%、创作 0%、投资 0%。本人在访谈里说研究约 64%、创业 20%、创作 11%、投资 5%。创业有 11 月 30 日的 MVP 截止，但近 4 周一小时也没排给它。
- **原因**：
  - 排程按截止分档再按重要性排。创业的里程碑截止远，留在任务库里。
  - 可用时段一直是默认的每周 39 小时，本人从没设置过；而本人说每周约 72 小时。默认时段装不下研究以外的工作。
- **建议**：
  - 每条主线设一个「保底份额」，取访谈里的比例，排程时先保底再按截止分档。
  - 默认时段改为由访谈的作息推出，并在计划页顶部持续提示「可用时段是默认值」。

**P1-5 助手确实在做杂事，但有重复劳动，也很少被看。**
- **数据**：
  - 41 个助手任务，37 个完成、4 个受阻。
  - 只有 5 个被审阅（采纳 3、退回 2），其余是准备步骤，自检通过即算完成。
  - 标题去重后只有 35 个：同一门课的「汇集课程讲义、作业与样题，形成材料目录」先后做了 4 次，「生成材料目录初稿」2 次。
  - 助手占 7 天用量的约 1/3（297 万 tokens）。
- **原因**：
  - 步骤规划器为同一门课的多个任务各自生成「收集材料」类准备步骤。
  - 已采纳的产出（`acceptedOutputs`）只在同一个任务内复用，没有按课程或项目共享。
- **能否代替本人做杂事**：能。材料目录、考试清单、复习提纲草稿属于真正的杂事，真实账号上有可用的产出。但 2 个被退回，而且重复劳动占了相当比例。
- **建议**：
  - 准备类产出按「项目 × 产出类型」去重，已有的直接引用。
  - 运行中显示步骤流，并允许中途接管（对标 ChatGPT agent 的 watch/takeover）。

**P1-6 额度没有被管理。**
- **数据**：7 天 913 万 tokens，占比前三：助手任务 297 万、教程写作 97 万、资料检索 89 万。额度已进入经济模式，里程碑设计在今天已降一档运行。
- 设置页只显示 tokens 数，**不显示剩余额度百分比和重置时间**。本人看不到自己离「后台全部暂停」还有多远。
- **建议**：
  - 设置页显示两个窗口的剩余百分比与重置时间。
  - 按功能设预算，教程写作、资料检索放在最后。
  - 走查和评估类脚本先检查额度。

**P1-7 访谈的几处不准。**
- 首轮已明确说「11 月底前做出 MVP」，访谈却问「Crossline MVP 在文件中标为待定，大致日期？」。本人没有上传任何文件，日期也没有记下来。
- 两轮之后，待决事项里仍写「访谈在『开场与规则』阶段（第 1/6 阶段）」。
- 跳过的问题下一轮原样再问。

## 4. 重点问题逐条回答

**用户的信息管理是否有效？**
- **结构上有效，实际流量不够。**
  - 有效的部分：项目、日期、事实都有出处，课程文件里的日期能读出来，归属有规则判断。今天临时账号首轮就从一段话里读出 5 个准确日期，并提议加入日历。
- **无效的部分**：
  - 信息只在访谈和上传时进来。日常的变化（新作业、邮件里的截止、和导师说定的事）没有低成本的入口：两周只有 6 条收集。
  - 收进来的东西在没有里程碑时停住（P1-1）。
  - 计划的信息量远大于现实的信息量（P1-2）。
- **对标**：Akiflow 把 20 多个来源汇进一个收件箱；Google CC 直接回邮件就能纠正它；Todoist Ramble 用语音。

**agent 能否代替用户完成琐碎任务？**
- **能，并且已经在做**：41 个任务，材料目录、考试清单、复习提纲草稿都有产出，守卫和审计到位。
- **不足**：
  - 重复劳动（P1-5）。
  - 2/5 的审阅被退回。
  - 不能看运行过程，也不能中途接管。
  - 「自动交给 Agent」开关今天刚上线，默认关闭，还没有真实运行数据。
- **判断**：「准备类杂事」可以交给它；「需要判断的杂事」（选题、取舍）按设计留给本人，这是对的。

**能否提升用户自己的工作效率？**
- **目前没有证据表明它提升了效率。**
  - 实测时长为 0，估时准确度没有数据，按时达成率「尚无到期里程碑」。
  - 能测到的是开销：每天 4.3 次决定，收集到排入要 16 小时。
- 文献也只支持一个弱效应：本人感到目标互相促进，会投入更多，解释方差约几个百分点。
- 要回答这个问题，先要有回流数据（P1-2）。

**用户摩擦能否优化？** 能，按收益从高到低：
1. 新用户第一天就能排进日历（P1-1）。
2. 每天批一次（P1-3）。
3. 到点一问即计时、完成一点即记时长（P1-2）。
4. 默认可用时段由访谈推出（P1-4）。
5. 浮动按钮不遮挡（P2）。

**可视化是否还需优化？** 需要：
- **今日页飞轮图谱**：37 个点仍显拥挤，今天已改为悬停或放大才显示名称。建议默认只显示有跨线关系的里程碑，其余折叠成「另有 N 个」。
- **计划页**：「容量与需求」和「完成预测」两张图清楚、有用；「计划 vs 实际」要几天数据才有意义；估时散点要实测数据。
- **缺一张图**：「每周回流」（收集、计时、交付）。

**登录流程是否通畅？**
- **对本人通畅，对其他人不通。** 注册邮件只能发给本人（P0-2）；Google 登录未配置；在 localhost 打开会报 `Invalid origin`（已修）。
- 用临时邮箱的完整路径是：注册提示已发送 → 实际 550 → 永远收不到。

**能否接入用户自己的 Codex？**
- **可以，详细设计见 `docs/model-providers.md`。** 要点：
  - **每个工作区一个 app-server 进程，各用自己的 `CODEX_HOME`**：协议里没有「按请求换凭据」的接口，所以只能分进程。
  - **登录方式**三种：浏览器 ChatGPT 登录、设备码、API key。
  - **密钥**放系统钥匙串或 DPAPI，不进账本、导出和备份。
  - **额度与 capability token** 按工作区隔离。
  - 先修 P0-1 与 P0-3。

**能否兼容其他基于 API 的模型？** 分两半：

## 7. 复核（2026-10-10 晚，逐条对照代码）

本节对照代码逐条复核第 3、4 节。结论分三类：**归因有误**、**问题比原文说的更深**、**原文成立**。修复按第 8 节的阶段进行，每一项都先写失败的测试。

### 7.1 归因有误

**P1-1 冷启动的原因找错了。**
- 原文说 `NEVER_DOWNGRADED` 把分析挡在降档之外。实际上它只在 `routeForSkill` 里出现（`model-policy.ts`），而且只影响本人手动点出来的那次运行。
- 自动分析停住，是因为 `autoAnalyzePass` 在额度不是 `normal` 时直接返回（`apps/worker/src/index.ts`）。
- 分析的输出 schema 和 automation-stripper 的 SKILL.md **本来就允许 `milestoneId` 为空**（「GTD 意义上不属于任何项目的下一步」）。挡住它的只有两处：
  - context 的 `approvedMilestones` 要求至少 1 项；
  - worker 有两处判断。
- 另外，批准里程碑并不会触发分析，被挡住的收集最多要等一个 tick（15 分钟）。
- 所以不需要另建「未挂里程碑」：去掉这三处门槛即可。

**P0-2 的机制和原文写的不同。** 验证邮件的回调是 `await sendMail(...)`，没有 try/catch（`packages/auth/src/index.ts`）。错误是被 better-auth 内部吞掉，还是变成 500，要装好依赖后实测，不能凭日志推断。另外两点原文没提：
- 没配 SMTP 时，注册页仍然显示，只是邮箱注册的路由根本不存在；
- 没有任何「重发验证邮件」的入口。

### 7.2 问题比原文说的更深

**P0-3：同一个额度信号有四种互相矛盾的解释。**

| 位置 | 读不到额度时 | 经济模式时 |
|---|---|---|
| worker 的 8 个 pass（各复制一份） | 停 | 停（含自动分析） |
| `setSpendModeProvider` | 当作 normal | 降档 |
| diligence、manualbook | 当作 manual_core_only | 照常或停，各不相同 |
| agent-service | **照样运行** | 到 95% 才停 |

API key 登录后「静默停止」只是其中一格。第一性原理：后台工作只需回答一个问题——「这一类工作此刻该不该花钱」。所以只需要一个函数、两个类别（核心 / 可省），读不到额度就明确说出来。

**P1-2 的「实测时长 0 条」，摩擦之外还有缺陷。**
- 实测时长只在 `evidence.accepted` 时写入。完成了但没验收的（证据审阅中、验收门判了不通过），一条都不记。
- 悬浮计时器的「结束」只是暂停，执行永远不会结束。
- 离线完成会丢掉报的分钟数（`api/commands/route.ts` 不读 `reportedMinutes`）。
- 结论：就算本人每天都计时，校准也学不到东西。这一条应该先修，再谈摩擦。

**P1-5：重复劳动有第二个来源。**
- 重新规划时，`saveStepPlan` 给仍是 planned 的步骤重新编号（`v{版本}s{序号}`），而派发去重的键是 `${任务}#${步骤}`，于是同一步骤换个 id 就会再派一次。
- 传给规划器的 `acceptedOutputs` 只含同一任务里已采纳的产出，待审阅的看不到。准备类步骤一跑完就标为完成，产出却在待审阅，所以规划器以为还没有。

**P1-4：用来对齐的数据早就有，只是没被用上。**
- 优化器从来不读 `PlannerTask.identityId`；
- 访谈记下的每周时长、比例只用于展示；
- 访谈提议的作息存在 `schedule.availability.proposed` 里，排程器不读。

**P0-1：评审的修法写在 Sign in with ChatGPT 发布之前。** 之后核实到的事实：
- 运行时支持 `chatgptDeviceCode` 登录和 `thread/start.ephemeral`；
- 公开 bug openai/codex#48465：app-server 的 apiKey 登录会覆盖本机共用的 `auth.json`。每个工作区各用一个 CODEX_HOME 正好绕开它；
- OpenAI 在 2026-09-29 推出 Sign in with ChatGPT：开源或本机应用可以动态注册（`client_id=dynamic_agent_client`，回调只允许 `127.0.0.1`），托管网站要申请合作方 client id。

### 7.3 原文成立，但需要补充

- **P1-3 决策负担**：「每天 4.3 次决定」没有区分系统自动生效的和本人主动做的，它衡量的是摩擦，不能说明工作量。
- **P1-6 额度显示**：supervisor 已有 `/v1/codex/cost`，网页从没读过。补一条路由和一张卡片就够。
- **方法**：数据只有本人两周，没有对照期，所以「能否提升效率」现在不可回答。要先修好回流（7.2），再用 `scripts/trial-report.ts` 比较修复前后各两周。
