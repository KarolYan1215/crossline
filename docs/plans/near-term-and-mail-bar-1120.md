# 访谈问近期任务、邮件转任务提高门槛（2026-11-20 设计，待本人定）

背景：本人 2026-11-20 的两条反馈。

1. 访谈里有没有问最近要做什么？近期任务反馈最快，也最能引起注意，要加到问各条主线和具体日程的部分。
2. 邮件写了某个活动就成了任务，或者被拿来问本人。门槛要提高，只报对主线有帮助的。

## 一、现状（2026-11-20 读代码）

### 访谈

- 访谈没有专门问「这周、下周要做哪些具体的事」的阶段或检查项。
- 最接近的是开始标准里的 `line_project:*`（`packages/core/src/interview-checklist.ts:215` 起）：「「{line}」这条线眼下在做的一件事是什么？大概什么时候要完成」。问的是一个项目和它的截止，不是近期具体要交的东西。
- `lines.md` 第 7 条写「试做和本周的事定到「哪天、做什么、交什么」就够了」。这条只说本周的事定到哪一步，没让模型去收集。
- 访谈不产生任务。抽取（`persistExtraction`，`apps/worker/src/onboarding-persist.ts`）只写事实、日期和只读日历块。
- 第一个任务要走完这条链：确认开始 → 里程碑草稿（`firstDraftsPass`）→ 本人在主线页批准 → `autoBackplanPass` 生成任务。而且只给截止在 21 天内的里程碑生成。
- 结果：本人访谈完，「今日」上要隔几步、可能几十分钟到几小时，才出现第一件自己的事。而本人这周要交的作业，访谈时可能根本没说出来。

### 邮件

- 分拣：`triageMail`（`apps/worker/src/mailbox.ts:178`），Skill 为 `crossline-mail-triage`。模型只看到主线的 `{id,label}`，看不到目标和里程碑。
- 按 `kind` 分路：
  - `todo` / `date` → `store.capture({ id: "cap-mail-…" })` → 分析 → `autoApprovalEligible`。默认自动生效，没有任何「对主线有没有用」的检查。
  - `event` → `mailEventFrom`。必去 / 可能去会成为提问卡（「要去吗」）。`relevance ≥ 70` 就算「可能去」，即使没有对上任何主线（`lineId` 可以是空）。
- 漏口 1：`date` 的标题不以「参加」开头时（SKILL 自己的示例「11/4 15:00 系里讲座，1240 教室」），会被当作任务捕获。分析器再把它写成「参加…讲座」，之后没有代码再把它转回活动。线上的「参加 DCC 电影之夜」「参加工程学院健康日」「参加 ECE 研究讲座」都是这一路进来的。
- 漏口 2：SKILL.md 和 runner 的 `developerInstructions` 互相矛盾。SKILL 里没有 `event` / `opportunity` 这两类，只有 runner 有。
- 文档过时：`docs/claude/personal-agent.md` 写的是 ≥ 50，代码是 70。

## 二、设计 A：访谈问近期任务

### A1 问什么、在哪问

**主线阶段（`lines`），每条主线问完当前项目和截止之后紧接着问一句：**

> 「「{line}」这周到下周，有哪几件已经定了要做完的事？比如要交的作业、答应别人的东西、要回的消息。说名字和哪天要完就行，没有也可以说没有。」

- 一轮问一条主线，`multi` 形式，一次最多收 3 件。
- 只问名字和哪天要完，不问要多久。时长由分析器和校准去估。

**日程阶段（`orientation`），问完固定日程和可用时段之后问一句，收跨主线的杂事：**

> 「这两周里，还有哪件不在课表上、但一定要做完的事？」

**文件和日历里已经看到的先拿来核对，不再空问：**

> 「文件里看到 11/24「作业 5」截止，这周要开始吗？」

- 范围：`fileDates` / 已导入日期里落在未来 14 天的。
- 本人答「要」：当作近期任务。
- 本人答「不做」：照常记下（不是本人的截止）。

### A2 检查项

- 新增 `near_term:<line>`：组「项目」，`owner: "interview"`，`start: true`。
- 计为完成的情况，任一即可：
  - 本人说了至少一件；
  - 本人明说「没有」；
  - 这条线标了「先不规划」（`skipped`）。
- 跨主线的那一问不进开始标准，只作为 `orientation` 的建议项。
- 进开始标准的理由：近期任务是开始使用后第一个能看到效果的东西。答「没有」也算完成，所以不会拖长访谈。

### A3 抽取和落账

- `OnboardingExtraction` 新增 `nearTerm`：`[{ lineId, title, due: "YYYY-MM-DD" | "", dueTime?: "HH:MM", quote }]`。
- 只收本人明确说要做的事，`quote` 必须是本人原话。「可能」「想」「也许会」不收，这与访谈只记本人陈述的规则一致。
- `persistExtraction` 每一轮就写，不等访谈结束。每件写一条 capture：
  - id：`cap-interview-<uuid12>`
  - context：「来自访谈：<quote>」
  - 带上 `lineId` 和 `due`
  - 进入现有的 `createCaptureAnalyzer` → WorkOrder
- 自动生效：本人亲口说的事，`autoApprovalEligible` 照常放行。录音的 capture 不放行，因为录音里可能是别人说的话；访谈没有这个问题。
- 去重：
  - 和文件日期、邮件任务、已有任务撞上时，走现有的 `duplicate-guard` / `task-merge`（W-194 的部件合并）。
  - 同一件事访谈里说两次，按 `quote` 的指纹只捕获一次。
- 和里程碑的关系：
  - 近期任务不挂里程碑，直接排。
  - 里程碑草稿生成时，把这些任务作为「当前项目」的证据交给 `createMilestoneProposer`。
  - 草稿批准后，backplanner 遇到同一件事时并入（`task-merge`），不重复生成。

### A4 本人看到什么

- 访谈右栏的「本周骨架草稿」（`skeletonDraft`）改为先列这些真实任务：
  - 一排进日历，就显示「已排：周三 19:00–20:30 作业 4 其余题目」，并带链接；
  - 还在分析时显示「整理中」。
- 访谈结束（或开始标准齐）时，「今日」的「下一项」就是其中最急的一件，不用等里程碑批准。

### A5 测试

- 检查项：说一件、说「没有」、`skipped` 都计为完成；三条主线各一项。
- 抽取 schema：「可能会做」「想做」不进 `nearTerm`；没有 `quote` 的拒收。
- 落账：
  - 一轮两件，写两条 `cap-interview-*`；
  - 同一 `quote` 重复抽取只写一次；
  - 和 `fileDates` 里同名同日的合并为一件。
- 端到端（fake Codex）：访谈一轮说「周五交作业 4」→ 分析 → 任务自动生效 → 计划里在周五前有块。
- 回放夹具：录一段真实模型把「打算」写成近期任务的回答，放进 `testing/fixtures/`。

## 三、设计 B：邮件转任务提高门槛

**原则：** 一封邮件只有在帮得上某条主线时，才会成为任务或提问卡。其余进周复盘的「邮件里提到、没有列入」，不打扰本人。

### B1 给模型看主线目标，要它说「帮哪条线」

- 分拣输入的 `lines` 从 `{id,label}` 改为 `LineBrief`：`{ id, name, goal, milestones[] }`，取进行中的里程碑，最多 5 个。这和机会侦察（`opportunity-tags.ts`）用的是同一个形状。
- `todo` / `date` / `event` 三类都要求填 `serves`：`{ lineId, milestoneId, relevance 0-100, why }`。

### B2 代码按门槛分路，模型只给证据

**`todo` / `date` 只在以下情况之一时才捕获为任务：**

1. **义务**：发件人是课程教师 / 助教 / 导师 / 雇主（`senderRole`，或本人设过的发件人规则），而且是对本人的要求：作业、截止、要交的材料、要回复的事。
2. **对主线有用**：`relevance ≥ 70`，`lineId` 是一条存在的主线，且 `milestoneId` 指向一个进行中的里程碑或该主线的目标。没有锚点时按 `relevanceOf` 的做法封顶在 45。

**其余：**

- 不满足门槛的 → `info`，进周复盘。
- 每轮最多 5 条（`MAIL_INBOX_PER_PASS`）不变，但只数过了门槛的。

**活动一律不成任务：**

- `isAttending` 除了查动词开头，还要查活动名词：讲座、研讨会、报告会、seminar、talk、colloquium、info session、电影之夜、健康日、联谊、coffee hour、mixer。命中而且没有交付动词（交、提交、准备、写、做完）时，按 `event` 处理。
- 分析器兜底：`cap-mail-*` 分析出的标题是「参加…」时，不生成 WorkOrder，转成邮件活动记录（`MAIL_EVENTS_SETTING`），按活动的规则处理。

**活动提问卡的门槛提高：**

| 情况 | 现在 | 改后 |
|---|---|---|
| 发给本人的邀请 / 本人是组织者 / 已接受 | 必去，排入 | 不变 |
| 课程教师说必须参加 | 可能去，提问 | 不变 |
| `relevance ≥ 70`，没对上主线 | 可能去，提问 | 进周复盘 |
| `relevance ≥ 70`，对上进行中的里程碑 | 可能去，提问 | 可能去，提问 |
| 群发通知（`listed`）、社交类（`SOCIAL`） | 进周复盘 | 进周复盘；`relevance ≥ 85` 并对上里程碑才提问 |

### B3 提示词

- 重写 `crossline-mail-triage/SKILL.md`，和 runner 一致：九类齐全，`date` 的示例换成截止（「作业 5 改到 11/24 交」），讲座示例归到 `event`。
- 明写门槛：「群发通知、讲座、社交活动默认 `info`；只有服务某条主线的进行中里程碑，或者是对本人的义务，才是 `todo` / `event`」。
- `developerInstructions` 删去和 SKILL 重复的部分，只保留按账号变化的内容。

### B4 清理现有任务（要本人点头，这是对真实账本的写操作）

一次性修复，仿 `mailReminderRepair`，满足以下全部条件的才处理：

- 范围：仍开着的 `cap-mail-*` WorkOrder；
- 标题是参加类（新的 `isAttending`）；
- 没计过时、没确认过块、没交过材料。

处理方式：

- 日子已过的：归档，原因写「邮件活动，未列入」，24 小时内可撤销（`op.applied`）。
- 日子未到的：转成邮件活动记录，按 B2 的门槛决定是否提问，原任务归档。

执行前先在待确认页列出要动哪几件，本人确认后才执行。

### B5 测试

- `mailbox.test.ts` 新增：
  - 「系里讲座 11/4」的 `date` 不捕获；
  - 「电影之夜」「健康日」群发通知不捕获、不提问；
  - 课程教师的「作业 5 截止改到 11/24」捕获；
  - 与主线无关的 `relevance 80` 通知进 `info`。
- `obligation.test.ts` / `mail-events.test.ts`：改后的表格逐行一条。
- 分析器兜底：`cap-mail-*` 分析出「参加…」时不生成 WorkOrder。
- 修复：只动满足条件的；动过的件可撤销；不碰本人计过时的。
- 同步改 `docs/claude/personal-agent.md` 里的门槛数字（50 → 70，以及新门槛）。
