## 一、现状诊断（读代码，2026-11-20）

### 1. 每个模型看见什么

| 判断 | 谁做 | 能看见 | 看不见（却要判断的） |
|---|---|---|---|
| 邮件是不是要做的事、算不算活动 | mail-triage（`mailbox.ts:202`，低档） | 主线名（无目标）、未完成任务标题（截 60 字，无 id、无截止）、等待项、邮件开头 | 里程碑、目标、日程、日历会议、已知邮件活动、文件里读到的日期 |
| 一段话是不是已有任务、怎么估 | 捕获分析（`analysis.ts:193`） | 已批准里程碑、开着的任务（≤60）、相关文件段落、画像 | 最近完成的、文件日期、等待项、日程 |
| 人的步骤怎么拆 | 步骤规划（`step-planner.ts:330`） | 任务、里程碑、材料、画像、项目日期 | 其他任务、真实日程、已有教程 |
| 两个任务是不是同一件 | 合并复核（`dedupe.ts:161`，低档） | 两边的标题、意图、里程碑、截止 | 主线、项目、步骤、来源原文 |

只有输入框（concierge）和访谈对话看得到真实日程和日历。没有一个共享的「账本快照」模块，各 Skill 各拼各的。

### 2. 硬代码替模型做语义判断的地方（节选，全表见附录 A）

- **活动：** `isAttending`（标题以「参加」等开头）、`SOCIAL`、`isRestEvent`、`SITTING`（含 final 就算考试）、`isMailReminderTitle`（以「确认」开头就算提醒，「确认提交 HW4」会误判）。

- **去重：**
  - `task-merge.ts` 的 Dice 阈值（0.4 / 0.6 / 0.85）、同义词表、「数字不同就不同」；
  - `similarTitles`（同课号就算同一事件，「ECE 555 Lecture」和「ECE 555 Office Hours」会被并成一件）。
- **门槛：** `LIKELY_RELEVANCE = 70`、`PUSH_RELEVANCE = 0.6`、按标题分类的义务等级。

### 3. 重复从哪里来

- 任务去重和事件去重是两套，互不相通：**任务和日历块、任务和邮件活动之间没有任何比较**。
- 已知的重复路径：
  - 文件里读到作业，之后发布邮件到达。分拣只看到任务标题；邮件被捕获后，靠分析器的 `extendsTaskId` 碰运气。「提交 HW4」和「完成 ECE 555 作业 4」的相似度可能低于 0.4，规则抓不住。
  - 日历上的会议，加邮件「要去吗」卡（卡片不对照日历）。
  - 日历上的会议，加「参加 X」任务。
  - 同一个会议的邀请和提醒两封邮件，生成两张卡（活动 id 按单封邮件算）。
- 「作业发布」邮件对应的等待（`wait-release-*`）的 `who` 为空，分拣按发件人匹配等待，所以对不上。

## 二、外部依据（2025–2026）

- **上下文要小而准。** 上下文越长越差，近似重复的干扰项尤其伤（Chroma「Context Rot」）。
  - 稳定的小块预先放入；大块用 id 加工具按需取（Anthropic「Effective context engineering for AI agents」）。
  - 前缀保持字节稳定以利缓存；错误留在上下文里，让模型别再犯（Manus「Context Engineering」）。
- **去重：先用便宜的信号圈候选，再让模型「从候选里选一个或都不是」。** 选择式比两两判断 F1 高约 16%（arXiv 2405.16884）。
  - 写入用 ADD / UPDATE / NOOP 一次决定（Mem0，arXiv 2504.19413）。
  - 候选要短：真正的匹配排得越靠后，准确率越低。
- **邮件产品：**
  - Copilot「Prioritize my inbox」按「是否需要你行动」排序，每封给出理由，用户用自然语言调。
  - Superhuman 自动归类营销、社交并归档。
  - Sunsama 和 Motion 不自动把邮件变任务。
- **粒度：**
  - 执行意图（何时何地做）的效应量 d≈0.65（Gollwitzer & Sheeran 2006）。
  - 子目标在进度清楚时反而降低表现（Amir & Ariely 2008）。
  - 拆解有助估时，但不必拆成给人看的任务（Kruger & Evans 2004）。
  - Reclaim 和 Motion 按时间切块，任务本身保持一件。
- **护栏：**
  - 模型自报的置信度偏高，用「不确定」选项或多次采样一致性来弃权（Xiong et al., ICLR 2024）。
  - 评测用真实误判做回归夹具，按二元标签打分（Husain & Shankar「AI Evals FAQ」）。

## 三、设计

### 3.1 一个共享的「账本简报」（`ledger-brief`）

所有入账类和规划类模型调用，用同一份由代码生成的简报做前缀。格式字节稳定，按 id 排序，不含当前时刻（当前时刻放在后缀）。

| 段 | 内容 | 上限 |
|---|---|---|
| 主线 | id、名称、长期目标、本人给 Crossline 的话 | 全部 |
| 里程碑 | 进行中的：id、标题、截止、完成标准一句、所属主线 | 全部进行中，约 40 |
| 任务 | 开着的：id、标题、主线、里程碑、截止、状态、下次时段；近 14 天完成的：id、标题 | 开着的 80，完成的 30 |
| 时间 | 今天起 21 天内：日历会议、固定日程、邮件活动（含状态）、文件里读到的日期（作业发布、截止、考试），每条带来源和 id | 约 150 条 |
| 等待 | 等谁、等什么、预计何时 | 全部 |
| 偏好 | 本人对系统的指示（「少问这类」「这类都不要」） | 30 |

- 超过上限的部分，用现有的 `read_ledger` / `ledgerLookup` 按 id 取。简报末尾注明「另有 N 条，可按 id 读」。
- 估算体量：真实账号约 5–7k token。各 Skill 自己的输入放在简报之后。
- 实现上，以 concierge 的 `conversation.ts` 快照为底（它已经是最全的），抽成 `apps/web/lib/ledger-brief.ts` 和 worker 侧同构的一个模块，共用一个 `buildLedgerBrief(store, workspaceId, now)`。

### 3.2 一个统一的「入账判断」（`crossline-intake`）

**所有来源的新东西都走同一个判断：**

- 邮件、文件里读到的日期、访谈里本人说的近期任务、录音里本人的承诺、输入框；
- 「作业发布」等待被满足时也走这里。

不再由各来源各自用正则决定是不是任务、是不是活动、是不是重复。

**输入：**

- 账本简报；
- 本条原文（邮件全文前 4k 字，或文件片段，或本人原话）；
- 来源的结构信息：发件人在不在课程教师名单、是不是群发、日历邀请头、组织者 / 已接受；
- 候选：代码按便宜信号圈出的最多 8 条已有任务或时间项（同主线或同课号、日期 ±14 天、标题相似度前几）。

**输出（严格 schema）：**

```
op: add_task | add_event | update | already_known | note | ignore
target: <已有项 id>            // update / already_known 必填，必须在候选或简报里
serves: { milestoneId | "line_goal:<lineId>" | "none" }
title, due, time, location     // 仅 add_* / update
attend: must | likely | optional   // 仅 add_event
evidence: [原文引语]           // 每个判断至少一条，代码核对确在原文里
why: 一句给本人看的理由
unsure: true | false
```

**代码只做核验和落账，不做语义判断：**

- 引语必须在原文里；
- `target` 必须存在；
- 日期必须能解析且在合理范围；
- `serves` 指向的里程碑必须是进行中的。

不合格的整条退回模型重做一次，并带上错误说明。第二次仍不合格就记 `note`，进周复盘，不写入。

**落账规则：**

| op | 结果 |
|---|---|
| `add_task` 且 `serves` ≠ none | 建任务。本人亲口说的直接生效，其余照现有自动生效规则 |
| `add_task` 且 `serves` = none | 不建，只记邮件日志，周复盘也不列（R1-1）。本人亲口说的例外，照建（R1-2） |
| `add_event` | 写入邮件活动或时间项：`must` 直接放进日程；`likely` 且对上里程碑才问「要去吗」；其余进周复盘 |
| `update` | 更新已有项（发布邮件给作业补上链接、精确时刻、改期），记一条 `item.updated`，24 小时内可撤销 |
| `already_known` | 不写入，只在邮件日志里记「已在 X 里」 |
| `note` / `ignore` | 只记日志；`note` 在周复盘列出 |
| `unsure: true` | 不写入，进周复盘的「没把握的」一栏，附理由和一键「加进来」 |

**这一个判断替掉的硬代码：**

`isAttending`、`isMailReminderTitle`、`SOCIAL`、`LIKELY_RELEVANCE`，`mailbox.ts` 的按 kind 分路，`date-pairs` 的「发布 / 截止」配对，`withMailEvent` 的按单封邮件去重，`mailEventClash` 之后的「转为提问」。

**保留的代码（它们核验事实或保证安全，不做语义判断）：**

- 引语核验；
- 每轮上限；
- 群发邮件头的结构判断（作为证据交给模型，不直接下结论）；
- 已取消事件的结构标记（Graph 的 `isCancelled`）；
- Graph 只写 Crossline 日历这条边界。

### 3.3 人的工作只到交付物

**步骤规划改成：**

- **对本人：** 一件交付物一步（「完成 ECE 555 作业 4」），带一个具体的第一步（`firstAction`：「打开题面，先写第 1 题的已知量」）和完成标准。只有本人自己会分开做的事才拆开，例如两份不同的交付物、要等别人反馈后再继续的两段。
- **对助手：** 材料整理（「提取题面约束」）照做，但不在本人的步骤列表里，只出现在教程里，作为「已备好：题面约束摘要」。助手做失败时，只有在缺本人能给的东西时才打扰本人。
- **「提交」：** 并入完成标准（「已在 Gradescope 提交」）。长任务可以按本人自己会分开做的部分拆成几段（R1-3）。
- **估时：** 模型内部仍按部件估时（`parts` 只用于估时和教程目录，不给人看）。
- **排程：** 按时间切块，沿用 `MIN_SPLIT_MINUTES`，一件任务可以排成几块，每块显示同一个任务名，加「第 2 块 / 共 3 块」。

**删掉或降级的代码：**

- 原型的必需角色（`requires solve, submit`、「先解后查」）从强制改为 Skill 里的说明；
- `workOwner` 的正则串只保留「对外动作必须本人做」这一类安全边界；
- `TRIVIAL_STEP` 删除；
- `needs` 写成「提供 X」步骤，改为任务上的「等材料」标记。

**保留：** 步骤数上限、时长范围、依赖无环、id 存在。

### 3.4 去重：一套，模型选，代码圈候选

**两个时点：**

- **入账前：** 由 3.2 的入账判断完成（`update` / `already_known`）。
- **每日回看：** 取代 `dedupePass` 的规则判断。代码圈出可能重复的组，包括任务对任务、任务对时间项、时间项对时间项。模型从组里选「哪些是同一件，保留哪个」，并给出引语。

**代码只做两件事：**

- 用便宜信号圈候选：同主线或同课号、日期窗口、标题相似度前 k；课号只用来圈候选，不再用来判定。
- 落账：合并写入、撤销。

**删除：**

- `task-merge.ts` 的阈值和同义词表；
- `similarTitles` 判同一事件的部分；
- 「数字不同就不同」这类规则改为写在 Skill 里的说明。

任务对日历会议的比较是新增的：「参加 X」任务和日历上的 X 是同一件时，任务归档，会议保留。

### 3.5 注意力门：只有和里程碑相关的进入注意力

「注意力」指今日的「下一项 / 也可以先做 / N 件需要处理」、待确认、计划页的「未排进」，以及推送。

**判断依据：** 入账判断的 `serves`。

**已有任务：** 由一次性的回看给每个开着的任务补上 `serves`（不直接改里程碑归属，只标注）。

**不进注意力的任务**（`serves` = none 且不是本人亲口说的）去向见问题 R1-1。

### 3.6 访谈：近期任务

已定为开始标准、直接生效。

- **问法：**
  - 每条主线问完当前项目后问「这周到下周有哪几件已经定了要做完的事」；
  - 日程阶段问一句跨主线的杂事；
  - 文件里已经读到的近期日期，改成拿来核对，不再空问。
- 本人说的每一件，作为 `source: interview` 进入 3.2 的入账判断。
- 访谈简报里加上已抽到的日期和已有任务，补上 onboarding-extract 的盲区，避免重复。
- 每一轮就写入，访谈还没结束，今日页就能看到。
- 检查项 `near_term:<line>`：本人说了一件、说「没有」、或这条线「先不规划」，都算完成。

### 3.7 清理现有的邮件活动（已获准）

对仍开着、没计过时、没确认过块的 `cap-mail-*` 任务，用新的入账判断，带账本简报重新判一次：

| 判断结果 | 处理 |
|---|---|
| `add_event` 或 `serves` = none | 归档，原因「邮件活动 / 与里程碑无关，未列入」 |
| 日期未到的活动 | 改为时间项，按 3.2 处理 |
| 与已有任务是同一件 | 合并 |

- 执行后在待确认页列一张「已清理 N 件」的回执卡，逐条可撤销，期限 24 小时。

## 四、批判性分析

1. **把判断交给模型，错误会变得安静。**
   - 正则错了可以复现，模型错了不一定能复现。
   - 对策：
     - 每个判断带 `evidence` 和 `why`，本人可见，可撤销；
     - 周复盘列出被挡在注意力外的东西；
     - 评测集作为回归。
   - 仍然的风险：一封真正的作业邮件被判成 `note`。所以要么不设例外，信任评测；要么给「课程教师加截止日期」这一结构信号设一条保底，不允许 `ignore`。见问题 R1-5。
2. **简报越大越不准。**
   - 150 条时间项加 80 个任务，正是「近似干扰项」最多的情形。
   - 对策：
     - 候选由代码圈好放在最后，模型主要看候选；
     - 简报做总览，不当主证据；
     - 评测时对比「有简报」和「只有候选」两种做法。
3. **成本和额度。** 从一批一次变成每封一次，额度紧时邮件会积压。积压时按发件人优先级排队，不丢弃。
4. **注意力门可能藏住真正要做的事。** 例如没建里程碑的行政事务（保存 GitHub 恢复码、更新 UW 个人信息）。见问题 R1-1、R1-2。
5. **步骤合并以后，「今天做到哪」的颗粒变粗。**
   - 进度改由计时和块确认承担（已有）。
   - 「部分」靠本人的一句话或模型读提交物判断（已有 progress-judge）。
   - 风险是长任务（7 小时以上）只有一个步骤，本人觉得太大。
