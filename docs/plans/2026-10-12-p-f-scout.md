# P-F 机会侦察实施计划

> 执行方式：按任务顺序逐个做（superpowers:executing-plans 或 subagent-driven-development）。每个任务先写失败的测试，再写最少的实现，跑通后再进下一个。

**目标**：一套通用的长期机会捕捉机制：每周从长期目标、主线、里程碑、画像与确认事实推出「本人可能需要但没说」的机会需求（带事实依据、类型、时间窗），本人确认后按监视规格从公开招聘接口、本地 Codex 的只读 apps、网页检索和一个后台专用浏览器收集信号，核实、去重、排序后变成待决事项、任务草稿或每周报告的「下周预览」。现有尽调（每条主线每周一次的网上调研）并入这套机制。

**依据**：`docs/loop-and-scout.md` §6（四段链路、信息来源、后台专用浏览器、节流与额度、跑通标准）、§11 第 1 条、§12「P-F 机会侦察：放最后」、§13.2 / §13.4（apps 通道与只读白名单）、§10（被确认的需求数与产生的任务数）。

**架构**（一条链：需求 → 监视规格 → 信号 → 行动）：

| 层 | 位置 | 说明 |
|---|---|---|
| 契约 | `packages/core/src/scout.ts` | 需求、监视规格、信号的类型；`SCOUT_NEEDS_SCHEMA`/`validateNeeds`；`SCOUT_SIGNALS_SCHEMA`/`validateScoutSignals`；`signalKey`、`rankSignals`、`watchCadence`、`signalAction`。纯函数。 |
| 招聘接口 | `packages/core/src/ats.ts` | Greenhouse / Lever / Ashby 的公开岗位接口地址与解析，`matchesQueries`。纯函数。 |
| 存储 | `packages/db`（新迁移）+ 设置 | 需求放设置 `scout.needs`（条数少、随备份走）；信号放新表 `scout_signals`（按 `(workspace_id, key)` 去重）。 |
| 需求 Skill | `crossline-opportunity-needs`（中档）+ `apps/worker/src/scout-needs.ts` | 推需求和每条需求的监视规格（查询词、公司清单、页面）；推断的需求进待决事项。 |
| 取信号 | `apps/worker/src/scout.ts` | 招聘接口按公司确定性拉取（不经模型）；其余来源一次 `crossline-opportunity-scout`（中档、开网页检索、带动态工具）；每条信号核实后入表。 |
| apps 工具 | 复用 P-A 的专用 apps 线程 | Gmail 只读搜索、Exa 等检索 app；只调白名单里的读工具。 |
| 专用浏览器 | `apps/worker/src/scout-browser.ts` + `scout-browser-policy.ts` | `playwright-core` 启动独立用户目录的 Chromium，无界面、管道连接；域名白名单 + 每跳公网检查 + 拦非 GET + 动作白名单。 |
| 行动 | `apps/web/lib/asks.ts`、`apps/web/lib/scout.ts`、`apps/worker/src/scout.ts` | 快截止 → 待决事项；需准备 → 写一条 capture，走现有分析 → 任务 → 代理（48 小时规则）；其余 → 每周报告「下周预览」。 |

**依赖**：

- **P-A 第 0 步**：`scripts/apps-probe.ts` 已提交并在机主与访客运行时各跑过一次（§13.2）。本计划用它列出 Gmail / 检索类 app 的真实读工具名。
- **P-A 第 13 步**：每个运行时一条专用 apps 线程（`ephemeral`、不跑模型回合、只用于 `mcpServer/tool/call`）和只读工具白名单（§13.4）。本计划把它当作已存在的接口，下文称 `appsCall(workspaceId, tool, args)` 与 `APPS_READ_TOOLS`——**以 P-A 落地时的实际导出名为准**，只往白名单里加读工具名。
- **P-A 第 4 步**：每周报告（复用周复盘页 `apps/web/app/review/page.tsx` + `apps/web/lib/review.ts`，新增「下周预览」与每周推送）。本计划只往「下周预览」里供数据；没有它，跑通标准最后一环无法验收。
- **P-A 第 5 步**：代理只为 48 小时内有排程的步骤做准备。本计划产生的任务直接受这条规则约束，不另写闸门。
- 不依赖 P-B～P-E。

**约束**：pnpm（`pnpm vitest run <file>`、`pnpm --filter <pkg> typecheck`、提交前 `pnpm verify`）；严格结构化输出规则（`packages/core/src/structured-output.ts`，按 `*_SCHEMA` 自动发现检查）；**不提交，除非本人要求**——「建议提交点」只是建议的切分。机会侦察属于可省工作：`spendAllows(spend, "discretionary")`，额度一紧就停（`packages/core/src/cost.ts`）。新增的每条可变路由走 `isCrossSiteWrite` 与 `resolveAccessContext`，worker 路由验能力令牌——两者都有发现式测试（`apps/web/app/api/csrf-protection.test.ts`、supervisor 路由扫描），新路由漏了会当天失败。

**安全边界（需在 CLAUDE.md 显式写明，§6 已由本人决定）**：这是一条新的对外**只读**路径。专用浏览器带本人登录态、页面内容会进模型上下文，所以：只访问本人确认过的域名；每一跳过公网主机检查；网络层拦下一切非 GET；只有打开 / 读 / 点链接 / 滚动 / 在搜索框搜索五个动作；不点按钮、不调 `page.evaluate`、不注入脚本；不绕验证码、不改用户代理、不改 `navigator.webdriver`、不装隐身插件；用户协议禁止自动化的站点（如 LinkedIn）只走本人转发。浏览器用户目录（含登录 cookie）**不进备份**。apps 只调白名单读工具，测试断言写工具调用 0 次。

**待本人确认的一点**（计划按左边默认写，确认后可改）：专用浏览器第一版**只给机主工作区**（`runtimeOwner`，与 `AGENT_OWNER_ONLY` 同理：浏览器进程在这台机器上、登录窗口弹在这台机器的桌面上，远程的访客无法在那里登录）；访客工作区用公开接口、网页检索与自己运行时里的 apps。用户目录仍按 §6 写成 `data/scout-browser/<workspace>/`，以后放开不用迁移。

```ts
const ctx = { today: "2026-10-12", lineIds: ["research", "startup"], factIds: ["startup/crossline/stage", "research/phd/year"],
  existingKeys: ["summer-internship-2027"], declined: ["不考虑咨询公司"] };
```

**实现要点**：

- `OpportunityNeed = { key; title; kind: "periodic" | "event"; category: "internship" | "conference" | "scholarship" | "competition" | "incubator" | "paper" | "industry_event" | "policy" | "research" | "other"; identityId; why; basedOnFacts: string[]; windows: Array<{ label; from; to }>; queries: string[]; companies: Array<{ name; ats: "greenhouse" | "lever" | "ashby" | "none"; board: string }>; pages: string[]; research: string }`。`research` 非空表示这条需求要做一次网上调研（并入的尽调，见阶段 7），内容是要回答的问题。

- `validateNeeds(value, ctx)`：硬错（schema 外的形状、未知事实 id、未知主线）抛错并写明哪条；重复与被拒绝的直接丢弃。用 `profileFactId`（`packages/core` 已有）的格式做事实 id。

**跑**：`pnpm vitest run packages/core/src/scout.test.ts packages/core/src/structured-output.test.ts` → 先失败，实现后通过。

### 任务 1.2：节奏、信号、去重键、排序与行动

**文件**：`packages/core/src/scout.ts`、`packages/core/src/scout.test.ts`

**先写失败的测试**：

- `watchCadence(need, today)`：今天落在任一关键窗口内 → `"daily"`，否则 `"weekly"`（§6「关键窗口内每日、其余每周」）。
- `signalKey`：招聘接口岗位 → `ats:<vendor>:<board>:<jobId>`；网页 → 规范化后的地址（小写主机、去掉 `utm_*`/`gclid`/`fbclid`/片段、去掉末尾斜杠）；邮件 → `mail:<messageId>`；同一岗位从两个来源来只算一条。

## 风险

- **P-A 未就绪**：apps 线程、每周报告、48 小时闸门任一缺失，对应环节无法验收；阶段 0 先核对，缺就停。
- **招聘接口字段与看板名会变**：解析对缺字段宽容；看板名由代码请求核实，`missing` 的不当真；每月复核清单。
- **全局检索缺失**：公开接口只能按公司查，公司清单的质量决定召回；清单由本人确认时增删，这是 §6 已接受的取舍。
- **专用浏览器被拦**：无界面更容易被拦；按设计停下交给本人、连续被拦降为转发，不做任何规避。小红书一类大概率只能转发。
- **提示注入经浏览器外泄**：导航只到白名单域名、每跳公网检查、非 GET 全拦、无脚本注入；剩余风险是白名单域名本身带查询串的 GET，这在本人确认的站点范围内，已写入设置页说明。
- **登录态与隐私**：用户目录含登录 cookie，只在本机、不进备份、不进账本；代理看不到密码，登录窗口期间代理暂停。页面内容发给模型服务商，设置页写明。
- **额度**：一次侦察运行可能较长；可省档在经济模式即停，且每次 pass 合并成一次 Skill 运行。上线后在设置的模型用量里按 Skill 看，按实测调节奏。
- **通知过多**（§9）：`opportunity_signal` 只给 7 天内截止的；其余进每周报告；统一走现有通知档位与 `decisionHorizon`。
- **浏览器只给机主**是本计划的默认假设，需本人确认（见头部「待本人确认的一点」）。
