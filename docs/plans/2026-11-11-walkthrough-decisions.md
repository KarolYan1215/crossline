## 1. 拟计时：本人忘了开计时，系统在后台推断、本人确认

### 现状（已经有一半）

- 采集已经有了，而且是本人 2026-10 定下的同意路径：设置 → 隐私与屏幕活动，三档「关闭 / 只记分钟 / 应用与窗口」，默认关闭（`apps/web/app/settings/local-activity-toggle.tsx`）。Windows 上 worker 每 60 秒读一次前台进程名、窗口标题（≤300 字）和距上次输入的时间（`apps/worker/src/activity-source.ts:65`），空闲 120 秒以上记为空闲，类别由 `classifyWindow` 判定（本人的规则 → 应用名 → 浏览器才看标题），隐私窗口和黑名单不写，标题 14 天后抹掉（`apps/worker/src/activity-recorder.ts`）。托管版由本人电脑上的设备模式上传类别和散列后的应用名，不带标题。
- 推断已经用在收工页：「按计时、屏幕活动和 Codex 用时预填了推断」（`apps/web/lib/wrap.ts:100`、`apps/web/lib/measured-capacity.ts:160`）。块时间内工作类别的屏幕分钟占 ≥60% 推为完成，<20% 推为没做。
- 缺的三样：
  1. **不分任务**：块时间内任何「编程/科研工具/写作/阅读」的分钟都算到这个块头上，在块里写别的论文也算。
  2. **只看排了块的时间**：块外做的工作（晚上临时做了 1 小时作业）没有任何地方提出来。
  3. **推断不变成实测**：收工页按「完成」只记块的结果，不进估时校准；估时只从计时学。

### 别人怎么做（调研）

- Clockify、Memtime、Timing：活动只留在本机，本人点一下才变成时间记录；Timing 把活动拖到项目上就生成一条规则。<https://clockify.me/help/apps/windows-desktop-app> <https://knowledgebase.memtime.com/en/where-does-memtime-store-my-data> <https://timingapp.com/>

- 教训：窗口标题本身就含隐私（邮件主题、病历、银行），无痕窗口也会漏（ActivityWatch 论坛 <https://forum.activitywatch.net/t/firefox-chrome-tab-names-logged-despite-denial-for-tracking-while-private-incognito-browsing/635>）；Microsoft Recall 默认开启加截屏，2024 年被迫改为默认关闭（<https://therecord.media/microsoft-reverses-course-recall-opt-in>）。

### 设计

1. **不加新的采集**。只用「应用与窗口」档已经在记的分段；不截屏，不读页面内容，不新增权限。没开这一档的人没有拟计时，设置里那一档的说明加一句「开了才会提出拟计时」。
2. **归到哪件任务，只用确定性规则，不交给模型**。窗口标题不离开本机，所以不送模型匹配。按顺序：
   - 本人的规则：「应用/网站/标题关键词 → 任务或主线」，存在 `localActivity.rules`（`classifyWindow` 已经在读本人的类别规则，扩一个「归属」字段）。
   - 时间重叠：分段落在某个工作块里，且类别与该步的类型对得上（写作步 ↔ 写作类，仿真步 ↔ 科研工具类），归该块的步。
   - 标题里出现任务或步骤标题里的专名（课程号、项目名，至少 4 个字符），归那件任务。
   - 都不中：归「未归属的工作时间」，不猜。
3. **生成「拟计时」**：连续的工作分段（中间空闲或别的类别不超过 5 分钟就并起来）够 15 分钟，且那段时间没有开着的计时，就生成一条拟计时 `{start, end, workOrderId?, stepId?, minutes, basis}`，basis 写明凭什么（规则名 / 块重叠 / 标题专名）。只存在本机账本，14 天不确认就丢。
4. **本人确认的地方**：
   - 收工页每个块的推断旁加「按拟计时记 N 分」，一按就记成实测。
   - 块外的拟计时在收工页单列一组「这些时间在做什么？」：选任务 / 不算工作 / 以后这类都算 X（生成一条规则）。
   - 不弹通知，不打断；早报只说「昨天有 2 段没确认的工作时间」。
5. **确认后算实测**：确认的拟计时写成 `durationObserved: true` 的执行记录（来源 `inferred_confirmed`），进估时校准；未确认的不进。这样「实测超时再逐步优化」（第 1 条决定）在本人忘了计时的日子也有数据。
6. **改一处现有的错**：收工页的推断只算归属到该任务的屏幕分钟（第 2 步的规则），不再把块时间内所有工作类别分钟都算进去。

边界：这是现有「应用与窗口」同意范围内的新用途（推断用时），不是新的采集路径；但它会把屏幕记录变成可校准估时的实测，按 CLAUDE.md 的规矩需要本人明确点头，设置的说明要写清。

工作量：规则字段和拟计时生成 M（worker + db 一张表或事件）；收工页 S–M；校准接入 S。

## 2. 必须去与不必去：怎么区分

### 现在为什么分不清

- 邮件分拣只有一类「活动」，再按「是否给本人的邀请」和相关度 ≥50 决定问不问（`docs/claude/personal-agent.md`）。「必须」这个属性不存在：期中考试和公告板上的讲座走同一条路。
- 课程大纲来的考试只有日期没有时间（W-256：`ece548-20261124-midterm2`），排不出固定块，就成了要找空位的任务。
- W-256 的修复用「参加/出席…」开头判断「这是一件活动」，判断的是**形式**（去某处），不是**义务**（不去有后果）。

### 别人怎么做（调研）

- Gmail 和 Outlook 只从**结构化预订**（航班、酒店、票务，发件人经过验证）里自动建日程，从不从自由文本推断「必须出席」。<https://developers.google.com/gmail/markup/reference/event-reservation> <https://support.microsoft.com/en-us/outlook/automatically-add-events-from-your-email-to-your-calendar>
- Reclaim：没回复的邀请算空闲，回复「是/可能」后才算忙。<https://help.reclaim.ai/en/articles/3639943-how-rsvp-affects-synced-events>
- iCalendar 自带义务信号：`ATTENDEE;ROLE=REQ-PARTICIPANT/OPT-PARTICIPANT`、`RSVP`、`PARTSTAT`（RFC 5545）。群发信号：`List-Id`、`List-Unsubscribe`（RFC 2369）。
- 研究：承诺/请求检测换了领域明显退化（Azarbonyad 等，WSDM'19）；没找到专做「出席义务」的公开工作。LLM 的主要错误是相对日期锚点，另外会被邮件里的提示注入操纵（<https://arxiv.org/html/2508.12175v1>）。

### 批判性分析

- **关键词规则**：「attendance required」常出现在群发讲座里；考试通知常常没有这个词；否定和转发（「不必参加」、引用旧邮件）会把规则带错。规则适合做**上限**（群发最多到「可选」），不适合做下限。
- **让模型判「必须」**：一次判错的代价不对称。把讲座判成必须，只是多一块固定日程，本人删掉即可；把考试判成可选，后果是缺考。所以模型只抽字段和证据原文，档位由确定性规则合成；拿不准时问，不猜。
- **最可靠的信号在结构里，不在文字里**：本人选的课（课表、大纲）、发给本人一人的邀请、本人是组织者、已接受的邀请、带分值的考试。这些在 Crossline 里大多已经有（课表进固定日程，大纲进日期列表，邀请有 iMIP），缺的是把它们连起来。
- **「必须」不等于「固定时间」**：作业截止是必须的，但不是要去的地方；考试既必须又固定；讲座固定但可选。要分开两个属性：`obligation`（必须 / 可能 / 可选）和 `timing`（固定时段 / 截止日 / 无）。

### 设计

1. **两个属性**，邮件分拣、大纲导入、日历导入都填：
   - `timing`：`fixed`（有起止时间的事）/ `due`（截止前完成的事）/ `none`。
   - `obligation`：`required` / `likely` / `optional`。
2. **`required` 只来自结构信号**（任一）：
   - 来自本人已确认的课程的大纲或课表，类型是考试、小测、上课、答辩（大纲导入已知道课程）；
   - 发给本人一人的邀请（收件人只有本人，没有 `List-Id`），且本人已接受，或 ICS 里本人是 `ROLE=REQ-PARTICIPANT`；
   - 本人是组织者；
   - 本人在 Crossline 里说过「要去」（「要去吗」卡答「去」）。
3. **上限**：带 `List-Id`/`List-Unsubscribe`、来自公告板或群发列表的，最高 `optional`，不论正文怎么写。
4. **`likely`**：发给本人的邀请还没回复；导师或课程组发的、正文有「必须/要求出席/attendance required」但不满足第 2 条；与本人主线高度相关的活动（相关度 ≥ 70）。
5. **怎么处理**：
   - `required + fixed` → 直接成固定日程（不移动的硬约束），不问。缺时间（大纲只有日期）→ 问一句「几点到几点」，答了才成块；问之前在当天列成全天提醒，不当任务排。
   - `likely + fixed` → 「要去吗」卡，默认推荐「去」。
   - `optional + fixed` → 只进周复盘「邮件里的活动」，不问（现状）。
   - `due` → 任务（现状），`required` 的截止算已确认截止。
   - 为考试复习是另一件 `due` 任务，截止 = 考试开始。
6. **本人的回答沉淀成规则**：某发件人或某列表的活动本人连续两次答「不去」→ 以后这个来源最高 `optional`；某课程组发的「必须」本人答「去」→ 这个来源以后可直接 `required`。规则在设置里能看能删。
7. **问本人的情形**：判 `required` 的证据只有正文关键词；与已有 `required` 冲突；第一次出现的发件人或课程。
8. 邮件正文只当数据：分拣提示里不执行正文里的指令（现有规矩），日期以邮件发送时间为锚并校验星期几。

已有的过去和未来「参加…」工单不迁移（本人决定）。新规则只作用于以后进来的邮件和导入。
