# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Crossline (跨人生主线执行看板) — a local-first execution board that unifies tasks and evidence across multiple "identities" (研究/科研, 创业, 自媒体, 投资) sharing one task/evidence ledger, with health treated as a capacity constraint rather than a competing identity. Everything runs on one machine against a local SQLite ledger; there is currently no live external write path (see Safety boundaries below). UI copy and commit-facing text in this repo are in Chinese.

Current closed loop (per README): natural-language capture → system infers identity + duration bucket → a `WorkOrder` is generated → next-action recommendation → one calendar (day / week / month) with the plan's differences folded under it, approved as a batch → manual completion submission → evidence acceptance on the approvals page. Plan versions, recurring milestone relations, state transitions, and approval events are written to local SQLite WAL — not static frontend data.

## Commands

Run from the repo root (pnpm workspace, Node >=22, pnpm 12.6.0):

```powershell
pnpm install
pnpm dev              # starts @crossline/web (Next.js) on http://127.0.0.1:3210
pnpm worker           # starts @crossline/worker in watch mode
pnpm test             # vitest run, across packages/**/*.test.ts and apps/**/*.test.{ts,tsx}
pnpm test:watch       # vitest watch mode
pnpm test:e2e         # playwright test (visual regression + flow coverage, see e2e/)
pnpm typecheck        # tsc --noEmit in every workspace package (pnpm -r typecheck)
pnpm build            # next build for @crossline/web
pnpm verify           # typecheck + test + build + e2e, the one command before a commit
pnpm doctor:ledger    # ledger health: orphan rows, half-migrations, retired tables, WAL size
                      # (not `pnpm doctor` — that is pnpm's own built-in and shadows the script)
```

Single test file / single package:

```powershell
pnpm vitest run packages/planner/src/planner.test.ts
pnpm --filter @crossline/db typecheck
pnpm exec playwright test e2e/crossline.spec.ts
```

Worker one-shot run (used for smoke checks — ticks once and exits instead of looping):

```powershell
$env:CROSSLINE_RUN_ONCE='1'; pnpm worker:start
```

Export a full ledger snapshot to JSON:

```powershell
pnpm export -- C:\path\to\crossline.json
```

Rebuild a database from a snapshot (never writes to the live ledger; target must not already exist):

```powershell
pnpm restore -- C:\path\to\crossline.json C:\path\to\target.db
```

Codex app-server contract smoke test (pins against the commit recorded in `codex-baseline.json`):

```powershell
pnpm exec tsx scripts\codex-smoke.ts
```

Production start / scheduled-task install / backup / restore are PowerShell scripts under `scripts/` — see "Operational scripts" below. Do not run `install-startup.ps1` unless the user explicitly asks; it registers a Windows Scheduled Task.

## Architecture

**Workspace layout:** `pnpm-workspace.yaml` wires `apps/*` and `packages/*`. Packages export raw TypeScript directly (`"exports": "./src/index.ts"`, no build step) and are consumed by `apps/web` and `apps/worker` via `workspace:*`. `better-sqlite3` and `esbuild` need `onlyBuiltDependencies` approval in `pnpm-workspace.yaml`. `apps/assess` is the public quick test (P-L1 of docs/beta-launch.md; deploy in docs/assess-deploy.md): 32 questions — per dimension three statements for each pole, measured on its own (both poles strong, or both weak, is said on the result), and two situations with an A/B choice (`QUIZ_ITEMS`, `quizResult`: ¾ pole difference + ¼ situations, a tie decided by the situations; every result made before 2026-10-17 was deleted by assess migration 6) → appearance → email gate (the result is made and the figure starts drawing) → what they want to do (chips plus a ≤60-character line; written combination, else an optional OpenAI-compatible text model off unless `ASSESS_TEXT_*` is set, else rules — `@crossline/core/assess-wants`) → a server-rendered 3:4 type poster with those three lines (the type's own until they answer), loop, best/hardest partner and an estimated rank, plus a no-account pair card made when a friend answers through the forwarded invite link. It is its own small Next server (`output: "standalone"`, Docker, one Linux VPS behind Caddy) with its own SQLite file (`apps/assess/server/`: `store.ts`, `mail.ts` over SMTP, `security.ts` rate limits and honeypot, `purge.ts` 90-day retention), posters by satori + resvg with subset Noto fonts (`server/poster/`; `satori` must stay in `serverExternalPackages` — bundled, it cannot find its own `.wasm`), and figures drawn from the type's template by an image model only when `ASSESS_IMAGE_API_KEY` is set (`server/avatar/`; per address `AVATARS_PER_EMAIL`, counted under an HMAC of the address in `avatar_draws` so deleting does not give one back; templates in `apps/assess/templates/` are `<CODE>-female.png`/`<CODE>-male.png`, full length 2:3 in the MBTI-avatar low-poly style the owner chose, picked by `templateVariant` from the person's 女生/男生/中性 answer; the 32 were drawn through the owner's own Codex (`scripts/assess-templates.ts candidates --via=codex`, numbered `sheet`, `redo N`, `pick`) and chosen on 2026-10-15 — angular faceted low-poly, one Morandi tone per group from `TYPE_GROUPS`). Type content and relation rules are pure in `@crossline/core/assess-content`; the contract is `apps/assess/lib/contract.ts`; anything another person sees is keyed by the invite token, never the result token. It never touches the private app's ledger, models or accounts; keep it that way, since it is the one thing meant to be hosted publicly while the private app's `external` mode stays blocked.

**The day head clock (`apps/web/app/analog-clock.tsx`):** a real dial — ticks, numerals, hour/minute hands, a green second hand — placed from the same instant the rest of the page uses, read in `CROSSLINE_TIME_ZONE` (falling back to `America/Chicago`) rather than the browser's own zone so the dial and the 「周三 11:25」 label cannot disagree. Under `CROSSLINE_FIXED_NOW` it does not tick and drops the second hand, which is what keeps the visual-regression snapshot reproducible. It replaced a bare circle with one motionless dot that carried `aria-label="此刻 …"` and showed nothing.

**Data flow:** `apps/web/lib/crossline.ts` is the sole server-side entry point into persistence for the web app — it lazily creates a singleton `CrosslineStore` (SQLite, WAL mode) rooted at `CROSSLINE_DATA_DIR` (default `../../data` relative to `apps/web`), seeds starter milestones/relations/work-orders/a draft plan on first run, and exposes read/write helpers used by the Next.js route handlers under `apps/web/app/api/`. `CROSSLINE_FIXED_NOW` overrides the dashboard's notion of "now" (used by e2e tests for deterministic snapshots); `CROSSLINE_PRIMARY_CLOCK_ID` (default `research`) picks which identity gets deadline-tier priority as the master clock.

**Event-sourced ledger (`packages/db`):** `CrosslineStore` owns the SQLite schema: an append-only `events` table keyed by `(workspace_id, idempotency_key)` plus current-state tables led by `work_orders`, versioned milestones, relations, plans, executions, evidence, capacity and connector bindings. `StoredTask` is gone. If an old `tasks` table exists, open-time migration first copies a file DB to `.v1.bak` or `.pre-r2.bak`, migrates non-health rows to WorkOrders and health rows to capacity commitments, then drops the legacy table. New databases never create it. `exportSnapshot()` returns typed current models plus the generic workspace-scoped table dump.

**Migrations are versioned and transactional.** `#runMigrations` walks an ordered array gated on `PRAGMA user_version`, runs each migration **whole, inside one transaction**, and writes the new version in that same transaction; before the first pending one it force-copies the file to `<path>.v<current>.bak`. This replaced a `PRAGMA table_info` guard that checked column A and then added A *and* B — a crash between the two `exec`s left the guard satisfied and the database permanently half-migrated with no way to notice. That matters more than it looks: shipping to anyone else means running schema changes on **their** database, which is the real productization blocker, not the engine. Migration 4 dropped six tables that were never written (`outbox`, `identities`, `projects`, `milestone_versions`, `insight_proposals`, `skill_versions`) plus `energy_observations.expires_at`, and added nine indexes. `importSnapshot` still accepts a snapshot taken before it: the retired names are skipped when empty and refused (`RESTORE_RETIRED_TABLE_NOT_EMPTY` / `RESTORE_RETIRED_COLUMN_NOT_EMPTY`) when not, because a backup that cannot be restored is not a backup. Deliberately **no** `busy_timeout` and **no** `journal_size_limit`: both were added, then measured out as non-problems (better-sqlite3 already defaults the busy timeout to 5000ms, and the oversized WAL beside a small database is the autocheckpoint threshold doing its job, not a missing checkpoint).

`listEvents(workspaceId, { type?, entityId? })` takes its scope and its filter in SQL. It used to take **no arguments at all** — every one of ~40 call sites read the whole ledger and `JSON.parse`d each row to filter in JS, three of them without filtering by workspace at all. Foreign keys are deliberately still absent (adding one to SQLite means rebuilding the table, and the `(id, version)` primary key on `milestones` blocks the most important one); `pnpm doctor:ledger` scans for orphan rows, half-migrations, retired tables and WAL size instead, and exits non-zero on findings. `applyMilestoneGate`, `revokeAutoAcceptance`, `refuteMilestoneRelation` and `resolvePlanChange` are each wrapped in one `.immediate()` transaction — all four were check-then-act sequences, and the 「账本写了已验收、作业还在 evidence_review」 split state was that, not a logic bug. `packages/db/src/isolation.test.ts` is what proves the `workspace_id` discipline actually holds.

**Offline command replay:** `CommandEnvelope` is validated and posted to `apps/web/app/api/commands/route.ts`, which re-checks scope and currently permits only `task.capture`. `clientCommandId` is the ledger idempotency key. Completion is intentionally not an offline shortcut: Today links to Workbench, where execution and evidence follow the WorkOrder state machine.

**Natural-language capture:** `addCapturedTaskWithId` in `apps/web/lib/crossline.ts` writes one `captures` row and nothing else — no identity, no estimate, no `Task` and no `WorkOrder`. Classification only happens when an explicit Analyze runs the `crossline-automation-stripper` Skill through the worker-owned Codex app-server (`apps/worker/src/analysis.ts`, `packages/codex/src/analysis.ts`) and the result passes `validateAnalysisProposal` (`packages/core/src/analysis.ts`); only then does `transitionWorkOrder` atomically promote the capture to an `awaiting_plan_approval` WorkOrder. A failed, refused, timed-out or unauthenticated analysis leaves a typed blocker on the capture, and a blocked capture can be re-analysed (each attempt gets its own idempotency key via `captures.attempt`). There is no keyword-regex identity guess and no 25/30/60 minute default anywhere in this path.

**Work orders:** WorkOrder is the only executable model: `captured → analyzing → awaiting_plan_approval → approved → preparing → ready_for_human → active → evidence_review → accepted`, plus `blocked`/`archived`. All execution and evidence changes route through `transitionWorkOrder`; a milestone-bound WorkOrder cannot be accepted with zero evidence. `archiveWorkOrder` (the 丢弃 button, reason required) is the only thing that emits `archived`; discarded orders leave the board for a drawer, never the ledger. Starting an order that already has materials on disk skips `preparing` — going back there would strand it, because the worker skips orders that already have materials.

**Pressing 完成 is acceptance; requests for a fact are steps; the board is merged daily (the owner's decisions of 2026-10-15).** `completeWorkOrderExecution` runs `human.completed` and then `evidence.accepted` with `onCompletion: true` — the one acceptance the `EVIDENCE_REQUIRED` guard lets through without evidence, milestone-bound or not; the gate now judges only what the person did not do themselves (the assistant's `agent.delivered`). It takes an optional `outcome {level: smooth|barely|gaps, note}` (the 「完成情况」; routes read it with `readCompletionOutcome`) and returns `completion {mode, followUp?}`. `completionRule` (`packages/core/src/completion.ts`) takes the person's choice (`payload.completionMode`, the 「完成方式」 switch on the proposal card and the task, `POST /api/work-orders/[id]/completion-mode`) over the judgement of the model that wrote the task (`payload.completion` `{mode, reason, why, question, askAfterHours}`, a required field of the analysis, backplan and step-plan schemas — the step planner's only fills a task that has none) over the old title rules (left for tasks written before it): handing in, homework, sending, attending, filing and practice are `self_evident`, and a result somebody else judges later (an exam's score, a competition round), hard-to-read quality and exploration `needs_assessment`: those write `assessment.pending`, which `apps/web/lib/outcome-check.ts` turns into an `outcome_check` ask — kept out of 待决, Today and every count (`listed` in lib/asks.ts), answerable from the idle-time `outcome_check` nudge (never urgent, so never busy or at night) or by typing —; 「结果还没出来」 with a date asks again that day, and a score against the milestone's one threshold writes `milestone_gate.judged` with `source: "person_outcome"`. The acceptance standard is frozen at `plan.approved` (`payload.acceptanceStandard`; `approveWorkOrderProposal(…, {acceptanceStandard})` takes the person's edited lines) and the gate is told to add nothing to it. A request for a fact (`packages/core/src/info-request.ts`: purpose is one fact or confirmation someone else holds, product a message plus reply, ≤15 minutes of the person's time, it unblocks other work) is never a task: the backplanner folds it into the task that needs it (`foldInfoRequests`, `payload.infoRequests`), the step planner plans it as an assistant-drafted email (never sent) plus the person's send, normalization keeps the send with the person, and analysis refuses an automation part that sends. Duplicates are first prevented where tasks are written (`apps/worker/src/duplicate-guard.ts`): the capture analysis and the backplanner are shown the open tasks (`existingTasks`) and name the one an item only adds to (`extendsTaskId`), and every new task — dates-pair homework too — is compared with the open ones by `duplicateOf` (`planMerges`' own rules) and folded into the one it duplicates or adds to (`task.duplicate_prevented`; an addition becomes a replan request on the kept task; an analysed capture is merged undoably, a backplan item is never created and its dependants depend on the kept task). `dedupePass` (`apps/worker/src/dedupe.ts`, once a day per workspace) folds standalone requests into the task they serve and merges duplicates by `planMerges` (same line and project, normalized-title Dice ≥ 0.6 with intents agreeing; different numbers, due days a week apart, or milestones whose deadlines are over 21 days apart never), asks `crossline-validation-reviewer` (`TASK_MERGE_REVIEW_SCHEMA`, discretionary spend) about pairs the rules leave open, keeps the task with the most progress, archives the rest `bySystem` with 「与「X」合并」 (shown in the 已归档 drawer as 「已合并」 with 撤销合并, `undoMerge`), records each merge as an undoable `task.unmerge` op and says it once with `sayToPerson`.

**Approval policy is centralized:** `requiredApproval(action)` in `packages/core` is the single source of truth for whether an action is `"automatic" | "batch" | "per_item" | "never"`. Actions like `broker_order` and `silent_source_calendar_write` are permanently `"never"` — connectors and UI should defer to this function rather than re-deriving policy.

**Every mutating route calls `isCrossSiteWrite` (`apps/web/lib/same-origin.ts`), first thing.** It refuses a POST/PUT/PATCH/DELETE whose `Origin` header names a different host than the one the browser actually addressed, and passes anything with no `Origin` at all — that is a local tool or the worker, not a browser form post, and this app is expected to support both. A red-team pass found seven routes that never called it (`commands`, `energy-observations`, `milestones`, `milestones/propose`, `codex/account`, `plans/[id]/approve`, `plans/changes/[id]`): a forged `Origin: https://evil.example` wrote real captures, energy observations and milestones, and against `codex/account` it started a real OAuth login. `apps/web/app/api/csrf-protection.test.ts` is the guard against this recurring — it is a **discovery** test, not a per-route one: `import.meta.glob` reads every `route.ts` under `app/api`, and every exported mutating method gets one forged-Origin request asserting 403. A route added without the check fails this test on day one instead of shipping unguarded, which is the property a per-route test cannot give you.

**Revoking auto-acceptance is keyed on the attempt, the same way a gate re-judgement is (see Gate 4 below).** `revokeAutoAcceptedWorkOrder` (`apps/web/lib/crossline.ts`) counts how many times this work order has already been revoked and builds `auto-acceptance-revoked:${workOrderId}:${attempt}` from that, rather than trusting the caller to number it. A work order that gets auto-accepted, revoked, re-judged and auto-accepted again is a normal cycle, and a fixed key reused the first revoke's on the second call: `appendEvent` silently no-ops on a repeated idempotency key, and the caller returned `{ ok: true }` without checking whether anything had actually changed — the person saw the page reload and believed the revoke worked, while the ledger never left `accepted`. `revokeAutoAcceptance` (`packages/db/src/index.ts`) now throws `REVOCATION_ALREADY_APPLIED` if `transitionWorkOrder` reports `changed: false`, mirroring `applyMilestoneGate`'s `GATE_ALREADY_APPLIED` — the store-level check is what turns a stale-key collision into an honest failure; the caller's attempt counter is what makes a genuine second revoke keep working instead of failing forever.

**The plan is one calendar** *(since 2026-10-10 only on Today; the plan page is long-range statistics — see 「Flywheel and views」)*. `apps/web/app/plan/page.tsx` + `plan-view.tsx` render day, week and month views (`apps/web/app/timeline/`) over one list of items: real calendar events, file-imported class meetings, and the blocks the scheduler placed for work orders. `timeline/model.ts` is pure (axis geometry, overlap packing into columns, the Monday-first month grid, conflict detection, the zone's current minute) and is where the tests are; `views.tsx` draws it — **day** is a horizontal 24-hour axis with one row per thing and a now line, **week** is seven columns sharing one vertical hour axis with a deadline strip on top, **month** is a block calendar of tags (colour is the line, outline says scheduled / calendar / file) with `+N` folding. `apps/web/lib/timeline.ts` builds the data: plan blocks, each live milestone's deadline from `milestone_anchors`, every confirmed `date_*` profile fact, and the person's unavailable hours as the complement of the availability windows. The same `CalendarPanel` is the day timeline on Today. **The plan takes effect by default** (docs/loop-and-scout.md §1, 2026-10-12): there are no plan versions to approve and no differences to settle. Migration 14 turned every `plan_changes` row into a `plan.change_archived` event and every older plan version into `plan.version_archived`, dropped the table and left each workspace one `plan_versions` row with status `current`; `importSnapshot` converts an older backup's `plan_changes` the same way instead of refusing it. `approvePlanVersion`, `resolvePlanChange`, the plan routes, the differences fold, the `calendar_stale` ask and the `approve_plan_changes` policy are gone. FullCalendar and the old B/C/A lenses are gone.

**One freeze model, locks per block** (`packages/core/src/schedule-frozen.ts`, `schedule.frozen`; 2026-10-12). A frozen block keeps its time while the rest is re-planned, for one of four reasons: `pinned` (the person started it — `lockOnStart` in `app/timeline/block-start.ts`, for scheduled and pencilled-in blocks alike), `locked` (the 「锁定在此时间」 button on the day panel, or the person dragging the block on their calendar app), `keep` (the local re-plan after an inserted event, a week) and `commit` (reserved for the commit window, §2). It replaced `schedule.pins` and `schedule.keep`, which `readFrozen` takes over once and deletes. The planner freezes the **segment**, not the task (`withoutFrozenMinutes` in `packages/planner/src/optimizer.ts`): a task keeps the rest of its minutes to place, work that must sit in one slot is never cut. It used to drop every task with any frozen block, so locking one segment of a long task left the rest unplanned — and the task's own validation then failed, sending the whole solve to the greedy pass. A frozen block keeps its own id (`scheduled:<order>[:<step>][:n]`); new segments skip ids a frozen block holds. The solver's answer is checked (`invalidBlocks`) on what **it** placed only: counting a frozen block as placed called a half-frozen step 「0 of 15 minutes」 and threw away every optimal plan on the real account for a day (2026-10-13; the week held 61 `keep` blocks); a rejected answer now logs `solver.answer_rejected` with the broken rule. Work that cannot start before the planned days end (`notBefore` past the last slot, or waiting on such work) is not a blocker — the window reaches it later. A `keep`/`commit` block a hard constraint now lands on moves; a `pinned`/`locked` one stays and is asked about (`locked_conflict`: next free time / tomorrow / keep the overlap → `overlapOk`). Re-planning everything (availability, packing numbers, weights, shares) clears `keep` only (`clearKept`). `POST /api/plan/pin` locks (`reason`, `overlapOk`), `DELETE` unlocks; both are undoable.

**What the person did on their calendar is judged once, for any provider** (`packages/connectors/src/calendar-edits.ts` `classifyCalendarEdits`). The publish ledger (`calendar.published`) now keeps title, start and end apart instead of one hash: the time moved → the worker locks that block at the new time (`apps/worker/src/calendar-publish.ts` writes `schedule.frozen`); only the title changed → not a lock, the time keeps following the plan under the person's title (`personTitle`); a future event deleted → `removedByPerson`, never created again; a finished task's leftover future event is deleted even if the person changed it (`forceRemove`). A ledger entry with only a `hash` is from before: the old rule holds until the event is found unchanged, when it is upgraded.

**The change summary** (`noteScheduleChanges` / `readChangeSummary` in `apps/web/lib/crossline.ts`, `schedule.changeSummary`, `app/schedule-summary.tsx`). When a `plan.reality_changed` has come in since the schedule was last read, each work block whose old time a newly added event covers becomes a line above Today's timeline — 「「作业 3」因 11:30 Sync up 后移 30 分钟」 — for a day. The re-plan is derived and has nothing to undo, so the button is 「钉回原位」: lock the block at its old time with the overlap accepted. Not written inside an impact preview.

**The completion check** (docs/loop-and-scout.md §3, 2026-10-13; `apps/web/lib/confirm.ts`, `app/confirm/[id]`, `/api/confirm/[id]`). Every work block of the day — deadline or not — is asked about once within thirty minutes of its end (`block_confirm` in `packages/core/src/nudges.ts`, which replaced `block_missed`); not one whose timer the person already stopped, one whose timer still runs, or at night (those go into the morning brief as 「昨晚 N 块待确认」, `unconfirmedLastNight` in `apps/worker/src/notify.ts`). The schedule keeps no past, so the two-minute nudge pass remembers the blocks it sees (`nudge.blocks:<day>`, `rememberBlocks`) and only one seen under way counts — the commit window holds a block at its time from fifteen minutes before, so every block that happened is seen, and one moved before it began is never asked about. The question goes to the desktop and the phone whatever page is open, and opens `/confirm/<message>`; nothing is written by following the link. The page: 按预估完成 / 超出预估 / 少于预估 / 未执行, then 15 / 30 / 60 minutes or a number, the screen record's estimate as one tap with the detail consent (`activityMinutes`), and evidence for a milestone-bound last step. A step that is not the last writes a closed session over the block's own times (`recordConfirmedSession`: ends an open one, else inserts one; `outcome: "confirmed"`, `reportedMinutes`) and marks the step done; the last step goes through `completeWorkOrderExecution` with the minutes, so `human.completed` writes the one duration observation (`one_tap`, or `activity`), and a task with no `family` is tagged `preparation` first so it is not left out. An active order with no open session opens one on start (`openSession`). The next day's `missed_block` skips anything answered (`block.confirmed`). Settings shows the estimate bias week by week (`weeklyBias`). `scripts/confirm-check.ts` runs the whole path on a copy of the real ledger with the person's ECE work (2026-10-13: 11 checks, the desktop notification shown once).

**Calendar reality (`apps/worker/src/graph-sync.ts`):** `GraphReadSource` is a read-only class with no write methods at all, kept separate from `MicrosoftGraphConnector` on purpose — that connector's `Crossline` name lock is what keeps writes off a real calendar, and reading the user's own calendar needs no lock because this class structurally cannot write. **It reads several calendars across several accounts.** `apps/worker/src/calendar-sources.ts` owns the choice: a `calendar.sources` settings row lists `{accountId, calendarId, label}`, and `calendar.sources.seeded` records which accounts have already been offered their default calendar. Both live in the ledger, next to the availability pattern and for the same reason — a backup that does not carry them restores a plan whose reality lane cannot be rebuilt. The label is stored too, so building a tick's sources costs **no Graph calls**; the catalogue is fetched only when someone opens the Connections page (`GET/POST /v1/calendar/sources` → `/api/calendar/sources` → `connectors/calendar-sources.tsx`). A newly signed-in account is seeded with its **default calendar only** — ticking everything would drag 「中国 节假日」 and 「生日」 onto the plan, and ticking nothing would make signing in appear to do nothing. The seeded marker is separate from the selection because deriving "is this account new?" from the selection meant unticking an account's last calendar silently ticked its default back on. `scripts/graph-add-account.ts` signs in an extra mailbox; `graph-readonly-check.ts` cannot, because it logs in only when there is no token at all. A **personal** Microsoft account additionally needs the Entra registration's supported account types to include personal accounts plus `CROSSLINE_MS_TENANT_ID=common` — a single-tenant registration answers AADSTS50059 at `/common` and AADSTS700016 at `/consumers`, and that is a portal setting, not a bug.

**Per-source authority is the rule that keeps this safe.** Each `(account, calendar)` pair is a `CalendarSource` with its own delta cursor (`external_bindings.external_id` is the source key) and stamps `sourceKey` on every block it produces. A source may only add, change or drop blocks carrying **its own** key. So a source that fails this tick keeps everything it contributed (an account being signed out must not read as its events having been deleted, and the outcome reports it in `failed` instead), while a source the person **unticked** loses its blocks, because nothing will ever update them again. Blocks imported before any of this carry no `sourceKey`, and may be dropped only when **every** selected source read its whole calendar that tick — `some(authoritative)` was wrong and did real damage: ticking a second calendar made that new source authoritative while the original stayed incremental, every legacy block was deleted as though the calendar had been emptied, and an approved plan forked into a draft full of 「日历中已不存在」 conflicts for events nobody had touched. Delta cursors live in `external_bindings` via `saveSyncCursor`/`readSyncCursor`. A meeting its organiser cancelled (「Canceled:」, `isCancelledEvent`) is dropped at sync; one carried from before that leaves the plan quietly and its pending change is excluded, since the delta never mentions it again and a pending conflict blocks approval. A 410 `resyncRequired` restarts from the base URL and the result is treated as the complete current set — items deleted during the gap never come back as tombstones, so anything locally present and missing from the resync is dropped. The current plan row is updated in place on every sync, and each sync that changed something appends `plan.reality_changed` (keyed on a hash of the changes, so two syncs a day with the same count no longer collide); the change summary on Today reads it.

**Milestone relations** *(generation replaced on 2026-10-10 by the artifact-first plan — see 「Flywheel and views」; drawing and decisions below still hold)*: `apps/web/app/milestones/page.tsx` renders the lines on one **date axis** (`milestone-timeline.tsx`, laid out by the pure `timeline-model.ts`; data from `apps/web/lib/milestone-board.ts` `loadMilestoneBoard`): a row per line, a ◆ at each milestone's deadline (dashed while a draft, undated ones in a 「未定日期」 zone after the last date), a course's score line as a ★ at the end of its chain, and the **ticks** before a milestone — steps with a `tickOutcome`, on their scheduled day, filled when done, hollow and dashed with a ghost at the old day when their day passed (「已顺延」, never red). **Planner (`packages/planner`):** Greedy `planSchedule` assigns WorkOrder-shaped inputs to availability slots while respecting deadline and continuity, returning typed capacity blockers. **Energy is how much an hour yields, not whether it may be used** (decided 2026-10-12, `packages/planner/src/optimizer.ts`): it was a hard filter, so work needing 「high」 had about three hours a day and a homework due the next day got nothing while those hours went to undated work. A slot one level short of the work's energy yields 0.8 of an hour (≈1.25× the time), two levels short 0.65 (≈1.5×) — assumptions, since the time-of-day literature shows real but moderate, task-dependent effects with no reliable percentage, to be calibrated against timed work; work is cut into even sessions of at most 90 minutes in a matching slot, 60 one level short and 45 two short, with ten-minute rests, several to a long slot; the solver counts the rests exactly (an integer `k` per slot where the work may run past one session). One level short is open to all work, two only to work with a deadline; each minute short costs a little in the objective, so a matching hour is always taken first but work is never left unplaced to avoid a weaker one. The greedy fallback (`fallbackSchedule`, tested directly) follows the same rules, matching slots first. Blocks placed short carry `efficiency` and the tag 「精力偏低」. **On the real account the solver runs out of its two seconds** (105 tasks, ~9,500 rows), so what the person sees is usually the greedy pass — three things follow (2026-10-12): a time-limited answer is compared with the greedy pass on the solver's own objective (`taskValue`/`worth`) and the better is kept (one had given an afternoon to line-share filler and left a homework due that night unplaced); the greedy pass keeps the gap only from the block just before in time (it used to take the last block placed anywhere, so one task on Friday emptied the whole week before it); and the relaxed run relaxes only the work with a deadline and what it waits on, then places everything else around it on the normal rules (relaxing the whole plan packed a day from 09:00 to 22:50 with no break), re-running the solver only if it had finished the first model in time. Its availability comes from `packages/core/src/availability.ts`: a weekly pattern (`AvailabilityWindow[]`) stored in the ledger under the `schedule.availability` setting — not an environment variable, because a backup that does not carry it restores a plan that cannot be rebuilt — which `availableSlots` turns into concrete slots by subtracting the calendar's own blocks and dropping anything under 15 minutes. `scheduledBlocks` in `apps/web/lib/crossline.ts` is its **first and only production caller**; until then the plan's AI lane was seeded example blocks computed from nothing, and those are gone. The schedule is **derived on read** from the work orders, so it cannot drift from them — **in two engines, with the optimal one cached by input** (docs/loop-and-scout.md §2, 2026-10-13): every read places with the greedy pass at once (`planSchedule(input, { solver: "none" })`, ~0.2 s on the real account) and asks for the optimal plan, which `apps/web/lib/optimal-schedule.ts` solves on a thread in the web process (`apps/web/solver-thread.mjs` + `lib/solver-pool.ts`: HiGHS outside the Next bundle, up to 20 s) and stores in `schedule.optimal` under `scheduleInputHash(input, epoch)` — the planner input without `now`, with the current slot's start and the self-reported energy as the epoch (`scheduleHashOf`). The next read of the same input uses it (blocks already over dropped); one solve per workspace at a time, only the latest input next. A preview (`withPreview`) neither reads nor asks for it, and `impact.ts` computes both sides inside a preview so the two engines' difference is never reported as a change's effect. The automatic publish waits up to a minute for the optimal plan (`blocksToPublish(…, { waitForOptimal })` → `pending`), then writes the greedy one; once solved it is published at once (`onOptimalWritten` → `publishNow`); the 发布 button never waits. **The commit window**: `commitSoon`, run by the two-minute nudge pass, freezes a block under way or starting within 15 minutes until it ends (`reason: "commit"`), so the optimal plan landing never moves what is about to start. The thread was verified in a production build (2026-10-13: `solver.optimal` in 1.1 s on the e2e board). `CROSSLINE_BACKGROUND_SOLVE=on|off` overrides the default (off under vitest and e2e); tests that need what only the solver does (line-share library work, the current slot ordered by the reported energy) read `settledPlan` (`lib/test-support.ts`). Measured on a copy of the real ledger (`scripts/schedule-bench.ts`): first read 277 ms, reads while solving 167 ms median, optimal cached 11 s later with 1806 line-share minutes, cache key changed at the slot boundary; the pattern is painted on a week × half-hour grid on the plan page (`app/plan/plan-controls.tsx`, pure conversion in `week-grid.ts`), and saving it re-runs the scheduler on the next load. Unknown energy stays unset and cannot become a low-energy recommendation. **The plan page's controls** (decided 2026-10-07; data from `apps/web/lib/plan-board.ts`): the availability grid, four packing numbers (`ScheduleParams` in `packages/planner`: gap between blocks, the share of a day that may be filled, a focus cap that moves the rest of a long task to another slot, and deadline-buffer days that aim to finish early but are dropped in the relaxed run so a buffer never makes a deadline impossible; `buffered`/`asap` are presets of them, stored as `schedule.preferences.params`), and a 0–100 importance slider per approved milestone. The weight orders work **inside** a deadline tier (`.9 × weight/100` of one tier step in the objective, and in `compareTasks`/the forecast), and a weight of 60 or more makes a milestone important for the tier itself. With no slider moved, `effectiveWeight` uses the person's older important/ordinary choice, else `importancePresets` (`packages/core/src/importance.ts`: the line's share of stated weekly hours, cross-line relations, grading and deadline distance, and the person's past slider offsets, each shown as points on hover; a slider save records the preset it moved away from as `presetWeight`). Every one of these is previewed first: `lib/impact.ts` change kinds `availability | params | weight` run the scheduler and forecast inside `withPreview` and report the next seven days' free and scheduled hours, moved blocks, unplaced tasks, milestones whose cautious finish moves, then apply. 「排程依据」 is `planRanking` — the planner's own tier, weight, deadline, first block and reason for anything unplaced — and the optional written explanation is given that same ranking (`/api/plan/explain` sends it; the runner narrates it rather than rebuilding an order). `recommendNextActions` uses lexicographic ordering; there is no contribution score, switching-cost score or HiGHS shadow solver.

**Energy model v2, capacity and learned efficiency (2026-10-14; design and competitor notes in `docs/energy-and-ecosystem.md`).**
- **Model and its constants.** The model in `packages/core/src/energy-model.ts` now follows Åkerstedt, Folkard & Portin 2004 as published. The constants were read off the paper itself; an earlier recollection of W as `−5.72·e^(−1.51t)` was wrong.
  - S is carried across the last 14 days of sleep (`homeostat`). Below 12.5 it recovers at the rate it has at 12.5, which is what makes short nights add up.

**Skill wire contracts** all live in `packages/core`: `analysis.ts`, `flywheel-schema.ts` (findings + candidate relations), `materials-schema.ts`, `milestone-gate-schema.ts` (gate result, criteria proposal, milestone proposal), and `reality.ts` (the pure calendar-vs-plan diff). Keeping them there is what stops a Skill's shape and its trust checks drifting apart.

A contract item is `{ kind, description, why, required }` in both `materialContract` and `evidenceContract`. `description` is the checklist line (≤300, no `{}[]`, refused if it lands exactly on the limit — that means it was cut off); `why` is the reason and carries no punctuation rule, because a reason is a sentence and sentences quote things. `why` exists because every split in the schema has a `rationale` and a contract item had none: the model had something real to say and one field to say it in, so it packed the reason into the name and filled whatever cap was set — 4000, then 300, then 200, then 80, each treated as a target. With `why` in place the names came back at 6–8 characters. The limit then went **back up** to 300, against instinct: constrained decoding concentrates repetition at structured-field terminals, so a tighter schema makes terminal degeneration *more* likely rather than less, and the tightening had been pushing the wrong way. The primary defence is now detect-and-retry in `runCodexSkill` — when `validateOutput` rejects an answer the rejection message is sent back as a **second turn on the same thread** (which already carries the context, so it is cheaper than a fresh run), at most twice, and the count lands in `audit.repairs` and `StoredCapture.audit`. A repair rate that stays above zero means the schema or the prompt needs work, not more retries. Two normalizations run before validation, both of which only ever remove text that repeats text already present: a tail of one character repeated eight or more times is trimmed, and a sentence whose whole second half already appeared earlier is dropped — both are now last-resort cleanup behind the retry, not the primary defence they used to be. `required` on `materialContract` is what lets the preparer tell "I cannot start without this" from "this would help" — without it one nice-to-have the person had not supplied blocked the entire preparation and they got nothing. `validateAnalysisProposal` names the offending quote or contract line in its blocker, because a bare code gave the person nothing to retry against.

**One structured-output loop, not two** (`packages/codex/src/skill-runner.ts`). **Every quantity is worked backwards from an outcome and carries a margin** (`packages/core/src/milestone-plan.ts`, `analysis.ts`, `packages/planner/src/forecast.ts`). A milestone's `plan` has `outcome` (the result the person wants) and `derivation` (the back-calculation in numbers); a `threshold` measure has `bareLine` (the value that only just reaches the outcome) next to `value` (the line actually set). `thresholdProblem` refuses a `value` that is not on the safe side of `bareLine` by at least `MARGIN_RATIO` (3%; a score may sit at 100) — `MILESTONE_NO_MARGIN` — and `validateMilestonePlans` refuses a threshold with no derivation containing a number (`MILESTONE_DERIVATION_MISSING`) or a milestone with no stated outcome (`MILESTONE_OUTCOME_UNSTATED`). The derivation is appended to the stored rationale and `bareLine` is shown beside the line on the milestone page; `bareLine` is optional in the stored type because hand-written and older criteria have none. Estimates: the analysis works back from the `evidenceContract` to its steps, `p50Minutes` is their unpadded sum, and the margin lives only in `p85Minutes` (`ANALYSIS_ESTIMATE_MARGIN_INVALID` unless it is 1.2–3x p50). The scheduler already reserves p85 for low-confidence work; `forecastGoals` now reports `slackDays` and flags a goal whose p85 finish is less than `DEADLINE_MARGIN_DAYS` (2) before its deadline.

**Targets are proposed by the model from the person's long-term goals, and changed by them in one click** (`milestone-plan.ts`, `milestone-proposer.ts`, `apps/web/lib/targets.ts`, `apps/web/app/milestones/milestone-drawer.tsx` `CourseDrawer`). Two earlier versions got this wrong in opposite directions: the architect assumed a course's total grade and derived every score line from a number nobody had chosen, and the next version made the person answer a question list before anything existed to react to. Now the architect, which has the person's goals, priorities and grade weights, proposes the target itself: `targetProposals: [{projectId, value, why}]` in its answer, stored by `persistTargetProposals` as an **inferred** `target_grade` fact with the reason in its value (`值（暂定：理由）`) and never over an existing one. `validateMilestonePlans` refuses a graded milestone in a course (`isCourse`: a `grading` fact, or quizzes/homework dated in its own files — a real interview recorded a syllabus's dates and never its percentages) when no target is on record and none is proposed in the same answer (`MILESTONE_TARGET_UNPROPOSED`), and when its `sourceFactIds` do not cite `<line>/<project>/target_grade` (`MILESTONE_TARGET_NOT_CITED`), so every score line traces to the one number the person can edit. On the Milestones timeline a course's target is the ★ at the end of its chain; its drawer shows the target with its reason, 批准 (confirms it), grade options or free text, and 「修改并重算草稿」 — `POST /api/targets` confirms the new value, then `POST /api/milestones/propose` with `only:[line]` redoes that line's untouched drafts (approved milestones are never touched; their score lines are edited in place in each milestone's drawer, with `bareLine` beside the input and a warning when an edit leaves under 3% margin). Proposed targets still waiting count in 待确认 (`pending.targets`). What is still asked as a question, because it is a fact the model cannot propose (`profileGaps`): a line that rests only on the interviewer's guesses (`LINE_UNCONFIRMED`, blocks 「ready」, `withGapQuestions` turns a premature 「ready」 back into 「ask」 and adds the question with options) and a graded part a file marks TBD (`DATE_UNDATED`, asked once, blocks nothing). Answers to those code-built questions are read straight out of the `【question】选择：label` message (`answeredGapFacts`) and written as confirmed facts before the model runs.

**TBD is not a date, and not nothing** (`date-schema.ts` `undated`, `latestFileDates` in `packages/db`). The ECE 555 schedule's last row is `TBD · Final Project Report · Due`; the date extractor rightly refused to invent a day, and the 25% project then had no milestone at all because the chain was built from dated items. **Skill deadlines are one hour per turn, not per run — finishing the task comes before speed, and the limit is there only to catch a run that has truly hung.** `openScope` (`packages/codex/src/skill-runner.ts`) gives every RPC and every turn its own `timeoutMs` window (`60 * 60_000` in every runner); it used to be one deadline from first call to last, so a long first answer left the repair that the validator then asked for a few seconds, and a run that was nearly right timed out with nothing to show (the interview did this to a real run). What bounds a run is the repair count (two). Milestone design is also asked one line at a time (see the milestone paragraph): in one answer it wrote ~11k tokens at ~4.5 minutes a turn. The web routes that wait on a run allow three hours (six for milestone design, which is several runs); the worker finishes and writes its outcome even if the page gave up. **Slow is allowed, silent is not.** A stalled turn is interrupted and resent; the interrupted turn's own late `turn/completed` is ignored (its id goes into `abandoned`), because it used to end the resent turn as 「已取消」 — two real assistant runs were lost that way after 96 minutes and 2.5 hours. The limit above is a ceiling, not the thing that catches a hang: `runTurnsUntilValid` also watches for *any* event from the runtime about the thread (`lastEventAt`), and a turn with none for 20 minutes (`CROSSLINE_SKILL_IDLE_MINUTES`) is interrupted and the same prompt sent again, twice at most (`audit.stalls`; then `SKILL_STALLED`). It exists because a real interview run sat for over an hour with the runtime logging nothing at all, and a startup-line milestone run took 43 minutes for 7k tokens — a stalled turn waits out the whole hour otherwise, and a long productive turn is never cut because it keeps producing events. **Measure, then tune:** Settings → 模型用量 shows each Skill's average **and longest** run, `scripts/user-journey-check.ts` prints the wall-clock of every step, so a limit is set from observed times and not guessed. ## Identity, sessions, and private deployment (stages two–six)

This was, until recently, a single-user app with no login at all — `OWNER_ID = "local-owner"` / `WORKSPACE_ID = "personal-crossline"` were the only "identity" anywhere in the repo. Stages two through six replaced that with real accounts, real per-workspace isolation, and real cross-device access over a private network, without ever adopting multi-tenant collaboration UI — it is still built for exactly one real person, just no longer a hardcoded one. `docs/user-guide.md` is the user-facing walkthrough; this section is the "what broke and why it's built this way" record the rest of this file already keeps for everything else.

**Two databases, two schemas, one story.** `auth.db` is Better Auth's own SQLite file (`user`/`session`/`account`/`verification`), migrated by calling `better-auth/db/migration`'s `getMigrations` directly (`packages/auth`'s `migrateCrosslineAuth`) rather than the separately-published `@better-auth/cli`, which trails this repo's pinned `better-auth` version and could generate a different schema than the one actually running. `crossline.db` gained `principals`/`workspaces`/`workspace_members`/`tailscale_bindings`/`device_leases`/`audit_events` in migration 5; `principals.better_auth_user_id` is a plain string reference to the other database, not a SQL foreign key, matching this repo's existing "deliberately absent foreign keys" stance. `session: { cookieCache: { enabled: false } }` is load-bearing, not a default left alone: every request re-checks `workspace_members` from the database, so a revoked session or a demoted role takes effect on the very next request, not after some cache window — `scripts/gate-identity-check.ts` signs a real session out and re-checks it to prove this rather than asserting it from the config alone.

**Mail that does not go out is said, not hidden (2026-10-10).** Better Auth sends verification and OTP mail through `runInBackgroundOrAwait`, which catches every error and only logs it, so a provider in test mode refusing every address but its owner's (a 550) still answered sign-up with success and the page said 「已发送验证邮件」. `deliver` in `packages/auth` notes the failed address and throws a typed `VERIFICATION_EMAIL_FAILED` (the resend route awaits the sender directly), and an `after` hook on the sending paths turns a noted failure into that error in the same request. The login page offers 「重发验证邮件」 after `EMAIL_NOT_VERIFIED`, and a six-digit **email code** (`emailOTP` plugin, only where mail can be sent) signs in — and on first use signs up — without a password; the web calls its two endpoints through `authClient.$fetch` because the plugin-typed client's type is not portable. Without mail (`isEmailAuthConfigured`), sign-up, reset and the code are not offered at all.

**Sign in with ChatGPT, for a copy run on the person's own machine** (`packages/auth/src/chatgpt.ts`, opt-in `CROSSLINE_CHATGPT_SIGNIN=1`). OpenAI's open-source flow: the first sign-in registers the install (`client_id=dynamic_agent_client` plus a persisted `ext_agent_host_id`; the issued `oaiapp_…` id comes back on the callback and is kept in `data/chatgpt-signin.json`, never in the ledger), PKCE S256 with state and nonce in a signed cookie, identity scopes only (`openid profile email`; models keep running through the person's own Codex login). OpenAI accepts only `http://127.0.0.1:<port>/auth/callback`, so `app/auth/callback/route.ts` forwards to the plugin's endpoint and the button shows only when the page is opened at 127.0.0.1 — a hosted site would need a partner client id. The ID token is verified with node's crypto against OpenAI's JWKS (issuer, audience = issued id, expiry, nonce) and `sub` is the account; Better Auth's own `handleOAuthUserInfo` links or creates the user. `ext_agent_host_id` goes on every authorize request and `agent_name_hint` (registration only) is `crossline`, the app-server's `clientInfo.name`, as OpenAI's sign-in page asks. **Same email, same account** (2026-10-13, replacing explicit-only linking, which refused the owner's own Google/ChatGPT sign-in with no way to link): `accountLinking: { enabled: true }` with no trusted providers, so a sign-in joins an existing account only when the provider verified the address (Google's `email_verified`; ChatGPT's `email_verified === true`) and the local account's email is verified too (`requireLocalEmailVerified`). Setup: `docs/setup-google-oauth.md`, `docs/setup-siwc.md`.

**`requireAccessContext` (`packages/auth/src/index.ts`) is the one place a request becomes an `AccessContext`.** It calls Better Auth's `getSession`, then — on a session's first-ever appearance — creates `principals`/`workspaces`/`workspace_members` for it in one transaction (a brand-new, empty workspace; logging in never adopts the old `personal-crossline` ledger data still sitting on disk), then separately checks that principal actually belongs to the workspace it is asking for. That second check did not exist anywhere before stage two — `packages/db/src/isolation.test.ts`'s own doc comment named the gap explicitly ("nothing verifies the caller is allowed to use this workspaceId"), and `scripts/gate-identity-check.ts` now proves two independently-signed-up accounts land in different workspaces and cannot see each other's work orders. `listPlanChanges` was the one `list*` method in `packages/db` that took no `workspaceId` at all — a real cross-tenant read, found and fixed while wiring stage three through, not a hypothetical.

**Eliminating the hardcoded identity was pure surface area, not depth.** Every API route gained an `access = await resolveAccessContext(request)` early-return, every exported function in `apps/web/lib/crossline.ts` gained a leading `ctx: AccessContext` parameter, every worker background job switched from a hardcoded owner to looping `listWorkspaces()`. `apps/web/lib/no-hardcoded-identity.test.ts` is the guard against regression — `import.meta.glob` over `apps/web/**` and `apps/worker/**` asserting the literal strings `"local-owner"`/`"personal-crossline"` appear zero times outside test files, the same "discovery test, not per-callsite" pattern `csrf-protection.test.ts` already uses.

**Each account runs on its own Codex (2026-10-10; `packages/codex/src/runtime-registry.ts`, design in `docs/model-providers.md`).** There used to be one app-server and one CODEX_HOME for the machine, with memories on, so a second account read the owner's Codex memories and spent the owner's ChatGPT quota. Now the machine owner's workspace (`runtimeOwner` in `apps/worker/src/owner.ts`: marked once in `RUNTIME_OWNER_SETTING`; else `CROSSLINE_RUNTIME_LEGACY_WORKSPACE`; else the first workspace created) keeps the existing runtime with everything — memories, web search, images and the shell assistant, which works for no one else (`AGENT_OWNER_ONLY`). Every other workspace gets its **own** home (`%LOCALAPPDATA%\Crossline\runtimes\<ws>\codex-home`, its own `auth.json`, which also sidesteps openai/codex#48465) and its own process, started on use, stopped after 30 minutes without an event (longer than the 20-minute stall limit, so a working turn is never cut), at most three at once. A successful login (and a provider's finished conformance run) calls `afterConnected` in the worker (`onConnected` on the registry, `onConformance` on the provider service): the quota is read again, which clears a 「后台自动工作已暂停」 written before the login, and capture analysis, backplanning and the first drafts run at once instead of at the next tick (2026-10-18). An account that has not connected one gets `RUNTIME_UNCONNECTED` from every model route — it **never** falls back to the owner's runtime. The supervisor picks the runtime from the verified capability's workspace (`modelClient`), and the worker's runners take `clientFor(workspaceId)`; lanes and the config lock are per runtime, the spend mode is cached per workspace. A guest connects in 设置 → 模型连接 with ChatGPT in the browser (only when the page is open on this machine — Codex calls back to its own localhost), a **device code** (from anywhere, a phone included), or an **API key**, which passes straight through to that runtime and is never kept, logged or echoed (`apps/web/app/api/codex/account/login.test.ts`); signing out deletes the guest's home. An API-key login has no quota windows, so its reading is this month's spend (`model_usage` × `CROSSLINE_API_PRICE_PER_MTOK`, deliberately high by default) against `model.budget.monthly` (default $10). Not verifiable without the Codex binary: real device-code and API-key logins, and per-process memory — run `scripts/codex-smoke.ts` on the Windows host.

**Codex supervisor capability tokens close the one real gap stage four's scope allowed touching:** before this, anything on the same machine that could reach 127.0.0.1:3211 could make the worker run a Codex skill — no `dynamicTools`/`skillQueue`/per-entity concurrency work was in scope, because none of it has a second real caller to matter yet. `packages/codex/src/capability.ts` signs a 30-second HMAC token (`CROSSLINE_SUPERVISOR_CAPABILITY_SECRET`, deliberately independent from `BETTER_AUTH_SECRET` — one leaking must not compromise the other) carrying the caller's real `AccessContext` plus a `jti` and the worker's own `supervisorBootId` (regenerated on every worker restart, so a token signed before a restart is dead on arrival). Every supervisor route except `GET /v1/codex/status` (needed to discover the current `supervisorBootId` in the first place) verifies it; a discovery test scans every route handler the same way `csrf-protection.test.ts` does, so a new route that forgets the check fails on day one.

**The offline workbench (`apps/web/app/offline-queue.ts`) is real Dexie now, not hand-rolled IndexedDB.** The database name is `crossline-offline-${workspaceId}`, not a fixed name — switching accounts never carries the previous principal's cached commands into the new session, for free. Payloads are encrypted with a non-extractable AES-GCM `CryptoKey` (browsers support storing `CryptoKey` objects in IndexedDB via structured clone directly) before being written. `CommandEnvelope` now dispatches `work_order.start/pause/resume/complete` through the same `transitionWorkOrder` state machine the online routes use — reusing its existing `expectedWorkOrder`/`PROPOSAL_VERSION_CHANGED` optimistic-concurrency check rather than inventing a second one. `classifyReplay` gained a third outcome, `"conflict"` (HTTP 409, distinct from `"dead_letter"`'s permanent rejection and `"retry"`'s transient one): a stale command against a work order that moved on under it lands in Dexie's `conflicts` store, shown in full with its reason rather than silently discarded or silently overwriting whatever the other device already did. A device must additionally hold an unexpired, unrevoked lease (`device_leases`, 24-hour, `POST /api/auth/device-lease`, renewed automatically on a successful sync) for its queued commands to be accepted at all — `issueDeviceLease` had no reader and no revoke UI until this pass found the gap while writing `docs/user-guide.md`'s "撤销设备" section: `listDeviceLeases` and a `GET`/`DELETE` on the route were missing entirely, so a lost device's lease could be revoked at the store layer (tested) but never actually reached from the app. `apps/web/app/connectors/device-leases.tsx` is the card that closes it.

**Private cross-device access rides Tailscale Serve, not a public deployment.** `CROSSLINE_DEPLOYMENT_MODE` is `local | private | external`: both `local` and `private` still bind loopback only — Serve's own TLS-terminating reverse proxy is what makes `private` reachable from elsewhere on the tailnet, the app itself never opens a non-loopback socket. `private` is the first mode that turns on HSTS/CSP/`X-Content-Type-Options`/`Referrer-Policy`/`X-Frame-Options` (`apps/web/next.config.mjs`'s `headers()`) — loopback-only traffic never needed them, since nothing outside the device could address it at all. `external` (real public exposure) is still refused at build time; `docs/external-deployment.md` tracks its remaining prerequisites, and `docs/private-network-deployment.md` covers the `private` setup end to end, including the one-time manual steps (enabling Serve at the tailnet level, adding a second Google OAuth redirect URI). The original plan assumed Tailscale Serve might forward some notion of node identity to the backend; verified against Tailscale's own docs before building on it, and it does not — only `Tailscale-User-Login`/`-Name`/`-Profile-Pic`, and Tailscale strips any spoofed versions of those headers on the way in, so they are trustworthy but incomplete. `tailscale_bindings.node_key TEXT NOT NULL` was written against the wrong assumption and never actually usable; migration 6 made it nullable and narrowed the uniqueness constraint to `(workspace_id, tailscale_login)`. The binding itself (`apps/web/app/connectors/tailscale-trust.tsx`, `POST/DELETE /api/connectors/tailscale`) is purely an audit record an already-logged-in owner creates by choice — Tailscale identity headers never participate in any access-control decision, on purpose, so "trust this Tailscale identity" cannot become an accidental login bypass. `apps/worker/src/export.ts` had its own stale-hardcoded-identity bug found in the same pass: it defaulted `CROSSLINE_WORKSPACE_ID` to `"personal-crossline"`, which stage three made real accounts never actually use, so an unset env var would have silently exported an empty snapshot; it now auto-detects a single real workspace and requires the var explicitly otherwise. `scripts/backup-crossline.ps1`/`restore-crossline-backup.ps1` now carry `auth.db` alongside the ledger (`scripts/checkpoint-auth-db.ts` WAL-checkpoints and copies it; `scripts/read-auth-db-counts.ts` reads it back after restore) — a backup that cannot restore a working login is not a backup, the same principle the ledger's own retired-table checks already apply.

**The installed copy for testers** (design, decisions and status in `docs/local-installer.md`; 2026-10-13). App-server's ChatGPT login may not back a hosted service, so testers run everything on their own Windows machine on their own ChatGPT login: an Inno Setup per-user installer (`installer/crossline.iss`, built by `scripts/package-installer.ts`) puts a portable `node.exe`, the built web app, the worker, the Skills and a **release** build of `vendor/codex` (`codex.exe` + `codex-code-mode-host.exe`, built from source with V8 fetched by `scripts/fetch-rusty-v8.ts`, never copied from the Codex desktop app) under `%LOCALAPPDATA%\Crossline\app`. A tray (`installer/tray/Crossline.cs`, compiled with the system `csc`) runs the launcher (`apps/launcher`: ports in 47210–47299, kept while free because the port is the origin, else one from the OS — the owner's machine holds 44000–47350 with no visible listener — never one on the Fetch standard's bad-port list, which a browser will not open (it was handed 4190); secrets made once; children restarted with backoff; workspace links as junctions; a line protocol with the tray; updates from the public releases repo's `latest.json`, GitHub hosts only, size and SHA-256 checked, `data\` copied aside first). Starting with Windows is off until the person turns it on in Settings → 通用 (`apps/web/lib/autostart.ts`, the same HKCU Run value the tray's menu writes; the uninstaller removes it). The packaging script scans every x64 binary with `dumpbin` and ships the VC++ runtime DLLs beside whatever imports them (only onnxruntime does), failing the build if one is missing — that, not a clean VM, is what shows the installer does not lean on the developer's machine (a VirtualBox VM on the owner's VBS-enabled host blue-screened or hung in Windows setup). `CROSSLINE_INSTALL_MODE=local` turns off every sign-in but the machine's own Codex (`packages/auth/src/codex-local.ts`: loopback-only session route — Next.js fills `x-forwarded-for`/`x-forwarded-host` in on every request that lacks them, so the check is that they name the loopback peer and the Host, not that they are absent; sessions dropped when Codex signs out or changes account). `scripts/installer-coexist-check.ts` runs the packaged stage beside the resident app and proves neither touches the other. The installed copy's auth cookies carry the prefix `crossline-local` (cookies are not kept apart by port, and both apps live on 127.0.0.1). Its sign-in and interview are redesigned per `docs/onboarding-v3.md` (decided 2026-10-14 over six rounds with the owner); `scripts/install-preview-server.ts` serves them in local-install mode on `localhost:3330` against a stand-in Codex. **`CROSSLINE_STATE_DIR`** moves the Codex home, guest homes and the MSAL cache into the install's own `state\`: on the owner's machine the resident app keeps `codex-home\`, `auth\` and `runtimes\` in the same `%LOCALAPPDATA%\Crossline`, and sharing them would run the installed copy on the owner's Codex login — the uninstaller likewise deletes only `data\`, `state\`, `backups\` and `launcher.json`. Usage metadata goes to the owner's collector (`apps/collector`, Cloudflare Worker + D1, dashboard behind Access with the JWT verified in the Worker) only through `sanitizeTelemetryBatch` (`packages/core/src/telemetry.ts`), both before sending and again on receipt; `apps/web/lib/telemetry-privacy.test.ts` is the discovery guard. The diagnostic snapshot (`apps/web/lib/diagnostic-snapshot.ts`) keeps numbers, times and code tokens by column and replaces every other string with `{len, h}` keyed by the install's salt.

## The profile-first loop: interview, dates, milestones, research, recordings

A new account no longer lands on four placeholder goals. It lands on `/onboarding`, and everything downstream is built from what that learns. `ensureSeeded` seeds the template library and an empty plan **only**; the example milestones, relations and work orders exist behind `CROSSLINE_SEED_EXAMPLES=1`, which `vitest.config.ts`, `playwright.config.ts` and `scripts/run-e2e.ts` set because the suites and the visual baselines were recorded against that board. **Every page but the interview, settings, sign-in and `/offline` is gated on the start standard** (decided 2026-10-12, `docs/loop-and-scout.md` §7): `gateUntilReady(ctx)` (`apps/web/lib/start-gate.ts`), called right after `requireSessionContext()`, redirects to `/onboarding` until `readyToStart` holds, and no account is exempt — one with work on its board is held too, so the first schedule anyone sees rests on what they said. It replaced `needsOnboarding`, which let any account with a session or a fact through. API routes are not gated (the worker, local tools and offline replay need them). The example board meets the standard (`seedExampleReadiness`, `apps/web/lib/example-readiness.ts`: lines with descriptions and adopted goals, the default hours as the interview's proposal, one no-deadline project per line), or the suites would land on the interview; `seedReadyToStart` in `apps/web/lib/test-support.ts` is the same for tests. `apps/web/lib/start-gate.test.ts`, `apps/web/app/empty-account.test.tsx` (an empty account is sent to the interview; a ready one with no milestone or work still renders every page) and the e2e test 「未达可开始标准时打开今日页回到访谈…」 (a second account of its own, `e2e/accounts.ts` `signUpAccount`) are the guards. `scripts/start-readiness.ts <copy.db>` prints what each workspace of a ledger copy still misses (it refuses the live ledger).

**The interview is a ledger conversation, not a form** (`apps/worker/src/onboarding-session.ts`, `packages/core/src/onboarding-turn-schema.ts`). Each turn asks several questions at once with 8–14 candidate options, and every `confirmed` fact must cite a `reply-N` or `src-N` with a verbatim `sourceQuote` (compared as letters and digits in order, ignoring punctuation and Markdown: a bulleted line copied as a sentence failed a real run twice); anything the model worked out is `inferred` with an empty quote and the store never lets a guess overwrite a confirmed fact. The messages, profile facts, projects and uploaded `source_documents` are all in SQLite, so a reload or another device resumes where it stopped. **The runtime forgets a conversation when it restarts** — a stored `codexThreadId` then answers `thread not found`, which is a JSON-RPC error object that used to surface as an anonymous `SKILL_RUNTIME_FAILED` and wedged the interview forever. `runContinuedTurn` now names it `SKILL_THREAD_LOST`, and the runner opens a fresh thread seeded with the profile, every file and the conversation so far (`history`, user lines carrying their `reply-N` id). Any new place that stores a thread id must handle that code the same way.

**Long runs stay alive on the wire.** A caller's `fetch` gives up when no byte arrives for five minutes (undici's default), and a Skill is allowed ten; a one-turn interview with a long history takes about seven. The supervisor therefore answers the interview turn, date extraction, milestone proposal and diligence routes through `sendJsonWhenReady`: status line at once, a space every twenty seconds, JSON at the end. Every outcome of those routes is already a typed `{state:"blocked", code}` in the body, so the status is 200 either way and a throw becomes one more blocked result. Do not "simplify" it back to `sendJson(await work())`.

**Model routing** (`packages/codex/src/model-policy.ts`): one table maps each skill to a tier, and a tier to `{model, effort}` — top `gpt-5.6-sol`/medium (interview, milestone architect, backplanner, flywheel), mid `gpt-5.6-terra`/high (analysis, materials, gate, weekly insight, diligence), low `gpt-5.6-luna`/high (date extraction, background facts, explainer, assistant). `CROSSLINE_MODEL_TOP|MID|LOW="model[:effort]"` override a tier and `CROSSLINE_MODEL_ROUTING=off` disables routing. The model goes in `thread/start` and, with the effort, in **every** `turn/start`, because a continued turn inherits the thread's model unless told.

**Dates from files are a batch the person confirms** (`packages/core/src/date-schema.ts`, `apps/worker/src/onboarding-session.ts`, `apps/web/lib/imported-dates.ts`). There is **no separate date-extractor Skill**: the interview turn already reads the files, so it returns the dates in a `fileDates` field of its own answer (`persistFileDates`), and the model that reads the syllabus is the one that knows today's date and the person's zone. A turn that re-reads the files replaces what nobody has answered yet; any other turn adds to it (`mergeDateExtractions`, same id → newer) — every turn used to replace it, and one that heard 「12–14 点午饭」 threw away an unanswered batch with both ECE 548 midterms. Weekly arrangements wholly outside hours the person stated and belonging to no project (meals, sleep) are left out (`withoutOffHours`), since the available hours already leave them out and as items they were offered for confirmation and for the calendar. Each date carries a verbatim quote that must contain the day itself (`quoteSupportsDate` accepts `10/27`, `27th Oct.`, `Oct 27`, `10月27日`; the year is not required). `sanitizeDateExtraction` drops an item that cannot be verified and reports it in `dropped` instead of failing the whole answer — the first real run lost a hundred good rows to one misquoted line and a four-minute repair. The quote comparison ignores punctuation and spacing only (`squash` keeps letters and digits): the model copying `27th Oct.` as `27th Oct` is the right quote, and refusing it dropped a real midterm. Weekly patterns are expanded in code (`expandRecurring`), never by the model, and only today-and-later reaches the calendar. A batch is two ledger events (`dates.extracted`, `dates.decided`); `extract({replace:true})` re-reads the files of a batch nobody has answered and retires it once the new one exists. Confirmed timed items become read-only plan blocks `import:<batch>:<item>` that calendar sync never touches (it only rewrites `graph_calendar:` blocks); untimed ones become `date_*` profile facts.

**Milestones are anchored to the person** (`packages/core/src/milestone-plan.ts`, `apps/worker/src/milestone-proposer.ts`). When the context carries a `profile`, each proposal needs a `plan` — `key`, `stage`, `deadline`, `baseline`, `target`, `stakeholders`, `sourceFactIds`, `dependsOn` — and `validateMilestonePlans` refuses what it can check: a generic or too-short title, a missing or past or >18-month deadline, an empty target, no source fact (or only inferred ones), an unknown fact id, no `outcome` criterion, fewer than three or more than five per covered line, a later stage due before an earlier one, an unchained stage, a dependency that is not earlier. The refusal's `detail` names the milestone, because a bare code gives the model nothing to repair. Anchors live in `milestone_anchors` keyed by milestone id (not in the versioned `milestones` row), so revising a milestone does not lose them. Proposing archives untouched `*-starter` milestones, the relations between them and untouched seeded work orders; an accepted order is history and stays. Accepted diligence proposals reach the architect as `diligence[]`.

**Web research is checked, then opened** (the opportunities question assumes no status or place: it is given the person's confirmed `person` facts beside the line's and lists only what they plausibly qualify for — it once asked 「是否对在读学生开放」 of everyone and offered a Hangzhou founder UC Berkeley's student fund) (`packages/core/src/diligence-schema.ts`, `apps/worker/src/diligence.ts`). The contract is built around sources: a source is a public https page (no IP literal, local name or port), every finding cites sources by id, every proposal rests on findings and on the person's own fact ids, and the investment line may not contain a trade call or price target. After the model answers, `verifySource` actually requests each page — manual redirects, every hop re-checked against a DNS lookup so a hostname cannot lead to a private address — and drops a source that does not open or whose content does not match its claimed title, together with every finding that depended only on it. `pageSupports` then requires the Latin names in a finding's claim to appear in the page it cites (a real run filed a Hult Prize deadline under NVIDIA's page); figures are not compared, because `2026-11-15` and "Nov 15" are the same date. A report with nothing left is a failure and writes no conclusions. Each line is researched at most weekly, in the background, only once the interview is complete or a report already exists, and stops when the budget is in economy mode. Nothing a report proposes becomes a goal until the person accepts it. **The runtime executes web search through `codex-code-mode-host`, which it starts from beside its own executable**; a fork built without it answers every search with `failed to spawn code-mode host` and the model reports "the research tool is unavailable". `webResearchBlocker()` checks for the file up front and names the path. Building it from `vendor/codex` needs a V8 prebuilt archive from GitHub; the installed Codex app's `bin\codex-code-mode-host.exe` was copied in instead (a newer build than the pinned 0.155.0 — it worked, but re-verify after any runtime bump).

**Recordings are transcribed on this machine** (`apps/worker/src/transcribe.ts`). `TranscriptionEngine` isolates the model and the decoder, so the consent gate, the status the screen reads, the 3-hour limit and the timestamped transcript are tested without either. The model (`onnx-community/whisper-small`, 8-bit, about 255 MB) is fetched only from a request carrying `consent: true`, which the screen sends only from the button that names the source and size; recognition afterwards runs with `allowRemoteModels = false`. **The language is detected, not assumed**: transformers.js does not detect it (it logs "defaulting to English"), so `detectLanguage` sums the first decoding step's scores for each language token over three half-minute clips (10%, 40%, 70% in) and the transcript's first line names the result; `CROSSLINE_TRANSCRIBE_LANGUAGE` pins it. Whisper tends to write Chinese in traditional characters; converting needs a library nobody has agreed to install yet. The engine imports `@huggingface/transformers` and `audio-decode` on use, so a machine without them reports `unavailable` rather than failing to start.

**The worker's per-workspace jobs** — nightly flywheel, the diligence pass and the screen-activity tracker — loop over every real workspace. The nightly used to be one instance bound to the pre-accounts workspace id, so no real account ever had its flywheel expanded.

**Model routing is more than a table** (`packages/codex/src/model-policy.ts`, `usage.ts`, `skill-runner.ts`). A Skill's route can be overridden per Skill (`SKILL_OVERRIDES`: the one input box's `crossline-concierge` runs at `medium` effort — on the thirty-sentence replay it read as well as `high` and answered a second faster; `CROSSLINE_ROUTE_<SKILL>="model[:effort]"` pins one) and carry its own `maxRepairs`. When the quota is tight (`budgetPolicy` says `economy`, read through `setSpendModeProvider`, cached for a minute, an unreadable quota counts as normal) a Skill **steps down one tier** instead of being refused, except the gate and the capture analysis (`NEVER_DOWNGRADED`): a weaker reading of either is a wrong answer, not a cheaper one. Runs wait in **a lane per tier** (`serializeSkillRun(skillName, …)`), so a one-second plan explanation no longer waits behind a ten-minute interview turn; only switching a Skill on and off is held in one line (`underConfigLock`), because that rewrites the runtime's one config file. A Skill belongs to exactly one tier, so two runs of the same Skill still never overlap. Every run reports `thread/tokenUsage/updated` totals to `setUsageSink`; the worker writes them to `model_usage` (per workspace, attributed through `enterUsageWorkspace` — the supervisor sets it from the verified capability, the tick loops set it per workspace) and Settings shows the last seven days per Skill. The old `ModelTier`/`model-tiers.ts` (never wired to anything) is gone.

**Manualbooks (phase 3, `apps/worker/src/manualbook.ts`, `packages/core/src/manualbook-schema.ts`, `safe-fetch.ts`).** A work order in `preparing` gets a per-task book in `CROSSLINE_DATA_DIR/materials/<workOrderId>/` (`manifest.json` with checksums, `flow.json`, `manual.md`, `nodes/<id>/{task,analysis,tutorial,sources}`) instead of one file. Three Skills in sequence: `crossline-manualbook-designer` (top tier) lays out the steps as a **DAG** that must cover every required `materialContract` item (`validateManualDesign`, `topologicalOrder`); `crossline-material-researcher` (mid, web) finds sources for each step that needs them; `crossline-material-writer` (mid) writes the step from those sources only. The worker, not the model, decides what is real: every source must be a public https URL that **actually opens** (`safeGet`: DNS public-host check on every hop, size/type caps; a title the model claimed must match the page), and the full text is downloaded only when the host passes `openAccessVerdict` *and* the model did not say no — everything else is `summary_only`. A write-up may cite only the source ids it was given and may not contain a URL of its own. `requiredApproval("download_open_access")` is `automatic`, `download_other` is `never`. A failure writes `materials.blocked` with a typed code; it never leaves half a book that looks finished. The task detail shows the book as a contents list (`TutorialView layout="toc"`: a row per person's step, opened in place, the current step open) and `/materials/<id>` reads it whole; both are served by `/api/work-orders/[id]/manualbook` and `/materials` (`manualbook-view.tsx` is gone). The assistant's outputs are cleaned before they are shown (`app/materials/humanize.ts`: no local paths, hashes, sizes, extensions or internal codes; hashed sources are named from `source_documents`; tables keep at most four readable columns), and Markdown renders `$…$`/`$$…$$` with KaTeX (`trust:false`, strict; a failure shows the source). Evidence: `scripts/manualbook-check.ts` (real Codex, throwaway DB; 2026-10-02: 6 steps, 6 verified sources, 9 minutes, checksums match). **Every step is researched** (decided 2026-10-09): `validateManualDesign` refuses a step without `needsResearch` and at least two questions, one of them answerable on the open web whatever course this is; the designer Skill says what to look for per kind (read: textbook chapter or open courseware; do: official docs and a maintained tutorial; decide: criteria and governing rules; verify: test method and reference values; write: author guidelines and exemplars). A page that answers 401/403/429 exists but refuses automated readers: it is kept as `kept: "unverified"` — link and the researcher's summary, labelled 「未能自动核实」 — instead of being dropped; anything else that does not open is still dropped. A real ECE 548 tutorial had one researched step out of seven and both of its sources dropped (a faculty page 403, a rating site 429).

**Screen activity (phase 5; `packages/core/src/activity-state.ts`, `apps/worker/src/activity-{source,recorder}.ts`, table `activity_segments`).** `ActivitySource` is the interface (`start(onReading)`/`stop()`), so a wearable or phone is another implementation later; the Windows one is a single long-lived PowerShell reading, every `CROSSLINE_ACTIVITY_INTERVAL_SECONDS` (60), the foreground app, its window title and the idle time — nothing else. `createActivityTracker` offers each reading to **every workspace** (the recorder used to be bound to `personal-crossline`) and each decides from its own settings, re-read per reading: `localActivity.consent` = daily aggregates only (the original promise: no app, no title), `localActivity.consentV2` = segments with app and title, `localActivity.pausedUntil`, `activity.blacklist` (the person's own words), `activity.rules`. A window matching `isPrivateWindow` (banking, password managers, InPrivate/incognito, …) is **not recorded at all** — not title, not app, not that it was open; its minute still counts as active in the aggregate. Titles stay on the machine: `ActivitySegment` (what core and the web read through `listActivitySegments`) has **no title field**, `exportSnapshot` blanks them, they are blanked after 14 days (minutes/app/category stay, rows go after 90), and `recentActivityEntries` is read by exactly one route — the settings card that shows the person what is kept, with 清除所有窗口标题. `apps/web/lib/activity-privacy.test.ts` is the discovery test: it fails if any other file reads titles or if anything that builds a Codex context touches the segments. `inferWorkState` is rules, not a model (focused / switching / in_meeting / away / leisure / mixed / unknown, each with reasons and a confidence; under five tracked minutes is `unknown`); the Today chip and the day timeline's 「实际」 blocks exist only with the V2 consent. `categoryMinutesOnly` is the only shape that may ever go to a model.

## End-to-end tests

`e2e/crossline.spec.ts` (Playwright, config at `playwright.config.ts`) drives a **production build** (`next build --webpack` then `next start`) on port 3310 (3211 belongs to the resident worker's Codex supervisor) with its own temp data dir (`CROSSLINE_DATA_DIR` under the OS temp dir, keyed by PID) and `CROSSLINE_NEXT_DIR=.next-e2e` so it never collides with the port-3210 dev server or its `.next` build. A production build rather than `next dev`, because `next.config.mjs` disables Serwist in development — the offline claim had no service worker to test against and could not have been verified here no matter what a test asserted. The offline test cuts the network and **first proves the cut** with a `fetch("/api/health")` that must fail, then reloads and asserts the page still renders; without that probe a passing test shows only a warm cache. The data dir is stashed in `CROSSLINE_E2E_DATA_DIR` so test workers (separate processes, different PIDs) can open the same ledger the server did — the C-lens tests write their own pending diffs into it, because the seeded example diffs no longer exist. `CROSSLINE_FIXED_NOW` pins the clock so visual-regression PNGs (`e2e/crossline.spec.ts-snapshots/`) are reproducible. When intentionally changing layout, regenerate snapshots with `pnpm exec playwright test --update-snapshots` rather than hand-editing the PNGs. The two screenshots hide (`visibility:hidden`, so layout is kept) the pending badge and everything the scheduler produced — `STABLE_FOR_SCREENSHOT` in the spec — because the badge's count depends on what parallel tests have written and the scheduler's block lengths come from a time-limited solve that gives a different feasible answer on a busy machine; before that, the baselines passed or failed by run. ## Safety boundaries (do not casually change)

These constraints are enforced in code, not just docs — read the relevant source before loosening any of them:

- Microsoft Graph writes only ever target a calendar/list literally named `Crossline`; `connectorWritePolicy` returns `"read_only"` for everything else. The schedule is written by default (no plan approval since 2026-10-12, `write_focus_block` is `automatic`); the boundary is the writer's: only the Crossline calendar, only events this app made and the person has not changed, deletes only in the future, preview and pencilled-in blocks never.
- UW Outlook and Google Calendar are read-only, imported only via the official Codex plugin (not implemented in this repo's connectors).
- Longbridge (`longbridgeToolAllowed`) permits only market-data/reference tools — no account or order-placement tools.
- `content-ops` only accepts idempotent `POST /v1/jobs` and reads real terminal state via authenticated `GET /v1/jobs/{id}`.
- No real Graph OAuth, outreach, publishing, or trading is currently wired up — `requiredApproval` returns `"never"` for `broker_order` and `silent_source_calendar_write` by design.
- **The camera.** The one camera path is the person's decision of 2026-10-14 (`docs/energy-and-ecosystem.md` §8).
  - Its scope: desktop only, its own consent (`energy.camera`) off by default, frames processed in the page and never stored or sent.
  - The energy API accepts from it only the five numeric `camera_aggregate` fields, and refuses them without consent (`CAMERA_NOT_ENABLED`).
  - Everything else stays refused: the old `camera_proxy` (`CAMERA_ENERGY_PATH_REMOVED`), raw media and unknown fields (`RAW_MEDIA_OR_UNKNOWN_FIELD_FORBIDDEN`), non-aggregate features (`AGGREGATE_FEATURES_ONLY`).
  - Widening any of it — phone camera, keeping frames, sending landmarks, sampling with the page in the background — requires another explicit decision, not a refactor.

- The one outbound path the notifications have is Web Push to the person's own subscribed devices (chosen 2026-10-07): end-to-end encrypted for the device, posted only to known push services. It carries notification text, nothing else.

If a change would add or enable a real external write path (Graph OAuth, publishing, trading, outreach) or would let raw camera/media data leave the browser, flag it explicitly — these are deliberate, currently-unimplemented boundaries per the project README, not oversights.

Design §12's nine acceptance criteria have reproducible evidence scripts: `gate-analysis-check.ts` (§12-1/2, a real Codex analysis into `awaiting_plan_approval`), `gate-loop-check.ts` (§12-3/4, material preparation through auto-acceptance), `gate-flywheel-check.ts` (§12-5, the only web-enabled Skill — expensive, never run as a side effect), and `gate-capacity-budget-check.ts` (§12-6/7). §12-8 is proven by `apps/web/lib/generality.test.ts`, which swaps the whole pack registry. All nine pass by real runs as of 2026-09-16; `docs/archive/implementation-todo.md` carries the table and the evidence.

**Skill wire contracts live in `packages/core`** (`analysis.ts`, `flywheel-schema.ts`, `materials-schema.ts`, `milestone-gate-schema.ts`). Two rules learned the hard way: structured output runs in strict mode, so every schema object needs `additionalProperties: false` *and* every property listed in `required` (express a union with `anyOf`, not optional fields); and this runtime's `web_search` takes `disabled | cached | live` — the wrong variant fails the whole `thread/start`, which is why the flywheel could never run before 2026-09-16.

## Operational scripts (`scripts/`)

- `start-crossline.ps1` — launches the **built** web app + worker, each under `keep-running.ps1`, (requires `pnpm build:prod` first, which builds into `apps/web/.next-prod`; fails fast if its `BUILD_ID` is missing). The resident app has its own build directory because `pnpm build`/`pnpm verify` write `.next`: a verify run while the server was up replaced the hashed CSS it was still naming, and every page lost its styles (found from the phone address on 2026-10-07, where nothing was cached). Idempotent by design: it skips the web app when port 3210 already listens, and always launches the worker because a free supervisor port does not prove the worker is dead. The worker guards itself with a heartbeat lock at `data/worker.lock` — a redundant copy logs `worker.already_running` and exits 0 rather than opening a second SQLite writer, a stale heartbeat (3× the tick interval) is taken over, and `EPERM` from `process.kill(pid, 0)` counts as alive.
- `keep-running.ps1 -Name web|worker` — the loop each resident process runs under (2026-10-15): starts it, waits, writes the exit (time, code in hex, minutes run) to `data\logs\restarts.log`, keeps the previous logs under a timestamp, and starts it again after 5 s (backing off to a minute when it keeps dying at once). It holds `data\<name>.keeper.lock`; `start-crossline.ps1` starts a keeper only when none is alive, so a crash is down for seconds instead of up to the watchdog's fifteen minutes. The web had died twice that day with `0xC0000409` and nothing on stderr; `restarts.log` is where the next one is recorded. To restart one, kill the process listening on its port and its keeper starts it again; to stop one, kill its keeper first.
- `install-startup.ps1` — registers a Windows Scheduled Task with two triggers: at logon, and repeating every 15 minutes. The repeating one is the watchdog for the keeper loops, which run only while this Windows user is logged on. Modifies Windows Task Scheduler; only run when the user explicitly asks.
- `backup-crossline.ps1` — exports the ledger to JSON, zips it, encrypts with DPAPI (current Windows user), and verifies SHA-256 before deleting the plaintext temp file. Its `& pnpm` call (and the one in `restore-crossline-backup.ps1`) is wrapped in `& { $ErrorActionPreference = 'Continue'; … }`: under `'Stop'`, PowerShell 5.1 turns a native command's stderr line into a terminating error whenever stderr is redirected, which is every non-interactive host. The script died before reading `$LASTEXITCODE`, so the backup worked by hand and silently never ran unattended.
- `migrate-workspace.ts` — moves one workspace between two installs on the same machine (2026-10-14: the resident copy's account into the installed app at `%LOCALAPPDATA%\Crossline`). It exports the source through an online backup, swaps in the target's workspace and owner ids, rewrites paths under the source data directory, copies `materials/`, `sources/` and the portrait folder, and imports into a target that holds exactly one workspace with no person data (its seeded rows are cleared; identity tables are never copied). Dry run by default, `--apply` to write; stop the target app and back up its `data\` first.
- `restore-crossline-backup.ps1` — decrypts a backup and **rebuilds a working SQLite ledger** from it via `pnpm restore`, then reads every table back through the normal query path to verify. `CrosslineStore.importSnapshot` only ever rebuilds into an empty workspace (`RESTORE_TARGET_NOT_EMPTY`), the CLI refuses the live database (`RESTORE_TARGET_IS_LIVE_LEDGER`) and refuses to overwrite an existing file (`RESTORE_TARGET_EXISTS`). Replacing the live ledger stays a manual act. Snapshot table and column names are validated against `sqlite_master`/`PRAGMA table_info` before reaching SQL.

## What is deliberately *not* ours to build

Audited against the vendored runtime (`vendor/codex`, rust-v0.155.0). Codex already provides, and we therefore use rather than reimplement: thread persistence/resume/fork/compaction, `outputSchema` structured output, per-turn model/effort/sandbox/approval overrides, `thread/tokenUsage/updated`, `account/rateLimits/read`, `account/usage/read`, `model/list`, login flows, web search modes, MCP, dynamic tools, hooks, memories, goals with a token budget, and image input. It does **not** provide, so we own: per-skill model/effort/schema (SKILL.md frontmatter only honours `name`/`description`), scheduling, PDF/docx extraction or OCR, batch audio transcription, a hard spend cap, and verification of what a model claims (quotes, URLs, DAGs, approvals). Before writing a script that wraps the model, check this list; the deterministic validators stay, the "ask the model to do it" scripts do not. Removed on this pass as having no caller: the orchestration skill, `validateMaterialPreparation`, the Graph/Longbridge/ContentOps connector classes were **kept** (Gate 3/5 roadmap) but flagged unwired, `readCodexAccount`/`startCodexChatGptLogin`, `readTailscaleIdentity`, `addCapturedTask`, `interviewQuestions`, `skipRecurringWorkOrder`/`tombstoneWorkOrder`/`notificationForTransition`, `normalizeCodexEvent`/`buildContextBundle`, three one-off scripts, and 91 CSS selectors of deleted components.
