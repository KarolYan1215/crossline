# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Crossline (跨人生主线执行看板) — a local-first execution board that unifies tasks and evidence across multiple "identities" (研究/科研, 创业, 自媒体, 投资) sharing one task/evidence ledger, with health treated as a capacity constraint rather than a competing identity. Everything runs on one machine against a local SQLite ledger; there is currently no live external write path (see Safety boundaries below). UI copy and commit-facing text in this repo are in Chinese.

Current closed loop (per README): natural-language capture → system infers identity + duration bucket → a `WorkOrder` is generated → next-action recommendation → one calendar (day / week / month) with the plan's differences folded under it, approved as a batch → manual completion submission → evidence acceptance on the approvals page. Plan versions, recurring milestone relations, state transitions, and approval events are written to local SQLite WAL — not static frontend data.

## Commands

Run from the repo root (pnpm workspace, Node >=22, pnpm 12.6.0):

```powershell
pnpm install
pnpm dev              # starts @crossline/web (Next.js) on http://127.0.0.1:3210
pnpm worker           # starts @crossline/worker in watch mode
pnpm test             # vitest run, across packages/**/*.test.ts and apps/**/*.test.{ts,tsx}
pnpm test:watch       # vitest watch mode
pnpm test:e2e         # playwright test (visual regression + flow coverage, see e2e/)
pnpm typecheck        # tsc --noEmit in every workspace package (pnpm -r typecheck)
pnpm build            # next build for @crossline/web
pnpm verify           # typecheck + test + build + e2e, the one command before a commit
pnpm doctor:ledger    # ledger health: orphan rows, half-migrations, retired tables, WAL size
                      # (not `pnpm doctor` — that is pnpm's own built-in and shadows the script)
```

Single test file / single package:

```powershell
pnpm vitest run packages/planner/src/planner.test.ts
pnpm --filter @crossline/db typecheck
pnpm exec playwright test e2e/crossline.spec.ts
```

Worker one-shot run (used for smoke checks — ticks once and exits instead of looping):

```powershell
$env:CROSSLINE_RUN_ONCE='1'; pnpm worker:start
```

Export a full ledger snapshot to JSON:

```powershell
pnpm export -- C:\path\to\crossline.json
```

Rebuild a database from a snapshot (never writes to the live ledger; target must not already exist):

```powershell
pnpm restore -- C:\path\to\crossline.json C:\path\to\target.db
```

Codex app-server contract smoke test (pins against the commit recorded in `codex-baseline.json`):

```powershell
pnpm exec tsx scripts\codex-smoke.ts
```

Production start / scheduled-task install / backup / restore are PowerShell scripts under `scripts/` — see "Operational scripts" below. Do not run `install-startup.ps1` unless the user explicitly asks; it registers a Windows Scheduled Task.

## Architecture

**Workspace layout:** `pnpm-workspace.yaml` wires `apps/*` and `packages/*`. Packages export raw TypeScript directly (`"exports": "./src/index.ts"`, no build step) and are consumed by `apps/web` and `apps/worker` via `workspace:*`. `better-sqlite3` and `esbuild` need `onlyBuiltDependencies` approval in `pnpm-workspace.yaml`.

**The day head clock (`apps/web/app/analog-clock.tsx`):** a real dial — ticks, numerals, hour/minute hands, a green second hand — placed from the same instant the rest of the page uses, read in `CROSSLINE_TIME_ZONE` (falling back to `America/Chicago`) rather than the browser's own zone so the dial and the 「周三 11:25」 label cannot disagree. Under `CROSSLINE_FIXED_NOW` it does not tick and drops the second hand, which is what keeps the visual-regression snapshot reproducible. It replaced a bare circle with one motionless dot that carried `aria-label="此刻 …"` and showed nothing.

**Data flow:** `apps/web/lib/crossline.ts` is the sole server-side entry point into persistence for the web app — it lazily creates a singleton `CrosslineStore` (SQLite, WAL mode) rooted at `CROSSLINE_DATA_DIR` (default `../../data` relative to `apps/web`), seeds starter milestones/relations/work-orders/a draft plan on first run, and exposes read/write helpers used by the Next.js route handlers under `apps/web/app/api/`. `CROSSLINE_FIXED_NOW` overrides the dashboard's notion of "now" (used by e2e tests for deterministic snapshots); `CROSSLINE_PRIMARY_CLOCK_ID` (default `research`) picks which identity gets deadline-tier priority as the master clock.

**Event-sourced ledger (`packages/db`):** `CrosslineStore` owns the SQLite schema: an append-only `events` table keyed by `(workspace_id, idempotency_key)` plus current-state tables led by `work_orders`, versioned milestones, relations, plans, executions, evidence, capacity and connector bindings. `StoredTask` is gone. If an old `tasks` table exists, open-time migration first copies a file DB to `.v1.bak` or `.pre-r2.bak`, migrates non-health rows to WorkOrders and health rows to capacity commitments, then drops the legacy table. New databases never create it. `exportSnapshot()` returns typed current models plus the generic workspace-scoped table dump.

**Migrations are versioned and transactional.** `#runMigrations` walks an ordered array gated on `PRAGMA user_version`, runs each migration **whole, inside one transaction**, and writes the new version in that same transaction; before the first pending one it force-copies the file to `<path>.v<current>.bak`. This replaced a `PRAGMA table_info` guard that checked column A and then added A *and* B — a crash between the two `exec`s left the guard satisfied and the database permanently half-migrated with no way to notice. That matters more than it looks: shipping to anyone else means running schema changes on **their** database, which is the real productization blocker, not the engine. Migration 4 dropped six tables that were never written (`outbox`, `identities`, `projects`, `milestone_versions`, `insight_proposals`, `skill_versions`) plus `energy_observations.expires_at`, and added nine indexes. `importSnapshot` still accepts a snapshot taken before it: the retired names are skipped when empty and refused (`RESTORE_RETIRED_TABLE_NOT_EMPTY` / `RESTORE_RETIRED_COLUMN_NOT_EMPTY`) when not, because a backup that cannot be restored is not a backup. Deliberately **no** `busy_timeout` and **no** `journal_size_limit`: both were added, then measured out as non-problems (better-sqlite3 already defaults the busy timeout to 5000ms, and the oversized WAL beside a small database is the autocheckpoint threshold doing its job, not a missing checkpoint).

`listEvents(workspaceId, { type?, entityId? })` takes its scope and its filter in SQL. It used to take **no arguments at all** — every one of ~40 call sites read the whole ledger and `JSON.parse`d each row to filter in JS, three of them without filtering by workspace at all. Foreign keys are deliberately still absent (adding one to SQLite means rebuilding the table, and the `(id, version)` primary key on `milestones` blocks the most important one); `pnpm doctor:ledger` scans for orphan rows, half-migrations, retired tables and WAL size instead, and exits non-zero on findings. `applyMilestoneGate`, `revokeAutoAcceptance`, `refuteMilestoneRelation` and `resolvePlanChange` are each wrapped in one `.immediate()` transaction — all four were check-then-act sequences, and the 「账本写了已验收、作业还在 evidence_review」 split state was that, not a logic bug. `packages/db/src/isolation.test.ts` is what proves the `workspace_id` discipline actually holds.

**Offline command replay:** `CommandEnvelope` is validated and posted to `apps/web/app/api/commands/route.ts`, which re-checks scope and currently permits only `task.capture`. `clientCommandId` is the ledger idempotency key. Completion is intentionally not an offline shortcut: Today links to Workbench, where execution and evidence follow the WorkOrder state machine.

**Natural-language capture:** `addCapturedTaskWithId` in `apps/web/lib/crossline.ts` writes one `captures` row and nothing else — no identity, no estimate, no `Task` and no `WorkOrder`. Classification only happens when an explicit Analyze runs the `crossline-automation-stripper` Skill through the worker-owned Codex app-server (`apps/worker/src/analysis.ts`, `packages/codex/src/analysis.ts`) and the result passes `validateAnalysisProposal` (`packages/core/src/analysis.ts`); only then does `transitionWorkOrder` atomically promote the capture to an `awaiting_plan_approval` WorkOrder. A failed, refused, timed-out or unauthenticated analysis leaves a typed blocker on the capture, and a blocked capture can be re-analysed (each attempt gets its own idempotency key via `captures.attempt`). There is no keyword-regex identity guess and no 25/30/60 minute default anywhere in this path.

**Work orders:** WorkOrder is the only executable model: `captured → analyzing → awaiting_plan_approval → approved → preparing → ready_for_human → active → evidence_review → accepted`, plus `blocked`/`archived`. All execution and evidence changes route through `transitionWorkOrder`; a milestone-bound WorkOrder cannot be accepted with zero evidence. `archiveWorkOrder` (the 丢弃 button, reason required) is the only thing that emits `archived`; discarded orders leave the board for a drawer, never the ledger. Starting an order that already has materials on disk skips `preparing` — going back there would strand it, because the worker skips orders that already have materials.

**Approval policy is centralized:** `requiredApproval(action)` in `packages/core` is the single source of truth for whether an action is `"automatic" | "batch" | "per_item" | "never"`. Actions like `broker_order` and `silent_source_calendar_write` are permanently `"never"` — connectors and UI should defer to this function rather than re-deriving policy.

**Every mutating route calls `isCrossSiteWrite` (`apps/web/lib/same-origin.ts`), first thing.** It refuses a POST/PUT/PATCH/DELETE whose `Origin` header names a different host than the one the browser actually addressed, and passes anything with no `Origin` at all — that is a local tool or the worker, not a browser form post, and this app is expected to support both. A red-team pass found seven routes that never called it (`commands`, `energy-observations`, `milestones`, `milestones/propose`, `codex/account`, `plans/[id]/approve`, `plans/changes/[id]`): a forged `Origin: https://evil.example` wrote real captures, energy observations and milestones, and against `codex/account` it started a real OAuth login. `apps/web/app/api/csrf-protection.test.ts` is the guard against this recurring — it is a **discovery** test, not a per-route one: `import.meta.glob` reads every `route.ts` under `app/api`, and every exported mutating method gets one forged-Origin request asserting 403. A route added without the check fails this test on day one instead of shipping unguarded, which is the property a per-route test cannot give you.

**Revoking auto-acceptance is keyed on the attempt, the same way a gate re-judgement is (see Gate 4 below).** `revokeAutoAcceptedWorkOrder` (`apps/web/lib/crossline.ts`) counts how many times this work order has already been revoked and builds `auto-acceptance-revoked:${workOrderId}:${attempt}` from that, rather than trusting the caller to number it. A work order that gets auto-accepted, revoked, re-judged and auto-accepted again is a normal cycle, and a fixed key reused the first revoke's on the second call: `appendEvent` silently no-ops on a repeated idempotency key, and the caller returned `{ ok: true }` without checking whether anything had actually changed — the person saw the page reload and believed the revoke worked, while the ledger never left `accepted`. `revokeAutoAcceptance` (`packages/db/src/index.ts`) now throws `REVOCATION_ALREADY_APPLIED` if `transitionWorkOrder` reports `changed: false`, mirroring `applyMilestoneGate`'s `GATE_ALREADY_APPLIED` — the store-level check is what turns a stale-key collision into an honest failure; the caller's attempt counter is what makes a genuine second revoke keep working instead of failing forever.

**The plan is one calendar.** `apps/web/app/plan/page.tsx` + `plan-view.tsx` render day, week and month views (`apps/web/app/timeline/`) over one list of items: real calendar events, file-imported class meetings, and the blocks the scheduler placed for work orders. `timeline/model.ts` is pure (axis geometry, overlap packing into columns, the Monday-first month grid, conflict detection, the zone's current minute) and is where the tests are; `views.tsx` draws it — **day** is a horizontal 24-hour axis with one row per thing and a now line, **week** is seven columns sharing one vertical hour axis with a deadline strip on top, **month** is a block calendar of tags (colour is the line, outline says scheduled / calendar / file) with `+N` folding. `apps/web/lib/timeline.ts` builds the data: plan blocks, each live milestone's deadline from `milestone_anchors`, every confirmed `date_*` profile fact, and the person's unavailable hours as the complement of the availability windows. The same `CalendarPanel` is the day timeline on Today. The plan's differences (`StoredPlanChange`) sit in a fold that opens by itself when something is pending. `approvePlanVersion(planId)` (`apps/web/lib/crossline.ts`, exposed at `apps/web/app/api/plans/[id]/approve/route.ts`) refuses to approve a plan with an unresolved `conflict`-kind change (`PLAN_HAS_UNRESOLVED_CONFLICT`), otherwise marks all pending changes approved and the plan version approved in one step, appending a `plan.approved` event. FullCalendar and the old B/C/A lenses are gone.

**Calendar reality (`apps/worker/src/graph-sync.ts`):** `GraphReadSource` is a read-only class with no write methods at all, kept separate from `MicrosoftGraphConnector` on purpose — that connector's `Crossline` name lock is what keeps writes off a real calendar, and reading the user's own calendar needs no lock because this class structurally cannot write. **It reads several calendars across several accounts.** `apps/worker/src/calendar-sources.ts` owns the choice: a `calendar.sources` settings row lists `{accountId, calendarId, label}`, and `calendar.sources.seeded` records which accounts have already been offered their default calendar. Both live in the ledger, next to the availability pattern and for the same reason — a backup that does not carry them restores a plan whose reality lane cannot be rebuilt. The label is stored too, so building a tick's sources costs **no Graph calls**; the catalogue is fetched only when someone opens the Connections page (`GET/POST /v1/calendar/sources` → `/api/calendar/sources` → `connectors/calendar-sources.tsx`). A newly signed-in account is seeded with its **default calendar only** — ticking everything would drag 「中国 节假日」 and 「生日」 onto the plan, and ticking nothing would make signing in appear to do nothing. The seeded marker is separate from the selection because deriving "is this account new?" from the selection meant unticking an account's last calendar silently ticked its default back on. `scripts/graph-add-account.ts` signs in an extra mailbox; `graph-readonly-check.ts` cannot, because it logs in only when there is no token at all. A **personal** Microsoft account additionally needs the Entra registration's supported account types to include personal accounts plus `CROSSLINE_MS_TENANT_ID=common` — a single-tenant registration answers AADSTS50059 at `/common` and AADSTS700016 at `/consumers`, and that is a portal setting, not a bug.

**Per-source authority is the rule that keeps this safe.** Each `(account, calendar)` pair is a `CalendarSource` with its own delta cursor (`external_bindings.external_id` is the source key) and stamps `sourceKey` on every block it produces. A source may only add, change or drop blocks carrying **its own** key. So a source that fails this tick keeps everything it contributed (an account being signed out must not read as its events having been deleted, and the outcome reports it in `failed` instead), while a source the person **unticked** loses its blocks, because nothing will ever update them again. Blocks imported before any of this carry no `sourceKey`, and may be dropped only when **every** selected source read its whole calendar that tick — `some(authoritative)` was wrong and did real damage: ticking a second calendar made that new source authoritative while the original stayed incremental, every legacy block was deleted as though the calendar had been emptied, and an approved plan forked into a draft full of 「日历中已不存在」 conflicts for events nobody had touched. Delta cursors live in `external_bindings` via `saveSyncCursor`/`readSyncCursor`. A 410 `resyncRequired` restarts from the base URL and the result is treated as the complete current set — items deleted during the gap never come back as tombstones, so anything locally present and missing from the resync is dropped. A **draft** plan is updated in place; an **approved** plan is never rewritten, and reality moving under it opens a new draft version whose changes are all `conflict`. `resolvePlanChange` plus the C-lens buttons exist because `approvePlanVersion` refuses while a conflict is pending and nothing could previously clear one — a single calendar change would otherwise have made the plan permanently unapprovable.

**Milestone relations:** `apps/web/app/milestones/page.tsx` renders the lines as a left-to-right flow chart (`flow-chart.tsx`, laid out by the pure `flow-model.ts`: columns are stages, rows are lines, milestones in the same line and stage stack, a link inside a line runs right edge to left edge, a cross-line or backwards link goes round by the gutter, dashed, dotted while still a candidate) and reads `milestone_relations` (`enables`/`reuses`/`informs`/`constrains`/`recurring_feedback`) between milestones across identities — cycles are allowed (e.g. media → research is a deliberate `recurring_feedback` loop), and there is intentionally no LLM-generated cross-identity score. A relation carries `explanation` (what it claims) and `refutedWhen` (what would show it wrong); both are NULL on pre-existing seed rows, which the review page shows as unreviewable rather than dressing up. The nightly flywheel proposes relations as `candidate` only, with a stable id (`flywheel:<from>-><to>:<kind>`) so re-proposals update one row; it never touches a relation that is already `approved` or `refuted`, and never clears recorded counterexamples. `decideMilestoneRelations` is the batch approval (`requiredApproval("approve_milestone_relations")` → `"batch"`, route at `apps/web/app/api/milestone-relations/decide/route.ts`): it moves only candidates, refuses to approve a relation with no evidence, and returns everything it did not move in `skipped`. Rejection writes `archived`; `refuted` stays reserved for the milestone gate finding evidence that contradicts a relation.

**Planner (`packages/planner`):** Greedy `planSchedule` assigns WorkOrder-shaped inputs to availability slots while respecting declared energy, deadline and continuity, returning typed capacity blockers. Its availability comes from `packages/core/src/availability.ts`: a weekly pattern (`AvailabilityWindow[]`) stored in the ledger under the `schedule.availability` setting — not an environment variable, because a backup that does not carry it restores a plan that cannot be rebuilt — which `availableSlots` turns into concrete slots by subtracting the calendar's own blocks and dropping anything under 15 minutes. `scheduledBlocks` in `apps/web/lib/crossline.ts` is its **first and only production caller**; until then the plan's AI lane was seeded example blocks computed from nothing, and those are gone. The schedule is **derived on read and never stored**, so it cannot drift from the work orders it came from; `apps/web/app/plan/availability-editor.tsx` is where the pattern is edited, and saving it re-runs the scheduler on the next load. Unknown energy stays unset and cannot become a low-energy recommendation. `recommendNextActions` uses lexicographic ordering; there is no contribution score, switching-cost score or HiGHS shadow solver.

**Energy observations (`apps/web/app/energy-probe.tsx` + `app/api/energy-observations/route.ts`):** The active input path is a 5-second L/M/H self-report. The MediaPipe/camera path and expiry model are removed. The API rejects camera input, raw media, unknown fields and non-aggregate features.

**Connectors (`packages/connectors`):** `ConnectorAdapter` is the common interface (`probe/pull/push/verify/health`) implemented by `MicrosoftGraphConnector` (personal Outlook calendar + Microsoft To Do, both hard-locked to targets literally named `"Crossline"` — the constructor throws `GRAPH_TARGET_NOT_CROSSLINE` otherwise) and `ContentOpsConnector` (idempotent `POST /v1/jobs` + authenticated `GET /v1/jobs/{id}` polling). Graph writes require `payload.approved === true` and, for updates, both an `etag` (`if-match`) and `externalId`; a 409/412 response surfaces as `GRAPH_SOURCE_VERSION_CONFLICT`. `reconcileExternalItems` dedups by `iCalUid`/`provider:externalId` and flags same-title-near-time items as `fuzzyGroups`, plus multi-etag `SOURCE_VERSION_CONFLICT`s. `longbridgeToolAllowed` is a hard allowlist of read-only market-data tool names — account/trading tools are never permitted here. Per the README, the MSAL/Graph adapter code path exists but is not yet live (no Entra app client ID configured, no real read evidence).

**Codex app-server bridge (`packages/codex` + `apps/worker` + `apps/web/lib/codex-runtime.ts`):** The worker owns one isolated app-server sidecar. On startup it installs `skills/marketplace/.agents/plugins/marketplace.json` into the isolated CODEX_HOME and verifies every `crossline:crossline-*` skill through `skills/list`. Analysis serializes the global skill setting, enables the target by path, invokes it with `$crossline:crossline-automation-stripper`, and restores the original state. SKILL.md text is never read into `baseInstructions`. The supervisor exposes safe status/account/login/cancel endpoints and typed runtime/plugin blockers.

**Skill wire contracts** all live in `packages/core`: `analysis.ts`, `flywheel-schema.ts` (findings + candidate relations), `materials-schema.ts`, `milestone-gate-schema.ts` (gate result, criteria proposal, milestone proposal), and `reality.ts` (the pure calendar-vs-plan diff). Keeping them there is what stops a Skill's shape and its trust checks drifting apart.

A contract item is `{ kind, description, why, required }` in both `materialContract` and `evidenceContract`. `description` is the checklist line (≤300, no `{}[]`, refused if it lands exactly on the limit — that means it was cut off); `why` is the reason and carries no punctuation rule, because a reason is a sentence and sentences quote things. `why` exists because every split in the schema has a `rationale` and a contract item had none: the model had something real to say and one field to say it in, so it packed the reason into the name and filled whatever cap was set — 4000, then 300, then 200, then 80, each treated as a target. With `why` in place the names came back at 6–8 characters. The limit then went **back up** to 300, against instinct: constrained decoding concentrates repetition at structured-field terminals, so a tighter schema makes terminal degeneration *more* likely rather than less, and the tightening had been pushing the wrong way. The primary defence is now detect-and-retry in `runCodexSkill` — when `validateOutput` rejects an answer the rejection message is sent back as a **second turn on the same thread** (which already carries the context, so it is cheaper than a fresh run), at most twice, and the count lands in `audit.repairs` and `StoredCapture.audit`. A repair rate that stays above zero means the schema or the prompt needs work, not more retries. Two normalizations run before validation, both of which only ever remove text that repeats text already present: a tail of one character repeated eight or more times is trimmed, and a sentence whose whole second half already appeared earlier is dropped — both are now last-resort cleanup behind the retry, not the primary defence they used to be. `required` on `materialContract` is what lets the preparer tell "I cannot start without this" from "this would help" — without it one nice-to-have the person had not supplied blocked the entire preparation and they got nothing. `validateAnalysisProposal` names the offending quote or contract line in its blocker, because a bare code gave the person nothing to retry against.

**One structured-output loop, not two** (`packages/codex/src/skill-runner.ts`). A fresh run and a continued conversation used to carry their own near-identical copies of the notification handler, the turn driver and the repair loop — the file said so, and said why it did not merge them. They now share `runTurnsUntilValid` (prompt → final message → parse → the caller's validator → on any rejection, the rejection goes back on the same thread, at most twice), `openScope` (timeout + cancellation) and `failureResult` (the blocker vocabulary); `startIsolatedThread` holds everything that makes an unattended run safe. **A final message that is not JSON now counts as a rejection and is repaired** — before, `JSON.parse` failing ended the run at once with `SKILL_SCHEMA_INVALID`, so the cut-off and repeating-itself outputs this loop exists for were exactly the ones it never saw. `packages/core/src/structured-output.ts` (`structuredOutputProblems`) states the strict-mode rules (every property required, `additionalProperties:false`, `anyOf` for unions, depth and size limits) and `structured-output.test.ts` checks every exported `*_SCHEMA` against them by discovery, so a new Skill's schema is held to them the day it exists. `scripts/structured-output-check.ts` is the real-run measurement; `docs/structured-output.md` is the guide.

**Two clean-ups that exist because of one real run** (`scripts/structured-output-check.ts`, 2026-10-03; numbers and the full account in `docs/structured-output.md`). (1) A model that ends a free-text field with alternating zero-width characters, a stray Malayalam letter and a leaked token got through the old "same character eight times" trim and was **stored**; `cleanAnswerStrings` (`packages/core/src/text-hygiene.ts`, applied to every Skill's parsed answer, skipping `*quote` keys because those are compared with the person's own text) strips invisible characters and `trimLeakedTail` cuts a foreign-script/bracket tail off the analysis contract strings. (2) A Skill that stops and says why (`*_BLOCKED`) is **not** repaired: the repair loop was sending 「缺少待整理材料」 back as an error, and the model answered by deleting its blocker and inventing the material. Every degenerate shape found leaves a fixture in `apps/worker/src/testing/fixtures/`.

**Milestones are per project, and lines are linked** (found by walking the real account, whose 主线 page showed milestones for one of four research projects and no cross-line link at all). `validateMilestonePlans` takes `requiredProjects` — projects with three or more confirmed facts — and refuses an answer that leaves one out (`MILESTONE_PROJECT_MISSING`); chains, stage order and `dependsOn` are checked per `(line, project)`, one project's chain is at most five, a line at most twelve, and a `projectId` that is not one of the line's projects is refused with the valid ones. **The architect is asked one line at a time** (`createMilestoneProposer`: `lineContext` gives each run only its line's identity, projects, facts, templates and diligence, so the identity it may name and the chains it owes are about that line alone). What succeeds is saved and what does not is reported — `skipped` plus a line in `assumptions` naming the line and why — instead of one line's trouble throwing the others away; a line the profile says too little about (fewer than two facts) is named as not scheduled; old untouched drafts are archived only in lines that got new ones. A blocker next to real milestones is kept as an assumption, and only an answer with no milestone is a stop. The links between lines are then a second, small run in a different mode (`crossline.milestone-relations.v1`, `MILESTONE_RELATIONS_SCHEMA`/`validateRelationsProposal`): milestones by id, **different lines only**, with `explanation`, `refutedWhen`, `sourceFactIds`; each is stored as a `candidate` relation whose evidence is the profile facts it rests on, so the 主线 page draws it dotted and the person approves or rejects it. A failed links run never takes the milestones with it. A milestone must be an **event, not a state** (`MILESTONE_NOT_CONCRETE`: 「课程学习保持可完成状态」, 「稳定推进」, 「做好准备」 are refused with what an event looks like — an exam with a score, a submission, a person's reply — and a target saying 保持 needs a number). The interview's `flywheel_*` facts were only ever profile facts — no milestone existed yet to connect them. `scripts/user-journey-check.ts` replays the whole path with the real Codex on a throwaway database (files → interview → dates → milestones → approval → the blocked capture → analysis); its checks are the ones that were false on the real account.

**Captures are analysed without a click.** The worker tick runs `capturesAwaitingAutoAnalysis` (`apps/worker/src/analysis.ts`): captures never attempted, only while the workspace has an approved milestone and the budget mode is `normal`, at most three per workspace per tick. A capture that came back blocked waits for the person — except one blocked only for want of an approved milestone (`ANALYSIS_APPROVED_MILESTONE_REQUIRED`), which is picked up again the moment one exists; the blocker text says to approve a milestone in 主线, not a bare code. The analysis validator also refuses an `identityId` that is not one of the lines (a real task had been filed under 「\」).

**Every quantity is worked backwards from an outcome and carries a margin** (`packages/core/src/milestone-plan.ts`, `analysis.ts`, `packages/planner/src/forecast.ts`). A milestone's `plan` has `outcome` (the result the person wants) and `derivation` (the back-calculation in numbers); a `threshold` measure has `bareLine` (the value that only just reaches the outcome) next to `value` (the line actually set). `thresholdProblem` refuses a `value` that is not on the safe side of `bareLine` by at least `MARGIN_RATIO` (3%; a score may sit at 100) — `MILESTONE_NO_MARGIN` — and `validateMilestonePlans` refuses a threshold with no derivation containing a number (`MILESTONE_DERIVATION_MISSING`) or a milestone with no stated outcome (`MILESTONE_OUTCOME_UNSTATED`). The derivation is appended to the stored rationale and `bareLine` is shown beside the line on the milestone page; `bareLine` is optional in the stored type because hand-written and older criteria have none. Estimates: the analysis works back from the `evidenceContract` to its steps, `p50Minutes` is their unpadded sum, and the margin lives only in `p85Minutes` (`ANALYSIS_ESTIMATE_MARGIN_INVALID` unless it is 1.2–3x p50). The scheduler already reserves p85 for low-confidence work; `forecastGoals` now reports `slackDays` and flags a goal whose p85 finish is less than `DEADLINE_MARGIN_DAYS` (2) before its deadline.

**Targets are proposed by the model from the person's long-term goals, and changed by them in one click** (`milestone-plan.ts`, `milestone-proposer.ts`, `apps/web/lib/targets.ts`, `apps/web/app/milestones/targets-panel.tsx`). Two earlier versions got this wrong in opposite directions: the architect assumed a course's total grade and derived every score line from a number nobody had chosen, and the next version made the person answer a question list before anything existed to react to. Now the architect, which has the person's goals, priorities and grade weights, proposes the target itself: `targetProposals: [{projectId, value, why}]` in its answer, stored by `persistTargetProposals` as an **inferred** `target_grade` fact with the reason in its value (`值（暂定：理由）`) and never over an existing one. `validateMilestonePlans` refuses a graded milestone in a course (`isCourse`: a `grading` fact, or quizzes/homework dated in its own files — a real interview recorded a syllabus's dates and never its percentages) when no target is on record and none is proposed in the same answer (`MILESTONE_TARGET_UNPROPOSED`), and when its `sourceFactIds` do not cite `<line>/<project>/target_grade` (`MILESTONE_TARGET_NOT_CITED`), so every score line traces to the one number the person can edit. The Milestones page opens with a targets panel: each course's target with its reason, 「就按这个」 (confirms it), a list of grade options or free text, and 「改并重算本线草稿」 — `POST /api/targets` confirms the new value, then `POST /api/milestones/propose` with `only:[line]` redoes that line's untouched drafts (approved milestones are never touched; their score lines are edited in place in the same panel, with the derived lowest line `bareLine` beside the input and a warning when an edit leaves no margin). Proposed targets still waiting count in 待确认 (`pending.targets`). What is still asked as a question, because it is a fact the model cannot propose (`profileGaps`): a line that rests only on the interviewer's guesses (`LINE_UNCONFIRMED`, blocks 「ready」, `withGapQuestions` turns a premature 「ready」 back into 「ask」 and adds the question with options) and a graded part a file marks TBD (`DATE_UNDATED`, asked once, blocks nothing). Answers to those code-built questions are read straight out of the `【question】选择：label` message (`answeredGapFacts`) and written as confirmed facts before the model runs.

**TBD is not a date, and not nothing** (`date-schema.ts` `undated`, `latestFileDates` in `packages/db`). The ECE 555 schedule's last row is `TBD · Final Project Report · Due`; the date extractor rightly refused to invent a day, and the 25% project then had no milestone at all because the chain was built from dated items. The interview turn now returns such rows in `fileDates.undated` (each with a verbatim quote, checked like a date), they are stored in the `dates.extracted` payload, counted as a graded part by `MILESTONE_COURSE_PARTS_MISSING`, and the architect gives them a milestone with a provisional deadline marked 「日期待定」. A date that is genuinely absent from the files is the person's to supply (the question above), not ours to find.

**The assistant is a second way of using Codex, with a shell** (design and decisions in `docs/assistant-agent.md`; `packages/codex/src/agent-mode.ts`, `skill-runner.ts` `startAgentThread`, `apps/worker/src/agent-task.ts`, `packages/core/src/agent-guard.ts`, `agent-summary.ts`, Skill `crossline-agent`). Structured Skills stay read-only with no tools; the assistant runs the same runner with `agent` set: `sandbox: danger-full-access`, `approvalPolicy: untrusted`, the task's own directory as `cwd`, every runtime tool on. `untrusted` is what makes the runtime ask before each command that is not on its own short list of harmless ones, and `JsonLineRpcClient.onServerRequest` (new — the client used to ignore requests from the runtime, so an approval would have hung to the timeout, and an id clash could resolve one of our own pending calls) hands each request to `registerAgentThread`, which routes by `threadId` to the run that owns it; `createAgentAnswerer` asks the guard. **The guard is a tripwire, not a sandbox**: it refuses secret paths, sending/publishing/paying/system changes, deleting a root, and writes outside the task directory, and asks about installs, pushes, uploads and recursive deletes; a script written to get round a text check will get round it, so the real protection is the rest (task directory or git worktree on `ai/<taskId>`, hashes of the inputs before and after, every command and file change recorded, an artifact check that rejects a claimed file that does not exist, and the last step of anything that leaves the machine being the person's). Verified on the real runtime on 2026-10-05: a learning-material task ran in 222s with 5 commands and left the originals untouched, and a task told to copy a `.env` into a note had its `Get-Content` of it refused by `secret.path` while the chart half of the task finished. Kinds of work (`AGENT_CATEGORIES`) are approved once (`agent.categories` setting) and earn trust only through accepted, fully checked results (`CLEAN_RUNS_TO_TRUST`); a rejected or failed one sends the kind back to review-all. The ledger keeps `agent.task.*` provenance (commands, changes, artifact hashes, verification), never content; the assistant has its own lane so a long task does not hold the capture analysis or the gate. **Phase 2 wired it into the board** (`packages/db/src/agent.ts`, `packages/core/src/agent-dispatch.ts`, `apps/worker/src/agent-{dispatch,service}.ts`, `apps/web/lib/agent.ts`, `/assistant`, `/api/agent/*`, `AssistantSection` on `/workbench/[id]`). State lives in the ledger as events (`agent.task.requested|completed|blocked|reviewed`, `agent.category.requested`, `agent.approval.requested|decided`) plus the `agent.categories`/`agent.paused` settings, folded by `listAgentTasks`, so the worker writes and the web app reads and records the person's answers without talking to each other except to start a task (`POST /api/agent/dispatch` → supervisor `/v1/agent/dispatch`, which answers at once). `planAssistantTask` turns an approved analysis into a task: the `automationParts` become the job, the `humanCore` becomes what the assistant must leave alone, the kind is read from the wording (wording that points at none is the person's to choose, and nothing starts without one), and graded coursework in a course gets the learning-aid-only note. The worker tick (`agentService.pass`) starts at most one task per workspace of an *approved* kind for an approved, not-yet-started order — a kind that is not approved is asked about once (it appears in 待确认 and on `/assistant`) and the order waits — unless paused or either quota window is ≥95%; runs are detached so the tick never waits. A guard question (`ask`) is written to the ledger (`ledgerAsk`) and answered from `/assistant`; unanswered for ten minutes it is declined. The review page shows the assistant's own summary labelled as its own, and the app's independent record (commands, refusals, hashes) apart from it; `reviewAgentTask` only counts a clean, checks-passed acceptance towards a kind's trust. The conversational widget that used to be labelled 助手 is now 问答 so the name belongs to this. Not yet built: task classification beyond the keyword reading, the shared calendar, proactive triggers, MCP account tools (any MCP prompt is declined), the local API and desktop notifications — see the phases in the design doc.



**Skills have no shell, and that is evidence, not neglect.** `scripts/shell-sandbox-probe.ts` ran read, write and network commands under four permission setups: every command was refused before execution, because on Windows without the Windows sandbox backend a restricted-filesystem profile under `approvalPolicy: never` forbids all commands (`vendor/codex/codex-rs/core/src/exec_policy.rs`). Enabling the backend is a system-level ACL setup, and even enabled Windows can enforce only a deny-read list, not "this one folder". Do not add an `allowShell` option to a structured Skill without redoing that probe; the assistant below is the deliberate exception, run on `danger-full-access` rather than through a restricted sandbox.

**The Phase 4 acceptance bullets are a test** (`e2e/design-audit.spec.ts`): every page at desktop and phone width must be Arial throughout, have no text under 12px, no text under 7:1 contrast, and no sideways scroll. It found real defects when first run — the line colours were 5.4–6.7:1 as text, the day-timeline blocks had black text on purple in light mode (a dark-mode rule missing its media query), and Today and Plan were 598 and 570px too wide on a phone because the calendar header's grid track sized to its content. `AUDIT_VERBOSE=1` prints what each page violates and which element pokes out.

**Skill deadlines are one hour per turn, not per run — finishing the task comes before speed, and the limit is there only to catch a run that has truly hung.** `openScope` (`packages/codex/src/skill-runner.ts`) gives every RPC and every turn its own `timeoutMs` window (`60 * 60_000` in every runner); it used to be one deadline from first call to last, so a long first answer left the repair that the validator then asked for a few seconds, and a run that was nearly right timed out with nothing to show (the interview did this to a real run). What bounds a run is the repair count (two). Milestone design is also asked one line at a time (see the milestone paragraph): in one answer it wrote ~11k tokens at ~4.5 minutes a turn. The web routes that wait on a run allow three hours (six for milestone design, which is several runs); the worker finishes and writes its outcome even if the page gave up. **Slow is allowed, silent is not.** The limit above is a ceiling, not the thing that catches a hang: `runTurnsUntilValid` also watches for *any* event from the runtime about the thread (`lastEventAt`), and a turn with none for 20 minutes (`CROSSLINE_SKILL_IDLE_MINUTES`) is interrupted and the same prompt sent again, twice at most (`audit.stalls`; then `SKILL_STALLED`). It exists because a real interview run sat for over an hour with the runtime logging nothing at all, and a startup-line milestone run took 43 minutes for 7k tokens — a stalled turn waits out the whole hour otherwise, and a long productive turn is never cut because it keeps producing events. **Measure, then tune:** Settings → 模型用量 shows each Skill's average **and longest** run, `scripts/user-journey-check.ts` prints the wall-clock of every step, so a limit is set from observed times and not guessed. When a limit and a finished answer disagree, lengthen the limit.

**The worker tick never overlaps itself.** `setInterval` fires a guarded callback that skips and logs `worker.tick_skipped` while the previous tick is still running; the web health probe is additionally bounded by a hard ten-second race. Material preparation and the gate each allow an hour a turn against a fifteen-minute interval, so overlap is the normal case — two concurrent ticks read the same pending list before either writes, prepare or judge the same order twice, and race on one delta cursor.

**Identity packs (`packages/identity-packs`):** `defaultIdentityPacks()` is the static registry of the four identities plus the `health` capacity pack (`kind: "capacity"`), each declaring its `workflowTemplates` and `evidencePolicy` (`"tiered"` vs `"telemetry"`). `research` is currently the only pack with `masterClock: true`.

**Skills (`skills/marketplace/plugins/crossline/skills`):** The repo-local `crossline` plugin contains one skill per phase (there is no orchestration skill: it was installed but never invoked, and described actions the app does not take). Identity structure remains in `packages/identity-packs`; user-specific overlay data remains under ignored `data/`. Do not duplicate plugin skills back into top-level `skills/`.

## Identity, sessions, and private deployment (stages two–six)

This was, until recently, a single-user app with no login at all — `OWNER_ID = "local-owner"` / `WORKSPACE_ID = "personal-crossline"` were the only "identity" anywhere in the repo. Stages two through six replaced that with real accounts, real per-workspace isolation, and real cross-device access over a private network, without ever adopting multi-tenant collaboration UI — it is still built for exactly one real person, just no longer a hardcoded one. `docs/user-guide.md` is the user-facing walkthrough; this section is the "what broke and why it's built this way" record the rest of this file already keeps for everything else.

**Two databases, two schemas, one story.** `auth.db` is Better Auth's own SQLite file (`user`/`session`/`account`/`verification`), migrated by calling `better-auth/db/migration`'s `getMigrations` directly (`packages/auth`'s `migrateCrosslineAuth`) rather than the separately-published `@better-auth/cli`, which trails this repo's pinned `better-auth` version and could generate a different schema than the one actually running. `crossline.db` gained `principals`/`workspaces`/`workspace_members`/`tailscale_bindings`/`device_leases`/`audit_events` in migration 5; `principals.better_auth_user_id` is a plain string reference to the other database, not a SQL foreign key, matching this repo's existing "deliberately absent foreign keys" stance. `session: { cookieCache: { enabled: false } }` is load-bearing, not a default left alone: every request re-checks `workspace_members` from the database, so a revoked session or a demoted role takes effect on the very next request, not after some cache window — `scripts/gate-identity-check.ts` signs a real session out and re-checks it to prove this rather than asserting it from the config alone.

**`requireAccessContext` (`packages/auth/src/index.ts`) is the one place a request becomes an `AccessContext`.** It calls Better Auth's `getSession`, then — on a session's first-ever appearance — creates `principals`/`workspaces`/`workspace_members` for it in one transaction (a brand-new, empty workspace; logging in never adopts the old `personal-crossline` ledger data still sitting on disk), then separately checks that principal actually belongs to the workspace it is asking for. That second check did not exist anywhere before stage two — `packages/db/src/isolation.test.ts`'s own doc comment named the gap explicitly ("nothing verifies the caller is allowed to use this workspaceId"), and `scripts/gate-identity-check.ts` now proves two independently-signed-up accounts land in different workspaces and cannot see each other's work orders. `listPlanChanges` was the one `list*` method in `packages/db` that took no `workspaceId` at all — a real cross-tenant read, found and fixed while wiring stage three through, not a hypothetical.

**Eliminating the hardcoded identity was pure surface area, not depth.** Every API route gained an `access = await resolveAccessContext(request)` early-return, every exported function in `apps/web/lib/crossline.ts` gained a leading `ctx: AccessContext` parameter, every worker background job switched from a hardcoded owner to looping `listWorkspaces()`. `apps/web/lib/no-hardcoded-identity.test.ts` is the guard against regression — `import.meta.glob` over `apps/web/**` and `apps/worker/**` asserting the literal strings `"local-owner"`/`"personal-crossline"` appear zero times outside test files, the same "discovery test, not per-callsite" pattern `csrf-protection.test.ts` already uses.

**Codex supervisor capability tokens close the one real gap stage four's scope allowed touching:** before this, anything on the same machine that could reach 127.0.0.1:3211 could make the worker run a Codex skill — no `dynamicTools`/`skillQueue`/per-entity concurrency work was in scope, because none of it has a second real caller to matter yet. `packages/codex/src/capability.ts` signs a 30-second HMAC token (`CROSSLINE_SUPERVISOR_CAPABILITY_SECRET`, deliberately independent from `BETTER_AUTH_SECRET` — one leaking must not compromise the other) carrying the caller's real `AccessContext` plus a `jti` and the worker's own `supervisorBootId` (regenerated on every worker restart, so a token signed before a restart is dead on arrival). Every supervisor route except `GET /v1/codex/status` (needed to discover the current `supervisorBootId` in the first place) verifies it; a discovery test scans every route handler the same way `csrf-protection.test.ts` does, so a new route that forgets the check fails on day one.

**The offline workbench (`apps/web/app/offline-queue.ts`) is real Dexie now, not hand-rolled IndexedDB.** The database name is `crossline-offline-${workspaceId}`, not a fixed name — switching accounts never carries the previous principal's cached commands into the new session, for free. Payloads are encrypted with a non-extractable AES-GCM `CryptoKey` (browsers support storing `CryptoKey` objects in IndexedDB via structured clone directly) before being written. `CommandEnvelope` now dispatches `work_order.start/pause/resume/complete` through the same `transitionWorkOrder` state machine the online routes use — reusing its existing `expectedWorkOrder`/`PROPOSAL_VERSION_CHANGED` optimistic-concurrency check rather than inventing a second one. `classifyReplay` gained a third outcome, `"conflict"` (HTTP 409, distinct from `"dead_letter"`'s permanent rejection and `"retry"`'s transient one): a stale command against a work order that moved on under it lands in Dexie's `conflicts` store, shown in full with its reason rather than silently discarded or silently overwriting whatever the other device already did. A device must additionally hold an unexpired, unrevoked lease (`device_leases`, 24-hour, `POST /api/auth/device-lease`, renewed automatically on a successful sync) for its queued commands to be accepted at all — `issueDeviceLease` had no reader and no revoke UI until this pass found the gap while writing `docs/user-guide.md`'s "撤销设备" section: `listDeviceLeases` and a `GET`/`DELETE` on the route were missing entirely, so a lost device's lease could be revoked at the store layer (tested) but never actually reached from the app. `apps/web/app/connectors/device-leases.tsx` is the card that closes it.

**Private cross-device access rides Tailscale Serve, not a public deployment.** `CROSSLINE_DEPLOYMENT_MODE` is `local | private | external`: both `local` and `private` still bind loopback only — Serve's own TLS-terminating reverse proxy is what makes `private` reachable from elsewhere on the tailnet, the app itself never opens a non-loopback socket. `private` is the first mode that turns on HSTS/CSP/`X-Content-Type-Options`/`Referrer-Policy`/`X-Frame-Options` (`apps/web/next.config.mjs`'s `headers()`) — loopback-only traffic never needed them, since nothing outside the device could address it at all. `external` (real public exposure) is still refused at build time; `docs/external-deployment.md` tracks its remaining prerequisites, and `docs/private-network-deployment.md` covers the `private` setup end to end, including the one-time manual steps (enabling Serve at the tailnet level, adding a second Google OAuth redirect URI). The original plan assumed Tailscale Serve might forward some notion of node identity to the backend; verified against Tailscale's own docs before building on it, and it does not — only `Tailscale-User-Login`/`-Name`/`-Profile-Pic`, and Tailscale strips any spoofed versions of those headers on the way in, so they are trustworthy but incomplete. `tailscale_bindings.node_key TEXT NOT NULL` was written against the wrong assumption and never actually usable; migration 6 made it nullable and narrowed the uniqueness constraint to `(workspace_id, tailscale_login)`. The binding itself (`apps/web/app/connectors/tailscale-trust.tsx`, `POST/DELETE /api/connectors/tailscale`) is purely an audit record an already-logged-in owner creates by choice — Tailscale identity headers never participate in any access-control decision, on purpose, so "trust this Tailscale identity" cannot become an accidental login bypass. `apps/worker/src/export.ts` had its own stale-hardcoded-identity bug found in the same pass: it defaulted `CROSSLINE_WORKSPACE_ID` to `"personal-crossline"`, which stage three made real accounts never actually use, so an unset env var would have silently exported an empty snapshot; it now auto-detects a single real workspace and requires the var explicitly otherwise. `scripts/backup-crossline.ps1`/`restore-crossline-backup.ps1` now carry `auth.db` alongside the ledger (`scripts/checkpoint-auth-db.ts` WAL-checkpoints and copies it; `scripts/read-auth-db-counts.ts` reads it back after restore) — a backup that cannot restore a working login is not a backup, the same principle the ledger's own retired-table checks already apply.

## The profile-first loop: interview, dates, milestones, research, recordings

A new account no longer lands on four placeholder goals. It lands on `/onboarding`, and everything downstream is built from what that learns. `ensureSeeded` seeds the template library and an empty plan **only**; the example milestones, relations and work orders exist behind `CROSSLINE_SEED_EXAMPLES=1`, which `vitest.config.ts`, `playwright.config.ts` and `scripts/run-e2e.ts` set because the suites and the visual baselines were recorded against that board. `needsOnboarding(ctx)` (`apps/web/lib/crossline.ts`) sends a workspace with no profile, no session, no live milestone and no work to the interview from `/`; `apps/web/lib/no-example-data.test.ts` and `apps/web/app/empty-account.test.tsx` are what prove an empty account still renders every page.

**The interview is a ledger conversation, not a form** (`apps/worker/src/onboarding-session.ts`, `packages/core/src/onboarding-turn-schema.ts`). Each turn asks several questions at once with 8–14 candidate options, and every `confirmed` fact must cite a `reply-N` or `src-N` with a verbatim `sourceQuote` (compared as letters and digits in order, ignoring punctuation and Markdown: a bulleted line copied as a sentence failed a real run twice); anything the model worked out is `inferred` with an empty quote and the store never lets a guess overwrite a confirmed fact. The messages, profile facts, projects and uploaded `source_documents` are all in SQLite, so a reload or another device resumes where it stopped. **The runtime forgets a conversation when it restarts** — a stored `codexThreadId` then answers `thread not found`, which is a JSON-RPC error object that used to surface as an anonymous `SKILL_RUNTIME_FAILED` and wedged the interview forever. `runContinuedTurn` now names it `SKILL_THREAD_LOST`, and the runner opens a fresh thread seeded with the profile, every file and the conversation so far (`history`, user lines carrying their `reply-N` id). Any new place that stores a thread id must handle that code the same way.

**Long runs stay alive on the wire.** A caller's `fetch` gives up when no byte arrives for five minutes (undici's default), and a Skill is allowed ten; a one-turn interview with a long history takes about seven. The supervisor therefore answers the interview turn, date extraction, milestone proposal and diligence routes through `sendJsonWhenReady`: status line at once, a space every twenty seconds, JSON at the end. Every outcome of those routes is already a typed `{state:"blocked", code}` in the body, so the status is 200 either way and a throw becomes one more blocked result. Do not "simplify" it back to `sendJson(await work())`.

**Model routing** (`packages/codex/src/model-policy.ts`): one table maps each skill to a tier, and a tier to `{model, effort}` — top `gpt-5.6-sol`/medium (interview, milestone architect, backplanner, flywheel), mid `gpt-5.6-terra`/high (analysis, materials, gate, weekly insight, diligence), low `gpt-5.6-luna`/high (date extraction, background facts, explainer, assistant). `CROSSLINE_MODEL_TOP|MID|LOW="model[:effort]"` override a tier and `CROSSLINE_MODEL_ROUTING=off` disables routing. The model goes in `thread/start` and, with the effort, in **every** `turn/start`, because a continued turn inherits the thread's model unless told.

**Dates from files are a batch the person confirms** (`packages/core/src/date-schema.ts`, `apps/worker/src/onboarding-session.ts`, `apps/web/lib/imported-dates.ts`). There is **no separate date-extractor Skill**: the interview turn already reads the files, so it returns the dates in a `fileDates` field of its own answer (`persistFileDates`), and the model that reads the syllabus is the one that knows today's date and the person's zone. A reread turn replaces what nobody has answered yet. Each date carries a verbatim quote that must contain the day itself (`quoteSupportsDate` accepts `10/27`, `27th Oct.`, `Oct 27`, `10月27日`; the year is not required). `sanitizeDateExtraction` drops an item that cannot be verified and reports it in `dropped` instead of failing the whole answer — the first real run lost a hundred good rows to one misquoted line and a four-minute repair. The quote comparison ignores punctuation and spacing only (`squash` keeps letters and digits): the model copying `27th Oct.` as `27th Oct` is the right quote, and refusing it dropped a real midterm. Weekly patterns are expanded in code (`expandRecurring`), never by the model, and only today-and-later reaches the calendar. A batch is two ledger events (`dates.extracted`, `dates.decided`); `extract({replace:true})` re-reads the files of a batch nobody has answered and retires it once the new one exists. Confirmed timed items become read-only plan blocks `import:<batch>:<item>` that calendar sync never touches (it only rewrites `graph_calendar:` blocks); untimed ones become `date_*` profile facts.

**Milestones are anchored to the person** (`packages/core/src/milestone-plan.ts`, `apps/worker/src/milestone-proposer.ts`). When the context carries a `profile`, each proposal needs a `plan` — `key`, `stage`, `deadline`, `baseline`, `target`, `stakeholders`, `sourceFactIds`, `dependsOn` — and `validateMilestonePlans` refuses what it can check: a generic or too-short title, a missing or past or >18-month deadline, an empty target, no source fact (or only inferred ones), an unknown fact id, no `outcome` criterion, fewer than three or more than five per covered line, a later stage due before an earlier one, an unchained stage, a dependency that is not earlier. The refusal's `detail` names the milestone, because a bare code gives the model nothing to repair. Anchors live in `milestone_anchors` keyed by milestone id (not in the versioned `milestones` row), so revising a milestone does not lose them. Proposing archives untouched `*-starter` milestones, the relations between them and untouched seeded work orders; an accepted order is history and stays. Accepted diligence proposals reach the architect as `diligence[]`.

**Web research is checked, then opened** (`packages/core/src/diligence-schema.ts`, `apps/worker/src/diligence.ts`). The contract is built around sources: a source is a public https page (no IP literal, local name or port), every finding cites sources by id, every proposal rests on findings and on the person's own fact ids, and the investment line may not contain a trade call or price target. After the model answers, `verifySource` actually requests each page — manual redirects, every hop re-checked against a DNS lookup so a hostname cannot lead to a private address — and drops a source that does not open or whose content does not match its claimed title, together with every finding that depended only on it. `pageSupports` then requires the Latin names in a finding's claim to appear in the page it cites (a real run filed a Hult Prize deadline under NVIDIA's page); figures are not compared, because `2026-11-15` and "Nov 15" are the same date. A report with nothing left is a failure and writes no conclusions. Each line is researched at most weekly, in the background, only once the interview is complete or a report already exists, and stops when the budget is in economy mode. Nothing a report proposes becomes a goal until the person accepts it. **The runtime executes web search through `codex-code-mode-host`, which it starts from beside its own executable**; a fork built without it answers every search with `failed to spawn code-mode host` and the model reports "the research tool is unavailable". `webResearchBlocker()` checks for the file up front and names the path. Building it from `vendor/codex` needs a V8 prebuilt archive from GitHub; the installed Codex app's `bin\codex-code-mode-host.exe` was copied in instead (a newer build than the pinned 0.155.0 — it worked, but re-verify after any runtime bump).

**Recordings are transcribed on this machine** (`apps/worker/src/transcribe.ts`). `TranscriptionEngine` isolates the model and the decoder, so the consent gate, the status the screen reads, the 3-hour limit and the timestamped transcript are tested without either. The model (`onnx-community/whisper-small`, 8-bit, about 255 MB) is fetched only from a request carrying `consent: true`, which the screen sends only from the button that names the source and size; recognition afterwards runs with `allowRemoteModels = false`. **The language is detected, not assumed**: transformers.js does not detect it (it logs "defaulting to English"), so `detectLanguage` sums the first decoding step's scores for each language token over three half-minute clips (10%, 40%, 70% in) and the transcript's first line names the result; `CROSSLINE_TRANSCRIBE_LANGUAGE` pins it. Whisper tends to write Chinese in traditional characters; converting needs a library nobody has agreed to install yet. The engine imports `@huggingface/transformers` and `audio-decode` on use, so a machine without them reports `unavailable` rather than failing to start.

**The worker's per-workspace jobs** — nightly flywheel, the diligence pass and the screen-activity tracker — loop over every real workspace. The nightly used to be one instance bound to the pre-accounts workspace id, so no real account ever had its flywheel expanded.

## Interface and model routing (phases 4 and 2)

**One typeface, one frame, four views.** Everything is Arial (with the system CJK sans behind it), 14px body, 13px secondary, nothing under 12px, and the secondary text is 8.9:1 on white; the five line colours (`--c-research|startup|media|investment|health`, set through `data-line`) are the only colour. `AppShell` (`apps/web/app/app-shell.tsx`) is the one frame — `SubpageShell` and Today both use it — with the four working views in the main row (今日 `/`, 主线 `/milestones`, 计划 `/plan`, 任务 `/workbench`) and 待确认 `/approvals` (with a count badge from `GET /api/pending`) and 设置 `/settings` to the side. `lib/pending.ts` is the one definition of "waiting for a decision"; the badge and the page list the same things. Settings holds what was Connections (`connectors/connections.tsx`; `/connectors` redirects there), the schedule editor, the activity consent and the model usage. Pages that only restated policy, "not calibrated" placeholders or a list of unconfigured connectors were removed rather than restyled. Cards are `repeat(auto-fill, minmax(…))` grids, never one task across a whole row.

**Model routing is more than a table** (`packages/codex/src/model-policy.ts`, `usage.ts`, `skill-runner.ts`). A Skill's route can be overridden per Skill (`SKILL_OVERRIDES`: reading a syllabus is `medium` effort; `CROSSLINE_ROUTE_<SKILL>="model[:effort]"` pins one) and carry its own `maxRepairs`. When the quota is tight (`budgetPolicy` says `economy`, read through `setSpendModeProvider`, cached for a minute, an unreadable quota counts as normal) a Skill **steps down one tier** instead of being refused, except the gate and the capture analysis (`NEVER_DOWNGRADED`): a weaker reading of either is a wrong answer, not a cheaper one. Runs wait in **a lane per tier** (`serializeSkillRun(skillName, …)`), so a one-second plan explanation no longer waits behind a ten-minute interview turn; only switching a Skill on and off is held in one line (`underConfigLock`), because that rewrites the runtime's one config file. A Skill belongs to exactly one tier, so two runs of the same Skill still never overlap. Every run reports `thread/tokenUsage/updated` totals to `setUsageSink`; the worker writes them to `model_usage` (per workspace, attributed through `enterUsageWorkspace` — the supervisor sets it from the verified capability, the tick loops set it per workspace) and Settings shows the last seven days per Skill. The old `ModelTier`/`model-tiers.ts` (never wired to anything) is gone.

**Manualbooks (phase 3, `apps/worker/src/manualbook.ts`, `packages/core/src/manualbook-schema.ts`, `safe-fetch.ts`).** A work order in `preparing` gets a per-task book in `CROSSLINE_DATA_DIR/materials/<workOrderId>/` (`manifest.json` with checksums, `flow.json`, `manual.md`, `nodes/<id>/{task,analysis,tutorial,sources}`) instead of one file. Three Skills in sequence: `crossline-manualbook-designer` (top tier) lays out the steps as a **DAG** that must cover every required `materialContract` item (`validateManualDesign`, `topologicalOrder`); `crossline-material-researcher` (mid, web) finds sources for each step that needs them; `crossline-material-writer` (mid) writes the step from those sources only. The worker, not the model, decides what is real: every source must be a public https URL that **actually opens** (`safeGet`: DNS public-host check on every hop, size/type caps; a title the model claimed must match the page), and the full text is downloaded only when the host passes `openAccessVerdict` *and* the model did not say no — everything else is `summary_only`. A write-up may cite only the source ids it was given and may not contain a URL of its own. `requiredApproval("download_open_access")` is `automatic`, `download_other` is `never`. A failure writes `materials.blocked` with a typed code; it never leaves half a book that looks finished. The Workbench detail page embeds `manualbook-view.tsx` (flow + tabs, polls while preparing), served by `/api/work-orders/[id]/manualbook` and `/materials`. Evidence: `scripts/manualbook-check.ts` (real Codex, throwaway DB; 2026-10-02: 6 steps, 6 verified sources, 9 minutes, checksums match).

**Screen activity (phase 5; `packages/core/src/activity-state.ts`, `apps/worker/src/activity-{source,recorder}.ts`, table `activity_segments`).** `ActivitySource` is the interface (`start(onReading)`/`stop()`), so a wearable or phone is another implementation later; the Windows one is a single long-lived PowerShell reading, every `CROSSLINE_ACTIVITY_INTERVAL_SECONDS` (60), the foreground app, its window title and the idle time — nothing else. `createActivityTracker` offers each reading to **every workspace** (the recorder used to be bound to `personal-crossline`) and each decides from its own settings, re-read per reading: `localActivity.consent` = daily aggregates only (the original promise: no app, no title), `localActivity.consentV2` = segments with app and title, `localActivity.pausedUntil`, `activity.blacklist` (the person's own words), `activity.rules`. A window matching `isPrivateWindow` (banking, password managers, InPrivate/incognito, …) is **not recorded at all** — not title, not app, not that it was open; its minute still counts as active in the aggregate. Titles stay on the machine: `ActivitySegment` (what core and the web read through `listActivitySegments`) has **no title field**, `exportSnapshot` blanks them, they are blanked after 14 days (minutes/app/category stay, rows go after 90), and `recentActivityEntries` is read by exactly one route — the settings card that shows the person what is kept, with 清除所有窗口标题. `apps/web/lib/activity-privacy.test.ts` is the discovery test: it fails if any other file reads titles or if anything that builds a Codex context touches the segments. `inferWorkState` is rules, not a model (focused / switching / in_meeting / away / leisure / mixed / unknown, each with reasons and a confidence; under five tracked minutes is `unknown`); the Today chip and the day timeline's 「实际」 blocks exist only with the V2 consent. `categoryMinutesOnly` is the only shape that may ever go to a model.

**The Crossline calendar (Phase 3 of the assistant; `packages/connectors/src/crossline-calendar.ts`, `apps/worker/src/calendar-publish.ts`, `apps/web/lib/calendar-publish.ts`).** The user's hard constraint: never alter a calendar they set by hand. `CrosslineCalendarWriter.#assertWritable` is the single gate for every non-GET: it allows creating a calendar named exactly `Crossline`, creating events in that calendar, and PATCH/DELETE only for ids just read back carrying the extended property `crosslineBlockId`. An owned event whose content no longer matches the hash in the ledger (`calendar.published` setting) was edited by the person and is left alone; deletes are future-only; events are `showAs: free`. **Two boundary changes the person chose on 2026-10-06:** (1) `requiredApproval("write_focus_block")` is `automatic` — `apps/web/instrumentation.ts` runs `autoPublishPass` (`apps/web/lib/auto-publish.ts`) every ten minutes as a `system-job` context and publishes when the blocks' hash changed (off with `CROSSLINE_AUTO_PUBLISH=off`, in vitest and in e2e); the button stays. (2) Reminders: work blocks remind 10 minutes ahead, and two marker kinds are written beside them — `followup:<waitingId>` on a waiting item's follow-up day and `deadline:<milestoneId>` two days before an approved milestone's deadline, each reminding at its start. The ledger records the reminder written; a reminder the person changed by hand is theirs (the content still follows the plan). What may be written did **not** move: only the calendar named Crossline, only events this app made and the person has not changed, deletes only in the future, `proposed:` preview blocks never. Only an approved plan version is written (the route returns 409 PLAN_NOT_APPROVED otherwise). The writer's account is a separate device-code login (`scripts/graph-write-login.ts`, scopes User.Read + Calendars.ReadWrite) stored in `calendar.write.account`; the read-only sync keeps its read scopes. `calendar-sources.ts` drops any calendar named Crossline from the catalogue and the selection so the plan never reads its own blocks back as constraints. Google Calendar is not read; see `docs/calendar-write-setup.md`.

**Daily-use friction found by walking the real account as the person (2026-10-05)** and what changed. (1) A capture is analysed **now**, not at the next tick: `POST /api/commands` (`task.capture`) asks the worker for `/v1/captures/auto-analyze` five seconds later (the grace is for attachments, uploaded in a second request), the worker's `autoAnalyzePass` is the tick's own pass pulled out (one per workspace at a time, same approved-milestone and quota-normal rules), and a real capture went from typed to a proposal in 71 s with no click. The capture form says 「已收到」 instead of reloading, sits above 「下一步」 on Today and its button is 「收集」. (2) `withoutShadowingDemos` (`apps/web/lib/crossline.ts`): the seeded demo work orders (`payload.seeded`) are neither recommended on Today nor scheduled on the plan once the person has any work of their own; before this the scheduler placed a demo order four mornings in a row and **that was published to the real calendar** (removed again; `blocksToPublish` also refuses `-starter-work-order` ids). Today's empty card says how many proposals are waiting rather than asking for input the person already gave. (3) The analysis is told which files the person already uploaded (`uploadedMaterialInputs`: names, size, a 300-character opening) so it stops asking for course material the system holds. (4) 主线 folds archived milestones and each card's 「依据与推导」; 待确认 proposal cards show what falls to the person and fold the rest. (5) `.subpage-inner` is `grid-template-columns:minmax(0,1fr)`: a one-track `auto` grid took the milestone flow chart's fixed ~1130px as its minimum and scrolled the whole page sideways in any window under ~1150px — the 1280px/phone audit never saw it, and the e2e data's chart is narrower, so the 1000px audit test is a guard for the class, not a reproduction.

**The second walk (2026-10-06) and what it changed.** Five frictions: the calendar stayed empty after onboarding behind ~11 approvals, 「问答」 knew nothing about the person, what the person waits for was not modelled, the plan page re-asked for availability, and several numbers and labels misled. Competitor and literature notes behind each decision are in `docs/competitors.md`.

- **Owner, not a constant.** Every worker job stamps rows with `ownerOf(store, workspaceId)` (`apps/worker/src/owner.ts`); the goal backplanner used to *filter* on the pre-accounts constant, so 「从此目标反推步骤」 failed on every real account. `no-hardcoded-identity.test.ts` now scans `apps/worker` too.
- **Risk-tiered default effect** (`packages/core/src/auto-approval.ts`). A proposal that is `routine`, `family: "preparation"` (or a byproduct's landing) and names no external action (`EXTERNAL_ACTION_PATTERN`, matched on intent and the person's own part, never a serialized payload) takes effect as soon as analysis or backplanning writes it: `plan.approved` with approver `system:auto-approval`, plus `work_order.auto_approved`. 待确认 lists the last day's ones with 撤销 (`approval.revoked` → back to `awaiting_plan_approval`, and `work_order.auto_approval_revoked` keeps it from being auto-approved again). Milestones, targets, relations and anything external stay a click. Batch routes: `api/work-orders/approve-batch`, `api/milestones/approve-batch` (「接受这条线的 N 个草稿」), each reporting `skipped` rather than failing the batch; accepting drafts calls the worker's `/v1/goals/auto-backplan`, which works backwards from approved milestones due within 21 days that nothing serves yet (`milestonesAwaitingBackplan`; the tick is the fallback). The person chose that auto-approved orders are also picked up by the assistant (when their kind is approved); the review card says so (`autoApproved`). The plan page draws where proposals *would* go as dashed `proposed:` blocks, solved in a second pass into the time approved work leaves, never published.
- **问答 knows the person** (`apps/web/lib/person-snapshot.ts`). The web route builds a plain-text snapshot — now, approved milestones with deadline and days left, drafts, the next seven days' scheduled, proposed and fixed blocks, open tasks, pending counts, confirmed facts; no screen activity — and it is sent on **every** turn (follow-ups get a `{snapshot, message}` envelope), so compaction cannot drop it. Output gained `proposals` (capture cards); a template is a card too. Nothing the assistant returns is written until the person clicks (`/api/assistant/capture`). `SKILL_THREAD_LOST` reopens the thread from history. The panel no longer reopens itself on every page; the conversation lives in `sessionStorage`.
- **Waiting, release and due dates** (`waiting_items`, `packages/db`). Analysis v2 (`ANALYSIS_CONTEXT_VERSION`) returns `dates[]` (`release`/`due`) and `waitingOn`, each with a verbatim quote that must name the day (`quoteSupportsDate`; an unverifiable one is dropped, not fatal). `recordWaitingAndDates` turns them into `payload.notBefore`, `payload.dueDate` and a waiting item. The planner never starts a task before `notBefore` (HiGHS, fallback, validation, forecast); an open waiting item past its day keeps its work off today until the person answers the Today card (到了 / 推迟 / 不等了, `api/waiting/[id]`). Only the person's answer closes it.
- **Notifications** (`apps/worker/src/notify.ts`): one morning brief at the first available hour, and single messages only for what would be missed today (a waiting item due, a milestone due today or tomorrow, a gate refusal), capped by the 设置 dial (`notify.level`: off/less/normal/more), on their own two-minute clock outside the tick, each recorded once as `notification.sent`. Delivery is a WinRT toast through PowerShell with the script passed encoded; `scripts/notify-check.ts` sends a test one.
- **Calibration is one residual model** (`packages/core/src/calibration.ts`, `workspaceCalibration` in `crossline.ts`). It learns `ln(actual / analysis p50)` with hierarchical shrinkage (overall toward 0, line × kind toward overall, k=5), 60-day half-life, half weight for another analysis version, an empirical-85th-percentile p85 once there are 20 residuals, and is applied only after a rolling backtest **against the frozen raw estimate** beats it by 10% in log error without worse p85 coverage; otherwise the screen says it is still learning. It replaced `effectiveEstimate` (a per-kind average that discarded the task's own estimate) and `calibrateEstimate` (an unshrunk global ratio). Analysis v2 no longer receives `historicalStats` or `rhythm.planActualRatio` — handing the model a correction and correcting its output again counted the bias twice; it gets `referenceClass` (raw past estimates and actuals) instead. Migration 10 adds the analysis estimate, source (`timer`/`one_tap`/`activity`), context version and `censored` to `duration_observations`, backfilled from work orders; an observation sums every session of the order and is one row per order. Completion offers one-tap durations (≈估时/一半/多一半/两倍/自填, plus the screen record's suggestion with the detail consent). The real ledger had zero observations on 2026-10-06, so nothing is calibrated yet.
- **Byproducts** (analysis `byproducts[]`, `#materializeByproducts`). At most one per other line, a concrete artifact, capture steps done during the main task (in its p50) and a short landing. Approving the main order creates `landing-<order>-<line>` on the other line: own milestone, own evidence (the gate judges each separately), default-effective, scheduled after the main order is handed in with a two-day window and the lowest tier. The weekly review counts planned / landed / missed.
- **系统体检** (`packages/core/src/effectiveness.ts`, `apps/web/lib/effectiveness.ts`, Settings): on-time milestones, estimate accuracy (from the calibration's own backtest), time by line and on deadline work, decisions per day and capture-to-scheduled time, and mechanism coverage (committed work with a dated block, milestones with recorded progress, waiting items answered on time). Minutes spent deciding are not recorded yet.
- **Smaller fixes**: Today's available minutes count from now and subtract calendar commitments; a paused order reads 「已暂停」; `riskTier: "milestone"` reads 「中（影响里程碑）」; the task page shows the person's part, the AI's part and the steps; the plan explainer reads `goalSettingKey`; the solver reports `empty`/`no_capacity` instead of 「优化器未给出可用解」; demo orders are archived once the person has work of their own; offline replays keep the device's times; the plan page compares the stated weekly hours with the pattern's hours (the real interview recorded 「合计每周约 72 小时」 but never the daily rhythm).

**Asks: when the system stops, it asks (2026-10-07).** An audit of every place work stopped for a person found a backplan refusal (「未提供实测 MoS₂ 参数数据…」) written to an event nothing read, which also closed that milestone to the timer for good — even for a logged-out runtime; a refused capture, stopped materials and a gate's real 「insufficient」 visible only on a detail page; a gate whose *run* failed toasted as 「没通过验收」 while a real verdict reached nobody; calendar read and publish failures as log lines; and no milestone ever at risk, because the forecast read deadlines only from goal settings. Now:

- **One shape** (`packages/core/src/asks.ts`): an `Ask` has an explanation (`why`), options written out with one `recommended`, follow-up `fields` per option (pick 「在等」 and it asks who and roughly when, prefilled with what the system knows), an urgency from the deadline it affects (`now` ≤2 days, `soon` ≤7, `later`), and a `fingerprint`. Snoozes (「明天再问」/「下周再问」, `ask.snoozed`) last until their day or until the fingerprint moves, as Linear's do. Patterns: LangGraph Agent Inbox (accept/edit/respond/ignore), MCP elicitation (flat typed form; accept/decline/cancel), Horvitz's mixed-initiative rule (act when confident, ask when only the person knows, otherwise stay quiet — the nightly flywheel's skips are still silent), and interruption research (Adamczyk & Bailey 2004; Fitz et al. 2019 batching).
- **Built on read, never stored** (`apps/web/lib/asks.ts` `collectAsks`): missing backplan inputs, a waiting item on its day (the old waiting card), a refused capture (not one waiting only for an approved milestone), stopped materials, a gate's real verdict, a gate run that failed, evidence with no milestone to judge it, a milestone at risk, a blocked assistant task, failed calendar publish/read (`CALENDAR_PUBLISH_FAILURE`/`CALENDAR_SYNC_FAILURE` settings), and — pages only, over the network — Codex signed out or the worker down. An ask goes away by itself when its cause does. `answerAsk` carries an answer out through the functions the rest of the app already uses and records `ask.answered` (counted on 系统体检 as a decision).
- **Missing inputs are split around, not stopped on** (the person chose this). `BACKPLAN_SCHEMA` blockers carry `what` and `whoHas`, and steps carry `acquires`; a first run's blockers are recorded (`missing` in `goal.backplan_blocked`, keyed per attempt) and a second run in the mode where each missing input becomes a step of its own (`acquires` = its id, drafts stamped with `inputsFrom`). The person is asked per input: 「我有」 (text → `goal.backplan_input_supplied`, the getting-it step withdrawn and its dependents freed, `goal.backplan_rerun_requested`), 「在等」 (a `wait-bp-<milestone>-…` waiting item holding the dependents; 「到了」 on its day hands it over and re-splits), 「还没要」 (keeps the step), 「先不拆」 (`goal.backplan_declined`). A rerun request bypasses every timer rule in `milestonesAwaitingBackplan`; a `SKILL_*`/`CODEX_*` failure is no longer recorded, so the next tick retries. Older events with only the joined message become one input per sentence (`missingInputsOf`).
- **Risk is explained, then decided** (Tability's forced decision, as a question). `loadGoalForecast` now falls back to the milestone's own approved deadline. An approved milestone with open work whose p85 finish leaves under two days (or does not finish in eight weeks) gets `explainRisk`: deadline and days left, hours of known work, the good-case and cautious finish days, by how much it misses, that only already-split steps are counted, and that it is a forecast. Options: add time, move the deadline (goal setting), lower the bar, or 「接受这个风险」 (`risk.accepted`, quiet for seven days unless the slack gets worse).
- **Where they show**: Today's 「需要你一句话」 lists the three most urgent and brings up the next after each answer without reloading; 待确认 lists all, and the badge counts them (`pending.asks`). The web's timer writes `ATTENTION_SNAPSHOT` (open asks + pending total) every ten minutes; `notify.ts` reads it while fresh (<30 min), so the brief, the badge and the desktop count the same things, and only `urgency: "now"` asks interrupt, inside the daily cap. A stale snapshot falls back to the worker's own reading.
- **Walking the cards on the real account** found four more. 「在等」 for what an open item already waits on — same person, same day, same project, not same milestone (the real pair sat on two milestones of one project) — adds to that item instead of opening a second (`waitingIndex` in `asks.ts`, linked by `goal.backplan_input_waiting`), and any answer to one of a pair already recorded answers both, 「到了」 re-splitting every milestone either held; the badge recounts on `crossline:pending-changed`, which `AskList` fires after each answer; one milestone's missing inputs sit under its name once; and the backplanner's `high_risk` reads only a step's intent, because 「首轮发布清单草稿」 as *evidence* made picking topics high-risk.
- **Fixed on the way**: the material-preparation block key now carries the retry count (a retry failing with the same code used to leave the retry as the last word and re-prepare every tick); a failed diligence report waits a day instead of rerunning every tick; `agent.task.blocked` stores the message; the backplanner's external-action check uses the shared `mentionsExternalAction` (W0 imported it and kept its own regex).

**The third walk (2026-10-07): from planning to doing.** On the real account, eleven days in, the ledger showed one accepted order, two executions, zero gate verdicts, 39 milestone drafts the architect had replaced, fifteen decisions waiting — and not one task ever handed to the assistant (no `agent.*` event at all). What changed:

- **Whole-task delegation** (`planAssistantTask` → `delegateWhole`, `packages/core/src/agent-dispatch.ts`). A backplanned step carries no AI/human split (`automationParts: []`), so `NOTHING_FOR_ASSISTANT` stopped every one. A `preparation`/`review` order that names no external action and is not graded coursework is now handed over whole (`delegated: true` on the plan, the task input and `agent.task.requested`): the assistant does the errand, reports what only the person knows in `needsHuman` instead of inventing it, and its files become the order's evidence. `deliverAgentResult` (`packages/db/src/agent.ts`) does that through a new transition, `agent.delivered` (approved/preparing/ready_for_human → evidence_review, evidence claims written like `human.completed`'s), which puts the order in front of the milestone gate. It runs when the person accepts the result on `/assistant` (`reviewAgentTask`) or, once a kind has earned trust, straight after a clean run (`agent-service.ts`). The gate now quotes `.md/.csv/.json` evidence as well as `.txt`.
- **「下一步」 was empty with five approved orders.** `plannerTaskOf` counted only `ready_for_human`/`active` as `inputsReady`, but an approved order with no material contract (every backplanned step) never passes through preparation — `startWorkOrderExecution` starts it directly. `inputsReady(order)` now says so.
- **What reviewing the first three delegated results taught** (2026-10-07). A content-source list was good and went through the gate; an ECE 548 outline came back an empty template because the interview's uploads sit under no project and the assistant was handed none of them; and 「选定一项创始人正在处理的真实事项」 was chosen *for* the person (it chose the app itself) after the assistant listed the home folder and tried to open the ledger (the guard refused). - **Replaced plans are not shown.** `milestonesRetiredBySystem` (archived and never edited by the person — every edit writes `milestone.revised`) leaves the 主线 page; `archivedBySystem` (`bySystem` on `work_order.archived`, or a known system reason for older rows) leaves the 已丢弃 drawer. Each milestone's reasoning stays in 「依据与推导」.
- **Yesterday's work that did not start** (`missed_block` ask, `apps/web/lib/schedule-memory.ts`). The schedule is derived and never stored, so the attention timer now records which orders got a time each day (`schedule.day:<date>`). The next day an unstarted one that bears on a deadline within a week is asked about (顺延 / 推到某天 — sets `notBefore` / 其实做了 / 不做了); the rest roll forward silently, as the scheduler already moves them.
- **Phone.** The tailnet address (`tailscale serve` → 3210, `CROSSLINE_DEPLOYMENT_MODE=private`) was already live. Added: generated PWA icons (`app/pwa-icon/[size]`, manifest and `apple-icon`), `appleWebApp` metadata, `viewport-fit=cover` with the bottom bar padded past the home indicator, 16px inputs on phones (iOS zooms into anything smaller and stays zoomed), 44px touch targets (`app/mobile.css`), and a 设置 → 在手机上用 card with the address and the three steps. Every auth form is `method="post"`: with its script blocked, a form without one fell back to GET and put the password in the address bar.
- **Phone push** (the person chose Apple's push service on 2026-10-07; `packages/connectors/src/web-push.ts`, `apps/web/lib/push.ts`, `/api/push*`, `app/settings/phone-push.tsx`, the `push`/`notificationclick` handlers in `app/sw.ts`). The worker's `notifyPass` sends each brief and urgent message to the desktop and to every subscribed device (`push.subscriptions` setting), and counts it as sent if either got it. Web Push: the payload is encrypted for the device (RFC 8291) and the request signed with this install's VAPID key (RFC 8292, `data/push-vapid.json`, made on first use, never in the ledger or an export), so the push service relays bytes it cannot read. The server posts only to known push services (`isAllowedPushEndpoint`: web.push.apple.com, FCM, Mozilla, WNS — never an address a client supplies), a subscription must come from the https tailnet origin, a device the service reports gone (404/410) is dropped, and the iPhone only allows it for the home-screen app, which the card says instead of failing silently.

**The product pass (2026-10-08): archetypes and steps, one task card.** The person's direction for the whole interface is in `docs/copy-style.md` (fixed vocabulary 主线 → 里程碑 → 任务 → 步骤, third person, no gamification, folds only for advanced content, every number drawn, model-written text in `.gen` — Microsoft YaHei — against the system's Arial + DengXian) and is checked by `e2e/design-audit.spec.ts` (two faces) and `e2e/copy-audit.spec.ts` (report-only until `COPY_AUDIT_STRICT=1`). Shared pieces live in `apps/web/app/ui/` (tags, segmented control, slider, date chip, duration bar, quarter ring, popover menu, sheet, tooltip, hand-rolled SVG charts — no chart library).
- **Archetypes and step graphs** (`packages/core/src/archetypes.ts`, `steps.ts`). Six structure primitives taken from the workflow control-flow patterns and HTA plan types (sequence, multiple instances, choice, wait/time window, loop until met, checkpoint), two compounds (explore→converge, learn-while-doing — descriptive frameworks, so not primitives) and recurrence as an attribute; eighteen archetypes built from them. An archetype is a *grammar* — roles, the few `firstBefore`/`requires`/`endsWith` rules, proportions, a quantity × minutes-per-unit size, an acceptance standard, a tick phrasing — never a fixed sequence: the step planner decides how many steps and in what order. Only the answer's shape is a hard check; `normalizeStepPlan` makes any shape usable (ids, ordered estimates, cycles broken, shares normalized) and `stepPlanWarnings` reports content problems, which `crossline-validation-reviewer` either dismisses or has redone **once** (a redo is never redone by the reviewer). Normalization's own fixes are not sent for review. Safety boundaries stay hard everywhere; only content-quality checks became warnings.
- **Steps are scheduled, tasks are tracked** (`task_step_plans`/`task_steps`, `CrosslineStore.saveStepPlan` keeps done steps on a replan). `plannerItemsFor` (`apps/web/lib/crossline.ts`) turns a planned task into one planner task per open schedulable step (`<order>#<step>`), so a homework is placed between its release and due day step by step; block ids are `scheduled:<order>:<step>[:n]` (`scheduledBlockId`/`plannerIdOfBlock`; step ids are `v<version>s<n>`), and everything that only needs the order still reads segment 1. The forecast counts only the open steps. Progress = done shares + a started step's quarters.
- **The worker's task pass** (`stepPlanPass`, also `POST /v1/tasks/pass` from the web): confirmed homework date pairs become default-effective tasks (`materializeDatePairs`; a fact's `projectId` may be the project's *name*), every committed task without a plan gets one (two a tick — this is also how existing tasks were migrated), replans asked for with feedback run, progress reports are judged (`crossline-progress-judge` → step quarters and `criteria.assessed`), and warnings are reviewed. The backplanner now proposes coherent tasks, not single actions. `acceptedOutputs` tells the planner what the assistant already produced.
- **One task card and dialog** (`apps/web/app/task/`). `TaskCard` (Today, Tasks, Approvals) shows line and course, progress and current step, the due date and the current step's duration edited in place, the next block, and 「→ 支持 …」 in the other line's colour; the whole card opens `TaskDialog` (steps with drag/add/remove and a one-line replan, standards as quarter rings a click confirms, a progress report box, every file openable via `/api/source-documents/[id]/file`, a task-scoped 小助手, the tutorial, the record). `/workbench/[id]` renders the same `TaskPanels`. 「开始计时」 opens that page and the floating `TimerFloat` counts down from the current step's usual minutes, notifies at zero and keeps counting; closing it pauses with 「本次计时结束」 and asks whether the step is done. Start/pause/resume still queue offline, signed as the viewer (`TaskDetail.viewerId`), not the order's owner. 「交给 Agent」 hands over the first step the planner judged the system can do (`executor` ≠ human; `taskFromStep`), and an accepted result marks that step done.
- **Every change is previewed** (`apps/web/lib/impact.ts`, `POST /api/plan/impact`). `withPreview` runs the scheduler and the forecast inside an `AsyncLocalStorage` scope that overrides a task's or step's minutes or a task's due date — nothing is written — and the diff (the task's next block, milestones moving or newly at risk, each line's hours this week) is shown before 应用. The day view's scheduled blocks can be stretched from their right edge (`estimate_delta`). An applied estimate change records `estimate.adjusted` for later personalisation.
- **One input box** (`apps/web/app/chat/composer.tsx`) for 快速收集 and 小助手: a ＋ menu (files, existing materials, batch, link a task or milestone), `@` mentions served by `/api/mentions`, paste and drop anywhere, Enter to send. A plain line is captured at once (offline-queued as before). A batch, or a line `looksLikeScheduleCommand` matches, goes to `POST /api/input/route` → worker `/v1/input/route` → Skill `crossline-input-router`, which returns captures and changes to open tasks (`due`, `defer` = not before, `estimate`); captures are written, each change is previewed through `lib/impact.ts` and applied on 应用 — or at once after the person ticked 「此后日程指令直接应用」 (`input.schedule.autoApply`). A change the router cannot tie to an open task falls back to a capture of the same words, and so does a failed run: nothing typed is lost. Mentions reach a capture as a 「关联：…」 line in its context and the assistant as a reference line in the message. 「问答」 is 「小助手」, 「需要你一句话」 is 「待决事项」, and the separate batch form is gone.
- **Review server** (`scripts/review-server.ts`, `.claude/launch.json` "review"): the resident build on port 3320 against a throwaway data dir with the example board, for walking the interface with a test account; `scripts/review-seed.ts` gives its tasks step plans.

## End-to-end tests

`e2e/crossline.spec.ts` (Playwright, config at `playwright.config.ts`) drives a **production build** (`next build --webpack` then `next start`) on port 3310 (3211 belongs to the resident worker's Codex supervisor) with its own temp data dir (`CROSSLINE_DATA_DIR` under the OS temp dir, keyed by PID) and `CROSSLINE_NEXT_DIR=.next-e2e` so it never collides with the port-3210 dev server or its `.next` build. A production build rather than `next dev`, because `next.config.mjs` disables Serwist in development — the offline claim had no service worker to test against and could not have been verified here no matter what a test asserted. The offline test cuts the network and **first proves the cut** with a `fetch("/api/health")` that must fail, then reloads and asserts the page still renders; without that probe a passing test shows only a warm cache. The data dir is stashed in `CROSSLINE_E2E_DATA_DIR` so test workers (separate processes, different PIDs) can open the same ledger the server did — the C-lens tests write their own pending diffs into it, because the seeded example diffs no longer exist. `CROSSLINE_FIXED_NOW` pins the clock so visual-regression PNGs (`e2e/crossline.spec.ts-snapshots/`) are reproducible. Runs `desktop-chrome` and `mobile-chrome` (Pixel 7) projects, `colorScheme: "light"`, `fullyParallel: false`. When intentionally changing layout, regenerate snapshots with `pnpm exec playwright test --update-snapshots` rather than hand-editing the PNGs. The two screenshots hide (`visibility:hidden`, so layout is kept) the pending badge and everything the scheduler produced — `STABLE_FOR_SCREENSHOT` in the spec — because the badge's count depends on what parallel tests have written and the scheduler's block lengths come from a time-limited solve that gives a different feasible answer on a busy machine; before that, the baselines passed or failed by run. The planner also rounds the solver's continuous minutes with a `+1e-6` so a half minute is not 25 on one run and 26 on the next.

## Safety boundaries (do not casually change)

These constraints are enforced in code, not just docs — read the relevant source before loosening any of them:

- Microsoft Graph writes only ever target a calendar/list literally named `Crossline`; `connectorWritePolicy` returns `"read_only"` for everything else and Graph writes require explicit approval (`payload.approved === true`) plus ETag-checked updates.
- UW Outlook and Google Calendar are read-only, imported only via the official Codex plugin (not implemented in this repo's connectors).
- Longbridge (`longbridgeToolAllowed`) permits only market-data/reference tools — no account or order-placement tools.
- `content-ops` only accepts idempotent `POST /v1/jobs` and reads real terminal state via authenticated `GET /v1/jobs/{id}`.
- No real Graph OAuth, outreach, publishing, or trading is currently wired up — `requiredApproval` returns `"never"` for `broker_order` and `silent_source_calendar_write` by design.
- The camera energy probe has been removed entirely; no browser media capture exists in this app. The energy API accepts only `self_report` with a numeric `responseSeconds` aggregate (`CAMERA_ENERGY_PATH_REMOVED`, `RAW_MEDIA_OR_UNKNOWN_FIELD_FORBIDDEN`, `AGGREGATE_FEATURES_ONLY`). Re-introducing any camera path requires an explicit decision, not a refactor.

- The one outbound path the notifications have is Web Push to the person's own subscribed devices (chosen 2026-10-07): end-to-end encrypted for the device, posted only to known push services. It carries notification text, nothing else.

If a change would add or enable a real external write path (Graph OAuth, publishing, trading, outreach) or would let raw camera/media data leave the browser, flag it explicitly — these are deliberate, currently-unimplemented boundaries per the project README, not oversights.

- Gate 4 (Codex material prep): done (real run on the live ledger, 2026-09-16). `apps/worker/src/manualbook.ts` builds a manualbook (see Phase 3 below) for work orders sitting in `preparing` — the old single-shot `crossline-material-preparer` is gone; `apps/worker/src/milestone-gate-runner.ts` invokes `crossline-milestone-gate` for work orders in `evidence_review`. **Both now run on the worker tick and both have a run-it-now supervisor route** (`/v1/work-orders/:id/prepare-materials`, `/v1/work-orders/:id/milestone-gate`, each answering 202 and finishing in the background) behind the 重新准备材料 and 现在判定 buttons — until 2026-09-16 the gate existed only inside `scripts/gate-loop-check.ts`, so on the real ledger nothing ever judged a submission. Neither job is retried on a timer: `pendingMaterialWorkOrders` and `pendingMilestoneGates` both apply last-word-wins over a `…blocked`/`…retry_requested` pair, and the gate additionally treats a revoked acceptance as closed, or the next tick would re-judge the same evidence and undo the revocation.

  **What `pass` means.** The gate answers one question: did this work order deliver what its own `evidenceContract` promised? It used to require every required measured criterion of the whole *milestone* to be met by one submission, which on a real ledger is almost never true — correct work came back 「证据不足」 and blocked. The milestone's criteria are still judged, all of them, and every judgement appends `milestone_gate.judged`; that is the milestone's progress record (best reading per criterion wins) and is what the Milestones and Review pages show. `applyMilestoneGate` throws `GATE_ALREADY_APPLIED` on a spent idempotency key rather than writing an acceptance audit for a transition that did not happen.

  Three things that check keeps honest, each of which it got wrong once: `validateMilestoneGateResult` takes the work order's **own** `evidenceContract` and requires every requirement back verbatim with a non-null `satisfiedBy` — `contractCoverage.every(...)` alone is satisfied by an empty array, so the gate could be passed by reporting nothing. A verbatim quote is demanded only for `met`/`partial`; `unmet` and `unverifiable` carry an empty `evidenceQuote`, because there is no text to quote for something the evidence does not contain and an unmet milestone criterion is now the normal case. And the two run-it-now routes detach through `runDetached`, not `void p.finally(...)` — the latter still propagates the rejection, and since Node 15 an unhandled rejection terminates the process, so one click on an order the store then refused would have taken the worker down.

**Calendar sync on demand:** `POST /v1/calendar/sync` → `/api/calendar/sync` → the Plan page's 立即同步日历. A read, awaited (unlike the two Skill routes) because it takes a second and the person clicked it to find out what changed; it only reloads the page when something did.

**Discarding:** a WorkOrder leaves the board through `archiveWorkOrder`, a raw capture through `CrosslineStore.discardCapture` (state `discarded`, event `capture.discarded`). Both require a reason and both land in the Workbench's 已丢弃 drawer. A capture previously had `分析` as its only exit, so removing a duplicate cost a real Codex turn.
- Gate 5 (content-ops / investment): partial — the content-ops authenticated read-only status endpoint passes its full check, but no real endpoint/token is configured for this deployment; investment tools only have the pre-call allowlist, no real report-run evidence yet.
- Gates 6–7 (long-run validation): partial — HiGHS was removed in v2, and the **encrypted-restore drill really ran on 2026-09-15** (DPAPI decrypt → unzip → rebuild SQLite → read every table back; 8 events / 6 work orders / 4 milestones / 28 rows matching the live ledger). `docs/archive/codex-test-plan.md` is the autonomous test plan: Codex drives every screen and script itself, and its third layer is a **red team** that tries to falsify the design's own uncertain bets rather than confirm the mechanism — is the auto-accepting gate a real filter or a rubber stamp (four deliberately inadequate submissions must all be refused), does loosen-plus-retry actually hold degeneration off across ten hostile captures, is the flywheel producing falsifiable relations or agreeable noise, does the energy reading change any recommendation, is the greedy schedule usable. ## Operational scripts (`scripts/`)

- `start-crossline.ps1` — launches the **built** web app + worker as background processes (requires `pnpm build:prod` first, which builds into `apps/web/.next-prod`; fails fast if its `BUILD_ID` is missing). The resident app has its own build directory because `pnpm build`/`pnpm verify` write `.next`: a verify run while the server was up replaced the hashed CSS it was still naming, and every page lost its styles (found from the phone address on 2026-10-07, where nothing was cached). Idempotent by design: it skips the web app when port 3210 already listens, and always launches the worker because a free supervisor port does not prove the worker is dead. The worker guards itself with a heartbeat lock at `data/worker.lock` — a redundant copy logs `worker.already_running` and exits 0 rather than opening a second SQLite writer, a stale heartbeat (3× the tick interval) is taken over, and `EPERM` from `process.kill(pid, 0)` counts as alive.
- `install-startup.ps1` — registers a Windows Scheduled Task with two triggers: at logon, and repeating every 15 minutes. The repeating one is the watchdog — the launcher exits as soon as it has spawned its children, so Task Scheduler's own restart settings would never fire. Modifies Windows Task Scheduler; only run when the user explicitly asks.
- `backup-crossline.ps1` — exports the ledger to JSON, zips it, encrypts with DPAPI (current Windows user), and verifies SHA-256 before deleting the plaintext temp file. Its `& pnpm` call (and the one in `restore-crossline-backup.ps1`) is wrapped in `& { $ErrorActionPreference = 'Continue'; … }`: under `'Stop'`, PowerShell 5.1 turns a native command's stderr line into a terminating error whenever stderr is redirected, which is every non-interactive host. The script died before reading `$LASTEXITCODE`, so the backup worked by hand and silently never ran unattended.
- `restore-crossline-backup.ps1` — decrypts a backup and **rebuilds a working SQLite ledger** from it via `pnpm restore`, then reads every table back through the normal query path to verify. `CrosslineStore.importSnapshot` only ever rebuilds into an empty workspace (`RESTORE_TARGET_NOT_EMPTY`), the CLI refuses the live database (`RESTORE_TARGET_IS_LIVE_LEDGER`) and refuses to overwrite an existing file (`RESTORE_TARGET_EXISTS`). Replacing the live ledger stays a manual act. Snapshot table and column names are validated against `sqlite_master`/`PRAGMA table_info` before reaching SQL.

## What is deliberately *not* ours to build

Audited against the vendored runtime (`vendor/codex`, rust-v0.155.0). Codex already provides, and we therefore use rather than reimplement: thread persistence/resume/fork/compaction, `outputSchema` structured output, per-turn model/effort/sandbox/approval overrides, `thread/tokenUsage/updated`, `account/rateLimits/read`, `account/usage/read`, `model/list`, login flows, web search modes, MCP, dynamic tools, hooks, memories, goals with a token budget, and image input. It does **not** provide, so we own: per-skill model/effort/schema (SKILL.md frontmatter only honours `name`/`description`), scheduling, PDF/docx extraction or OCR, batch audio transcription, a hard spend cap, and verification of what a model claims (quotes, URLs, DAGs, approvals). Before writing a script that wraps the model, check this list; the deterministic validators stay, the "ask the model to do it" scripts do not. Removed on this pass as having no caller: the orchestration skill, `validateMaterialPreparation`, the Graph/Longbridge/ContentOps connector classes were **kept** (Gate 3/5 roadmap) but flagged unwired, `readCodexAccount`/`startCodexChatGptLogin`, `readTailscaleIdentity`, `addCapturedTask`, `interviewQuestions`, `skipRecurringWorkOrder`/`tombstoneWorkOrder`/`notificationForTransition`, `normalizeCodexEvent`/`buildContextBundle`, three one-off scripts, and 91 CSS selectors of deleted components.
